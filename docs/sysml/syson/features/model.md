## Validation & model checks

### Validation view

- **Validation view**: a workbench view titled 'Validation' in the left side panel (Warning icon in the left sidebar) that lists the diagnostics for the whole project. Diagnostics are grouped by kind, derived from severity (Error, Warning, Info or Unknown; the docs write ERROR, WARNING, INFO), each kind in an accordion that starts collapsed and can be expanded or collapsed so critical issues can be handled first. The header shows the kind name (a third of the header width) followed by the count in secondary text ('1 diagnostic' / 'N diagnostics'). Expanded, it lists one plain-text message per diagnostic, separated by dividers; messages are not clickable and the view does not react to selection. With no diagnostics, or once the subscription completes, it shows 'No diagnostic available'. It is the third view of the default left panel (Explorer, Views, Validation, Search), closed by default while the Explorer starts open, and is itself a collapsible view section titled 'Validation' whose content scrolls. Accordions appear in the order in which their kind first occurs in the (rule-sorted) diagnostic list, not in a fixed severity order. Accordions are keyed by kind, so per the code an expanded accordion stays expanded across live refreshes. The view contributes no saved workbench configuration and ignores selection (applySelection is null). Its strings ('N diagnostic(s)', 'No diagnostic available') come from the sirius-components-validation bundle, which ships English and French. SysON's user manual flags the Validation page as experimental. Per the how-to and e2e tests, clicking the Validation icon in the left bar adds the view to the left panel next to the views already open (Explorer and Validation then both shown and both icons highlighted) rather than replacing them; clicking the icon of an active view while the panel is expanded collapses the whole panel, and clicking any view icon while it is collapsed expands it again. The left panel always shows project-level information, not the current selection. The view's id 'validation' can be set active or inactive in a workbench configuration (e.g. passed in the project URL's workbenchConfiguration query parameter). The view has no toolbar, filter, search or sort control, and no way to jump from a diagnostic to its element; the kind names in the headers are the backend's untranslated strings ('Error', 'Warning', 'Info', 'Unknown'), and every diagnostic gets a new random id each time the validation is recomputed. _(Sirius Web; experimental)_ · `ValidationView.tsx`, `site.cy.ts`, `user-interface-navigation.adoc`
- **Live validation refresh**: the view keeps a subscription to the editing context (GraphQL `validationEvent(input {id, editingContextId, representationId})`, the frontend always passing representationId 'validation://' with no caching; it streams ValidationRefreshedEventPayload {validation {id, diagnostics {id, kind, message}}} or ErrorPayload) and the backend recomputes the diagnostics on every semantic change, so edits by any user update it without reloading. Semantic change is the default refresh policy; a refresh-policy registry can supply another one for the validation description. Subscription errors appear as toasts. Since v2026.11.0 the recomputation runs outside the validation event processor, which only receives the new state through a provisional IValidationEventProcessor#update method and publishes it to subscribers. _(Sirius Web)_ · `useValidationViewSubscription.tsx`, `ValidationRefresher.java`, `validation.graphqls`
- **Large diagnostic counts**: the Validation view renders projects whose models have very many errors without recursion failures (the 'too many recursions' failure was fixed in v2026.1.0). _(Sirius Web)_ · `CHANGELOG.adoc` v2026.1.0
- **Only SysML rule diagnostics shown**: the view gathers diagnostics from every registered validation service. Sirius Web's generic EMF validator (which reports every non-OK EMF diagnostic) runs only when the property `sirius.web.enabled` includes 'validation' (or everything), and SysON does not set it, so in SysON the view lists only the diagnostics of SysON's SysML rules from SysONSysMLValidationService. Listing 'validation' in `sirius.web.disabled` turns the generic validator off even when it is enabled. When it is on, it validates every resource (libraries included), labels objects with their item-provider label, and also answers per-feature validation for Details widgets, keeping only the diagnostics whose data contains both the object and the feature. · `EMFValidationService.java`, `ValidationDescriptionProvider.java`, `SysONSysMLValidationService.java`
- **Automatic validation, not shown in diagrams**: SysON automatically checks models for conformance to the SysML v2 metamodel and key structural rules, and the rules can be extended or customized. Results appear only in the Validation view (left sidebar); the FAQ says they are not yet shown inside the graphical editors and that integrated feedback is planned. · `faq.adoc`

### Diagnostic display

- **Diagnostic message format**: each diagnostic reads '#<ruleName>·····[<document name>/<element qualified name>]·····Constraint on type 'sysml:<Metaclass>' is not respected: <rule message>', so the label says which document and which element break which rule. Each separator is five middle dots (U+00B7), and an invisible left-to-right mark (U+200E) follows the closing bracket; 'sysml' is the namespace prefix of the rule's EPackage, so an extension rule on another metamodel shows that package's prefix. If the document has no name its resource URI is used; if the element has no qualified name, '<ID: <id>>' is shown. The diagnostic's severity comes from the rule, its source is the rule name, its code is 0 and its data is the element. · `SysONSysMLValidator.java`, `2026.3.0.adoc`
- **Diagnostic ordering**: diagnostics are sorted by rule name alphabetically; within a rule, by containing document (in resource-set order) and then by the validated element's qualified name, falling back to element ID. Diagnostics without a rule name, without an element or without a qualified name go last. · `SysONDiagnosticComparator.java`, `SysONSysMLValidationService.java`, `2026.3.0.adoc`

### Details view

- **Widget validation diagnostics**: each form widget receives a list of diagnostics (id, kind, message); when there are any, the widget is drawn in its error state and the first diagnostic's message appears as red helper text under it. Applies to text fields, text areas, checkboxes, selects, multi-selects, radios, lists, date/time fields and reference widgets. The diagnostics come from each validation service's per-feature validate(object, feature) call. Sirius Web's manual describes these as inline validation messages next to fields when a constraint fails; its e2e test clears a reference widget's value with its clear button and checks that the red error helper text then appears under the widget. _(Sirius Web)_ · `FormEventFragments.ts`, `PropertiesValidationProvider.java`, `widget-reference.cy.ts`
- **No per-property SysML diagnostics in SysON**: SysON's validation service answers per-feature validation (used for widget diagnostics) with an empty list, and Sirius Web's EMF validator is disabled, so per the code the Details view widgets show no SysML rule diagnostics; rule results only appear in the Validation view. · `SysONSysMLValidationService.java`, `EMFValidationService.java`
- **Widget diagnostics expression (View-based forms)**: in a studio's form description, every WidgetDescription has a 'diagnosticsExpression' (next to its label and help expressions) whose result is shown as the widget's validation message; the expression can return a string prefixed 'INFO:', 'WARNING:' or 'ERROR:' to give the severity, an EMF Diagnostic, or a list of either (since v2025.2.0, ADR-180). _(Sirius Web, studio)_ · `form-description.adoc`, `CHANGELOG.adoc` v2025.2.0

### Validation scope

- **Project models only**: validation covers the whole editing context, running an EMF Diagnostician recursively (VALIDATE_RECURSIVELY) from every resource's root elements and keeping the child diagnostics, but skips the standard library resources and libraries referenced from other projects, since users cannot fix them there; the library owner fixes issues in the project that contains the library. Validation runs longer than 200 ms are logged at debug level. · `SysONSysMLValidationService.java`, `2025.8.0.adoc`, `2026.3.0.adoc`
- **Library updates can raise new diagnostics**: the library documentation warns that updating an imported library modifies the project's contents and may break parts of it (library elements removed or with a changed identity), so validation errors may appear afterwards. · `library-import.adoc`

### Validation engine

- **SysML validation engine (AQL rules)**: a SysML validator registered for the SysML package checks every Element that is not a root namespace. For each element it runs every rule declared on the element's EClass or any supertype (so a PartUsage is also checked against the Usage, Feature, Type, Namespace and Element rules). Each rule has a metaclass, a name taken from the specification, an 'aql:' boolean expression evaluated with 'self' bound to the element, an English message and a severity. A rule whose expression is not true (false, null or evaluation failure) produces one diagnostic. An `interval(lower, upper)` AQL service stands in for OCL's '..' range operator; it returns the integers from lower to upper inclusive, or an empty list when upper is below lower. The AQL interpreter is built once, with the SysML package plus the packages, service classes and service instances the rules provider supplies. · `SysONSysMLValidator.java`, `SysMLValidationRuleQueryServices.java`, `SysMLValidatorRegistrationConfiguration.java`
- **SysML v2 specification rules**: SysON implements the constraints (validation rules) of the SysML v2 specification as 383 built-in rules (the SysMLValidationRule enumeration) and runs them on the user's models. The rules were introduced in v2025.2.0, turned into an enumeration in v2026.3.0, and updated for the 2024-12 specification (v2025.4.0) and aligned with the 2025-04 specification (v2025.8.0). The user manual marks this experimental. _(experimental)_ · `SysMLValidationRule.java`, `validation.adoc`, `2025.8.0.adoc`
- **All spec rules are warnings**: every specification rule currently has severity WARNING ("arbitrarily", per the code), so all results appear under the Warning accordion. · `SysMLValidationRule.java`, `2025.8.0.adoc`
- **Pluggable rule set with severities**: a rules provider (SysONValidationRulesProvider) chooses which rules run, by default all spec rules; downstream applications can override it, possibly dynamically, and add their own rules with their own severities. The provider contract (IValidationRulesProvider) has four parts: the rules applicable to an EClass (by default every rule whose metaclass is that EClass or a supertype), extra AQL service classes, extra AQL service instances, and extra EPackages, so custom rules can call Java services and check elements of other metamodels. A rule is an IValidationRule (eClass, ruleName, 'aql:' expression, message, EMF severity int), e.g. a ValidationRule record. SysONSysMLValidationService's steps (resources to validate, diagnostician, diagnostician options, result sorting) are protected methods a subclass can override. · `SysONValidationRulesProvider.java`, `2026.3.0.adoc`, `CHANGELOG.adoc` v2026.3.0
- **Library-dependent rule expressions**: the rule expressions lean on SysML metamodel operations rather than plain OCL: 162 of the 383 rules call specializesFromLibrary('<library qualified name>') (e.g. 'Actions::Action', 'Parts::Part::ownedActions', 'Actions::TransitionAction::accepter'), and others call redefinesFromLibrary, redefines, specializes, isSubactionUsage, isTriggerAction, isSubstateUsage, inputParameters, inputParameter, referencedFeatureTarget, resolveGlobal, multiplicityHasBounds, ownedCrossFeature and similar. Each rule's message quotes the specification sentence, e.g. 'An ActionDefinition must directly or indirectly specialize the ActionDefinition Actions::Action from the Systems Model Library.' · `SysMLValidationRule.java`
- **Validation as a non-creatable representation**: the Validation view's content is a Representation (GraphQL type Validation {id, metadata, diagnostics}) produced from a ValidationDescription with id 'validation_description' and label 'Validation'. Its creation predicate is always false, so it is never offered as a new representation; it has no icons, and its target object is the editing context itself. A representation id starting with 'validation://' selects the validation event processor. Its representation metadata (id 'validation://', label 'Validation') carries the icon validation/validation.svg. A diagnostic object that is not an EMF Diagnostic is shown with kind 'Unknown' and an empty message. _(Sirius Web)_ · `ValidationDescriptionProvider.java`, `ValidationEventProcessorFactory.java`, `validation.graphqls`
- **One validation per project, computed on subscription**: the first subscriber for a project creates its validation event processor, which computes the diagnostics at once; every subscriber immediately receives the current validation, then each recomputation is broadcast to all open Validation views of that project. Recomputation happens through the refresher on qualifying changes, keeps the validation's id, and each computation's duration is recorded in a 'validation' metrics timer. _(Sirius Web)_ · `ValidationEventProcessor.java`, `ValidationCreationService.java`, `ValidationEventProcessorInitializer.java`
- **No EMF structural checks on SysML elements**: per the code, SysON's validator is registered as the EValidator of the SysML package and does not delegate to EMF's default object validator, so EMF's built-in checks (multiplicities, required features, unresolved proxies) are not reported for SysML elements; only rule results are. Every applicable rule is evaluated, with no stop at the first failure, so one element can produce several diagnostics. EDataType values are never checked (always valid). · `SysONSysMLValidator.java`, `SysMLValidatorRegistrationConfiguration.java`
- **Rule robustness fixes**: several AQL rules no longer raise AQL errors when evaluated (v2025.12.0); loading the rules no longer triggers AQL parser failures (v2026.9.0); AQL errors in the Class specialization rules were fixed (v2026.11.0). Every rule expression is parseable and validation data is sent on subscription without AQL errors on large projects (tests). · `2025.12.0.adoc`, `2026.9.0.adoc`, `ValidationRulesTests.java`
- **Rule set consistency checks**: unit tests guard the rule enumeration: it holds exactly 383 rules; each Java literal equals the rule name from the specification; every expression starts with 'aql:' and parses; every rule's metaclass belongs to the SysML package; and rule names start with 'check<Metaclass>' or 'validate<Metaclass>', except four spec names (checkIncludeUseCaseSpecialization, checkVerificationCaseSpecialization, validateSendActionParameters, validateSpecificationSpecificNotConjugated). · `SysMLValidationRuleUnitTests.java`
- **Fewer false featuring-type warnings**: the computation of a Feature's featuringType was improved (v2026.3.0) so that features owned through a FeatureMembership no longer wrongly fail checkFeatureFeatureMembershipTypeFeaturing ('If a Feature is owned via a FeatureMembership, then it must have a featuringType for which the operation isFeaturingType returns true.'). · `2026.3.0.adoc`

### API and scripts

- **uploadDocument multipart mutation**: POST /api/graphql/upload with a GraphQL multipart request (operations + map + file part) runs uploadDocument(input {id, editingContextId, file, readOnly: Boolean!}; the file variable is null in the operations and supplied as the multipart file part), returning UploadDocumentSuccessPayload {id, report} or ErrorPayload {messages {body, level}}. The UI upload uses it; a .sysml file uploaded this way becomes a model document, optionally read-only. The frontend sends it with fetch to <httpOrigin>/api/graphql/upload as FormData parts 'operations', 'map' ({"0": "variables.file"}) and '0' (the file), with credentials included, CORS mode and an X-XSRF-TOKEN header read from the XSRF-TOKEN cookie. On the server the success result also holds the new document (id, name, kind) and a map from old to new element ids, but the GraphQL payload exposes only id and report; each upload is logged ('Document <id> uploaded'). _(Sirius Web)_ · `document.graphqls`, `import_sysml_file.py`
- **insertTextualSysMLv2 mutation**: insertTextualSysMLv2(input {id, editingContextId, objectId, textualContent}) parses SysML v2 text and creates the elements inside the element identified by objectId, returning SuccessPayload (with messages) or ErrorPayload with messages. · `syson-import.graphqls`, `new_objects_from_text.py`
- **Textual export over REST**: GET /api/editingcontexts/{id}/documents/{documentId} with Accept: text/html returns the model as SysML v2 text when the document's first root is a SysML Element. The Accept values are tried in order (quality values ignored) until an exporter matches; the response is an attachment named after the document ('resource' if it has no name), with the matched Accept type as Content-Type and a Content-Length. A browser's Accept list goes on to application/xml after text/html, so a document whose first root is not a SysML Element, or an empty document, downloads as XML instead. ### Configuration

- **Node.js runtime required for textual import**: the textual parser is a JavaScript CLI started as an external 'node' process, so upload of .sysml/.kerml files, New objects from text and expression parsing need Node.js on the server's PATH; the installation requirements name Node.js 18.7, and the application Docker image installs nodejs 20.15.1 with npm. · `requirements.adoc`, `Dockerfile`, `SysmlToAst.java`

### Import pipeline

- **Textual import pipeline**: an uploaded file or inserted text is written to a temp .sysml file and parsed by the bundled syside-cli.js under Node ('dump') into a JSON AST in which every SysML concept is a node. ASTTransformer builds the containment tree (AstTreeParser with containment, attribute and non-containment reference handlers), records non-containment references as proxies, resolves them by name and type, and runs fix-up passes before and after resolution. Older docs describe the same flow with an ObjectFinder and generic/specific mappers. The input and (by default) the copied CLI are temporary files deleted after each parse (a CLI given by property is left in place); any parser output lines before the first '{' are skipped when reading the AST, and a JSON read failure is reported as a conversion error. · `SysmlToAst.java`, `ASTTransformer.java`, `Syson-DeveloperGuide.adoc`
- **Insert-text backend behavior**: for New objects from text, the AST is converted into SysML elements attached under the selected element and parser reports become INFO/WARNING/ERROR messages. Whenever at least one object is produced, the result is a semantic change and a SuccessPayload carrying all messages (shown as 'limitations'), even if some are errors; only an empty result fails, with 'Unable to convert the input into valid SysMLv2'. The text is always parsed as a .sysml fragment, without the upload's syntax-check pass, and DEBUG-level parser statuses are dropped. If objectId does not resolve to a SysML Element, the mutation returns an ErrorPayload with no messages and nothing happens. Per the code, the event handler does no read-only check of its own (only the menu hides the entry on read-only items), so a direct call to the mutation, e.g. from the recipe script, is not stopped on a read-only target. Each request increments an event-handler metrics counter. · `InsertTextualSysMLv2EventHandler.java`, `SysideSysMLTextImporter.java`
- **Placement of inserted top-level elements**: for New objects from text, the fragment is parsed as a standalone file, and the members of its root namespace are attached to the selected element one by one according to their kind: imports go straight into its owned relationships; an Expression that is not a Usage goes into the first expression ownership compatible with the target; a Feature under a Type gets a new FeatureMembership; anything under a Package or a plain Namespace gets a new OwningMembership (so a 'package' inserted into a package becomes its child, per the tests); a Relationship is added directly. Per the code, other combinations (e.g. a definition inserted under a part definition or a part usage) are not attached to the target, although they still count as created objects. · `ASTTransformer.java`, `SysideSysMLTextImporter.java`
- **Text-to-model importer API**: text insertion goes through a replaceable ISysMLTextImporter service, importSysMLText(editingContext, parent, text, messages), which returns the created elements and appends its diagnostics; the default implementation parses with SysIDE and converts with the AST transformer. ### Publishing a project as a library

- **Omnibox command 'Publish SysML project contents as library'**: in a project's omnibox (command palette, Ctrl/Cmd+K), the command (id publishProjectSysMLContentsAsLibrary, icon `/images/omnibox/publish.svg`, description 'Publishes the SysML contents of the project as a library that can be referenced by other projects.') is listed only when the PredicateCanEditingContextPublishSysMLProject predicate allows it, i.e. the project's semantic data uses the SysML domain (documents with SysML elements as root contents). Selecting it opens the publish dialog with publication kind Project_SysML_AllProperContents. Publishing is how dependencies between projects are defined (Sirius Web leaves the command to each studio maker; SysON ships this one). Like every workbench omnibox command, it is found by typing any part of its label (case-insensitive substring match, e.g. 'library' lists both the publish and import commands). The provider ignores the current selection. · `PublishProjectSysMLContentsAsLibraryCommand.tsx`, `SysONOmniboxCommandProvider.java`, `PredicateCanEditingContextPublishSysMLProject.java`
- **Publish library dialog**: small (sm), full-width dialog titled 'Publish SysML project contents as library' with the text 'Extracts the SysML contents of the project to publish them as a library that can be referenced by other projects.'. Fields: a required 'Version' text field (autofocused, placeholder 'Enter your version here...', helper 'The version cannot be empty', shown in error styling once edited and still blank) and an optional 'Description' field (placeholder 'Enter your description here...'). A 'See the published libraries' link opens `/libraries` in a new tab. The 'Publish' button is disabled while the trimmed version is empty and shows a loading spinner while publishing; the server's success or error messages are shown as toasts and the dialog closes as soon as a response arrives. Both fields are single-line, underlined (standard-variant) text fields; the helper text sits under Version at all times and only turns red once the field has been edited and is still blank. Only the emptiness check uses the trimmed value: the version (and description) are sent exactly as typed, so leading or trailing spaces become part of the published version string. There is no Cancel button and no Enter-to-submit: Escape or a backdrop click closes the dialog (and the omnibox) without publishing. A network failure shows the toast 'An unexpected error has occurred, please refresh the page'. _(Sirius Web)_ · `PublishLibraryDialog.tsx`, `usePublishLibraries.ts`, `publication.adoc`
- **Library namespace and name from project identity**: the publication handler (kind 'Project_SysML_AllProperContents') publishes the project's editing context as one library with namespace = project id, name = project name, and the version and description entered in the dialog; if the project or editing context can't be resolved it fails with "Could not find project with following editingContextId '<id>'.". Unlike import/update, `publishLibraries` is not routed through the editing-context dispatcher, so no project edit or view capability is checked, and the handler loads the project's editing context through the editing-context search service (the stored project state) rather than through the project's live event processor. Because the name is the project's name at publication time and versions are grouped by namespace and name, publishing again after renaming the project creates a separate library, which the 'Update library' dialog of consuming projects won't list as a newer version of the old one. · `SysONLibraryPublicationHandler.java`, `MutationPublishLibrariesDataFetcher.java`, `LibraryApplicationService.java`
- **Published contents: one library of all .sysml documents**: every proper document of the project whose name ends in '.sysml' (case-insensitive) goes into a single semantic data; KerML/SysML standard library resources, resources coming from referenced (imported) published libraries and non-.sysml resources are excluded. The new library's domains are the distinct EPackage nsURIs of the published documents. Each published document is serialized (as not read-only at serialization) before the library's semantic data is created. The result is one self-contained library named after the project. · `SysONSysMLLibraryPublisher.java`, `publication.adoc`, `SysONResourceService.java`
- **Published resources become read-only; element ids kept**: before publication each published resource's 'imported from textual SysML' flag (EAnnotation) is cleared and its metadata set read-only, so whether consumers can edit it depends only on the import kind (by reference = read-only, by copy = editable). - **Automatic library dependencies on publication**: SysON builds a dependency graph from the non-containment cross-references of the published resources; every referenced resource that comes from an already published library makes that library (namespace/name/version) a dependency of the new one, deduplicated, so the published library has no unresolved proxies. - **Library record created after publication**: publication first stores the published documents as new semantic data (documents, domains, computed dependencies); a follow-up transactional listener then creates the Library record (namespace, name, version, description) pointing to that semantic data, which makes the library appear in the Libraries page and the import dialog. · `SysONLibraryPublicationListener.java`, `SysONPublishedLibrarySemanticDataCreationRequested.java`

A representation whose content is missing is skipped with the server warning 'Cannot find representation content with id <id>'. ### Library concepts

- **Library: immutable, versioned, namespaced snapshot**: a library is a read-only snapshot of a project that other projects or libraries can reference; it has a namespace (id of the authoring project), name, version and description, can be neither unpublished nor overwritten, and several libraries may share a name and version if their namespaces differ. The Sirius Web user manual marks the libraries feature as experimental. _(Sirius Web; experimental)_ · `concepts.adoc`, `libraries.adoc`
- **Library versions are unordered strings**: versions are free strings with no natural order or semantic meaning, so moving between versions can have any size of impact, decided by the library authors. _(Sirius Web)_ · `library-import.adoc`
- **Library record storage**: libraries are stored in a `library` table (id, namespace, name, version, description, semantic_data_id, created_on, last_modified_on). Every column is mandatory, so an omitted description is stored as an empty string. A database unique constraint on (namespace, name, version) backs the immutability rule. The library's content lives in the referenced semantic data; a `library_dependency` table (library, dependency library, index) was added at the same time, and dependencies were later moved to the semantic data (v2025.4). Publishing emits a LibraryCreatedEvent. _(Sirius Web)_ · `03-add-library-table.xml`, `Library.java`, `ILibraryRepository.java`
- **Library document identity**: a library document's identity is its namespace plus its name, so renaming a document can break cross-document references for projects using the library. _(Sirius Web)_ · `library-import.adoc`

### Read-only library content

- **Read-only rules for libraries and imported resources**: a resource is read-only only when it is a library imported by reference (resource from a referenced library), a textual SysML file / model imported as read-only (metadata flagged read-only), or a KerML/SysML standard library (URI scheme) or SysON default library resource; everything else (local resources, copied imports containing Package and/or LibraryPackage, resources with no URI or no content) is editable. A Resource, EAnnotation or SysML Element inside a standard LibraryPackage is read-only even if its resource isn't. The check goes through IReadOnlyObjectPredicate and drives Explorer, Details and diagrams (disabled widgets, no edit actions). That predicate asks its registered delegates in turn; the first one that handles the object (SysON's delegate for Resources, EAnnotations and SysML Elements) decides. Otherwise the Sirius Web default applies, which reads the read-only flag of the object's document (false when the object has no document or no metadata). · `SysONReadOnlyObjectPredicateDelegate.java`, `SysONReadOnlyObjectPredicateDelegateTests.java`, `2025.10.0.adoc`

### Typing and specialization edits
- **One typing, subsetting, subclassification or redefinition per edit**: the shared helpers behind diagram direct edit (': T', ':> X', ':>> X'), dropping a Definition on a Usage, the 'New Feature Typing' / 'New Subsetting' part tools and the subject, actor, stakeholder and objective tools never stack relationships. ### Edge and connector semantics
- **Connector creation with feature-chain ends**: creating a binding, connection, flow or interface adds the connector to its container with two unnamed end features (FlowEnd for flows, PortUsage for interfaces, ReferenceUsage otherwise), each with a ReferenceSubsetting to its target; when the target is nested, the shortest feature chain from the container through the graphical container is built, otherwise the target is referenced directly. · `MetamodelMutationElementService.java`, `FeatureChainComputer.java`

### Deletion
- **Delete from model with cascade**: deleting an element (diagram or Explorer) removes it with its owning Membership and recursively collects what would dangle: Dependencies whose client or supplier is deleted (with their membership), Annotations, MembershipExposes of the deleted membership, FeatureTypings, Redefinitions, ReferenceSubsettings, Subclassifications and Subsettings pointing to it (e.g. a part's subsetting; since v2024.11.0 for subsetted Features), Successions whose source or target is deleted (with membership and any owning TransitionUsage), and transitions whose accept trigger referenced a deleted action; the same applies to all contained elements. ### Identity, persistence and references
- **SysML metamodel registration**: the SysML EPackage and its item-provider adapter factory are registered, supplying EMF labels, icons and property metadata for Explorer and Details. · `SysMLv2EMFConfiguration.java`
- **elementId assigned at creation**: every SysML element created through the SysML factory (e.g. Explorer New object, diagram tools) gets its elementId immediately, a random v4 UUID since a new element is not yet inside a library. The same generator gives a name-based v5 UUID (from the qualified name) to elements already inside a standard LibraryPackage; it also runs for duplicated copies and for the default 'Package1'/'LibraryPackage1' of new models. As coded, a standard LibraryPackage itself gets the v5 UUID of 'https://www.omg.org/spec/SysML/<qualified name>' (or '.../KerML/' for resources with the kermllibrary scheme) in the URL namespace 6ba7b811-9dad-11d1-80b4-00c04fd430c8; a named element inside it gets the v5 UUID of its qualified name in the namespace of its library package's elementId; Imports, Memberships, Specializations, TypeFeaturings and elements without a declared name stay random v4. An element counts as standard-library content when its nearest LibraryPackage has isStandard = true; standard library resources are those whose URI starts with 'kermllibrary' or 'sysmllibrary'. · `SysmlFactoryImpl.java`, `ElementUtil.java`, `SysONDefaultResourceProvider.java`
- **Stable ids for standard library elements**: the identity service returns the elementId (stable across library updates) as the id of standard-library elements, so diagrams and selections pointing at them survive library upgrades; other elements keep the default id. · `SysONIdentityService.java`
- **Ids for implied relationships**: implied relationships are not serialized; when asked for an id they get a generated deterministic UUID so implicit specializations can be shown and selected (e.g. Related Elements view). · `SysONIdentityService.java`
- **Library references persisted by elementId**: copied library resources use forced default reference serialization, so references from user models to library elements store the elementId instead of the Sirius Web id; a shared copier copies all cross-references after all elements so inter-library references stay correct. · `StandardLibrariesLoader.java`
- **Modeled identifiers in JSON resources**: EMF's intrinsic ID-to-EObject map is enabled for JSON resources so languages with modeled ids (SysML elementId) resolve objects by them. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Inter-model references within a project**: elements can reference elements of other models (documents) of the same project, with proxy resolution. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Inverse reference navigation**: an ECrossReferenceAdapter on the editing context allows navigating who references an element; since v2025.12.0 it is EMF's default ECrossReferenceAdapter (obtained with ECrossReferenceAdapter.getCrossReferenceAdapter), replacing Sirius Web's custom EditingContextCrossReferenceAdapter. - **Reachable elements of a metaclass from the cache**: the getAllReachable(metaclass) service behind edge semantic candidates (e.g. all AllocationUsages, SuccessionAsUsages, states) reads the per-metaclass element cache of the project's resource set instead of walking the model (v2024.3.0 #112). ### Service organization
- **Layered editing services**: since v2025.10.2/v2025.12.0 SysON's semantic services are split by layer: atomic SysML queries/mutations in `syson-sysml-metamodel-services` (no Spring, Sirius Web, diagram or table dependency), Sirius-Web-backed model services and 'accelerators' combining atomic operations (e.g. a connection with its required ports) in `syson-model-services`, and per-representation services in diagram, table, tree, form and representation modules. Classes are named by purpose (ModelQuery/ModelMutation, DiagramQuery/DiagramMutation, DiagramQueryLabel/DiagramMutationLabel, same for tables, trees, forms), and each module exposes its AQL-callable entry points only through *AQLService classes that delegate to the others; older services are migrated progressively (e.g. ImportService became MetamodelMutationImportService, the Details services became FormMutationElementService/FormQueryElementService in v2026.11.0). · `index.adoc`, `CHANGELOG.adoc` v2025.12.0, `CHANGELOG.adoc` v2026.11.0
- **Type-safe AQL service calls**: AQL service-call expressions are built from serializable Java method references (`ServiceMethod.of0..ofN`, `ofStatic0..`, arity = parameters after self), producing the same AQL strings as the string helpers; since v2026.3.0 a call built with the wrong number of arguments throws, so the application fails to start; a test checks that every public method of the AQL service classes is used in some AQL expression. · `index.adoc`, `CHANGELOG.adoc` v2026.3.0, `JavaServiceTests.java`
