## APIs & integrations

### SysML v2 REST API: overview and documentation
- **SysML v2 REST API (OMG Systems Modeling API subset)**: a partial implementation of the OMG Systems Modeling API (SysML v2 REST API, introduced in 2024.11.0) for tool integrations. Every endpoint starts with `/api/rest/`. It covers projects, branches, commits, commit changes, elements, relationships and roots. Each project has exactly one commit and one branch, both carrying the project's ID; in the first version, before commits existed, the commitId could simply be the projectId. In SysON, the object endpoints are backed by SysONObjectRestService and the data-versioning endpoints by SysONProjectDataVersioningRestService. Tests cover projects, elements, element by id, relationships, roots, changes and change by id, and unknown projects return an error. The docs say the standard API is not fully available yet and point to SysML textual file exchange for interoperability in the meantime. Sirius Web's own REST and GraphQL developer pages carry the "experimental" banner. _(Sirius Web)_ · `api-details.adoc`, `api.adoc`, `CHANGELOG.adoc` v2024.11.0
- **Swagger UI and OpenAPI document**: a running server serves an interactive Swagger UI at `http://<server>:8080/swagger-ui/index.html`. It lists every endpoint with every response code and lets you try requests with parameters and see the responses. The machine-readable OpenAPI v3 description is served under `/v3/api-docs`, with the group "rest-apis" covering `/api/rest/**` at `/v3/api-docs/rest-apis`. The documentation site's "API details" page embeds a static copy (`sirius-web-openapi.json`) with "Try it out" disabled. For uploads, the docs advise sending the correct Content-Type (typically application/json). _(Sirius Web)_ · `OpenApiConfiguration.java`, `api-details.adoc`, `api-rest.adoc`

### REST: projects
- **List projects (keyset pagination)**: `GET /api/rest/projects` returns Project records {`@id`, `@type: 'Project'`, `created` (always the epoch 1970-01-01, serialized as an ISO-8601 string), `defaultBranch {@id}`, `description` (null), `name`}. Query parameters are `page[size]` (default 20) and `page[after]` / `page[before]` (Relay global-id cursors). When more pages exist, a `Link` response header carries the page URL with `rel="next"` (going forward) or `rel="prev"` (going backward). _(Sirius Web)_ · `ProjectRestController.java`, `RestProject.java`, `CHANGELOG.adoc`
- **Get project by id**: `GET /api/rest/projects/{projectId}` returns the project (`@id`, `name`...) with 200, or 404 Not Found when it does not exist. _(Sirius Web)_ · `ProjectRestController.java`
- **Create project**: `POST /api/rest/projects?name=...&description=...` creates a project and returns 201 Created with its `@id` and `name`. It uses the default project template provider when one is registered and the blank project template otherwise; SysON registers no default provider, so the project is always blank. The `description` parameter is accepted but not stored. If creation fails (for example, the template cannot be applied), the controller returns no response entity, because the specification defines no other status, so the client gets an empty body. _(Sirius Web)_ · `ProjectRestController.java`
- **Rename project (update)**: `PUT /api/rest/projects/{projectId}?name=...` only renames the project and returns 200 with the updated project. The `description` and branch parameters are accepted but ignored. It returns 404 when no name is given, the project is unknown or the rename fails. _(Sirius Web)_ · `ProjectRestController.java`
- **Delete project**: `DELETE /api/rest/projects/{projectId}` deletes the project and returns 200 with the deleted project's `@id` and `name`, or 204 No Content when the deletion produces an error. _(Sirius Web)_ · `ProjectRestController.java`

### REST: commits and changes
- **List commits (single implicit commit)**: `GET /api/rest/projects/{projectId}/commits` always returns exactly one Commit {`@id` = projectId, `@type: 'Commit'`, `created` = 1970-01-01T00:00:00Z, `description: 'The one and only commit for this project'`, `owningProject`, `previousCommits: []`} that represents the project's current state, or 404 for an unknown project. The API cannot create additional commits. _(Sirius Web)_ · `CommitRestController.java`, `DefaultProjectDataVersiongRestService.java`, `api-details.adoc`
- **Get commit by id**: `GET /api/rest/projects/{projectId}/commits/{commitId}` returns the single commit only when commitId equals the project id, otherwise 404. _(Sirius Web)_ · `CommitRestController.java`, `DefaultProjectDataVersiongRestService.java`
- **Create commit (create, update and delete elements)**: `POST /api/rest/projects/{projectId}/commits` takes an optional `?branchId`, which is ignored, and a Commit body {`@type`, `description`, `change: [DataVersion]`}. It amends the project's single commit instead of adding one. Each DataVersion is handled as follows:
  - A payload with no identity creates an element of the payload's `@type`, which must be a concrete, non-interface class; abstract and interface types are skipped.
  - An identity with a payload updates that element.
  - An identity with no payload deletes that element.

  Deletions run first, then new objects are filled from their payloads, then updates. A new object that no containment reference attaches becomes a root of the project's first document. The call returns 201 with that same commit; the request `description` is not stored. On failure, or for an unknown project, the response has an empty body. The call did nothing in 2025.1.0 and has amended the commit since 2025.4.0. _(Sirius Web)_ · `CommitRestController.java`, `DefaultProjectDataVersiongRestService.java`, `CHANGELOG.adoc` v2025.4.0
- **Commit payload semantics (partial, additive)**: when a DataVersion creates or updates an element, only the features named in its payload are set; unknown and transient features are ignored. Attributes are set by converting each value's string form. Single-valued attributes and references are replaced. Multi-valued references are appended to, not replaced. References are given as `{"@id": ...}` objects, and each id is looked up among existing elements, then among the objects created in the same commit under that payload `@id`. Linking a new object through a containment reference attaches it, so a single commit can create and nest objects. _(Sirius Web)_ · `EObjectRestDeserializer.java`, `DefaultProjectDataVersiongRestService.java`, `create_element_recipe.adoc`
- **REST recipe: create an element through two membership commits**: a documented recipe creates a PartDefinition under Package1 from Swagger UI or any REST client:
  1. POST a commit that creates an OwningMembership with a client-chosen random `@id`/`elementId` and links it to the package through `ownedRelationship`.
  2. POST a commit that creates the PartDefinition (`declaredName`) and links it to the membership through `ownedRelatedElement`.
  3. GET `/elements` to confirm the result.

  The client-supplied random id becomes the element's final `@id`/`elementId`. · `create_element_recipe.adoc`
- **List commit changes**: `GET /api/rest/projects/{projectId}/commits/{commitId}/changes` returns every model element as a DataVersion {`@id`, `@type: 'DataVersion'`, `identity {@id: elementId, @type: 'DataIdentity'}`, `payload`: the element as SysML v2 JSON}. Implied relationships and the standard libraries are excluded. The change id is a name-based UUID (`UUID.nameUUIDFromBytes(commitId + elementId)`), so it stays the same across calls. The listing cannot tell CREATED, UPDATED and DELETED apart. The optional `changeTypes` query parameter (CREATED, UPDATED, DELETED) is accepted but ignored, because the controller always passes an empty list, so the full element list always comes back. A commitId other than the project id returns an empty list. SysON overrides Sirius Web's default here, which since a Sirius Web fix returns valid JSON. · `SysONProjectDataVersioningRestService.java`, `CommitRestController.java`, `GetCommitChangeRestEventHandler.java`
- **Get one commit change by id**: `GET /api/rest/projects/{projectId}/commits/{commitId}/changes/{changeId}` returns the single DataVersion whose computed change id matches (the element serialized as SysML v2 JSON), or 404. · `SysONProjectDataVersioningRestService.java`, `CommitRestController.java`

### REST: branches
- **List branches (single default branch)**: `GET /api/rest/projects/{projectId}/branches` returns one Branch {`@id` = projectId, `@type`, `created` (epoch), `head` (the project's commit), `name: 'defaultBranch'`, `owningProject`}, or 404 for an unknown project. Sirius Web's default implementation handles the branch endpoints. _(Sirius Web)_ · `BranchRestController.java`, `DefaultProjectDataVersiongRestService.java`
- **Get branch by id**: `GET /api/rest/projects/{projectId}/branches/{branchId}` returns the default branch only when branchId equals the project id, otherwise 404. _(Sirius Web)_ · `BranchRestController.java`
- **Create branch (not supported)**: `POST /api/rest/projects/{projectId}/branches` (body with a branch name and head commit) exists in the API, but the implementation does not allow several branches per project, so it creates nothing and returns nothing. _(Sirius Web)_ · `BranchRestController.java`, `DefaultProjectDataVersiongRestService.java`
- **Delete branch (no-op in SysON)**: `DELETE /api/rest/projects/{projectId}/branches/{branchId}` never deletes the only branch. SysON's implementation looks the branch up and returns it with 200, or returns 404 for an unknown branch. · `SysONProjectDataVersioningRestService.java`, `BranchRestController.java`

### REST: elements, relationships and roots
- **Get all elements**: `GET /api/rest/projects/{projectId}/commits/{commitId}/elements` returns every element of the project as SysML v2 JSON: each root element plus all its contents. Implied relationships (`isImplied = true`) and the KerML/SysML standard library resources are excluded. In practice commitId is the project id. It returns 404 when the project or commit is unknown or when the editing context does not answer within 20 s. · `SysONObjectRestService.java`, `ObjectRestController.java`, `fetch_elements.py`
- **Get element by id**: `GET /api/rest/projects/{projectId}/commits/{commitId}/elements/{elementId}` returns one element as SysML v2 JSON, or 404 Not Found. The delete recipe uses the 404 to check that a deletion worked. · `SysONObjectRestService.java`, `ObjectRestController.java`, `get_owned_elements.py`
- **Get relationships of an element by direction**: `GET .../commits/{commitId}/elements/{relatedElementId}/relationships?direction=IN|OUT|BOTH` returns the relationships related to an element, with direction defaulting to BOTH when omitted. In SysON, OUT returns the element's `ownedRelationship`, IN returns the Relationship objects that reference the element through inverse (non-containment) cross-references found by the cross-reference adapter, and BOTH returns the union without duplicates. Implied relationships are filtered out, and an unknown project returns 404. · `SysONObjectRestService.java`, `ObjectRestController.java`, `Direction.java`
- **Get root elements**: `GET /api/rest/projects/{projectId}/commits/{commitId}/roots` returns the owned elements of each user document's root Namespace (typically the top-level packages) and skips the standard library resources. It returns 404 otherwise. · `SysONObjectRestService.java`, `ObjectRestController.java`

### REST: JSON serialization
- **SysML v2 JSON serialization of elements**: every JSON response of the object REST endpoints and commit-change payloads uses a custom serializer. Each element is a JSON object with `@id` (always the elementId) and `@type` (the metaclass name), then every attribute and reference sorted alphabetically by name (since 2025.8.0). The `@id` equals the `elementId` attribute (since 2025.8.0); the standard has not decided whether the two must match, and SysON does this for ease of use. Null values are written explicitly as `null`. Enum values use their lowercase literal. Primitive values are typed JSON numbers and booleans rather than strings (since 2025.8.0). Dates are ISO strings. A single reference is written as `{"@id": ...}` and a multi-valued reference as an array of `{"@id"}`. Implicit (virtual-link) elements are omitted, and so are standard-library elements in lists, which means a non-inherited reference to a library element is not serialized either. Ecore `eAnnotations` are skipped (since 2025.12.0). The custom mapper is applied by a response-body advice scoped to the object REST controllers' package (other endpoints keep the default Jackson mapping), runs only for JSON-compatible responses, writes dates as ISO strings rather than timestamps, and is hidden from the OpenAPI document. · `SysMLv2JsonSerializer.java`, `SysMLv2SerializerConfig.java`, `CHANGELOG.adoc` v2025.8.0
- **Date serialization fix (successive calls no longer crash)**: date fields are serialized with jackson-datatype-jsr310, so successive REST API calls no longer crash the server. · `2025.2.0.adoc`, `CHANGELOG.adoc` v2025.2.0

### APIs cookbook (Python scripts)
- **Cookbook setup**: the Developer guide's "APIs Cookbook" ships standalone Python scripts adapted from the OMG SysML v2 API Cookbook, which was originally written for Jupyter Lab. They need the `requests` and `pandas` libraries (`pip install requests pandas`). `init_api.py` defines the host `http://localhost:8080/api/rest` (replace it for a remote server) and a shared argument parser for `project_id` and an optional `element_id`. Element ids are generated randomly by the server, so outputs differ from run to run. · `api-cookbook.adoc`, `init_api.py`
- **Recipe: fetch projects**: `python fetch_projects.py` sends `GET {host}/projects` and prints `Project Name: <name>, ID: <@id>` for each project, or the status code and error text. · `fetch_projects.py`, `project_commit_branch_tag_recipe.adoc`
- **Recipe: create project**: `create_project.py` lists the projects, POSTs a project named `New Project - <timestamp>`, then lists the projects again. · `create_project.py`, `project_commit_branch_tag_recipe.adoc`
- **Recipe: fetch commits / latest commit**: `python fetch_commits.py <project-id>` lists the commit ids through `GET {host}/projects/{id}/commits`. Its `get_last_commit_id()` takes the last entry, and the other recipes reuse it to address elements. · `fetch_commits.py`, `project_commit_branch_tag_recipe.adoc`
- **Recipe: fetch elements**: `python fetch_elements.py <project-id>` gets the latest commit, then `GET .../commits/{commitId}/elements`, and prints each element's `@id` and name. · `fetch_elements.py`
- **Recipe: owned elements (immediate and recursive)**: `python get_owned_elements.py <project-id> <element-id>` GETs an element and follows its `ownedElement` references. It prints the immediate owned elements, then the whole owned hierarchy recursively and indented, as ` - name (id, type)`, with `N/A` for unnamed elements such as LiteralString. · `get_owned_elements.py`, `element_owned_elements_recipe.adoc`
- **Script: parts, behaviors and requirements trees**: `python get_feature_members.py <project-id> <element-id>` recursively follows `ownedFeature` while the element type matches a member type. It prints three trees: "Parts Tree" (PartUsage), "Behaviors Tree" (ActionUsage) and "Requirements Tree" (RequirementUsage). · `get_feature_members.py`
- **Recipe: delete an element and verify**: `python delete_element.py <project-id> <element-id>` gets the latest commit, checks that the element exists and prints its name, id and type. It then POSTs a commit with a DataVersion that carries only the identity. Finally it re-reads the latest commit and checks that the element endpoint returns 404, printing "deleted successfully", or reports "Deletion verification failed". · `delete_element.py`, `delete_element_recipe.adoc`
- **Recipe: import a .sysml file (GraphQL upload)**: `python import_sysml_file.py [url] <file-path> <project-id> [--read-only]` (url defaults to `http://localhost:8080`) checks that the file exists, resolves the project's editing context with `viewer.project(projectId).currentEditingContext.id`, then POSTs a GraphQL multipart request (`operations`, `map` = `{"0": "variables.file"}`, the file part sent as text/plain) to `/api/graphql/upload` running `uploadDocument(input: {id, editingContextId, file, readOnly})`. On UploadDocumentSuccessPayload it prints "SysML file imported successfully: <path>" and then "Import report:" with the server's report, if any; on an ErrorPayload it prints each message as `LEVEL: body`. The recipe advises importing dependent SysML/KerML files first, or some relationships stay unresolved. · `import_sysml_file.py`, `import_sysml_file_recipe.adoc`
- **Recipe: new objects from text (insertTextualSysMLv2)**: `python new_objects_from_text.py [url] <file-path> <project-id> <namespace-elementId>` reads a SysML v2 text file and calls the `insertTextualSysMLv2` mutation with the project's editing context id and the target element id, creating the file's content under that element. It prints "SysML v2 file imported successfully: <path>" on a SuccessPayload, or "Error: <body>" for each ErrorPayload message. · `new_objects_from_text.py`, `new_objects_from_text.adoc`
- **Recipe: download a document as a .sysml file**: `python download_sysml_file.py [url] <project-id> <document-id> <output-path>` resolves the editing context through GraphQL, then GETs `/api/editingcontexts/{editingContextId}/documents/{documentId}` with `Accept: text/html` (the media type that selects SysON's textual exporter). It streams the body to the output file in 8192-byte chunks so large models are not buffered, and prints "SysML file downloaded successfully: <path>". The Explorer has no "copy document id" action, so the document id comes from the retrieve-project-documents recipe or from the create/upload operation. · `download_sysml_file.py`, `download_sysml_file_recipe.adoc`
- **Recipe: retrieve project documents**: `python retrieve_project_documents.py [url] <project-id>` downloads the project ZIP from `/api/projects/{id}` and finds `*/manifest.json`. It prints `Document Name: X, Document ID: Y` for each entry of `documentIdsToName`, sorted by name case-insensitively, or "No documents found in the project manifest" when there are none. · `retrieve_project_documents.py`, `retrieve_project_documents_recipe.adoc`
- **API troubleshooting guidance**: for 400/500 errors, check the endpoint URLs, project_id, commit_id and authentication tokens, and confirm the API is running. For empty responses, check that the queried elements exist in that project and commit, and inspect them in the SysON web UI. On large models, limit the recursion depth. · `api-cookbook.adoc`

### HTTP download and locale endpoints
- **Document download with content negotiation**: `GET /api/editingcontexts/{editingContextId}/documents/{documentId}` downloads one document; the Explorer's document Download action uses it. It walks the request's `Accept` media types in order until a registered exporter can handle the document; quality values are ignored and each exporter matches only its exact type, so an `Accept: */*` header alone (curl's default) matches nothing and gets 404. In SysON, `text/html` gives SysML v2 text (only when the document's first root is a SysML Element), `application/json` gives the EMF JSON format (with schema location and the platform's UUID id manager, the same as the stored format) and `application/xml` gives XMI (UTF-8, schema location and `xmi:type` attributes); a serialization failure is logged as a warning. The response is an attachment: Content-Disposition carries the document name as filename, Content-Type is the accepted type, and Content-Length is set. It returns 404 when the document or a matching exporter is missing. The file name is the document's name, or "resource" when it has none. Pluggable document lookups run before the editing-context search; SysON adds one that finds standard-library documents by id, so the KerML and SysML library documents can be downloaded too (they answered 404 before 2025.2.0). The Explorer's Download entry is a plain link, so the browser's navigation Accept header (text/html first) makes SysON return SysML documents as SysML v2 text. The cookbook's download-SysML-file recipe uses this endpoint. _(Sirius Web)_ · `DocumentDownloadController.java`, `SysMLv2DocumentExporter.java`, `download_sysml_file_recipe.adoc`
- **Project archive download**: `GET /api/projects/{projectId}` downloads the project as a zip archive named `<project name>.zip` (Content-Type `application/zip`, Content-Length set, attachment disposition). The optional `?name=` parameter selects which semantic data to export; without it the project's default semantic data is used. It answers 404 when the project or semantic data is unknown or when the Project download capability is denied. In the UI it is reached from the "Download" entry of the project's navbar menu (and the project browser row menu), a plain link that adds `?name=` when a semantic data name is known. _(Sirius Web)_ · `ProjectDownloadController.java`, `DownloadProjectMenuItem.tsx`, `retrieve_project_documents.py`
- **Export selected objects (e.g. CSV)**: `GET /api/editingcontexts/{editingContextId}/objects?contentType=...&objectIds=...` (ids comma-separated) exports the objects in the requested content type as an attachment named `objects.csv`. Unknown ids are skipped. The only exporter handles `text/csv` and writes a header row `id,type,label`, then one row per object: its id, its EClass name (or Java class name, or "null") and its label, in UTF-8. Any other content type, or an unknown editing context, returns 404. The Query view's "Export as CSV" button links to it with `contentType=text/csv` and the objects returned by the evaluated expression. _(Sirius Web)_ · `ObjectDownloadController.java`, `CsvObjectExporter.java`, `ExportAsCsvButton.tsx`
- **Locale bundle endpoint**: `GET /api/locales/{language}/{namespace}.json` serves the UI translation file `classpath:i18n/{language}/{namespace}.json`, or 404 when it does not exist. The frontend loads every namespace listed by `Viewer.namespaces` for `Viewer.language` from it. _(Sirius Web)_ · `LocaleController.java`, `URLConstants.java`, `i18n.graphqls`

### GraphQL API: endpoint and conventions
- **GraphQL API endpoint**: all client-server traffic goes through one GraphQL API at `POST /api/graphql`, which holds every query and mutation the SysON UI uses and lets clients fetch only the data they need. A WebSocket subscriptions endpoint at `/subscriptions` delivers live updates. The schema is schema-first, assembled from every `schema/**/*.graphqls` file on the classpath, with paginated fields. Queries run asynchronously and mutations run serially in request order. Files are sent as multipart uploads through the `Upload` scalar, and dates use the `Instant` scalar. Every mutation returns a union of ErrorPayload or a success payload, both carrying messages with a level (SUCCESS, INFO, WARNING, ERROR) that the UI shows as toasts. Connections return PageInfo with count, start/end cursors and hasNext/hasPrevious. The SysON cookbook's `new_objects_from_text.py` and `import_sysml_file.py` call it. _(Sirius Web)_ · `core.graphqls`, `GraphQLConfiguration.java`, `api.adoc`
- **GraphQL introspection and usage practice**: the schema mirrors UI concepts (projects, libraries, representations...) and can be introspected (e.g. `__schema { types { name } }`) with GraphiQL or any GraphQL IDE. Mutations mirror UI actions such as creating projects and representations or executing tools. The recommended practice is to watch the browser's network tab to see the client's queries, and to add rate limiting or query-complexity guards when exposing the API. _(Sirius Web; experimental)_ · `api-graphql.adoc`, `api.adoc`
- **GraphQL upload endpoint**: the GraphQL controller also accepts multipart POSTs on `/api/graphql/upload`, and every file upload uses it. The request has the parts `operations`, `map` and `file`, is sent with credentials, and carries an `X-XSRF-TOKEN` header read from the `XSRF-TOKEN` cookie. It follows the GraphQL multipart request spec but handles only one file, the part with index 0, which is put into the operation's file variable. A successful run answers 201 Created with the GraphQL result; an `operations` or `map` part that cannot be parsed answers 400 Bad Request. _(Sirius Web)_ · `GraphQLController.java`, `sendFile.ts`
- **HTTP GraphQL responses and error logging**: `POST /api/graphql` takes `{query, variables, operationName}` and always answers 200 OK with the standard GraphQL result (`data` and/or `errors`). When the result carries GraphQL errors, the server logs the whole pretty-printed result as a warning. An exception thrown by a data fetcher is logged as a warning with its stack trace and returned as a standard "exception while data fetching" error at that path instead of failing the whole request. At startup each schema file is logged at DEBUG ("Processing the GraphQL schema: <url>", with the count found) and the complete merged schema is printed at TRACE. _(Sirius Web)_ · `GraphQLController.java`, `GraphQLDataFetcherExceptionHandler.java`, `GraphQLConfiguration.java`
- **GraphQL over WebSocket (subscriptions)**: subscriptions run over a WebSocket at `/subscriptions` (`ws://` or `wss://` on the same host) using the "graphql-ws" subprotocol of the legacy subscriptions-transport protocol: the client sends `connection_init` and gets `connection_ack`, sends `start` messages with its own id and `{query, variables, operationName}`, receives `data` messages with that id, and sends `stop` to unsubscribe. Queries and mutations can be sent the same way. The server answers `connection_init` with `connection_ack` followed at once by a `ka` keep-alive, ends an operation with a `complete` message, and reports a failed execution with an `error` message carrying the operation id. Any message without a textual `type`, of an unknown type or that cannot be parsed gets a `connection_error` reply (and a warning in the log). A `start` is accepted even without a prior `connection_init`, and `connection_init` carries no authentication. Closing the socket cancels every running subscription of that session. The server sends a keep-alive every 28 seconds, accepts text and binary messages up to 100,000 bytes, and checks the origin against `sirius.components.cors.allowedOriginPatterns`. The web client splits traffic with Apollo: subscriptions go through a lazy, auto-reconnecting WebSocket link, everything else through HTTP. Every query, watched query and mutation uses the `no-cache` fetch policy, so results always come from the server, the Apollo devtools are enabled, and a logging link writes "<kind> <operationName>: request sent" and "... response received" to the browser console at debug level. Integrators can adjust the HTTP, WebSocket, cache and client options through frontend extension points. _(Sirius Web)_ · `GraphQLWebSocketHandler.java`, `WebSocketConfiguration.java`, `useCreateApolloClient.ts`
- **Standard API error messages**: the backend returns a fixed set of messages in ErrorPayloads, which the UI shows as toasts:
  - "Invalid input type, "{0}" has been received while "{1}" was expected" for an input sent to the wrong handler
  - "The request has been interrupted due to a timeout" (5-second fallback)
  - "You are not authorized to perform this operation"
  - "An unexpected error has occurred, please contact the server administrator"
  - "The object with id "{0}" does not exist", "The object has not been found" or "Not found"
  - "The creation of the new object has failed", "Invalid name", "Failed to rename the element", "Failed to delete the element"
  - "An error occurred while executing the operation: {0}"
  - "Unable to create a new instance of "{0}" in feature "{1}" because it has reached its upper-bound cardinality", "No containment feature found for this element" and "An element is already present for this mono-valued feature" for creations that the metamodel forbids
  - "The dropped object is invalid", "The duplication of the object has failed", "The file is unreadable" and "Failed to find the dependencies of the project"

  The backend messages also exist in French and follow `spring.mvc.locale`. _(Sirius Web)_ · `messages.properties`, `sirius-components-collaborative.properties`, `sirius-components-emf.properties`

### GraphQL API: platform queries and mutations
- **Viewer root and editing context lookup**: `Query.viewer` is the root of every read. `viewer.editingContext(editingContextId)` returns an editing context, a project's live model space. `viewer.project(projectId).currentEditingContext(name)` resolves a project's editing context id, optionally by semantic-data name ("main" by default). Scripts use it to call editing-context mutations. For example, `viewer { project(projectId) { currentEditingContext { id stereotypes { edges { node { id label } } } } } }` returns the editing context id and the document stereotypes (model kinds). _(Sirius Web)_ · `siriusweb.graphqls`, `getCurrentEditingContextId.ts`, `api.adoc`
- **Object lookup queries**: `editingContext.object(objectId)` and `objects(objectIds)` return model elements as Object {id, kind, label, iconURLs}, plus their library when the element comes from a library. A model is labelled with its name and shown with the `/icons/Resource.svg` icon; a representation uses its metadata label and icons. Selection, the Details view and the omnibox use these queries. _(Sirius Web)_ · `core.graphqls`, `DefaultLabelService.java`, `libraries.graphqls`
- **Object labels lookup**: the `getObjectsLabels` query returns the id and label of a list of objects in a project, given their ids. The Explorer's and the diagram's reveal-selection toolbar buttons use it to build tooltips listing the labels of the selected elements; errors are shown as toasts. _(Sirius Web)_ · `useObjectsLabels.ts`, `RevealSelectionButton.tsx`, `RevealSelectionInDiagramButton.tsx`
- **Query-based (AQL) fields**: EditingContext and Object both expose `queryBasedString`, `queryBasedInt`, `queryBasedBoolean`, `queryBasedObject` and `queryBasedObjects(query, variableName?)`. These data fetchers evaluate an AQL/interpreter expression on the editing context's content on the server and return the typed result, so clients can compute ad-hoc model data without a dedicated API. _(Sirius Web)_ · `core.graphqls`, `QueryBasedObjectsEventHandler.java`, `CHANGELOG.adoc`

### Interchange and integrations
- **Interoperability support matrix (project/model exchange)**: projects and models can be exchanged with other tools through the Explorer and project download/upload actions and the API. The key features list these levels:
  - Download/Upload JSON: supported, in SysON's own format only.
  - SysML v2 textual format: partial.
  - Standard SysML v2 JSON: not supported, for import or export.
  - SysML v2 Standard API: partial.

  The underlying platform exchanges projects and models as JSON, and its architecture overview also names REST, GraphQL and API builders for developers. · `key-features.adoc`, `interoperability.adoc`, `collaboration.adoc`
- **Model sharing with other SysML v2 tools**: models are meant to be exchanged with other vendors' SysML v2 tools through the SysML v2 textual notation (download as `.sysml`) and the SysML v2 API. · `faq.adoc`
- **SysML v2 textual export format**: the textual exporter serializes only the document's first root element (normally the root Namespace) with tab indentation, the server platform's line separator and escaping of special characters. Cross-references are written as the shortest name that resolves from the referencing element's context, computed with caches of visible memberships, deresolved names and qualified names. A name is written between single quotes when it contains characters outside the basic-name set, does not start with a letter or underscore, or is a SysML keyword. Comment bodies cannot contain `*/` in the grammar, so that sequence is written as `* /` and a warning is reported (since 2026.9.0); backslashes in LiteralString values are escaped. Serializer status messages are written to the server log, and a document that serializes to nothing gives an empty file. The text is encoded with the server JVM's default charset. A per-export membership cache speeds up large models. · `SysMLv2DocumentExporter.java`, `NameHelper.java`, `CHANGELOG.adoc` v2026.9.0
- **SysML v2 API and Services for cross-domain linking and traceability**: SysON is built on the SysML v2 API and Services and exposes model content through standard REST APIs for integration with requirements tools, simulation tools and PLM. Compliance is described as partial, aiming for full. · `faq.adoc`, `key-features.adoc`
- **Integration foundations for linking with other models**: there is no generic model-integration feature, but import/export, references and the APIs allow SysML v2 models to be linked with, for example, Polarion requirements, Arcadia architectures or domain models. · `faq.adoc`
- **Office documents via M2Doc**: integrating model-to-text tools such as M2Doc lets SysON generate Word documents (documentation, reports, specifications) that stay in sync with the SysML v2 model. Unverified in code. · `faq.adoc`, `index.adoc`
- **Capella integration (envisioned)**: a planned integration, not yet implemented, in which SysON would serve as a SysML v2 editing component inside Capella, synchronizing and co-designing SysML v2 models with Capella projects. · `capella.adoc`
- **Papyrus and Capella positioning**: the README describes SysON as the core of Papyrus's SysML v2 model-editing feature and as enabling co-design of SysML v2 models alongside Eclipse Capella. It commits to the standard API and the SysML v2 textual notation as exchange formats, and offers graphical, textual, form-based and table editors. Unverified in code. · `README.md`
- **VS Code extension (Sirius Web client)**: a "Sirius Web" VS Code extension connects to a Sirius Web server. ### Backend extension and integration APIs
- **Embedding the collaborative runtime (editing contexts, inputs and handlers)**: an application that embeds Sirius Components connects to the IEditingContextEventProcessorRegistry and must provide two services: IEditingContextSearchService, which loads an editing context (from a database or anywhere else; it only needs a unique id), and IEditingContextPersistenceService, which saves it (a no-op for purely in-memory use). Every change is an `IInput` dispatched with `dispatchEvent`, handled by the first IEditingContextEventHandler that accepts it, and answered with an `IPayload` whose id must equal the input id (a correlation id). A handler emits the payload on one Reactor sink and a ChangeDescription on another; a SEMANTIC_CHANGE refreshes every impacted representation and saves the editing context. ICausalityChainVisitor#findFirstCauseOfType finds the original input behind a chain of causes. Custom inputs, payloads and handlers can be added the same way. _(Sirius Web)_ · `embed-sirius-components.adoc`
- **Reusable backend stack and per-representation GraphQL schemas**: the backend is built on Spring Boot, Project Reactor, GraphQL Java (its own HTTP and WebSocket integration, which predates Spring GraphQL and Netflix DGS), EMF and Sirius, and AQL. Each collaborative representation module ships its own `.graphqls` fragment (core is required; diagrams, forms, selection, trees and validation are optional), and the GraphQL layer merges the fragments it finds on the classpath at startup, so leaving a module out removes its part of the schema. Adopters can embed the whole `sirius-web-starter`, depend only on the Sirius Components modules they need and bring their own controllers, security or persistence, or replace the GraphQL wiring while calling the same collaborative services. _(Sirius Web)_ · `technical-stack.adoc`
- **GraphQL server customization hooks**: integrators can contribute Spring beans that change the GraphQL server without forking it:
  - IGraphQLInstrumentationProvider adds GraphQL Java instrumentations (since 2026.7.0).
  - IGraphQLCodeRegistryTransformer post-processes the GraphQLCodeRegistry builder (since 2024.9.0).
  - ITypeResolverDelegate resolves the concrete GraphQL object type of an interface or union (since 2024.7.0).
  - IGraphQLWebSocketHandlerListener is told when a WebSocket connection opens or closes and about every text message.
  - The DataFetcherExceptionHandler used for queries, mutations and subscriptions can be replaced by declaring another bean (the default logs the exception and returns a standard error; subscription exception handling was added in 2025.2.0), and the customization of GraphQL error messages was improved in 2026.1.0.

  _(Sirius Web)_ · `IGraphQLCodeRegistryTransformer.java`, `ITypeResolverDelegate.java`, `CHANGELOG.adoc` v2026.7.0
- **Subscription flux customizers and delivery scheduler**: every representation subscription goes through the registered IRepresentationEventProcessorFluxCustomizer beans, which can rewrite the payload stream of a representation (for example to add payloads). Since 2025.8.0 payloads are published on a dedicated scheduler before they are sent, so a GraphQL subscription body can re-enter the editing context's event processor to fetch more data, and payloads keep their order; the scheduler comes from IEventProcessorSubscriptionSchedulerProvider and can be replaced (since 2025.10.0). _(Sirius Web)_ · `EventProcessorSubscriptionProvider.java`, `IRepresentationEventProcessorFluxCustomizer.java`, `CHANGELOG.adoc` v2025.8.0

## Versioning, migration & data management

### Versioning and configuration management
- **No built-in version control or configuration management**: neither SysON nor the Sirius Web platform offers built-in versioning, branching, access control or configuration management. Organizations are expected to plug in an external CM or version-control solution. · `faq.adoc`, `index.adoc`
- **Versioning through downloaded project archives**: to keep versions, download the project as a zip archive from the homepage or project menu at each iteration, and commit the archive into an external Git repository. · `cm.adoc`
- **No project data versioning (single commit and branch)**: each project has exactly one commit and one branch, both identified by the project id. Commits sent through the REST API amend that commit, so there is no history, no extra branches and no tags. Commit change listings cannot separate created, updated and deleted data. _(Sirius Web)_ · `api-details.adoc`, `project_commit_branch_tag_recipe.adoc`, `DefaultProjectDataVersiongRestService.java`
- **Published library versions (immutable snapshots)**: the only versioned snapshots of model content are published libraries, identified by namespace, name and version (unique together in the database), and `Library.versions` lists every published version of one library. SysON refuses to publish a namespace:name@version that already exists ("Library '<ns>:<name>@<version>' already exists."), because the platform relies on published libraries being immutable. A publication copies the project's own `.sysml` documents (not the standard libraries or referenced libraries) into new read-only semantic data, clears their imported flag, records the libraries they reference as dependencies, and answers "Successfully published library '<ns>:<name>@<version>'." or "Failed to publish library ...". · `SysONSysMLLibraryPublisher.java`, `libraries.graphqls`, `03-add-library-table.xml`
- **In-memory change history (undo/redo)**: each editing context keeps, in memory, the EMF change recorded for each mutation input, keyed by the input id, plus representation changes (node, edge and label layout and appearance, hide, fade, collapse, view requests). Undo applies the reverse of one input's change and redo reapplies it. The web client keeps undo and redo stacks of mutation input ids in sessionStorage, reset when the page loads: every mutation except `undo`, `redo` and `layoutDiagram` pushes its id and clears the redo stack. Known read-only inputs (palettes, creation descriptions, searches, tooltips, selection dialogs...) and layout changes are not recorded, which also avoids the recording cost. The history is not persisted and is lost when the editing context is unloaded. _(Sirius Web)_ · `UndoEventHandler.java`, `ApolloLinkUndoRedoStack.tsx`, `UndoRedoIgnoreInputPredicate.java`
- **Multiple named semantic data per project**: a project links to its semantic data by name ("main" by default). `currentEditingContext(name)` and the project download endpoint's `?name=` parameter select which semantic data to open or export. _(Sirius Web)_ · `ProjectSemanticDataCreator.java`, `ProjectDownloadController.java`, `siriusweb.graphqls`

### Model and project exchange
- **Upload a model (XMI / JSON)**: in the project workbench, the "Upload model" button of the Explorer toolbar opens the "Upload new model" dialog, where the user clicks the dashed zone ("Click here to select a file", then the file name) to pick one file. XMI and JSON files are supported (SysON adds textual SysML/KerML), and the uploaded model is created and opened automatically. A split button submits either "Upload" or "Upload (read-only)"; after success the dialog reads "The document has been successfully uploaded", may offer "Download report" (saved as `upload-document-report.txt`), and "Close" dismisses it. A transport failure shows "An unexpected error has occurred, the file uploaded may be too large". _(Sirius Web)_ · `model-management.adoc`, `UploadDocumentModal.tsx`, `UploadDocumentReport.tsx`
- **Model upload JSON format restriction**: only JSON models exported in the tool's own JSON format through the Download Model action can be uploaded again; arbitrary JSON is not accepted. _(Sirius Web)_ · `model-management.adoc`
- **Upload format detection and sanitization**: an uploaded file is read fully, then the first loader that recognizes it is used: a first line starting with `<?xml` is loaded as XMI, a first line starting with `{` as EMF JSON (with migration participants applied), and otherwise a name ending in `.sysml` or `.kerml` (case-insensitive) is parsed as SysML/KerML text by SysIDE and marked as imported. Anything else fails with the unexpected-error message. The loaded content is copied into a JSON resource, every element gets a fresh random id (the old-to-new id map is kept for the import), and the result is re-saved as UTF-8 EMF JSON before becoming a new document with the chosen read-only flag. A document still holding unresolvable proxies is refused ("The resource <name> contains unresolvable proxies and will not be uploaded" in the log). The import report shown in the dialog joins the loader's messages (for text, the parser and AST-transformation messages, such as "[ERR] Reference of X not found for Y"). Successful uploads are logged ("Document <id> uploaded"). _(Sirius Web)_ · `DocumentSanitizedJsonContentProvider.java`, `XMIExternalResourceLoaderService.java`, `SysMLExternalResourceLoaderService.java`
- **Upload a project archive (ZIP)**: the "+ Upload project" card ("Start with an existing project") of the project browser opens the `/upload/project` page titled "Upload a project", with a file picker and an "Upload" button that stays disabled until a file is chosen and shows a spinner while sending. The archive goes through the `uploadProject` mutation on the GraphQL upload endpoint. The project takes the name of the archive's top-level folder and the natures listed in its manifest, its documents and representations are recreated, and the browser then opens `/projects/<new id>/edit`. Errors come back as toasts ("The file is unreadable", "Failed to find the dependencies of the project", or "An unexpected error has occurred, the file uploaded may be too large" for a transport failure). Without the upload capability the page redirects to the 404 page. The server reads every archive entry into memory, takes the project name from the first path segment of an entry (an archive with no files, or no top-level folder, is "unreadable"), and parses `<name>/manifest.json`; a missing or invalid manifest is logged as a warning and treated as empty, but a manifest without a `natures` list makes the mutation fail with a data-fetching error instead of a message. A successful upload is logged as "Project <id> uploaded". _(Sirius Web)_ · `UploadProjectView.tsx`, `ProjectUploadApplicationService.java`, `ProjectZipContentProvider.java`
- **Duplicate a project through an archive round-trip**: duplication exports the project to an in-memory archive and imports it again as a new project named "<name> - Copy", with the same natures, so the copy gets fresh element ids and recreated representations exactly like an upload. It fails with "not found" for an unknown project and with the unexpected-error message when the archive cannot be read back. In the UI it is the "Duplicate" entry of the project's navbar menu in the workbench: the entry shows a spinner and is disabled while the `duplicateProject` mutation runs (which requires the Project duplicate capability), then the browser does a full-page navigation to `/projects/<copy id>/edit`. _(Sirius Web)_ · `ProjectDuplicationApplicationService.java`, `DuplicateProjectMenuItem.tsx`, `MutationDuplicateProjectDataFetcher.java`
- **Download a model**: the "Download" entry of a model's Explorer context menu downloads that model as a file named after it. Sirius Web's docs describe the tool's own JSON format, but the entry is a plain browser link whose Accept header starts with text/html, so in SysON a model whose first root is a SysML element downloads as SysML v2 text; a client asking for `application/json` or `application/xml` gets JSON or XMI. The textual-format page warns that the document must be named with a ".sysml" suffix to download as a textual SysML v2 file; the exporter itself checks only the first root, and the saved file simply takes the document's name, so a model named without the suffix downloads as a file without the extension. _(Sirius Web)_ · `model-management.adoc`, `DownloadDocumentTreeItemContextMenuContribution.tsx`, `DocumentDownloadController.java`
- **Project archive format**: an exported project zip contains:
  - `<name>/manifest.json`
  - `<name>/documents/<documentId>.json`, each model as JSON
  - `<name>/representations/<representationId>.json`, with id, projectId, descriptionId, targetObjectId, label, kind and the representation content

  The manifest holds natures, metamodels (sorted nsURIs), `documentIdsToName`, dependencies (library semantic-data ids) and a representations map whose entries give type, descriptionURI, targetObjectURI, migrationVersion and latestMigrationPerformed. Representation content is migrated to the latest version before export. Only the documents that pass the persistence filters are written, so the SysML/KerML standard libraries and the documents of referenced libraries are left out and only referenced through `dependencies`. Each zip entry is stamped with the export time. Project download, duplicate and upload all use this format. _(Sirius Web)_ · `ProjectExportService.java`, `ProjectSemanticDataExportParticipant.java`, `ProjectRepresentationDataExportParticipant.java`
- **Project import re-identifies content and rebuilds representations**: on upload or duplicate:
  - Each document gets fresh element ids, and cross-document references (proxies) are rewritten to the new ids.
  - Documents whose references still cannot be resolved are dropped with a warning.
  - Library dependencies are re-added.
  - Before anything is created, the archive is read and its manifest's library dependencies are checked: an unreadable archive fails with "The file is unreadable", and a dependency that does not exist on the server fails with "Failed to find the dependencies of the project" (logged as "Unknown dependencies").
  - Each representation is recreated against its remapped target object. Diagrams keep node, edge and label layout, bend points, hidden/faded state, and the user-customized node, label and edge appearance, and their unsynchronized nodes are re-created.
  - A representation that cannot be recreated no longer blocks the upload of the rest of the project (since 2025.10.0), and an archive whose representation has an unknown description id no longer deadlocks the import (fixed in 2026.3.0).

  _(Sirius Web)_ · `SemanticDataProjectContentImportParticipant.java`, `RepresentationProjectContentImportParticipant.java`, `DiagramImporterUpdateService.java`
- **Custom node styles kept on project import**: when a project with diagrams is uploaded or imported, the customized background, border color, border size and border style (plus border radius for view frames) of Package, ImportedPackage, Note and ViewFrame nodes are re-applied to the recreated diagrams. A dedicated DiagramImporter…NodeStyleAppearanceChangeHandler exists for each node kind. · `DiagramImporterSysMLPackageNodeStyleAppearanceChangeHandler.java`, `DiagramImporterSysMLViewFrameNodeStyleAppearanceChangeHandler.java`, `CHANGELOG.adoc`
- **Relative references from uploaded folders fixed**: while documents load, a reference URI starting with `../` in a document with a flat URI is rewritten to the Sirius resource scheme without the `../` prefixes. Upload sanitization resolves links against the folder-bearing file name before the document gets its flat URI, so cross-document links from uploaded folder structures still resolve (fixed in 2026.9.0). · `SysONJsonResourceProcessor.java`
- **Standard libraries excluded from proxy rewriting**: when Sirius Web rewrites proxies across resources (for example after an upload or duplication), standard-library resources are skipped, and so is a null resource. · `SysMLv2RewriteProxiesResourcesFilter.java`
- **No SysML v1 support or v1/v2 transformation**: SysON is SysML v2 only. It cannot model in or hold SysML v1 models, and it transforms neither v1 to v2 nor v2 to v1. · `faq.adoc`
- **Studio domains stored as structured JSON**: every studio domain is stored as structured, JSON-serializable data, so it can be versioned in Git, reviewed, reused across workspaces, or processed as a model (EMF Compare, M2Doc documentation). _(Sirius Web, studio; experimental)_ · `domain.adoc`
- **Stored model document format (EMF JSON)**: each model document is stored, exported and archived as EMF JSON: a header `"json": {"version": "1.0", "encoding": "utf-8"}`, an `ns` map from prefix to nsURI (`"sysml": "http://www.eclipse.org/syson/sysml"`), an optional `migration` object, and a `content` array of root objects {`id`, `eClass` such as `sysml:Namespace`, `data`} with contained objects nested in their containment features. SysML elements carry a separate `elementId` attribute next to the platform `id`, and documents created from textual SysML carry an `org.eclipse.syson.sysml.imported` annotation. · `Batmobile.json`, `JsonDocumentExporter.java`, `MigrationData.java`

### Persistence
- **Model persistence (automatic save)**: after changes, every model of the project is saved as a JSON document of the project's semantic data, together with the list of metamodels it uses. The save runs after every handled input whose change kind is SEMANTIC_CHANGE (representation-only, rename or no-op inputs do not save the model), and it rewrites the whole set of documents at once, using only resources of the editing context's own URI scheme. A read-only document whose read-only version is already stored is never overwritten: the stored version is kept, so read-only documents stay effectively read-only. Library resources and other filtered resources are excluded from the save; SysON adds a filter that never persists the SysML/KerML standard library resources. Save time is recorded in the `siriusweb_editingcontext_save` metric and logged at DEBUG ("<n>ms to persist the semantic data"). _(Sirius Web)_ · `EditingContextPersistenceService.java`, `EditingContextSaver.java`, `SysMLv2EditingContextPersistenceFilter.java`
- **Document loading with migrations and the read-only flag**: project documents are loaded from their JSON content. All migration participants are applied when requested, and each document's stored read-only flag and name are set. A document that fails to load is logged ("An error occured while loading document <id>") and dropped instead of breaking the project. · `SysONResourceLoader.java`
- **Read-only documents and standard library elements**: SysON treats a document as read-only when it is a standard library resource or when its metadata carries the read-only flag (set by "Upload (read-only)" and on the documents of a published library), and an element as read-only when its document is read-only or when it belongs to a standard library package, whatever its document. Annotations follow their document. · `SysONReadOnlyObjectPredicateDelegate.java`, `EditingContextPersistenceService.java`
- **Stable identities of standard library elements**: SysON reports a standard library element's id as its `elementId`, so references to library elements stay valid across library reloads and updates. Library elementIds are name-based v5 UUIDs: a standard LibraryPackage's comes from the library base URI plus its qualified name, and a named member's from its library package's elementId plus its qualified name (imports, memberships, specializations and type featurings excepted). An implied relationship that has no id yet gets one on first request through `ElementUtil.generateUUID`, kept in an IDAdapter for as long as the model stays loaded. · `SysONIdentityService.java`, `ElementUtil.java`
- **Database schema**: the Liquibase-managed PostgreSQL schema holds these tables:
  - `project` (id, name, created/modified dates) and `nature` (project_id, name)
  - `project_semantic_data` (project_id, semantic_data_id, name, unique per project and name), `semantic_data`, `semantic_data_domain` (the metamodel URIs used) and `semantic_data_dependency` (ordered library dependencies)
  - `document` (id, semantic_data_id, name, JSON content, is_read_only, dates), keyed by id and semantic data
  - `representation_metadata` (target object, description id, label, kind, documentation, semantic data), `representation_metadata_icon_url` and `representation_content` (JSON content, migration version, last migration performed)
  - `library` (namespace, name, version unique together, semantic_data_id, description)
  - `image` (global images, unique label) and `project_image` (per-project images), both storing content type and bytes
  - `project_style_customization` (project_id, style customization description id, unique together)

  Changelogs are grouped by release (2024.3 to 2026.11), for example splitting representation metadata from content in 2024.11, adding libraries in 2025.2 and the read-only document column in 2025.10. _(Sirius Web)_ · `db.changelog-master.xml`, `01-initial-schema.xml`, `03-add-library-table.xml`
- **Loading and saving models that reference standard library elements**: models and diagrams that reference standard library elements load and save correctly (fixed in 2025.8.0). · `2025.8.0.adoc`, `CHANGELOG.adoc` v2025.8.0
- **Layout persistence (layoutDiagram mutation)**: every manual layout change (move, resize, label move or resize, bend points, handles, anchors) sends the `layoutDiagram` mutation with the whole layout. The mutation carries:
  - node layout data: position, size, resizedByUser, movedByUser, handle layout data, minComputedSize
  - edge layout data: bendingPoints, relativePositionBendingPoints, edgeAnchorLayoutData
  - label layout data: position, size, flags
  - an autoLayoutState of UNCHANGED, ACTIVATE or DEACTIVATE

  Layout is therefore stored on the server and shared with other users. Errors show "An unexpected error has occurred, please refresh the page". _(Sirius Web)_ · `useSynchronizeLayoutData.ts`, `useSynchronizeLayoutData.types.ts`

- **Representation content saved after each refresh and layout**: a diagram is refreshed from the model when its event processor starts (much like Sirius's auto-refresh on opening), after every change that requires a refresh, and after each layout update, and every time the new content goes through the representation persistence strategy. The default strategy saves it only when content for that representation id already exists in the database, so representations that were never stored (transient ones, such as the Papaya sample's dashboard diagram built on the fly) stay in memory only. Integrators can replace the strategy through IRepresentationPersistenceStrategy (since 2026.3.0). _(Sirius Web)_ · `RepresentationPersistenceStrategy.java`, `DiagramEventProcessor.java`, `CHANGELOG.adoc` v2026.3.0
- **Editing-context snapshots for impact analysis**: tools flagged `withImpactAnalysis` and library updates are previewed by taking a snapshot of the editing context (every resource serialized as a document, plus the library metadata of library resources), running the operation, computing the report from the changes, and restoring the snapshot by clearing the resource set and reloading the documents. SysON's snapshot service leaves the standard libraries out of the snapshot and, on restore, first re-runs its editing-context set-up (standard library copy, element cache, library namespace index) before reloading the user documents. · `SysONEditingContextSnapshotService.java`, `EditingContextSnapshotService.java`, `InvokeDiagramImpactAnalysisToolEventHandler.java`
- **Aggregate persistence with Spring Data JDBC and domain events**: the server is a modular monolith in domain-driven-design layers: `sirius-web-domain` (aggregates, repositories, domain services), `sirius-web-application` (transactions, REST, GraphQL and WebSocket controllers, static frontend), `sirius-web-infrastructure` (Spring Data, PostgreSQL, Liquibase, GraphQL wiring) and the `sirius-web-starter` that bundles them. Aggregates are stored with Spring Data JDBC rather than JPA, only through their aggregate root's repository, and every mutation goes through the root, which emits timestamped domain events; listeners in the application layer react to those events in their own transactions to keep other aggregates in sync. PostgreSQL is the only supported database. _(Sirius Web)_ · `architecture.adoc`

### Automatic model migrations (SysON participants)
- **Migrations apply to all projects**: SysON's migration predicate accepts every editing context, since there is no SysML/SysON project nature, so all migration participants run on every project, according to SysON's own predicate. The JSON-level participants (annotation, ConnectorAsUsage source/target, ViewUsage exposedElement) act only on documents whose `ns` entry is the SysML nsURI. They collect the JSON objects whose eClass is `sysml:<Type>` or a subtype of the target metaclass. · `SysONEditingContextMigrationParticipantPredicate.java`, `MigrationParticipantService.java`
- **New documents stamped with the latest migration version**: every new SysON document, whether created from a template, a stereotype or a quick action, gets resource metadata carrying the most recent migration participant's version and is marked read-write, so migrations never run on freshly created models. · `SysONDefaultResourceProvider.java`
- **Migration 2025.4.0: Annotation annotatingElement no longer serialized**: participant 2025.4.0-202503140000. Before a SysML document is deserialized, it removes the `annotatingElement` key from every Annotation and the `annotation` key from every AnnotatingElement, because both features became derived in 2025.4.0. Tests cover loading annotations that have no source feature. · `AnnotationAnnotatingElementMigrationParticipant.java`, `AnnotationMigrationParticipantTest.java`
- **Migration 2025.4.0: ConnectorAsUsage source/target derived**: participant 2025.4.0-202502270000. - **Migration 2025.6.0: diagrams moved onto ViewUsages**: since 2025.6.0, diagrams must target a ViewUsage. The migration runs in two phases:
  1. On model load, participant 2025.6.0-202505150000 finds every non-ViewUsage element (for example a Package) that is the target of a SysON standard diagram (General View, Interconnection View, Action Flow View, State Transition View) and marks it with an adapter.
  2. When the project starts, the hook handles only the resources this participant migrated. - **Migration 2025.8.0: model references to the standard libraries use elementId**: participant 2025.8.0-202506301600. It rewrites non-containment references whose URI points into the `sysml`/`kerml` library schemes (for example a FeatureTyping to `ScalarValues::String`) so the fragment becomes the target's stable elementId instead of its old id. - **Migration 2025.8.0: diagram elements targeting library elements use elementId**: diagram migration 2025.8.0-202506301700. - **Bundled map of old library ids to elementIds**: `migration/stdlib_oldId_to_elementId.txt` holds 123,773 `oldId=elementId` lines covering all standard-library elements from before the SysML v2 2025-04 metamodel update. It is read into memory at startup, with the time logged, for the 2025.8.0 library-reference migrations. · `StandardLibrariesIdsResourceToMapParser.java`, `stdlib_oldId_to_elementId.txt`
- **Migration 2025.10.0: one merged standard-diagram description**: in 2025.10.0, the separate General View, Interconnection View, Action Flow View and State Transition View modules and descriptions were merged into one `syson-standard-diagrams-view` description, with synchronized nodes based on the ViewUsage's exposed elements. ### Platform migrations (Sirius Web)
- **Migration of stored models and representations**: on load and upload, migration participants upgrade older data.
  - For studio-capable projects, they migrate view descriptions: connector tools, layout option, expanded toolbar, label border size, diagram style, toolbar, edge source/target descriptions, edge tool palette, header separator display, node label expression, layout strategy, user-resizable, show-icon, delete-from-diagram, node style colors, reference-widget buttons, selection-dialog labels and candidates, tree icon expressions and widget layout properties.
  - Stored diagrams are migrated too: alignment, anchors, customized properties, handle layout data, label size, minimum computed size, position, routing points, size, user-resizable, edge handle layout data, relative bending points and hierarchy children.

  SysON adds its own participants on top. A downstream application or studio that changes its own metamodel adds an `IMigrationParticipant` Spring service with a unique version: it can, for example, map a renamed feature to its new EStructuralFeature in `getStructuralFeature`, and it runs after the built-in migrations, only on models whose stored version is older. _(Sirius Web)_ · `EditingContextMigrationParticipantHandler.java`, `ResourceLoader.java`, `DiagramRoutingPointsAttributeMigrationParticipant.java`
- **Semantic data migration with last-migration tracking**: stored semantic models are migrated when they load. Each JSON document stores a `migration` object {lastMigrationPerformed, migrationVersion} ("none"/"0" when absent), so only the needed migration participants run. Participant versions follow `YYYY.M.N-YYYYMMDDhhmm` and are compared numerically by year, month, patch and timestamp (malformed versions sort lowest); only participants newer than the document's version run, in ascending order, and after each one the document is stamped with its class name and version. A participant can edit the raw JSON before deserialization, map an old feature name to a new feature, map an old type name or nsURI to a new EClassifier or EPackage, post-process each loaded object, and adjust the JSON after serialization. The same pipeline runs on uploaded JSON documents. _(Sirius Web)_ · `MigrationService.java`, `MigrationVersionComparator.java`, `MigrationData.java`
- **Representation migration on load and import**: persisted representations such as diagrams are migrated by representation migration participants when they load, with no overhead when no migration is needed. Exported representations carry their migration version, so imported or out-of-date representations are migrated to the latest version. Projects exported before 2025.6.0 can be imported, and participants compare versions correctly. _(Sirius Web)_ · `CHANGELOG.adoc`

## Administration, deployment, security & performance

### Installation and deployment
- **Client-server architecture**: SysON is a web application. One server computer runs the SysON Server, and any number of client computers on the same network use it through web browsers. · `architecture.adoc`
- **Fully browser-based, no local installation**: the application runs entirely in a web browser, so end users install nothing locally; all users connect to a shared server. _(Sirius Web)_ · `overview.adoc`
- **No additional software required**: the FAQ states that no other software products are needed to use SysON. · `faq.adoc`
- **Documented installation patterns**: the installation guide offers four install patterns plus a separate "HTTPS" page on certificate setup:
  - "Basic Local Test Setup": single user, Docker Compose, no security.
  - "Multi-User Local Test Setup": adds self-signed HTTPS and a shared IP.
  - "Production-Grade Deployment": executable JAR, managed PostgreSQL, CA certificate.
  - "Ecosystem-Only Deployment": PostgreSQL in Docker plus the JAR, for development.

  · `install.adoc`, `nav.adoc`
- **Deploy with Docker Compose**: the shipped `docker-compose.yml` starts two services on a `syson` network:
  - `database`: `postgres:15` with POSTGRES_DB=postgres, POSTGRES_USER=username, POSTGRES_PASSWORD=password.
  - `app`: image `${IMAGE_TAG:-eclipsesyson/syson:v2026.11.0}` on port 8080, with SPRING_DATASOURCE_URL=jdbc:postgresql://database/postgres, the matching username/password, SIRIUS_COMPONENTS_CORS_ALLOWEDORIGINPATTERNS='*' and SERVER_PORT=8080. It depends on `database`.

  Start it with `docker compose up` and open http://localhost:8080. The image is meant for tests. · `docker-compose.yml`, `local_test.adoc`

### Requirements and sizing
- **Server hardware requirements and sizing**: the reference sizing covers 10 projects or fewer, about 10-30 users, 100k semantic elements and 1000 representations in total:
  - RAM: 4 GB required, 8 GB recommended.
  - CPU: dual-core required, quad-core recommended, at 2 GHz.
  - Disk: 10 GB for the installation plus space for data, on a 7200 RPM or faster disk.

  Assign more memory as usage grows, and use multi-core CPUs to handle many concurrent requests. · `requirements.adoc`
- **Server OS and database requirements**: the server runs on any OS with a supported Java runtime: Linux 64-bit (Ubuntu, CentOS or RHEL preferred) or Windows Server 2016 or later. It needs PostgreSQL 15 with a dedicated database and administrator rights (Sirius Web requires PostgreSQL 15 or later), Eclipse Temurin as the recommended Java runtime, and a stable network connection. Platforms not listed are neither tested nor supported. · `requirements.adoc`, `CHANGELOG.adoc`
- **Client-side requirements**: users need a desktop browser, the latest stable Chrome or Firefox, on Windows 10 or later, macOS 13 Ventura or later, Linux or ChromeOS. Internet Explorer and mobile browsers are not supported (the FAQ adds that the web app can still be opened from mobile devices but is optimized for desktop use), the minimum screen resolution is 1024 x 768 in a maximized browser, and browser plugins or extensions can cause speed, upload, download or interface problems. · `requirements.adoc`
- **Java 21 requirement**: SysON requires Java 21 or later since 2026.5.0. Sirius Web requires Java 21 or later to build and run, and its 2026.7.0 release notes tell administrators to update their runtime before upgrading. · `2026.5.0.adoc`, `migration-process.adoc`, `2026.7.0.adoc`
- **Node.js requirement for textual import**: the server needs Node.js 18.7 on the PATH for the import module, which imports SysML v2 textual files. · `requirements.adoc`, `SysmlToAst.java`
- **Network deployment recommendations**: keep client-server latency as low as possible and host the server and the database on the same physical machine. Avoid VPNs and wireless links, because dropped connections can cause instability and data loss; if one is mandatory, use an SSH tunnel. SysON should be the only way the database's information is edited. SysON comes with no warranty of error-free operation. · `requirements.adoc`
- **Antivirus configuration guidance**: if the server is slow, try running it with virus checking disabled. Exclude the application folders from scans, schedule scans off-peak, tune or disable real-time scanning for SysON processes, monitor CPU and disk I/O, and consult the antivirus vendor; in some cases a restart or an uninstall is needed. _(Sirius Web)_ · `anti-virus.adoc`
- **Secure context requirement (HTTPS or localhost)**: the frontend uses browser APIs that are only available in a secure context, so the application must be served over `https://` or `http://localhost`; plain HTTP deployments are not supported. _(Sirius Web)_ · `extend.adoc`

### Scaling limits
- **Scaling limit: model size about 10 MB**: models up to about 10 MB are handled efficiently. Larger models may load slowly and respond sluggishly, so very large models should be split into smaller sub-models. · `scaling-limits.adoc`
- **Scaling limit: 150,000 semantic elements**: a model can hold up to 150,000 semantic elements, counting elements, relationships and attributes. Beyond that, memory use grows and query responses slow down. · `scaling-limits.adoc`
- **Scaling limit: 2,000 representations per project**: a project supports up to 2,000 distinct representations, though too many representations make navigation harder. · `scaling-limits.adoc`
- **Scaling limit: 1,000 elements per representation**: a single representation can display up to 1,000 elements. Denser views become cluttered and slower to render and interact with, so splitting them into smaller focused views is advised. · `scaling-limits.adoc`
- **Scaling limit: 1,000 concurrent projects per server**: a server supports up to 1,000 concurrent projects. Each project adds compute and storage load, so server capacity should be scaled accordingly. · `scaling-limits.adoc`
- **Scaling limit: 80 concurrent users per server**: a single server is designed for up to 80 concurrent users collaborating in real time. Larger teams should monitor server load and may need to split users across servers. · `scaling-limits.adoc`
- **Scaling recommendations**: the scaling-limits page advises partitioning large models into smaller modular sub-models, using several focused representations instead of one overloaded view, running on infrastructure that can scale with project load and user concurrency (for example cloud resources allocated on demand), monitoring performance and user activity regularly to spot bottlenecks, and contacting the team for needs beyond the stated limits. · `scaling-limits.adoc`
- **Limits on number of projects and models (FAQ)**: both FAQs confirm there are limits on how many projects or models can be created and point to the scaling-limits page for the figures. · `faq.adoc`, `index.adoc`
- **Maximum node nesting depth of 13**: the diagram subscription query expands child nodes and border nodes recursively up to 13 levels below the root nodes (MAX_NODE_HIERARCHY_DEPTH). Elements nested deeper are not fetched by the client. _(Sirius Web)_ · `diagramFragment.ts`

### Security and access control
- **No built-in security mechanisms**: SysON includes none of the following, which are to be handled with external tools:
  - authentication or authorization (guidance is given for external systems, including SSO)
  - encryption of data at rest or in transit
  - audit logging or monitoring
  - data integrity checks or backups
  - enforced secure development practices

  · `security.adoc`
- **No authentication or user accounts**: the documented deployments add no login or authorization layer. The single-user Docker setup "doesn't include any security configurations", and the multi-user setup "doesn't apply any specific security configurations" beyond HTTPS. The SysON backend declares no Spring Security dependency or filter chain, so anyone who can reach the server can open and edit every project. The platform itself has no opinion on authentication: Sirius Components dropped its Spring Security dependency (v2022.01.0, with the last traces removed in 2023.4.0), leaving security to the embedding application. · `local_test.adoc`, `multi_user_test.adoc`, `production_deploy.adoc`
- **Vulnerability reporting and security policy**: SysON follows the Eclipse Foundation Vulnerability Reporting Policy. Vulnerabilities are reported through a confidential issue in the Eclipse Foundation vulnerability-reports tracker, never in public issues or pull requests, with the issue type, affected versions, impact, reproduction steps, affected source, configuration, logs and any proof of concept. Sirius Web's policy is best effort: no version is formally supported, and security fixes go only into the latest release. · `SECURITY.md`, `security-policy.adoc`
- **Projects are public; sharing by URL**: in SysON (and in the default Sirius Web setup) every project is visible to everyone, and there is no per-project visibility setting. Sharing a project or representation URL (deep link) is enough for the recipient to open and view it, with no sharing procedure. · `concepts.adoc`, `representation-operations.adoc`, `project-management.adoc`
- **Capability-based authorization model**: every sensitive operation, in GraphQL as in the controllers, asks the capability evaluator `hasCapability(type, id, capability)`. Backends contribute ICapabilityVoter beans whose `vote(type, identifier, capability)` returns GRANTED, DENIED or ABSTAIN. A capability is granted only if every non-abstaining voter grants it, and when no voter takes part the result comes from an IDefaultCapabilityEvaluator, whose default implementation (DefaultCapabilityEvaluator) grants everything; since 2026.11.0 an integrator can replace it, for example to deny by default. The types and capabilities are:
  - Project: list, view, create (also needed to list templates), upload, download, rename, delete, edit, duplicate, list-style-customizations, update-style-customizations-state
  - Library: list, view
  - ProjectSettings: view
  - `ProjectSettings#<tab>`: view, for the tabs images, general and appearances

  The UI reads the results as GraphQL booleans (canList, canCreate...), and denied features are hidden or disabled. The developer doc describes `CapabilityResult.granted()/denied(reason)`, but the code uses a CapabilityVote enum. SysON contributes no voter of its own. _(Sirius Web)_ · `SiriusWebCapabilities.java`, `DefaultCapabilityEvaluator.java`, `capabilities.adoc`
- **Server-side access enforcement on every request**: every query sent to an editing context needs the Project view capability (Library view for a library's editing context), and every representation subscription is checked the same way; otherwise the reply is "You are not authorized to perform this operation". Every mutation needs Project edit, and form mutations use the form's canEdit. Any mutation on a published library's editing context is always refused, so library content cannot be edited through the API. _(Sirius Web)_ · `EditingContextDispatcher.java`, `EventProcessorSubscriptionProvider.java`, `FormCapabilitiesService.java`
- **Capability checks on REST and download endpoints**: the object, commit and branch REST endpoints go through the editing-context dispatcher, so reads need Project view (or Library view) and creating a commit or a branch needs Project edit, while deleting a branch is dispatched as a query and needs only view. The `/api/rest/projects` endpoints (list, get, create, rename, delete), the document download endpoint and the selected-objects export endpoint call no capability check at all, so a capability voter (such as the demo profile's) does not restrict them. The project archive download checks Project download. _(Sirius Web)_ · `ProjectRestController.java`, `BranchRestController.java`, `DocumentDownloadController.java`
- **Unauthorized operation handling**: a mutation called without the required capability returns an ErrorPayload reading "You are not authorized to perform this operation", which the UI shows as a toast. A query called without it returns an empty connection or list (projects, templates, libraries) or null (project), and the download endpoint returns 404. _(Sirius Web)_ · `messages.properties`, `MutationCreateProjectDataFetcher.java`, `ViewerLibrariesDataFetcher.java`
- **Viewer and project capability queries**: the client queries capabilities to enable or hide UI:
  - `viewer.capabilities.projects {canList, canCreate, canUpload}`
  - `viewer.capabilities.libraries {canList}`
  - `project.capabilities {canDownload, canRename, canDelete, canDuplicate, canEdit, canUpdateStyleCustomizationsState}`
  - `project.capabilities.settings {canView, tabs(tabIds){tabId, canView}}`

  _(Sirius Web)_ · `capabilities.graphqls`, `ProjectSettingsCapabilitiesTabsDataFetcher.java`, `stylecustomizations.graphqls`
- **Projects collection capabilities gate the project browser**: each page waits for the viewer's capabilities to load before rendering. Type Project with a null identifier controls three things: `canList` shows the project browser and the Projects menu entry, `canCreate` shows the "Create a new project" area and the "New project" command, and `canUpload` allows ZIP project uploads through the upload card and page. ### Search indexing (Elasticsearch)
- **Set up a development Elasticsearch/Kibana**: install with `curl -fsSL https://elastic.co/start-local | sh`, or with Docker:
  1. Create a data volume and run Elasticsearch single-node with `-m 2g` (limits memory) on ports 9200/9300.
  2. Reset the `elastic` password, create a Kibana enrollment token, copy `http_ca.crt` and test with curl.
  3. Run Kibana on port 5601 with its verification code.
  4. Import the certificate into the JVM cacerts with keytool (default password `changeit`) so SysON can connect.

  _(experimental)_ · `elasticsearch-integration.adoc`
- **Debug indexing with Kibana**: in Kibana (`http://localhost:5601/`), Elasticsearch > Index Management lists each project's index with its size and document count, and "Discover index" lists its documents (500 at most). The Console panel runs full-text searches (`GET <index>/_search?q=...`), Query DSL and ES|QL queries, including ES|QL `lookup join` across references. Sirius Web's default indexing stores each EObject as a simplified EMF JSON document whose references hold only the target ids. The how-to names indices `project-<id>`, while the code names them `editing-context-<id>`. _(Sirius Web; experimental)_ · `debug-elasticsearch.adoc`, `IndexLifecycleManager.java`
- **Platform Elasticsearch indexing of project content**: opt-in, asynchronous indexing with one index per editing context, named `editing-context-<id>`. By default every element is indexed with its id, type (`package:Class`), label, icons and the value of every attribute and reference (referenced ids). Icons, the editing-context id and the entry type are stored but not searchable. Indices are built for all projects at startup, rebuilt fully and asynchronously after each save, and deleted with the project's semantic data, and indexing exceptions are caught. SysON plugs in its own entry provider for SysML elements in non-studio projects. _(Sirius Web)_ · `IndexLifecycleManager.java`, `DefaultIndexUpdateService.java`, `ElasticsearchConfiguration.java`
- **SysML-specific index creation**: SysON indexes into Elasticsearch with its own logic rather than Sirius Web's default, which keeps indices compact and stores only what cross-project search needs. When Elasticsearch is configured, each non-Studio project gets an index named `editing-context-<id>` (settings mode `lookup`), created with the project. The technical fields `iconURLs`, `editingContextId`, the index entry type and every `*@nestedIndexEntryType` field are stored but not indexed. An index that already exists is ignored, and other errors are logged as warnings; since 2026.9.0, concurrent creation of these indices is handled safely. _(experimental)_ · `SysONIndexCreationService.java`, `2026.3.0.adoc`, `CHANGELOG.adoc` v2026.9.0
- **SysML index entry structure**: only Namespace elements (packages, definitions, usages and other Namespaces) become index documents; relationships and other plain elements appear only as nested entries. Each document holds `@editingContextId`, `@id`, `@type`, `@label` (the styled label), `@iconURLs`, name, shortName, qualifiedName, a nested `owner` and nested `ownedElement` entries, and Types also hold nested `ownedSpecialization` entries. The `@` prefix avoids clashes with SysML attributes, but those fields are queried like any other. `@type` is the metaclass name with the "Usage" suffix dropped for usages (PartUsage is indexed as `Part`), except ConnectorAsUsage, BindingConnectorAsUsage and SuccessionAsUsage. A nested Element carries `@id`, `@type`, `@label`, name, shortName and qualifiedName; a nested Specialization adds a nested `general`. So nested fields are queryable 2 levels deep for Element (e.g. `owner.name`) and 3 levels deep for Specialization (e.g. `ownedSpecialization.general.name`). The documented example queries are `name:Batmo*`, `name:/part<0-9>/ AND @type:Part`, `owner.name:Package1` and `ownedSpecialization.@type:FeatureTyping AND ownedSpecialization.general.name:PartDefinition1`. · `elasticsearch-integration.adoc`, `cross-project-search.adoc`, `IndexEntrySwitch.java`
- **Index update on model change (standard libraries excluded)**: when changes are detected in a project, Sirius Web calls SysON's index update service. It deletes the project's index, recreates it and fully re-indexes it with a bulk ingester, so cross-project search results follow model edits. Every resource is indexed except the SysML and KerML standard libraries, which are copied into every project; they are skipped for performance and to avoid polluting search, so they never appear in cross-project search results. The service is skipped when Elasticsearch is absent. Projects containing Studio data use Sirius Web's default indexing instead. · `SysONIndexUpdateService.java`, `cross-project-search.adoc`
- **Index query**: searches against the index use an Elasticsearch query-string query over all indices (`*`) with leading wildcards allowed and at most 10,000 hits (the Elasticsearch maximum). Errors are logged as warnings and give an empty result, and the query time is logged at TRACE. The projects omnibox search uses it, and it reports itself unavailable when no Elasticsearch client is configured. _(Sirius Web; experimental)_ · `IndexQueryService.java`, `ProjectsOmniboxSearchCommandProvider.java`

### Performance mechanisms
- **Standard libraries loaded once at server start**: at startup the KerML and SysML libraries load into one shared resource set (`mustLoadDefaultLibrariesOnStart` is true). All non-derived references are resolved, and the library namespaces are registered as immutable for qualified-name lookup; every Namespace stored in those immutable library packages is cached for quick access (since 2025.10.0). The log reads "Initialization of default libraries completed in Xms". The configuration can be overridden to add extra default libraries or EPackages for all SysML projects. · `SysONDefaultLibrariesConfiguration.java`, `SysONLoadDefaultLibrariesOnApplicationStartConfiguration.java`
- **Standard library loading into SysML editing contexts**: the KerML and SysML standard libraries are loaded into SysML editing contexts but not into Studio ones. Each project's editing context gets its own in-memory copy of every library resource from the shared startup resource set: one copier keeps the original element ids and cross-references between library files, marks each copied resource read-only, and serializes references to library elements with their elementId. The time is logged at INFO as "Copied all default libraries in the editing context in <n> ms"; SysON's ADR-003 measured this copying at up to 10 minutes of CI build time across the integration tests, which led to the test-only library cache. Library loading definitions accept absolute paths and Windows separators, and cross-document parent-relative references resolve. · `SysMLEditingContextProcessor.java`, `StandardLibrariesLoader.java`, `003_improve_performances_of_integration_tests.adoc`
- **Per-project cache of SysML elements by metaclass**: when a non-Studio project's editing context is set up, SysON adds a SysONEContentAdapter to its resource set. The adapter tracks content changes and caches every SysML element by metaclass, so semantic-candidate queries for all elements of a metaclass avoid walking the whole model. Memberships are skipped, except RequirementConstraintMemberships (other than verification) and FeatureValues, which are drawn as nodes or edges. The adapter is installed again whenever a snapshot is restored. · `SysONEContentAdapter.java`, `SysMLEditingContextProcessor.java`, `SysONEditingContextSnapshotService.java`
- **Reachable-element search without standard libraries**: candidate searches can scan only user (editing-context) resources and skip the standard libraries, instead of using the full cache. · `UtilService.java`
- **getAllReachable performance improvement**: the utility service that retrieves all reachable elements of a given type was optimized to reduce execution time (2024.3.0). · `CHANGELOG.adoc` v2024.3.0
- **Fast deletion skipping derived references**: deletion searches for usages without browsing derived references, which are costly to compute in SysML. It removes inverse references only in changeable features and detaches cross-resource children. · `SysONEcoreUtil.java`, `NoDerivedCrossReferencer.java`
- **Faster "Become nested part"**: the "Become nested part" edge tool was sped up by fixing a slow `EcoreUtil.delete` usage (2024.5.0). · `2024.5.0.adoc`, `CHANGELOG.adoc` v2024.5.0
- **Membership cache during textual export**: during textual export, a MembershipCacheAdapter is installed on the resource set (or the resource) to cache membership computations and is removed afterwards, which speeds up the export of large models. · `SysMLv2DocumentExporter.java`, `CHANGELOG.adoc`
- **Explorer rendering cache of representations**: when the SysON Explorer renders, the representation metadata of the whole project is loaded once into a render variable (`existingRepresentations`) and reused for every tree item, avoiding repeated database access. · `SysONExplorerRenderVariablesCustomizer.java`
- **Editing context loading with dependencies**: opening a project loads all of its documents, then every dependency (libraries, recursively) as read-only resources tagged with the library namespace, name and version, skipping anything already loaded. It also installs a cross-reference index so incoming references can be found quickly. Load time is recorded in the `siriusweb_editingcontext_load` metric. _(Sirius Web)_ · `EditingContextLoader.java`, `EditingContextDependencyLoader.java`, `EditingContextSearchService.java`
- **Resources unloaded when an editing context is disposed**: EMF resources are unloaded by default when an editing context is disposed, freeing memory. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Project load and save performance mechanisms**: the platform includes these mechanisms:
  - AQL services cached per EPackage
  - fewer database reads when a project opens
  - Explorer rendering with a constant number of queries
  - faster EMF JSON load and save, for data saved after the update
  - proxy checks only on non-derived references
  - uploads into the existing resource set, which a system property can turn off
  - no change recording for known read-only operations
  - an image cache

  _(Sirius Web)_ · `CHANGELOG.adoc`
- **Diagram rendering performance mechanisms**: diagram rendering is memoized, which speeds up selection on large diagrams, and node and edge styles are memoized too. Dragged-node selectors were removed, palette rendering was optimized, ReactFlow pane and drag events were optimized, and arrange-all overlap resolution has lower complexity. Representation content is not fetched when only metadata is needed. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Server-driven lazy tree expansion**: the tree is fetched through a GraphQL subscription whose representation id carries the list of expanded item ids (`treeId?expandedIds=[...]`). The query nests children only up to a `maxDepth` that grows, and never shrinks, as deeper items are expanded. The server computes and sends only the expanded branches. _(Sirius Web)_ · `useTreeSubscription.tsx`, `getTreeEventSubscription.ts`, `TreeRepresentation.tsx`
- **index.html not cached; single-page routing**: browsers do not cache `index.html` (Cache-Control no-store, must-revalidate), so new frontend deployments are picked up immediately (since 2026.7.0). Every GET that is not under `/api/**`, `/v3/api-docs/**` or `/subscriptions`, not a static file (css, html, js, js.map, json, ico, fonts, jpg/jpeg/png/svg) and not claimed by a contributed backend-path predicate gets the `index.html` of the first static location that has one, so deep links such as `/projects/<id>/edit` load the app. Contributed index processors can rewrite the file on the server before it is sent; with no `index.html` those requests get 404. _(Sirius Web)_ · `FrontendRouterConfiguration.java`, `CHANGELOG.adoc` v2026.7.0
- **semanticElementIds optimization for unsynchronized nodes**: the `semanticElementIds` variable lists the ids of the elements that should appear with the current description: those already on the diagram plus those a create-view operation would add. Unsynchronized descriptions can use it in node expressions to avoid scanning the whole model. _(Sirius Web, studio)_ · `node-description.adoc`
- **REST request timeout (20 seconds)**: the commit, branch and element REST controllers dispatch each request to the project's editing context and wait at most 20 seconds. If no success payload arrives in time, the GET endpoints answer 404 Not Found. _(Sirius Web)_ · `CommitRestController.java`, `BranchRestController.java`, `ObjectRestController.java`
- **Request timeout fallback (5 seconds)**: if an input sent to an editing context gets no response within 5 seconds, the backend sends back an ErrorPayload with a timeout message and logs "Timeout fallback for the input", so the frontend does not wait forever. The processing itself is not cancelled. _(Sirius Web)_ · `EditingContextEventProcessorRegistry.java`, `CHANGELOG.adoc`

### Monitoring and logging
- **SysON event-handler usage metrics**: the create-expression, edit-expression, insert-textual-SysML and custom-node appearance handlers each increment a Micrometer counter, tagged with the handler's class name, every time they run, for monitoring. · `InsertTextualSysMLv2EventHandler.java`, `CreateExpressionEventHandler.java`, `EditSysMLViewFrameNodeAppearanceEventHandler.java`
- **Platform operational metrics**: every backend event handler registers a Micrometer counter tagged with its name (through MeterRegistry and the Monitoring constants), so administrators can monitor how many inputs of each kind are handled; monitoring was expanded in v2024.1. Editing-context load and save durations are recorded as the timers `siriusweb_editingcontext_load` and `siriusweb_editingcontext_save`. The platform registers only an in-memory SimpleMeterRegistry, so these meters are not exported anywhere unless the integrator adds a metrics registry or exposes them through Spring Boot Actuator (which the SysON application bundles). Some representation event processors (Explorer, model browser, selection dialog trees, tables) are created with their own throw-away SimpleMeterRegistry, so their counters never reach the shared registry. The WebSocket handler also counts `connection_error` replies. GraphQL over HTTP is timed by `siriusweb_graphql_http` (tag kind = request or upload), and the WebSocket endpoint counts messages by type in `siriusweb_graphql_ws_messages` (connection_init, start, stop, connection_terminate) and times sessions in `siriusweb_graphql_ws_sessions`. _(Sirius Web)_ · `EditingContextPersistenceService.java`, `CreateDocumentEventHandler.java`, `AddPageEventHandler.java`
- **Spring Boot Actuator and build info in the SysON server**: unlike the bare platform, the `syson-application` module depends on `spring-boot-starter-actuator` and `micrometer-core`, and its Spring Boot Maven plugin runs the `build-info` goal, so the delivered JAR carries build information and has Actuator's management endpoints on the classpath. SysON's properties set no `management.*` keys, so Spring Boot's default endpoint exposure applies; an administrator who exposes more endpoints, such as metrics, can read the platform's Micrometer meters there. `spring-boot-devtools` is declared only with runtime scope for development. · `pom.xml`, `index.adoc`, `MonitoringConfiguration.java`
- **Performance logging**: `logging.level.sirius.web.performance=DEBUG` logs key performance metrics, including every AQL expression that takes more than 200 ms ("<n>ms to execute the expression <expr>"), and the frontend also logs the order and timing of requests and responses. `sirius.web.performance` is a Spring logging group that Sirius Web's sample application defines over the editing-context search, persistence, event-processor and AQL-interpreter loggers. SysON's dev profile sets the level but SysON defines no such group, so in SysON the setting reaches those loggers only if an administrator adds the group. SysON instead defines the group `org.eclipse.syson.test.performance` (editing-context caching and cached standard-library loading), set to DEBUG in the dev profile. _(Sirius Web)_ · `CHANGELOG.adoc`, `debug-performance.adoc`, `AQLInterpreter.java`
- **Access and project operation logging**: logs follow a logging policy, with messages for access to project templates, projects, libraries, editing contexts and subscriptions and for project manipulation. GraphQL schema registration is logged at DEBUG. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Event processor trace logging**: the inputs and payloads handled by the editing context event processor can be logged with `logging.level.org.eclipse.sirius.components.collaborative.editingcontext.EditingContextEventProcessor=trace`. _(Sirius Web)_ · `EditingContextEventProcessor.java`, `InputDispatcher.java`, `CHANGELOG.adoc`
- **Standard library loading log messages**: at startup the server logs these messages, which let an administrator check which library files were loaded:
  - `Registered EPackage '<name>' (prefix '<prefix>') against URI '<nsURI>'` for each default EPackage
  - `Loaded <KerML|SysML Standard Library> resource: <file>` for each library file
  - the warning "Could not load resource '<file>' because there already is a resource with the same URI" for a file whose URI is already loaded
  - "There was an unexpected issue while loading the contents of '<file>'" for a read failure

  · `SysONDefaultLibrariesConfiguration.java`, `SysONLibraryLoader.java`

- **Logging policy**: backend log messages use the SLF4J fluent API (`atWarn().setMessage(...).addArgument(...).addKeyValue(...)`), name only machine-readable identifiers (never labels or other user-supplied text), carry the useful local variables as key/value pairs, are written in English without translation, and are short and factual ("Project xxx created", "20 project(s) retrieved", "Diagram xxx refreshed. Reason: SemanticChange, Correlation Id: xxx"). ERROR is reserved for non-recoverable failures such as a missing database at startup, every caught exception and every failed operation logs at least one WARN with a message describing the interrupted process, failed assumptions log at DEBUG and successful ones at TRACE. Existing messages were realigned with this policy in 2026.5.0. _(Sirius Web)_ · `logging-policy.adoc`, `CHANGELOG.adoc` v2026.5.0

### Troubleshooting
- **Troubleshooting: connection refused at startup**: a "Connection to localhost:5434 refused" Liquibase BeanCreationException at startup means the database is not reachable or not clean. Start a clean database with no earlier data, for example by running `docker rm syson-postgres` and `docker rmi <image-ID>` for a fresh start. · `troubleshooting.adoc`
- **Troubleshooting: changelog not found**: "The file classpath:db/changelog/syson.db.changelog.xml was not found" at startup means the java command arguments do not match the JAR version. Use the documentation version that matches the JAR. · `troubleshooting.adoc`
- **Troubleshooting: empty page when accessed remotely (HTTPS required)**: opening a SysON server from another machine over plain HTTP shows an empty page, with "Uncaught TypeError: crypto.randomUUID is not a function" in the browser console. The fix is to configure HTTPS. · `troubleshooting.adoc`
- **Troubleshooting: non-standard container runtimes (Podman)**: access problems under container runtimes other than standard Docker, such as Podman, are solved by adding `privileged: true` to both the database and app services in `docker-compose.yml`. · `troubleshooting.adoc`
- **Known issue: NetworkError on document download**: downloading a document from the UI may report a "NetworkError" in the browser. This is a known Sirius Web issue (#6319), and the document is downloaded anyway. _(Sirius Web)_ · `troubleshooting.adoc`
- **Debugging persistence problems**: the developer how-to suggests inspecting PostgreSQL with DBeaver or pgAdmin (tables `project`, `semantic_data`, `databasechangelog` for Liquibase, and a table-size query over `information_schema.tables`), listing sessions with `pg_stat_activity` (idle "PostgreSQL JDBC Driver" pool connections are normal, an idle session with a meaningful last query may be an uncommitted transaction, a long-running active one a slow query), logging JDBC transactions and SQL with `logging.level.org.springframework.jdbc=debug`, temporarily adding datasource-proxy to log bound parameters, profiling with `EXPLAIN (analyze, buffers)`, and starting the Docker PostgreSQL with `-c logging_collector=on -d 5` for verbose server logs. _(Sirius Web)_ · `debug-persistence.adoc`
- **Professional support and maintenance policy**: there is no commercial edition; the open-source project ships updates and fixes on a best-effort basis for the latest release only. Obeo, co-leader of the project, offers training, expertise, custom development, enterprise add-ons, SaaS access and support plans, and the FAQ points there for CM integration, custom validation rules and tool integrations. · `faq.adoc`, `support.adoc`

### Server endpoints and static resources
- **Image server endpoint**: `GET /api/images/**` serves gif, png, jpg/jpeg and svg images. They come either from registered classpath folders (icons, templates, omnibox, impact-analysis...) or, when the path is a UUID, from stored project or custom images. Responses use the matching media type and a one-day public cache; anything else returns 404. _(Sirius Web)_ · `ImagesController.java`, `URLConstants.java`
- **SysON image paths served by the application**: classpath images under the folders `/img`, `/images`, `/icons` and `/palette` are registered as application images. Examples are `/images/sysmlv2-logo.png` (template cards), `/images/omnibox/publish.svg` and `import.svg` (omnibox) and `/palette/create.svg` (the New expression tool). · `ImagePathService.java`

### Development, contribution and testing
- **Developer environment setup (SysON)**: the developer guide sets up Spring Tools 5 for Eclipse with Java 21, the Eclipse Checkstyle plug-in 13.3.0 and the EMF SDK, then imports the clean-up profile, code templates, formatter and import order (`CleanupProfile.xml`, `codetemplates.xml`, `JavaFormatter.xml`, `syson.importorder` from `backend/releng/syson-resources/editor`) and the project-relative Checkstyle configuration from `backend/releng/syson-resources/checkstyle`, set as default. The backend runs from a "Spring Boot App" run configuration with its project, main type and profile filled in; if the console shows the Spring logo instead of the SysON banner, or sources do not compile, a forced Maven update or a clean rebuild is advised. Frontend work uses VS Code or VSCodium with the Prettier extension, and NVM is recommended for switching Node versions. · `index.adoc`
- **Workstation requirements (Sirius Web)**: a developer machine runs Windows 10+, macOS 13+ or a Linux with good Docker support, with Git (Git Bash on Windows), Temurin JDK 21, Maven 3.9.x, Node.js 24.20.0 / npm 11.19.0 (NVM advised), Docker with at least 4 GB of RAM, and a GitHub token with `read:packages`. Any IDE works (IntelliJ IDEA, VS Code, WebStorm), with Altair, GraphiQL or an IDE plugin to try GraphQL queries. GitHub and docker.io must be reachable, and antivirus scanning of Docker volumes or node_modules may slow builds. A short script checks every tool version. _(Sirius Web)_ · `workstation.adoc`
- **Contribution workflow and commit format**: contributors fork the repository, work on a branch and open a pull request against `main`. The commit message must follow `[XXXX] Short description` (70 characters at most on the first line), then an empty line, `Bug: https://github.com/eclipse-syson/syson/issues/XXXX` and a `Signed-off-by:` line with name and e-mail. · `index.adoc`
- **Backend services organization and ServiceMethod**: since 2025.10.2, SysON's services are split by what they touch: atomic model queries and mutations in `syson-sysml-metamodel-services` (no Spring, Sirius Web, diagram or table dependency), Sirius Web-based model services and "accelerators" in `syson-model-services`, and diagram, table, tree, form and cross-representation services in their own modules. Classes are named by purpose (`ModelQueryService`, `ModelMutationService`, `DiagramQueryService`, `DiagramMutationLabelService`...), and each module exposes the services callable from AQL through `*AQLService` entry-point classes. The `ServiceMethod` helper builds AQL service-call strings from type-safe Java method references (`of0`...`of3`, `ofStatic0`..., then `aqlSelf(...)` or `aql(var, ...)`), so renames and find-usages work. Older services are being moved into these modules release by release. · `index.adoc`, `CHANGELOG.adoc` v2025.12.0
- **Testing strategy**: both projects keep backend unit tests, backend integration tests, end-to-end tests and manual exploratory tests (Sirius Web adds frontend unit tests). The rule is to default to backend integration tests, which can seed domains, views and services and run a representation's whole lifecycle quickly and deterministically; end-to-end tests are kept for risky UI interactions such as diagram gestures and drag-and-drop, because they are slow, brittle and hard to seed. Manual scripts are dropped once automated, and flaky end-to-end tests are deleted, tracked in an issue, then stabilized or replaced. Sirius Web writes new end-to-end suites in Playwright (faster in CI, parallel workers, better selectors) while its older Cypress suites are migrated. · `index.adoc`, `testing.adoc`
- **SysON integration-test infrastructure**: backend integration tests extend AbstractIntegrationTests, which starts a reusable Testcontainers `postgres:latest`, points the datasource at it and re-caches editing contexts after each test; tests that need search extend AbstractIntegrationTestWithElasticsearch (an `elasticsearch:9.2.1` container with TLS turned off). Each test loads a project fixture with `@Sql` from `scripts/database-content/*.sql` and wipes every table with `cleanup.sql` afterwards. `initialize-test-data.sh <file>` loads a fixture into a local `syson-test-postgres` container (port 5433) and `dump-test-data.sh <file>` dumps the edited data back with `pg_dump --data-only --column-inserts`. The `syson.test.enabled=no-default-libraries` property skips loading the standard libraries, SemanticRunnableFactory emits the right change description for editing-context updates (since 2026.11.0), and rule tests check coding rules on all modules (since 2025.10.0) and that every public service method is called from an AQL expression. · `AbstractIntegrationTests.java`, `dump-test-data.sh`, `JavaServiceTests.java`
- **End-to-end test suites**: SysON's Cypress suite (`npm run start` opens Cypress) targets http://localhost:8080 with a 1920 x 1080 viewport, 60-second command, request and response timeouts, 2 retries, no video and JUnit reports in `target/result-[hash].xml`; `npm run start:dev` uses the Vite dev server on port 5173 with no retries. The Playwright suite (`npx playwright test`, `--ui` for dev) runs in Chromium and Firefox with one worker, 2 retries and port 8080 on CI (no retries and port 5173 locally), traces on retries and an HTML report. Tests create their projects through the GraphQL `createProject` mutation (template `sysmlv2-template`) and delete them afterwards, and CI runs both suites against the freshly built Docker image. · `cypress.config.ts`, `playwright.config.ts`, `PlaywrightProject.ts`
- **Documentation site build (Antora in Docker)**: the user manual, installation guide and developer guide are AsciiDoc modules built with Antora. `doc/generate-local.bash` builds a `syson_doc_generator:local` Docker image (which bundles the UI from `doc-ui` with gulp, then installs Antora, Asciidoctor, asciidoctor-pdf, Rouge and kramdown-asciidoc) and runs it on the repository with the local playbook `antora-playbook-local.yml`, failing on warnings; a PowerShell variant exists for Windows. Architecture decisions are recorded as ADRs under `doc/adrs` (for example ADR-002 on services organization and ADR-003 on integration-test performance), and `doc/sysml-import` holds short user and developer notes on the textual import (AST, ObjectFinder and mappers). · `generate-local.bash`, `Dockerfile`, `Syson-DeveloperGuide.adoc`
- **GraphQL test runners for downstream applications**: Sirius Web offers IQueryRunner, IMutationRunner and ISubscriptionRunner implementations that hide the request body and transport when tests call the backend APIs. `IGraphQLRequestor#subscribe` returns the raw payload Flux without running child data fetchers, while `subscribeToSpecification` returns spec-compliant JSON strings with every referenced data fetcher executed, for assertions with JsonPath and StepVerifier. Since 2025.6.0 the integration tests of the main `sirius-web` module are also published as a test JAR for reuse. _(Sirius Web)_ · `test-sirius-web-apps.adoc`, `CHANGELOG.adoc` v2025.6.0
