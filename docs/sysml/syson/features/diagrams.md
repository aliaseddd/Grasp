## Diagram: viewport & navigation

### Diagram toolbar
- **Diagram toolbar panel**: a floating horizontal toolbar (MUI Paper overlay panel) pinned at the top-left of the diagram canvas, just below the representation tabs, grouping the global diagram actions with tooltips. In order: Toggle full screen mode, Fit to screen, Show/Hide mini map, Zoom in, Zoom out, Share diagram, export image, Toggle snap to grid mode, Show/Hide helper lines, Arrange all (main button of a split button), Reveal hidden elements, Reveal faded elements, Unpin all elements, Reveal selected elements, Manage selection, then contributed actions (Filter elements, SysON's Diagrams Options). SysON's manual lists: Display full screen, Fit selection to screen, Zoom group, Share the diagram link, Export diagram as SVG, Toggle snap to grid, Show helper line, Arrange all elements, Reveal hidden elements, Reveal faded elements, Unpin all elements, Select element in the diagram from the Explorer selection, Filter elements, SysML actions. The toolbar is rendered only when the diagram description declares a toolbar; older descriptions were migrated to declare one, and an API enables or disables it. SysON declares one (and an empty default diagram style) on all its descriptions: General, Interconnection, Action Flow and State Transition View. The export button's tooltip reads "Export the diagram as an image" with an "Experimental" marker; Sirius Web's manual describes it as downloading the view as SVG, HTML SVG or PNG. In read-only diagrams Show/Hide helper lines, Arrange all, Reveal hidden elements, Reveal faded elements and Unpin all elements are disabled. Test ids: diagram-toolbar, fit-to-screen, hide-mini-map/show-mini-map, zoom-in, zoom-out, share, hide-helper-lines/show-helper-lines, reveal-hidden-elements, reveal-faded-elements, unpin-all-elements. Sirius Web's manual also lists a "Smart Edges" toolbar action (experimental edge routing that avoids crossing nodes, computed client-side and not saved), but the 2026.11.0 toolbar has no such button: Smart Manhattan exists only as an edge type in the appearance editor. The manual's tip: combine Arrange All, Helper Lines and Snap to Grid to clean up complex diagrams quickly. _(Sirius Web)_ · `DiagramToolbar.tsx`, `manage-toolbar-diagram.adoc`, `diagram.adoc`
- **Toolbar collapse/expand**: a chevron button (ChevronLeft/ChevronRight) at the right end of the toolbar collapses it to the chevron alone (tooltip "Collapse toolbar") or expands it again ("Expand toolbar"), animating width and visibility over 0.5 s to free canvas space. The initial state comes from the toolbar description's expandedByDefault flag, default true, so SysON toolbars start expanded. Test ids toolbar-collapse / toolbar-expand. _(Sirius Web)_ · `DiagramToolbar.tsx`, `DiagramToolbarImpl.java`, `toolbar.spec.ts`
- **Toolbar action contribution slot**: after the built-in buttons the toolbar renders contributed toolbar action components, each given the editing context id and diagram id. In SysON the slot holds Sirius Web's "Filter elements" button, then SysON's "Diagrams Options" menu button with switches for showing/hiding icons, inherited members, and inherited members from standard libraries. _(Sirius Web)_ · `DiagramToolbarExtensionPoints.tsx`, `SysONExtensionRegistry.tsx`, `SysONDiagramPanelMenu.tsx`
- **Toggle full screen mode**: the first toolbar button (Fullscreen icon, tooltip "Toggle full screen mode") requests browser full screen on the diagram's DOM element for distraction-free modeling; while active the button becomes "Exit full screen mode" and calls document.exitFullscreen(). _(Sirius Web)_ · `DiagramToolbar.tsx`, `useFullscreen.tsx`, `diagram.adoc`
- **Full screen state synchronization and look**: the full screen flag lives in a per-diagram context that listens to the browser 'fullscreenchange' event, so leaving full screen by other means (e.g. the browser's Esc) switches the icon back. In full screen the diagram background keeps its color (not black) and tooltips and menus stay visible: SysON's theme (like Sirius Web's) mounts MUI menus and tooltip poppers into document.fullscreenElement when one exists, else document.body. _(Sirius Web)_ · `FullscreenContext.tsx`, `useFullscreen.tsx`, `sysonTheme.ts`
- **Fit to screen**: toolbar button (AspectRatio icon, tooltip "Fit to screen") animates the viewport over 200 ms to fit the currently selected nodes, or all nodes when nothing is selected. _(Sirius Web)_ · `DiagramToolbar.tsx`, `useFitView.tsx`, `diagram.adoc`
- **Zoom in / Zoom out**: two toolbar buttons (ZoomIn/ZoomOut icons, tooltips "Zoom in" / "Zoom out", test ids zoom-in / zoom-out) change the zoom by one step with a 200 ms animation. _(Sirius Web)_ · `DiagramToolbar.tsx`, `diagram.adoc`
- **Share diagram**: toolbar button (Share icon, tooltip "Share diagram", test id share) opens a full-width dialog titled "Shareable link" showing the diagram's direct URL (origin + representation path), with the URL text auto-selected; when the clipboard API exists and the page has focus it is copied and the title reads "Shareable link (copied into the clipboard)". The dialog has no buttons and closes on Esc or a click outside. The path is `/projects/{projectId}/edit/{representationId}` in a project, or `/libraries/{namespace}/{name}/{version}/edit/{representationId}` for a diagram inside a library; opening it loads the project with that diagram active. The path comes from the host application's RepresentationPathContext (getRepresentationPath), and the link carries no ?selection= or ?workbenchConfiguration= parameters, unlike the project Share link and the address bar URL (which tracks the active representation and the current selection). Sharing a diagram works like sharing a project, by giving the link. The how-to's steps: click Share in the toolbar at the top of the representation area, then copy the link to the clipboard. Because everything in SysON (and Sirius Web) is inherently public, anyone with the link can open and view that representation directly; there is no access check or permission setting on the link. _(Sirius Web)_ · `ShareRepresentationModal.tsx`, `EditProjectView.tsx`, `DisplayLibraryView.tsx`
- **Show / hide mini map toggle**: toolbar button showing "Hide mini map" (CreditCardOff icon) when visible and "Show mini map" (CreditCard icon) when hidden. The choice is remembered per diagram in browser localStorage (key 'sirius-single-diagram-mini-map-visibility', a map of diagram id to {visible, lastAccessedAt}; a legacy key is removed), so hiding it on one diagram does not affect another and the diagram still has it hidden when reopened. Added to SysON's toolbar in 2025.2.0. _(Sirius Web)_ · `DiagramToolbar.tsx`, `MiniMapContext.tsx`, `diagram.spec.ts`
- **Toggle snap to grid**: toolbar button "Toggle snap to grid mode" (GridOn icon) makes node moves and resizes snap to a 10 px grid; when on it becomes "Exit snap to grid mode" (GridOff icon). Off by default and held per opened diagram (not persisted). While on, the grid is visible (also while moving a non-droppable node); the docs call the grid invisible. _(Sirius Web)_ · `DiagramToolbar.tsx`, `SnapToGridContext.tsx`, `diagram.adoc`
- **Show / hide helper lines toggle**: toolbar button "Hide helper lines" when on, "Show helper lines" when off (test id hide-helper-lines). Helper lines are on by default for each opened diagram; the button is disabled on read-only diagrams. _(Sirius Web)_ · `DiagramToolbar.tsx`, `HelperLinesContext.tsx`, `diagram.adoc`

### Canvas navigation
- **Pan by dragging the background**: dragging on empty diagram background pans the viewport (nodes can move out of view). _(Sirius Web)_ · `arrange-all.spec.ts`
- **Alt + drag to pan**: holding Alt and dragging pans the diagram without moving any element, useful on large zoomed-out diagrams where elements fill the background under the cursor. Implemented by a document-wide listener: pressing Alt makes all nodes undraggable until Alt is released or the browser window loses focus, so dragging works again after Alt+Tab (fixed 2024.9.0). _(Sirius Web)_ · `keyboard-shortcuts.adoc`, `useNodesDraggable.ts`, `CHANGELOG.adoc` v2024.9.0
- **Zoom limits and no double-click zoom**: mouse wheel / pinch zoom is bounded between 0.1x and 40x; double-click zoom is disabled so double-click stays free for other interactions. _(Sirius Web)_ · `DiagramRenderer.tsx`, `CHANGELOG.adoc`
- **Mini map overlay**: a pannable and zoomable (zoom step 2) overview of the whole diagram, 150x100 px at 75% opacity in the bottom-right corner, highlighting the current viewport; click, drag or scroll in it to navigate. Initial visibility comes from the description's minimapVisible flag (can be configured hidden by default) unless a per-diagram choice is stored; SysON's SDV description (used by General, Interconnection, Action Flow and State Transition Views, and their registration stubs) sets minimapVisible(true). On the server, DiagramDescription.minimapVisible is answered by IMinimapVisibilityProvider contributions: every provider that handles the description must return true, and the value defaults to true when it cannot be computed; the view-DSL provider reads the description's minimapVisible flag. Its size and opacity were reduced in 2025.10.0. _(Sirius Web)_ · `DiagramRenderer.tsx`, `SDVDiagramDescriptionProvider.java`, `MinimapVisibleEventHandler.java`
- **Viewport performance**: panning and zooming large diagrams was optimized (label rendering while dragging the viewport, moving or zooming the viewport, node drags), and selecting an element does not trigger a layout. _(Sirius Web)_ · `CHANGELOG.adoc` v2025.12.0, `CHANGELOG.adoc` v2025.4.0, `CHANGELOG.adoc` v2023.12.0

### Automatic viewport behavior
- **Initial fit to screen on open**: when a diagram opens, once its non-hidden nodes are measured, the viewport does one animated fit (400 ms) on all nodes. For an empty diagram the initial fit is skipped and marked done, so dropping a first element keeps zoom at 1 with the node in view (no auto zoom-in). Tests disable it via document.DEACTIVATE_FIT_VIEW_FOR_CYPRESS_TESTS. _(Sirius Web)_ · `useInitialFitToScreen.tsx`, `animation.spec.ts`, `Diagram.ts`
- **Fit to screen after Arrange all**: once an Arrange all has finished and the re-laid-out nodes are measured, the toolbar fits the view to all nodes with a 400 ms animation. _(Sirius Web)_ · `DiagramToolbar.tsx`, `CHANGELOG.adoc` v2024.7.0, `CHANGELOG.adoc` v2025.10.0
- **Viewport not persisted**: zoom and pan live only in the open renderer; nothing stores them, so each opening (including from a shared link) starts with the initial fit to screen. All fit operations go through one hook that the test flag can switch off. _(Sirius Web)_ · `useFitView.tsx`, `useInitialFitToScreen.tsx`, `DiagramRenderer.tsx`
- **No automatic zoom on select or create**: selecting or creating a node does not zoom in, and the viewport does not pan/zoom to a new or selected node that is already fully visible. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Reveal selected nodes in the viewport**: when a selection is applied from outside the diagram (e.g. Explorer) with fit enabled and any selected node is not fully inside the pane, the view pans at the current zoom to show them all, with a 400 ms animation. Applying a selection skips hidden nodes and edges, does not also select a nested occurrence whose ancestor node is already selected for the same element, skips an edge whose element is already selected as a node, and for each selected edge includes its source and target nodes in the area to reveal. Selecting an element in the Explorer can select and focus the matching edge too (2023.12.0); a selection whose node is hidden is not synchronized from the Explorer (2025.2.0). _(Sirius Web)_ · `useRevealNodes.ts`, `useApplySelection.ts`, `CHANGELOG.adoc`

### Background, grid and helper lines
- **Grid background**: while snap to grid is on, the canvas shows a small grid every 10 px (#f1f1f1) and a large grid every 100 px (#cccccc) over the background; off, only the plain background shows. When a nested (non-border) node is dragged over bare diagram where the description says it is not droppable, the background turns the theme's disabled color and both grids become transparent. _(Sirius Web)_ · `DiagramRenderer.tsx`, `useDropDiagramStyle.tsx`
- **Helper lines while moving nodes**: while dragging one or several nodes (as one bounding box), if its left/right edges, top/bottom edges or center come within 10 px of another node's edges or center, a vertical and/or horizontal guide is shown and the nodes snap to it (closest match wins); works for multi-selection moves. _(Sirius Web)_ · `useHelperLines.tsx`, `layoutParams.ts`, `CHANGELOG.adoc`
- **Helper lines while resizing nodes**: resizing from right/bottom snaps the right or bottom edge (10 px) to other nodes' edges with a guide; resizing from left/top (resize plus move) snaps the left or top edge and adjusts size so the opposite edge stays fixed. _(Sirius Web)_ · `useHelperLines.tsx`, `CHANGELOG.adoc`
- **Helper lines exclusions and reset**: candidates ignore hidden nodes, edge-anchor and handle utility nodes, the moving nodes and their ancestors/child nodes of the moved container; pinned nodes are not snapped. Border nodes snap only along their side (east/west vertically, north/south horizontally). Lines disappear as soon as the drag or resize ends. _(Sirius Web)_ · `useHelperLines.tsx`, `CHANGELOG.adoc`
- **Helper lines rendering**: guides are drawn on a full-size, non-interactive, DPI-aware canvas overlay as dashed lines (4/2 pattern) in the theme's primary color spanning the visible canvas and following pan/zoom. _(Sirius Web)_ · `HelperLines.tsx`
- **"Add your first element" empty-diagram background**: standard diagrams use a conditional diagram style: while the ViewUsage exposes nothing and the diagram is empty, the background shows an embedded 'AddYourFirstElement' PNG (centered, contained, no repeat, non-white background color). It counts as empty when there is no previous diagram, previous nodes are none or only the placeholder, every previous node's semantic element is gone (undo of a synchronized creation), or deletion requests cover all previous nodes (undo of an unsynchronized creation). It disappears and the background turns white once an element is added, including after creating a namespace import in a General View; since 2026.9.0 Add existing elements tools that add nothing no longer remove it. First shown on General View in 2024.1.0. · `AddYourFirstElement.java`, `SDVDiagramDescriptionProvider.java`, `DiagramQueryElementService.java`
- **Empty-diagram background message (studio)**: diagrams render in a React Flow wrapper (rf__wrapper) with a background element (rf__background); a conditional diagram style can show a message such as 'Drag and drop elements to get started' while empty, disappearing once an element is dropped from the explorer. _(Sirius Web, studio)_ · `diagram.spec.ts`, `PapayaColorPaletteProvider.java`

### Backend and debug
- **Diagram subscription and refresh causes**: diagramEvent(editingContextId, diagramId) streams the full diagram (nodes, edges, background style, layout data) on every change for all users. Each refresh says whether it is a model refresh or a layout change (cause refresh/layout) and can carry a reference position (parentId, positions, causedBy) telling the client where a creation or drop happened so new elements are placed there. _(Sirius Web)_ · `diagram.graphqls`
- **Diagram loading and unavailable states**: until the first diagram event arrives the panel shows the representation loading indicator; when the subscription completes (e.g. the diagram was deleted) it shows "The representation is not available anymore" and tells the workbench the representation is gone; error payloads on the subscription become toasts. _(Sirius Web)_ · `DiagramSubscriptionProvider.tsx`, `sirius-components-diagrams.json`
- **Diagram debug panel**: when a diagram description enables debug, a horizontally scrollable panel at the bottom-left of the canvas shows one card per item: "Hovered Node" and one "Selected Node" per selected node (Type : Node, Label, Node id, Height, Width, ParentId, x, y, TargetObjectId, TargetObjectKind), and one "Selected Edge" per selected edge (Type : Edge, Label, Edge id, Source, Target). _(Sirius Web, unclear in SysON)_ · `DebugPanel.tsx`, `NodePanelInfos.tsx`, `EdgePanelInfos.tsx`
- **React Flow props customizer extension point**: frontend contributions to 'diagramRenderer#reactFlowPropsCustomizer' (since 2024.7.0) can rewrite the props passed to the canvas, e.g. to add overlay children; the Papaya sample uses it to add an information panel over its diagrams. _(Sirius Web, studio)_ · `DiagramRendererExtensionPoints.tsx`, `DiagramRenderer.tsx`, `PapayaExtensionRegistry.tsx`

### Removed or replaced
- **Sprotty renderer (__SPROTTY suffix)**: React Flow became the default renderer in v2023.12 with Sprotty reachable by suffixing a diagram name with __SPROTTY; Sprotty was removed entirely in v2024.3, replaced by the React Flow renderer. _(Sirius Web)_ · `CHANGELOG.adoc`

## Diagram: selection, editing & direct manipulation

### Selecting elements
- **Click to select**: left-clicking a node or edge selects it (class 'selected') without opening the palette; right-click opens the element's palette. _(Sirius Web)_ · `keyboard-shortcuts.adoc`, `group-selection.spec.ts`, `PlaywrightEdge.ts`
- **Click on background selects the diagram**: left-clicking empty canvas clears selected nodes and edges and makes the diagram representation itself the workbench selection, so e.g. the Details view shows the diagram. _(Sirius Web)_ · `useOnClickElement.ts`
- **Ctrl/Cmd + click multi-selection**: click one element, then Ctrl (Cmd on Mac) + click others to add them to, or remove them from, the selection; works on nodes and edges, and also in the Explorer view. _(Sirius Web)_ · `keyboard-shortcuts.adoc`, `diagram.adoc`, `PlaywrightEdge.ts`
- **Rectangle (marquee/lasso) selection with Shift + drag**: holding Shift and left-dragging draws a rectangle; nodes are selected live and on release every element it touches is selected, even partly inside (partial selection mode). If the drag starts inside a node, that node and all its ancestors are made temporarily unselectable (and deselected while dragging), so nested elements can be selected without their containers; started outside any node it can select containers. _(Sirius Web)_ · `useRectangleSelection.ts`, `DiagramRenderer.tsx`, `2026.9.0.adoc`
- **Click-through multi-selection box**: the rectangle React Flow draws around a multi-selection has pointer events disabled (in both SysON's and Sirius Web's ReactFlow.css), so clicks, drags and right-clicks pass through to the nodes and edges underneath. _(Sirius Web)_ · `ReactFlow.css`, `CHANGELOG.adoc`
- **Last-selected element marker**: in a multi-selection one node is the "last selected": the most recently added, or after deselections the latest remaining one; during a rectangle selection, the node whose border is closest to the cursor. Its round resize handles are filled with the theme's 'selected' color (#8321FF violet in SysON's theme; #BE1A78 pink in Sirius Web's default theme) while others are white. Border nodes never become last-selected. It stays correct after diagram refresh, after tool-driven selection and after lasso unselection; the global selection targets it and most multi-selection layout tools align or size relative to it. _(Sirius Web)_ · `useLastElementSelectedChange.ts`, `Resizer.tsx`, `diagram.adoc`
- **Diagram selection published to the workbench**: each change of the canvas selection publishes the semantic elements (target object ids) of all selected nodes and edges as the global selection, with the last-selected node's element first, so the Details view (and other right-side views) and the address bar's ?selection= parameter follow it. The Explorer does not: selecting a node does not select or reveal it in the Explorer tree until the user clicks the Explorer toolbar's "Reveal selected elements" button (test id explorer-reveal-selection-button) or uses the palette's Show in > Explorer entry (which also pushes a node-plus-edge multi-selection); likewise selecting in the Explorer does not select in the diagram until Reveal selected elements or Show in is used; an empty canvas selection publishes nothing (a background click publishes the diagram itself). The diagram also keeps its own ordered list of selected element ids (elements still selected keep their order, newly selected ones are appended), which decides the group palette's targets and the last element for the selection context menu. _(Sirius Web)_ · `useDiagramSelection.ts`, `SelectionSynchronizer.tsx`
- **Selection and hover outline**: a selected or hovered node (free-form, list or icon-label) gets a 1 px solid outline in the theme's 'selected' color; a selected edge switches its stroke and arrow markers to the selected color. _(Sirius Web)_ · `FreeFormNode.tsx`, `IconLabelNode.tsx`, `MultiLabelEdge.tsx`
- **Node hover tracking**: entering a node sets its hovered state; leaving clears hovered state on all nodes and resets their connection-line indicator; ignored while a node drag is in progress. _(Sirius Web)_ · `useNodeHover.ts`
- **Edge hover tracking**: entering an edge sets its hovered flag, leaving clears it; the flag decides which edge becomes the target when a new or reconnected edge is released over an edge, and highlights compatible edges during a connection. _(Sirius Web)_ · `useEdgeHover.ts`, `useConnector.tsx`
- **Edge selection handles**: edge end handles on nodes are invisible by default and shown only while their edge is selected (two black connection handles); auto-placed handles draw as small black squares, custom-positioned ones white with a black border; they are never directly connectable (pointer events off). Selecting an edge also marks it reconnectable and deselecting it clears that; in a read-only diagram this step is skipped, so a selected edge shows neither its end handles nor reconnect grips. _(Sirius Web)_ · `ConnectionHandles.tsx`, `useSelectEdgeChange.tsx`, `edge-handle.spec.ts`
- **Zoom-adaptive edge hit areas**: the invisible edge interaction path takes its stroke width from the CSS variable --edge-selection-width, set to max(1, 20/zoom) px on .react-flow__edge-interaction; bend-point grab radius is max(3, 20/zoom), segment drag strip max(1, 8/zoom); the visible bend dot stays 3 px. _(Sirius Web)_ · `useDynamicEdgeSelectionArea.ts`, `BendPoint.tsx`, `ReactFlow.css`
- **Selection preserved across refresh**: selected edges stay selected after a diagram refresh, and the diagram selection survives a change made in the Details view. On a 'layout' refresh each node keeps its selected and last-selected flags and its in-progress drag/drop flags, and each edge its selected flag; on a model ('refresh') refresh the flags are copied back from the current store after the client layout. _(Sirius Web)_ · `DiagramRenderer.tsx`, `CHANGELOG.adoc`
- **Opening a diagram keeps the workbench selection**: opening a diagram no longer replaces the selection made elsewhere in the workbench (2025.12.0); selecting an element shown by several nodes sends the Details view one update, not two (2024.11.0); edges stay visible while nodes are selected (2023.10.0). _(Sirius Web)_ · `CHANGELOG.adoc` v2025.12.0, `CHANGELOG.adoc` v2024.11.0, `CHANGELOG.adoc` v2023.10.0
- **Details view shows the last-selected node**: with several nodes selected (click, then Ctrl+click), the Details view shows the last selected one (e.g. its Name field holds that node's name). 2026.9.0 fixed the Details view not always showing the last selected element and made the global selection target it. _(Sirius Web)_ · `selection.spec.ts`, `2026.9.0.adoc`, `CHANGELOG.adoc` v2026.9.0
- **Palette opening updates global selection**: opening the palette on a diagram element updates the workbench-wide selection so other views follow it. _(Sirius Web)_ · `2026.11.0.adoc`

### Toolbar selection tools
- **Reveal selected elements**: toolbar button (test id diagram-reveal-selection) applies the workbench global selection (e.g. Explorer items, or an edge's semantic element) to the diagram once, selecting all top-level occurrences of each element (the diagram no longer follows global selection automatically); a selected edge shows its two connection handles. On hover the tooltip loads ("Reveal selected elements (loading details...)") and lists labels: "Select A, B" for up to 5, then "(and N more)". _(Sirius Web)_ · `RevealSelectionInDiagramButton.tsx`, `sirius-components-diagrams.json`, `selection.spec.ts`
- **Manage selection menu**: toolbar dropdown (Deselect icon plus arrow, tooltip "Manage selection") asks the server (filterSelectionMenuItems(diagramElementIds)) for translated selection-filter items computed from the selected nodes and edges, shows them in a fading menu, and on click (invokeFilterSelection) replaces the diagram selection with the returned ids, deselecting the rest; an empty result also clears the workbench selection. Errors show as toasts; applications can contribute more items and handlers. _(Sirius Web)_ · `FilterSelectionToolbarButton.tsx`, `useInvokeFilterSelection.tsx`, `2026.11.0.adoc`
- **Manage selection: Select nodes / Select edges**: offered only when nothing is selected. "Select nodes" selects every top-level node and recursively their child nodes (border nodes not included); "Select edges" selects every edge. _(Sirius Web)_ · `SelectNodesFilterSelectionHandler.java`, `SelectEdgesFilterSelectionHandler.java`, `sirius-web-application.properties`
- **Manage selection: Unselect nodes / Unselect edges**: with nodes selected, "Unselect nodes" keeps only selected edges; with edges selected, "Unselect edges" keeps only selected nodes. _(Sirius Web)_ · `UnselectNodesFilterSelectionHandler.java`, `UnselectEdgesFilterSelectionHandler.java`
- **Manage selection: Unselect child nodes**: offered when the selection has at least one nested node; keeps only selected top-level nodes and selected edges. _(Sirius Web)_ · `UnselectChildNodesFilterSelectionProvider.java`, `UnselectChildNodesFilterSelectionHandler.java`
- **Manage selection empty state**: when the server returns no applicable filters the menu shows one non-actionable entry "No available tools". _(Sirius Web)_ · `FilterSelectionToolbarButton.tsx`, `sirius-components-diagrams.json`

### Selection after tools
- **Post-tool selection mechanism**: node and edge tools can define an 'Elements to Select Expression'; when a palette or connector tool returns a newSelection it is registered and, on the next refresh with cause 'layout', exactly one visible diagram element per requested semantic element is selected (edges checked first, then nodes; priority nodes before edges, containers before children, then node description order), the last node marked last-selected and everything else deselected, then applied globally to the workbench. Explicit synchronization (toolbar button or Show in) instead selects all top-level occurrences. Tool messages (info, warning, error) show as toasts; an unexpected failure shows "An unexpected error has occurred, please refresh the page". _(Sirius Web)_ · `usePostToolSelection.ts`, `useSingleClickTool.tsx`, `CHANGELOG.adoc`
- **New elements auto-selected, type to rename**: most SysON diagram tools select what they create or expose (since 2026.1.0), so typing right away starts direct edit; Enter commits, the node stays selected and the selection shows in other views (e.g. New Port on a part). Tools that set elementsToSelect to their result: New Action (action flow), compartment item tools (plain and In/Inout/Out), New Parameter In/Inout/Out, New Actor, New Stakeholder, New Subject, New Objective, New Objective Documentation, New Reference (compartment variant), New State, New Parallel State, New Comment on a Dependency edge; New End and New Port as end select the Connection/Interface Definition itself. Tools that select nothing: New Perform Action, New Reference on background or package, free-form tools (New Accept Action, New Assignment Action, control nodes, start/done actions and states), Exhibit states, Entry/Do/Exit actions, Satisfy tools, Framed Concern, Require/Assume constraint, Snapshot/Timeslice, PartUsage relationship tools, set-as tools and Namespace Import. 2026.9.0 fixed selecting the concerned node after a tool and updating the last-selected element when a tool redefines the selection. · `AbstractCompartmentNodeToolProvider.java`, `diagram-selection.spec.ts`, `2026.1.0.adoc`

### Moving nodes
- **Node dragging**: nodes move by dragging after a 5 px drag threshold (was 1 px), so a click does not nudge them; free-form and image nodes drag from their body (custom drag handle). A moved node is brought to z-index 1, flagged movedByUser, and its x/y persisted in the diagram layout and shared with other subscribers. Dragging is disabled on read-only diagrams. _(Sirius Web)_ · `useMoveChange.tsx`, `DiagramRenderer.tsx`, `diagram.spec.ts`
- **Layout pass when a move or resize ends**: when a resize ends, or a drag ends inside the same parent, from background to background, or on a border node, the client re-runs its layout on the diagram and sends the result as a layout synchronization (cause 'layout', switching off automatic layout); a drag that ends in another container is not laid out locally but waits for the server's refresh after the drop tool. _(Sirius Web)_ · `useLayoutOnBoundsChange.ts`, `DiagramRenderer.tsx`
- **Move multiple selected elements**: all selected elements can be dragged together without changing their graphical or semantic parents. _(Sirius Web)_ · `manage-group-elements.adoc`
- **Border node movement**: a border node (port) can only be dragged within an extent around its parent's border (overlapping 5 px, entering the parent by 8 px), moves smoothly to any side, and its side (WEST, EAST, NORTH, SOUTH) is recomputed after a move (corner cases keep the previous side). It is never re-parented by drag and drop, stays movable when an edge is selected or child nodes aren't draggable, keeps position across parent changes, parent bounds changes and hidden edges, and its label does not overlap the parent. Dragging a border node more than 5 px into its parent's interior snaps it back onto the nearest side (north, east, south or west by shortest distance); a parent's node layout handler can instead compute the position itself (calculateCustomNodeBorderNodePosition, used by Sirius Web's sample ellipse node to keep ports on the outline). Border nodes cannot be resized; resizing the parent keeps each border node on its side and attached to the parent, a hidden edge is not considered when positioning border nodes, and dragging a border node highlights no other node as a drop target. _(Sirius Web)_ · `layoutBorderNodes.ts`, `useDropNodes.ts`, `CHANGELOG.adoc`
- **List child movement constraints**: children of a list node cannot leave their container or take inconsistent positions; any move is forced back to x = the list's border width, so items only move vertically. _(Sirius Web)_ · `useResizeChange.ts`, `CHANGELOG.adoc`

### Resizing nodes
- **Node resize modes**: a selected node's resize controls follow its description's userResizable (BOTH, HORIZONTAL, VERTICAL, NONE). ### Edge routing styles
- **Edge Type option**: in the edge palette's Appearance section, the "Edge Type" select switches routing between "Manhattan", "Smart Manhattan" and "Oblique". The style's edgeType selects the renderer, and Manhattan is the fallback for unknown values. Changing or resetting it removes the edge's custom bend points and layout data, so a Manhattan edge with bend points switched to Oblique becomes a straight line. SysON's edge descriptions set no edge type, so SysON edges are Manhattan by default. _(Sirius Web)_ · `EdgeAppearancePart.tsx`, `convertEdge.ts`, `appearance.spec.ts`
- **Manhattan (rectilinear) edges**: without stored bend points, a Manhattan edge computes a smooth-step route between its handles, turns the curve's control points into orthogonal bend points, and draws them as straight L segments. With stored bend points it draws them as-is (a "custom" edge) and keeps the first and last segments aligned with the moving endpoints. _(Sirius Web)_ · `SmoothStepEdgeWrapper.tsx`, `useBendingPoints.ts`
- **Auto-straightening of nearly aligned edges**: when both ends of a Manhattan edge use top/bottom handles and their x coordinates differ by less than 10 px, both handles move to the midpoint x and the edge becomes one straight vertical segment, dropping its bend points. The same applies horizontally for left/right handles and y coordinates. This removes small misalignment jumps, but not on edges or handles the user customized. _(Sirius Web)_ · `SmoothStepEdgeWrapper.tsx`, `228_auto_alignment_on_edge_path.adoc`, `CHANGELOG.adoc` v2026.5.0
- **Smart Manhattan (obstacle-avoiding) edges**: a SmartManhattan edge routes around nodes with jump-point pathfinding (no diagonal moves) on a 10 px grid. The obstacles are the source and target, their siblings and ancestors' siblings up to the lowest common ancestor, and the parents of border-node ends, each padded by 5 px. Handle coordinates are rounded to the nearest 10 px, and the label sits at the middle of the path. If no path is found it falls back to a plain smooth-step path. These edges have no editable bend points. Routes are computed on the client and not persisted. The Sirius Web manual lists a "Smart Edges" toolbar entry; no such toolbar toggle exists in the v2026.11.0 code, so the routing is reached through Edge Type. _(Sirius Web; experimental)_ · `SmartStepEdgeWrapper.tsx`, `getSmartEdge.ts`, `diagram.adoc`
- **Oblique edges with editable bend points**: an Oblique edge is a straight polyline from the source through its bend points to the target, set by the style or from the Appearance palette. When it is selected, each bend point shows as a black dot and each segment midpoint as a white dot with a black outline. Dragging a midpoint inserts a new bend point; dragging a bend point moves it and recomputes the midpoints. On release the bend points (absolute, and relative to the source) are persisted. _(Sirius Web)_ · `ObliqueEdgeWrapper.tsx`, `MultiLabelObliqueEditableEdge.tsx`, `CHANGELOG.adoc` v2026.1.0
- **Edge-type feature differences**: Manhattan edges have draggable bend points and segment strips, connection-creation arrows on the selected edge, compatible-edge dimming and highlighting while connecting, and reconnect circles inset into the end node, and they keep ELK's bend points after arrange-all. Oblique edges have only bend-point and midpoint dots, and lose their bend points on arrange-all. Smart Manhattan edges are recomputed by pathfinding and have no path editing, no creation arrows and no connection highlighting. All three support draggable and resizable labels, crossing gaps and reconnection. _(Sirius Web)_ · `MultiLabelRectilinearEditableEdge.tsx`, `SmartStepEdgeWrapper.tsx`, `useElkLayout.ts`
- **Edges avoid passing through other nodes**: edge routing uses a pathfinding algorithm so that edges do not pass through other nodes, and an edge between a child and its parent no longer passes entirely through the child. _(Sirius Web)_ · `CHANGELOG.adoc` v2024.5.0, `CHANGELOG.adoc` v2024.9.0
- **Edges end at the node border**: edges stop at the border of their end nodes (figure bounds intersection) rather than at the creation handles. _(Sirius Web)_ · `CHANGELOG.adoc` v2023.12.0
- **Multiple edges and self-loops**: several edges between the same nodes and self-loop edges are laid out properly. _(Sirius Web)_ · `CHANGELOG.adoc` v2022.01.0
- **Edges between icon-label nodes**: edges can connect icon-label nodes (e.g. compartment items) and render correctly. _(Sirius Web)_ · `edge.spec.ts`

### Edge bend points and segments
- **Editable edge paths**: selecting an edge shows handles to edit its route, and the custom route is persisted. The Sirius Web manual describes three gestures: drag a black handle to move an existing segment, drag a gray midpoint handle to insert a new bend point, and double-click a bend point to remove it. Later releases refined this. A single click no longer adds a bend point. Bend points have a larger interaction radius, and new ones are placed in the middle of a segment. New ones are created only when the source or target handle would change side. Segments are kept from running parallel to node borders, and nodes do not overlap their edges' bend points. Custom routing points are kept when one end moves, and deleting an edge does not change the layout of other edges. _(Sirius Web)_ · `diagram.adoc`, `edge.spec.ts`, `CHANGELOG.adoc` v2025.8.0
- **Rectilinear bend point dragging**: a selected Manhattan edge shows its bend points as black dots (`bend-point-N`). Dragging one moves its neighbours with it so every segment stays orthogonal. Dragging the first or last point slides the edge end along the source or target side. Dragging that point beyond the node's side creates a new bend point, and the handle jumps to the middle of the side facing the drag. _(Sirius Web)_ · `useBendingPoints.ts`, `RectilinearEdgeCalculation.ts`, `BendPoint.tsx`
- **Rectilinear segment dragging**: each segment of a selected Manhattan edge has an invisible draggable strip (`temporary-moving-line-N`; cursor ns-resize on horizontal segments, ew-resize on vertical ones) that moves the whole segment perpendicular to itself. The edge's handles are hidden during the drag. Dragging the first or last segment slides the edge end along the node side, which is also how an edge end is moved along a node border, and dragging it past the node side adds a bend point at the middle of the node border. Moving a middle segment leaves the source handle where it was on its node side. _(Sirius Web)_ · `useTemporaryLines.ts`, `BendPoint.tsx`, `edge.spec.ts`
- **Bend point cleanup on drop**: when a bend-point or segment drag ends, consecutive bend points within 10 px of each other are merged and the next point is realigned to stay orthogonal. Aligning an edge's segments so that no bend point remains straightens it, aligning the source or target; this is the quick way back to a straight edge. The handle side is recomputed from the first or last segment direction, the handle's exact position is stored, and the edge layout is persisted. _(Sirius Web)_ · `useEdgeDragStopHandler.ts`, `RectilinearEdgeCalculation.ts`, `CHANGELOG.adoc` v2025.12.0
- **Bend points follow when both ends move**: each edge stores relativePositionBendingPoints (bend points relative to the source endpoint) next to its absolute bend points. When both end nodes move together, either both in a multi-selection drag or both inside a container being dragged, the bend points move with them and the custom route keeps its shape. - **Rectilinear edges stay rectilinear**: customized rectilinear edges keep their rectilinearity when nodes move or the diagram refreshes. _(Sirius Web)_ · `CHANGELOG.adoc` v2025.4.0, `CHANGELOG.adoc` v2025.6.0

### Edge handles (connection points)
- **Automatic handle side selection**: each edge end attaches to the side of its node that faces the other end. With a vertical arrange direction (DOWN/UP), angles between 30 and 150 degrees (and their opposites) pick top or bottom, otherwise left or right. With a horizontal direction (RIGHT/LEFT), angles up to 60 degrees or from 300 degrees pick left or right. With UNDEFINED, the larger of dx and dy decides. In practice RIGHT gives horizontal edges and DOWN vertical ones; all SysON views use DOWN. An edge between a container and its descendant uses the inner side. A border node uses its own side, or the opposite side when the other end is inside its parent. With bend points, the side faces the first or last bend point. _(Sirius Web)_ · `EdgeLayout.ts`, `edge-handle.spec.ts`, `layoutParams.ts`
- **Live handle side update while dragging**: while a node that is not pinned is being dragged, the handle sides of its connected edges without bend points are recomputed continuously from its live position. Edges anchored on another edge take their side from the host edge segment. Border nodes of the dragged node that the user has not moved also flip to the side facing their edge's other end, re-stacked with a 10 px gap. _(Sirius Web)_ · `useHandleChange.tsx`, `layoutBorderNodes.ts`
- **Handle ordering on a node side**: each edge has its own handle. When several edges attach to the same side of a node, their handles are spread evenly along it and ordered by the position of each edge's other-end node center: by x on the top and bottom sides, by y on the left and right sides. After a node is moved, the handles are repositioned this way, which reduces crossings. _(Sirius Web)_ · `layoutHandles.ts`, `ConnectionHandles.tsx`, `CHANGELOG.adoc` v2024.1.0
- **Manually positioned edge handles**: an edge end can be pinned to an exact point on a node border, either by reconnecting it to the same node or by editing the first or last segment. When a connection line hovers a node's border, the handle goes at that point; hovering the node's middle places it automatically. Positions are stored per node and edge in handleLayoutData (edgeId, position, side, type) and persisted, and survive moves, resizes and refreshes. When the node is resized, alone or with a move, a custom handle slides proportionally with the new width and height and stays on the same side. A custom position is preserved during edge reconnection. Handles take bend points into account and keep the target position chosen at edge creation. _(Sirius Web)_ · `useHandleResizedChange.tsx`, `edge-handle.spec.ts`, `CHANGELOG.adoc` v2026.3.0
- **Precise edge-end position from creation point**: after an edge is created or reconnected, the refresh's referencePosition (caused by InvokeSingleClickOnTwoDiagramElementsToolInput or ReconnectEdgeInput) puts the new edge's handle on the target node border point nearest the release position, so edge ends land where the user dropped them. _(Sirius Web)_ · `UpdateHandleFromReferencePosition.ts`, `CHANGELOG.adoc` v2025.6.0
- **Reset handles positions**: palette quick-access tool "Reset handles positions" (id `reset-handles-position`), offered on an edge when its source or target node holds a stored non-zero handle position for it. It clears those custom positions on both end nodes so the handles return to automatic placement, then persists the layout. _(Sirius Web)_ · `useHandlesLayout.tsx`, `PaletteDefaultToolsProvider.java`, `useInvokePaletteTool.tsx`
- **Edge-on-edge handle placement**: for an edge whose end is another edge (through an edge anchor node), the handle sides on the anchor follow live moves: dragging the node at the other end, or one of the host edge's end nodes (which moves the anchor), updates the source and target handle sides during the drag and keeps them after the drop. ### Edge crossings
- **Edge crossing tunnels (cross-fade gaps)**: wherever two edges really cross, the edge drawn underneath gets an 18 px gap (a stroke-dasharray with round caps), so it looks as if it passes under the other. The under edge is the one with the lower zIndex, otherwise the one whose id sorts higher. Crossings within 18 px of a path end or 12 px of an end node are ignored, as are touching or colinear segments. Hidden edges and edges that already have a dash pattern are skipped. Detection is O(E^2) and runs after a drag ends, never during it, to keep interactions smooth. Hiding a node so that the crossing disappears removes the tunnel; "Reveal hidden elements" restores it. _(Sirius Web)_ · `detectEdgeCrossings.ts`, `buildCrossingDashArray.ts`, `edge.spec.ts`

### Border nodes
- **Border node default placement and parent resize**: a border node without a stored position honors its initial side and is stacked along that side, starting 8 px from the corner with 25 px spacing, overlapping the parent border by 5 px (e.g. north at y=-15, east at x=parentWidth-5, size 20). Dragging one slides it along the parent border. When the parent is resized, each border node stays on its side: EAST ports follow the right edge and SOUTH ports the bottom edge, ports beyond the new size are pulled back inside, and the extents are updated. Border nodes have no resize handles. _(Sirius Web)_ · `layoutNode.ts`, `useResizeChange.ts`, `border-node.spec.ts`
- **Default border node side (EAST)**: a border node starts on the side given by the server's initialBorderNodePosition (WEST, EAST, SOUTH or NORTH), or on EAST when that value is NONE or unknown. - **New border node side from creation point**: a border node created from the palette goes on the side of its parent nearest the click: WEST in the left 20% of the width, EAST in the right 20%, NORTH in the top 20% of the height, SOUTH in the bottom 20%. _(Sirius Web)_ · `layoutBorderNodes.ts`, `layoutParams.ts`
- **Border node side follows connected edges**: on refresh and as nodes move, a border node the user has not moved switches to the side of its parent facing the other end of its edge (left, right, top or bottom), which simplifies paths, and is re-stacked on that side with a 10 px gap. ### Containers and free-form layout
- **Free-form container auto-sizing**: a free-form container is sized to fit its children's box, including their border-node footprints and outside labels. To that it adds 8 px padding, the header and footer label heights, its own north/south/east/west border-node footprints, the label width (NONE overflow) and its 1 px border. The first child therefore sits at (9, 9 + parent label height). The result is never smaller than the default size: 150x70 unless the description sets defaultWidth/defaultHeight. minComputedWidth and minComputedHeight are recorded and persisted. _(Sirius Web)_ · `FreeFormNodeLayoutHandler.ts`, `freeform-layout.spec.ts`, `layoutParams.ts`
- **Child placement inside containers**: existing children keep their previous position but are pushed below the header and inside the 8 px padding; free-form children get a top and bottom margin, and the height of outside labels is counted. New children go at their creation position (still at least below the header). Children without any layout are laid out left to right with a 25 px gap, after the previous sibling's east border nodes and their own west border nodes. An icon-label child dragged inside a free-form parent keeps its new position, unlike one inside a list, which snaps back. _(Sirius Web)_ · `FreeFormNodeLayoutHandler.ts`, `layoutNode.ts`, `2026.9.0.adoc`
- **Free-form parent grows to contain a moved child**: moving a child partly outside its free-form parent enlarges the parent so the child fits inside. Hidden child nodes are ignored when computing that resize (2026.9). _(Sirius Web)_ · `resize.spec.ts`, `2026.9.0.adoc`, `CHANGELOG.adoc` v2026.9.0
- **Children keep their place when the parent is resized**: resizing a free-form parent from any corner, smaller or larger, keeps its children at the same place on screen. Their relative coordinates shift by the parent's top/left delta, several children move by the same delta, and their layout relative to each other is preserved (2026.9). _(Sirius Web)_ · `resize.spec.ts`, `2026.9.0.adoc`, `CHANGELOG.adoc` v2025.12.0
- **User-resized size kept by later layouts**: a node resized by the user is flagged resizedByUser and persisted. Later layouts keep its size unless the computed content minimum becomes larger, so it only grows. Nodes not resized by the user are sized as max(default size, content minimum). Specifiers on the description indicate whether a node can be resized. _(Sirius Web)_ · `useResizeChange.ts`, `FreeFormNodeLayoutHandler.ts`, `CHANGELOG.adoc` v2024.1.0
- **Keep aspect ratio**: for node descriptions with keepAspectRatio, each layout corrects the computed size to the default width/height ratio by enlarging the width or height, and interactive resizing locks the ratio. _(Sirius Web)_ · `layoutNode.ts`, `Resizer.tsx`
- **Deep node nesting**: nodes nested 12 levels deep (self-contained elements) all render, down to the deepest child. _(Sirius Web)_ · `child-node-depth.spec.ts`
- **Rendered size matches layout size**: rectangular and icon-label nodes have the same DOM size as the dimensions stored in the diagram layout. _(Sirius Web)_ · `diagram.spec.ts`

### Lists and compartments
- **List node (compartment list)**: a node whose children layout strategy is List (the layout strategy is separate from the style) renders as a list node that stacks its children vertically, with no unwanted space between the header and the first item. Its options are areChildNodesDraggable (default true), topGap, bottomGap (default 0) and growableNodeIds. Children are placed at x = border width, starting below the header plus topGap, each directly under the previous one. List compartments get a bottom separator border (0 0 1px); free-form compartments get none. Children span the parent width (minus the 2 px border) and follow horizontal resizes. Moving a list keeps its size. _(Sirius Web)_ · `ListNodeLayoutHandler.ts`, `ListNodeConverter.ts`, `list.spec.ts`
- **List width and growable-height layout**: all children of a list share one fixed width: the largest of the widest child, the label width, the north/south border-node footprints, the previous content width and any forced width. Growable children (those in growableNodeIds and not resized by the user) split the remaining content height equally, so they absorb the extra space when the list is enlarged. Non-growable children keep their own height (default width 150, non-growable default height 70). _(Sirius Web)_ · `ListNodeLayoutHandler.ts`, `growable-list.spec.ts`, `CHANGELOG.adoc` v2024.3.0
- **Free-form compartments grow inside SysON nodes**: in definition and usage nodes, every reused free-form child compartment (action flow, state transition, interconnection) is registered as a growable node of the parent's list layout, so it takes the remaining height when the node is resized. The interconnection compartment was made growable in 2026.1.0; resizing a part in an Interconnection View changes both the width and the height of its interconnection compartment. · `AbstractUsageNodeDescriptionProvider.java`, `diagram.spec.ts`, `CHANGELOG.adoc` v2026.1.0
- **Free-form compartments inside list nodes**: a node can contain free-form compartments, whose children are laid out freely, even inside a list layout. _(Sirius Web)_ · `CHANGELOG.adoc` v2023.3.0
- **List node resize rules**: a list node cannot be resized shorter than its layout requires, but its width can be reduced below the default (Adjust size restores it). Resizing vertically increases its height, and its layout survives resizes. The resizedByUser flag applies to list children. Its width no longer grows on each layout. Children are not placed at (0,0) or misplaced after a sibling is hidden. Feedback is shown when a list node is resized and moved in the same action. _(Sirius Web)_ · `list.spec.ts`, `CHANGELOG.adoc` v2026.1.0, `CHANGELOG.adoc` v2025.4.0
- **List items re-stacked under the header during resize**: while a list with a TOP header label is resized, the header label is measured in the DOM (divided by zoom). The border is added (twice when a header separator is shown), plus topGap, and the children are re-stacked from that height. Label wrapping during a resize therefore never overlaps the items: when widening reduces the wrapped header's line count, the children move up. _(Sirius Web)_ · `useResizeChange.ts`, `list.spec.ts`
- **Manually resized list shrinks when items disappear**: when a list node was resized by the user and children disappear between two refreshes (deleted or hidden), the height they used is subtracted from the list's stored height, unless the content minimum is larger. The list therefore shrinks (e.g. to 400 px) instead of leaving a gap, and the remaining items reflow without gaps. _(Sirius Web)_ · `ListNodeLayoutHandler.ts`, `growable-list.spec.ts`, `CHANGELOG.adoc` v2025.8.0
- **Icon-label node (list item) sizing**: an icon-label node, the compact icon-plus-text row used for compartment items, is sized from its inside label: width is the forced width (e.g. the list's shared width) or the label width constraint plus 8 px padding on each side, and height is the measured label height. Those values are recorded as its minimum computed width and height. _(Sirius Web)_ · `IconLabelNodeLayoutHandler.ts`
- **List items snap back**: dragging an icon-label child of a list node elsewhere without a valid drop puts it back at its list position, and the parent list does not move. _(Sirius Web)_ · `dnd.spec.ts`

### SysON custom node layouts
- **Package node layout**: children of a Package are kept below the header tab with 8 px padding. New children are clamped under the header, a negative x is moved to 8 px, and unplaced children are stacked after their previous sibling. Border nodes are positioned on the package. The package grows to fit its children, border-node footprints and (unless user-resized) its default size. A user-resized package can grow but never shrinks below its content. An empty package uses its default size (fallback 75x50), or, when user-resized, keeps its size with a 75x50 minimum. It is always tall enough for its label plus 16 px. Since 2025.2.0, Package and Namespace Import nodes in the General View can be resized smaller than their default size. · `SysMLPackageNodeLayoutHandler.ts`, `2025.2.0.adoc`
- **Package children keep their positions across tab switches**: the children of a Package node keep their positions when the diagram is rendered again after switching representation tabs (fixed 2025.6.0). · `2025.6.0.adoc`, `CHANGELOG.adoc` v2025.6.0
- **Imported package node layout**: imported package nodes are always laid out as leaves, ignoring children. Without a user resize they take their default size (fallback 75x50); when user-resized they keep their size with a 75x50 minimum. They are always tall enough for the label plus 16 px padding. · `SysMLImportedPackageNodeLayoutHandler.ts`
- **Note node layout**: a note without stored layout defaults to 200x70, or its description's defaults. The width keeps the current or forced width, and the height is at least the label height plus borders. User-resized notes keep their size unless it is smaller than that minimum. The aspect ratio is kept when the node description requires it. · `SysMLNoteNodeLayoutHandler.ts`, `SysMLNoteNodeConverter.ts`
- **Custom nodes report their stored size to avoid edge blinking**: SysON's package, imported package, note and view frame converters set the node's measured width and height from its stored layout size when converting, as the xyflow documentation recommends, so connected edges do not blink while the diagram refreshes. · `SysMLPackageNodeConverter.ts`, `SysMLNoteNodeConverter.ts`, `CHANGELOG.adoc` v2025.10.0
- **View frame node layout**: view frames (ViewUsage frames) lay out children like packages: below the header with 8 px padding, growing to fit content and border nodes, respecting user resize. The difference is that an existing child is pushed below the header only if its previous position was above it. · `SysMLViewFrameNodeLayoutHandler.ts`

### Placement of new elements
- **New element placement at the click point**: elements created by a tool are placed at the referencePosition sent by the server, which is the palette click point converted to the parent's coordinates; this also applies to two-element tools. When several elements are created at once, each following sibling is offset along the arrange direction (DOWN, UP, LEFT, or RIGHT/UNDEFINED) by the previous element's size plus a 25 px gap and the border-node footprints, so new nodes no longer stack on one spot. Children created in a compartment start at padding 8 below the 37 px header. When the new element's parent differs from the clicked element, it is placed next to the clicked element along the layout direction, and shifted again (up to 10 times) if a sibling already occupies that spot. Grandchildren and growable nodes are positioned correctly. _(Sirius Web)_ · `layoutNode.ts`, `node-creation.spec.ts`, `CHANGELOG.adoc` v2026.1.0
- **Root node default placement**: top-level nodes with no known position are laid out left to right on the row y=0, separated by 25 px plus the border-node widths on facing sides. Nodes with a previous or server position keep it. _(Sirius Web)_ · `layout.tsx`

### Layout engine and persistence
- **Client-side incremental layout**: diagram layout is computed in the browser, on ReactFlow; the server-side ELK layout engine and server-side diagram export were removed. Each refresh is laid out in steps: labels are measured in a hidden area, the layout runs, then a callback. Previous in-memory positions and sizes take priority. Nodes seen for the first time with server layout data use that data. Brand-new nodes, which have no layout data, get the default size and a computed placement. Layout data is shared between all subscribers of the diagram. _(Sirius Web)_ · `useLayout.ts`, `LayoutEngine.ts`, `CHANGELOG.adoc` v2024.11.0
- **Stable node positions across refresh**: nodes do not move on a diagram refresh; only their size is updated. The layout does not run on a simple selection. _(Sirius Web)_ · `CHANGELOG.adoc` v2023.12.0
- **Initial layout persisted on open**: opening a diagram triggers a layoutDiagram mutation with cause "refresh", which persists the computed initial layout. _(Sirius Web)_ · `PlaywrightDiagram.ts`
- **Layout after move or resize**: when a resize ends, or a move ends without a reparenting drop (same parent, diagram to diagram, or a border node), the diagram re-runs its layout pass on the new bounds, so parents grow and handles update. It then persists the positions and sizes for all viewers. _(Sirius Web)_ · `useLayoutOnBoundsChange.ts`, `DiagramRenderer.tsx`
- **Pluggable node layout handlers**: the client LayoutEngine lays out each node with the first registered handler whose canHandle accepts it; the built-in ones are FreeForm, List and IconLabel. A custom node type registers its own handler through the node type registry (nodeLayoutHandlers, with nodeConverters and nodeTypeContributions), and a handler can also supply calculateCustomNodeEdgeHandlePosition, used by Manhattan, Smart Manhattan and Oblique edges to place edge ends on non-rectangular shapes, and calculateCustomNodeBorderNodePosition, for border-node placement. SysON registers its Package, Note, Imported package and View frame handlers this way and uses neither hook. _(Sirius Web)_ · `LayoutEngine.ts`, `LayoutEngine.types.ts`, `SysONNodeTypeRegistry.tsx`
- **Server handling of layoutDiagram**: a layout with cause "layout" (moves, resizes, tools, arrange) is always applied. A layout with cause "refresh" is applied only if its id is the id of the diagram's current refresh, so a stale layout computed for an older refresh is silently ignored with a SuccessPayload. Applying one replaces the diagram's whole node, edge and label layout data with what the client sent, recomputes autoLaidOut, runs any registered diagram post-processors, persists the diagram and broadcasts it to all subscribers with refresh cause "layout". On a server refresh, existing layout data is carried over unchanged; a new diagram starts with empty layout data and autoLaidOut true unless its layoutOption is NONE. _(Sirius Web)_ · `DiagramEventProcessor.java`, `DiagramCreationService.java`, `DiagramRenderer.tsx`
- **Persisted diagram layout data**: each diagram stores layout data on the server. The client sends every node that has a measured width and height, only the first outside label of each node, the begin, center and end labels of each edge, the bend points of every edge (absolute and relative), and handle positions only for handles with a custom non-zero position. Per node: position, size, movedByUser, resizedByUser, minimum computed size, and per-edge handle positions (side, source/target). Per edge: bending points (absolute and relative) and anchor position ratios. Per label: position and size with moved/resized flags. Plus an autoLaidOut flag. `layoutDiagram(cause, diagramLayoutData)` saves client layout changes, with autoLayoutState UNCHANGED, ACTIVATE or DEACTIVATE. Moves, resizes and bend points therefore persist and sync to other users. If the layout mutation fails, the toast "An unexpected error has occurred, please refresh the page" is shown; messages returned in the payload are shown as toasts too. _(Sirius Web)_ · `diagram.graphqls`, `useSynchronizeLayoutData.ts`
- **Diagram post-processors (backend layout hook)**: an application can register IDiagramPostProcessor beans to change a diagram, its layout data included, on the server. Each one whose canHandle(editingContext, diagramContext) accepts the diagram gets postProcess(editingContext, diagramContext) and may return a modified Diagram, after every render (creation and refresh) and after every applied layoutDiagram. The DiagramContext they receive is freshly built around the diagram, so its diagram events, view creation and deletion request lists are empty. Added in 2025.12 as "the ability to programmatically change the layout of a diagram on the backend"; SysON registers none. _(Sirius Web, studio)_ · `IDiagramPostProcessor.java`, `DiagramCreationService.java`, `DiagramPostProcessorControllerTests.java`
- **Layout and view state kept on project import**: uploading a project with diagrams restores their layout and unsynchronized nodes (2025.6), keeps each node's view state modifier (hidden, faded, normal) for unsynchronized diagrams (2025.6), preserves label positions (2025.10) and custom edge handle positions (2026.5). Label layout data gained a size in 2025.12, with a migration participant for existing diagrams. _(Sirius Web)_ · `CHANGELOG.adoc` v2025.6.0, `CHANGELOG.adoc` v2025.10.0, `CHANGELOG.adoc` v2026.5.0
- **Diagram description display settings**: the client loads per-diagram settings from the description. Node descriptions give userResizable, keepAspectRatio, and the allowed child and border node descriptions. The description also gives toolbar expandedByDefault, drop compatibility, a debug flag, arrangeLayoutDirection (UNDEFINED/RIGHT/DOWN/LEFT/UP), layoutOption (NONE/AUTO_LAYOUT/AUTO_UNTIL_MANUAL) and minimapVisible. _(Sirius Web)_ · `DiagramRepresentation.tsx`, `DiagramDescriptionContext.ts`, `diagram.graphqls`

### Diagram description options (studio)
- **Automatic layout option**: a diagram description's layoutOption can be NONE (no automatic layout), AUTO_LAYOUT (laid out with ELK on open and on every refresh, so manual moves snap back to the computed position, e.g. the first node at 12,12; move, resize and arrange are not meant to be used there), or AUTO_UNTIL_MANUAL (laid out on open and refresh until the user first moves or resizes something; moved nodes then keep their position). - **Children layout strategy: List or FreeForm**: a node style's childrenLayoutStrategy is either FreeForm (children placed freely) or List. List stacks children vertically and takes areChildNodesDraggableExpression (default `aql:true`; false makes the children undraggable), topGapExpression and bottomGapExpression (free space before or after the items, to ease inserting into a list), and growableNodes (children that stretch to fill the space). ### Visibility backend API
- **Hide, fade and pin mutations**: `hideDiagramElement(elementIds, hide)`, `fadeDiagramElement(elementIds, fade)` and `pinDiagramElement(elementIds, pinned)` act on several elements at once. Each element has a view state (Normal, Faded or Hidden) and a pinned flag, all persisted and shared with other users. Unknown ids produce an ErrorPayload reading "At least one error during the deletion:" followed by 'Edge "<id>" not found' and 'Node "<id>" not found'; the known ids are still applied and the diagram still refreshes. Success payloads carry any feedback messages, shown as toasts. _(Sirius Web)_ · `diagram.graphqls`, `HideDiagramElementEventHandler.java`, `sirius-components-collaborative-diagrams.properties`
- **View modifier computation**: each node and edge keeps its own set of modifiers (Hidden, Faded). Its displayed state is Hidden if the set holds Hidden, else Faded if it holds Faded, else Normal. A node inside a hidden parent, or inside a collapsed node, is rendered Hidden but keeps its own modifiers, so revealing or expanding the parent restores each child's previous state. An edge is Hidden whenever its source or target is hidden. A node's default modifiers (hidden- and faded-by-default expressions) and collapsed-by-default state are evaluated only on its first render; afterwards the previous modifiers carry over. A reset-view-modifiers event restores a node's defaults, but edges have no defaults and ignore resets. Pinning applies to nodes only: edges have no pinned flag, so the edge ids that Unpin all sends are ignored. _(Sirius Web)_ · `NodeComponent.java`, `EdgeComponent.java`, `ViewStateProvider.java`

### Node and edge description options (studio)
- **Node synchronization policy**: SYNCHRONIZED creates a node automatically for each candidate, removed only when its element is no longer reachable by the candidates expression. UNSYNCHRONIZED shows a node only when a tool explicitly asks for it. Another tool can remove it without deleting its element, and it is removed automatically when the element becomes unreachable. Unsynchronized descriptions keep diagrams of large models manageable; their candidates and precondition expressions get a `semanticElementIds` variable listing the elements already on the diagram plus those a create-view operation is adding, so they need not scan the whole model. A group-palette "Delete from diagram" for unsynchronized nodes is built with `aql:diagramServices.deleteViews(selectedNodes)`. In SysON, the definition, usage, package and compartment-item node descriptions are SYNCHRONIZED; a few, such as the annotating, done-action and fake nodes, are UNSYNCHRONIZED. _(Sirius Web, studio)_ · `node-description.adoc`, `AbstractDefinitionNodeDescriptionProvider.java`, `AnnotatingNodeDescriptionProvider.java`
- **Edge synchronization policy**: SYNCHRONIZED shows an edge automatically when a semantic relation (reference-based or domain-based) is found, and removes it only when the relation is gone. UNSYNCHRONIZED shows an edge only when a tool asks for it. A tool can remove it without deleting the relation, and it is removed automatically when the relation becomes unreachable. _(Sirius Web, studio)_ · `edge-description.adoc`
- **Diagram visibility services in tool expressions**: every View-based diagram's AQL interpreter has a `diagramServices` service with collapse(nodes), expand(nodes), hide(elements), reveal(elements), fade(elements), unfade(elements), resetViewModifiers(elements), deleteViews(nodes), isHidden(element) and isFaded(element). Tool bodies and preconditions use them to change or test visibility; isHidden and isFaded test the element's own modifiers, not an inherited hidden state. SysON's Show/Hide palette tools and its group-palette tools are written with them. _(Sirius Web, studio)_ · `DiagramServices.java`, `ViewAQLInterpreterFactory.java`, `DiagramDefaultToolsFactory.java`
- **Hidden by default expression**: a node description's isHiddenByDefaultExpression decides whether the node starts hidden (variables self, editingContext, previousDiagram, diagramEvent). SysON uses it on its compartments (e.g. the interconnection compartment) and control nodes. _(Sirius Web, studio)_ · `node-description.adoc`, `InterconnectionCompartmentNodeDescriptionProvider.java`, `CHANGELOG.adoc` v2024.5.0
- **Faded by default expression**: a node description's isFadedByDefaultExpression decides whether the node starts faded (variables self, editingContext, previousDiagram, diagramEvent). _(Sirius Web, studio)_ · `node-description.adoc`, `CHANGELOG.adoc` v2024.5.0
- **Collapsible and collapsed by default**: a node description's `collapsible` flag (default false) makes the node collapsible; a collapsed node hides its child nodes. "Is Collapsed By Default Expression" (isCollapsedByDefaultExpression; variables self, editingContext, previousDiagram, diagramEvent) sets whether the node first renders collapsed. _(Sirius Web, studio)_ · `node-description.adoc`, `diagram.ecore`, `CHANGELOG.adoc` v2024.5.0
- **collapsingState variable in expressions**: node semantic candidates, precondition and label expressions (and node style conditions) receive a `collapsingState` variable (COLLAPSED or EXPANDED), so a studio can give a collapsed node a different conditional style, e.g. with the condition `aql:collapsingState.toString() = 'COLLAPSED'` (since 2023.3). ## Diagram: palette & tool UI

### Opening the palette
- **Right-click opens the contextual palette**: In every diagram the palette opens on right-click (context menu) at the cursor; it opened on left-click before SysON 2025.2. Right-click on a node or edge that is not selected adds it to the selection and targets it alone. Right-click on an element that is part of a multi-selection opens the group palette for every selected element. Right-click on the background clears the selection, selects the diagram in the workbench and opens the diagram palette. Shift+right-click does nothing, and Alt+right-click or Ctrl+right-click shows the browser's native context menu instead. A selection-context-menu handler can also open the group palette, but SysON's CSS makes the multi-selection rectangle click-through. The palette contents (quick-access tools, tool sections, tools) are fetched from the server for the targeted element ids. The tools' semantic target is the first element's target object (or the diagram's). A failed fetch shows the toast "An unexpected error has occurred, please refresh the page". Tutorials call it the "Contextual Toolbar". _(Sirius Web)_ · `useOnClickElement.ts`, `DiagramPalette.tsx`, `2025.2.0.adoc`
- **Left-click selects without the palette**: Left-clicking an element only selects it; the palette appears only on right-click (keyboard-shortcuts page). _(Sirius Web; experimental)_ · `keyboard-shortcuts.adoc`
- **Palette targets: background, node, label, edge, multi-selection**: Right-clicking the background, a node, a label or an edge opens the palette (testid `Palette`) at that position with quick tools and collapsible tool sections (`toolSection-{name}`, e.g. Structure, Behavior, Requirements, Create, Edit, Show/Hide, Related Elements) holding tools (`tool-{name}`), plus a close button (`Close-palette`). On a multi-selection it is a group palette, rendered by the same component with the same `Palette` testid: no `GroupPalette` testid exists in the v2026.11.0 frontend, and that name survives only in an unused helper of SysON's Cypress page objects. Its tools depend on the selection (one element, several, or the diagram) and on the domain and representation description. _(Sirius Web)_ · `palette.spec.ts`, `nodeCreationTests.cy.ts`, `diagram.adoc`
- **Diagram background palette**: The background palette holds the diagram-level tools; Fade and Hide are not offered on the background. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Element palette on nodes**: The node palette shows the tools of the current selection, with creation tools in a stable order. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Edge palette and edge selection feedback**: Selected edges get visual feedback, edges stay visible when nodes are selected, and an edge has its own palette with its tools; single-click tools can target edges. _(Sirius Web)_ · `CHANGELOG.adoc`
- **Selection kept in sync with the palette**: Opening or closing the palette updates the diagram selection and the workbench selection. _(Sirius Web)_ · `CHANGELOG.adoc`

### Palette contents and layout
- **Palette data structure**: `palette(diagramElementIds)` returns the palette for one or more selected elements or for the background: quick-access tools shown as top-level icons, then entries that are tool sections (label, icon, tools) or dividers. Every entry has an id, a label and icon URLs. Single-click tools also declare target descriptions, an optional dialog description (input dialog), whether to show an impact analysis, whether to ask for deletion confirmation, and key bindings (key plus ctrl/meta/alt flags). On the server, requested ids that match no node, edge or the diagram itself are silently skipped. The field is non-null (`Palette!`), so when no palette provider handles the request the query fails and the client shows the generic 'An unexpected error has occurred, please refresh the page' toast. _(Sirius Web)_ · `palette.graphqls`, `GetPaletteEventHandler.java`, `DiagramDescriptionPaletteDataFetcher.java`
- **Palette kinds in the View DSL: diagram, node, edge, group**: Each palette kind has fixed slots. DiagramPalette: dropTool (drop from the explorer onto the background), dropNodeTool, nodeTools, quickAccessTools, toolSections. NodePalette: deleteTool, labelEditTool (with initialDirectEditLabelExpression), dropNodeTool, nodeTools, quickAccessTools, toolSections. EdgePalette: deleteTool, centerLabelEditTool, beginLabelEditTool, endLabelEditTool, nodeTools, quickAccessTools, edgeReconnectionTools (SourceEdgeEndReconnectionTool, TargetEdgeEndReconnectionTool), toolSections. GroupPalette: nodeTools, quickAccessTools, toolSections. Tool sections are NodeToolSection or EdgeToolSection groups of node tools. _(Sirius Web, studio)_ · `diagram.ecore`, `diagram-description.adoc`
- **Quick-access tool bar**: Below the header sits a horizontal row of icon-only quick-access tools that run directly without opening a section. Each icon is at least 24x24, with small gaps; the row scrolls horizontally and never wraps, and a divider follows it. Each icon shows the tool label as a tooltip, and clicking it runs the tool. Frontend-contributed quick tools for the representation kind are appended. The bar is hidden when it has no tools. The backend supplies the tools as the palette's quickAccessTools; SysON puts tools such as Delete, Edit and 'New Attribute' there (the flashlight tutorial uses 'New Attribute' on a part to add 'fov:Real' and 'illuminationLevel:Real'). Quick-access icons carry the testid '<label> - Tool' (e.g. 'Pin - Tool', 'Delete from model - Tool'), whereas section tools use 'tool-<label>'. SysON's 2025.1 release notes present them as shortcuts for actions such as delete and edit. The tooltip is only the icon image's native title attribute, not a styled tooltip. A quick tool whose icon list is empty still renders as a blank 24px clickable cell. Quick-access tools are never part of the palette search results, and they are never shown as the last used tool. _(Sirius Web)_ · `PaletteQuickAccessToolBar.tsx`, `Tool.tsx`, `flashlight.adoc`
- **Default quick tools and Edit section**: For nodes and edges the default tools are split in two. The quick-access row holds Edit (if the label is editable), Pin/Unpin (nodes), the conditional reset tools (reset outside label position, reset label resize, reset bending points, and reset handles position, shown only when handles were moved), Adjust size (nodes), Fade/Unfade, Hide, and Delete from model (if deletable, including deletable and editable edges). A default 'Edit' section holds Edit, Collapse/Expand (collapsible nodes) and Delete from model. Only this section's copy of Delete from model carries a key binding, the bare 'Delete' key with no modifier; the quick-access copy has none. The section label 'Edit' is hard-coded in English, not translated. The tooltips/labels shown are 'Edit', 'Pin' / 'Unpin', 'Reset outside labels positions', 'Reset labels sizes', 'Reset bending points', 'Reset handles positions', 'Adjust size', 'Fade' / 'Unfade', 'Hide', 'Delete from model', 'Collapse' / 'Expand'. _(Sirius Web)_ · `PaletteDefaultToolsProvider.java`, `sirius-components-view-emf.properties`, `CHANGELOG.adoc`
- **Quick tools ordering and section merging**: Quick tools contributed by backend tool providers (Sirius Web's default tools, SysON's extensions) come before the quick tools declared in the view model, in node, edge and group palettes alike; a 2026.9 fix stopped group-provider quick tools from being shown after the view model's. Node and edge palettes order tools and sections the same way. Tool sections with the same id from several providers are merged into one: the merged section keeps the first section's label and icon, and its tools follow in provider order (this is how SysON's expression and Rotate tools land in the default 'Edit' section, id 'edit-section'). _(Sirius Web)_ · `ViewGroupPaletteProvider.java`, `DiagramPaletteCustomizerToolSectionMerger.java`, `CHANGELOG.adoc` v2026.9.0
- **Tool sections with drill-down navigation**: Tool sections (defined in the palette of diagram, node and edge descriptions) appear as list entries with an ellipsized label (full label in a right tooltip) and a '>' chevron. Clicking one slides that section's tools in from the side. A bold, autofocused header row ('<' plus the section title) goes back with a slide-right animation. A history stack makes nested sections return to the previous level. Tool names can span several lines, and an unfolded section always stays visible above the rest of the palette. Section entries never show an icon: the entry renders only the label and the chevron, although the API carries an iconURL (View-based sections send an empty list). _(Sirius Web)_ · `PaletteToolSection.tsx`, `ToolSectionEntry.tsx`, `ToolSectionHeader.tsx`
- **Empty tool sections hidden**: Tool sections with no available tool (all filtered out by preconditions) are not displayed, so a section can disappear after the element changes (e.g. after renaming it to 'Empty'). _(Sirius Web)_ · `palette.spec.ts`, `CHANGELOG.adoc`
- **Palette dividers**: Backend palette descriptions can insert divider entries (PaletteDivider) between tools or sections; they render as horizontal separator lines. _(Sirius Web)_ · `Palette.tsx`, `PaletteToolSection.tsx`
- **Tool list item**: Each tool row shows a 16x16 icon (several icon URLs can be layered as an overlay), an ellipsized label, a right-side tooltip with the full label, and the tool's first key binding right-aligned in disabled-gray text (testid 'key-binding-<label>'). The binding reads 'Ctrl+' if Ctrl is set, then a Command-key icon if Meta is set, then 'Alt+', then the key, e.g. 'Ctrl+s' or 'Ctrl+e'. Clicking the row closes the palette, records the tool as last used, then runs it. Tools still run when their tooltip is visible. Backend-contributed tools declared with an empty icon list (e.g. SysON's Rotate before its frontend override) show no icon. _(Sirius Web)_ · `ToolListItem.tsx`, `Palette.tsx`, `NodeToolConverter.java`
- **Last used tool pinned at the top**: Each palette remembers the last tool invoked from it, keyed by palette id (per kind of diagram element) and held in a React context for the browser session. It shows that tool as the first entry, above a divider, so the same creation (e.g. 'New Package') can be repeated in one click. This pinned row sits outside the sliding list, so it stays visible while the user drills into a tool section or an extension section. The lookup searches only the palette's top-level entries, its tool sections and the frontend-contributed tools. If the remembered tool is not in the current palette, nothing is pinned; an older changelog entry described it as shown disabled instead. A quick-access tool is recorded but never shown as last used. Overridden tools must call `onInvoked()` to register (fixed for tree palette overrides), and the feature applies to diagram and tree palettes. Reuse became more reliable in 2026.7. - **Extension sections: Appearance, Layout, Show in**: After the backend tools, the palette root lists built-in entries: 'Appearance' (at least one element selected), 'Layout' (more than one element selected) and 'Show in' (at least one element selected). - **'Show in' section**: Diagram and Explorer palettes have a 'Show in' section listing targets as 'Show in {target}', or 'No available targets' when there are none. - **Tool preconditions respected**: Tools whose precondition expression is false for the element are not shown in its palette. Preconditions are evaluated on the server each time the palette is computed, for every tool in quick-access, section-less and sectioned slots. A tool is shown only if its expression yields true; an evaluation error or a non-boolean result hides it, while warnings are tolerated. A blank precondition always passes. _(Sirius Web)_ · `NodePaletteProvider.java`, `CHANGELOG.adoc`
- **Variables available to palette tool preconditions**: For a node, edge or background palette the expressions get self (the semantic element), editingContext, environment, diagramContext, diagramServices, selectedNode or selectedEdge (the clicked diagram element, null for the other kind) and convertedNodes. For a group palette self is the list of the selected elements' semantic targets, alongside selectedNodes and selectedEdges. - **Palette assembly order (backend)**: A node or edge palette is assembled as: quick-access tools from the backend tool providers, then the description's quick-access tools; entries are the description's section-less tools, its tool sections, a divider, then the providers' extra tool sections (after the section customizers, which merge same-id sections). ### Palette search
- **Palette search field ('Search Tool')**: An autofocused text field with a search icon and the placeholder 'Search Tool' filters tools across all sections as the user types, which helps when a representation defines many element types (e.g. to find 'New Required Constraint'). - **Fuzzy matching with smart case and highlighting**: A tool matches when the typed characters appear in its label in order, as a subsequence: 'pdf' matches 'Part Def', and 'att def' or 'NAD' find 'New Attribute Definition'. Matching is case-sensitive only when the search term starts with an uppercase letter. The matched characters are highlighted individually in the navigation background color. Contributed and overridden tools are included without dropping matching entries (2026.7/2026.9 fixes). - **Flat search results with keyboard navigation**: While the search has text, the sectioned list is replaced by one flat list of every matching tool, top-level or inside a section; dividers and section entries are not shown. - **Single-click tool execution and dispatch**: The tools with ids edit, reset-outside-label-position, reset-label-resize, reset-bending-points, reset-handles-position and adjust-size run client-side. - **Palette tools run from keyboard shortcuts**: A key press on the diagram (not in a text field, not a lone modifier) fetches the palette of the current selection, or of the diagram when nothing is selected. ### Appearance backend
- **Appearance edit and reset services**: GraphQL mutations edit appearance on lists of elements, recording each changed property as customized per element. editRectangularNodeAppearance(nodeIds, appearance) sets background, border color, radius, size and style. editImageNodeAppearance sets image-node border properties, and editEllipseNodeAppearance sets ellipse background and border. editLabelAppearance(diagramElementIds, labelIds, appearance) sets font size, italic, bold, underline, strike-through, border color/radius/size/style, text color, background and visibility. editEdgeAppearance(edgeIds, appearance) sets SIZE, COLOR, LINESTYLE, SOURCE_ARROW, TARGET_ARROW and EDGE_TYPE. Matching resetNodeAppearance(nodeIds, propertiesToReset), resetLabelAppearance(diagramElementIds, labelIds, propertiesToReset) and resetEdgeAppearance(edgeIds, propertiesToReset) drop the chosen customizations so they return to the description's style. Results are shown as toasts, and customized appearances are stored with the diagram and survive project export/import. _(Sirius Web)_ · `appearance.graphqls`, `EditRectangularNodeAppearanceEventHandler.java`, `useEditEdgeAppearance.tsx`
- **Appearance mutation validation and errors**: The node, image-node, edge and reset mutations check every id first. If any is missing, nothing is applied and the ErrorPayload reads 'Node "<id1 - id2>" not found', even for edge ids. Label edits and resets are all-or-nothing: each element must resolve exactly one of the requested label ids (inside, outside, begin, center or end label). If the matched count differs from the number of label ids, nothing is applied and the error reads 'Diagram element "<ids>" not found', which lists only unknown element ids and so can be 'Diagram element "" not found'. A wrong input type gives 'Invalid input type, "<received>" has been received while "<expected>" was expected'. Values are not validated: any color string or number is stored as given. Errors reach the user as toasts through the palette's reporting hooks. _(Sirius Web)_ · `EditLabelAppearanceEventHandler.java`, `EditEdgeAppearanceEventHandler.java`, `sirius-components-collaborative-diagrams.properties`
- **Appearance resolution order**: At each render a node's style is computed in three steps. The description's style provider runs first (conditional styles included). Every registered node style customizer then runs in turn, which is where SysON's family theme applies. Last, the first appearance handler that accepts the resulting style type applies this refresh's appearance edits and re-applies the properties customized earlier. Edges go through the same steps without the customizer stage, so no theme or customizer can restyle edges. A style type with no appearance handler keeps the computed style and records no customization. _(Sirius Web)_ · `DiagramAppearanceHandler.java`, `INodeStyleCustomizer.java`
- **Undo and redo of appearance edits**: Each appearance edit or reset made from the palette records an undo step on the diagram input that caused it. Undo restores each touched property's previous value if it was customized, or resets it if it was not; undoing a reset re-applies every property that was customized before. Redo replays the original changes. Recorders exist for rectangular, image and ellipse node styles, for node and edge labels, and for edges. SysON registers none for its package, imported-package, note and view-frame styles, so edits made in their Style part record no undo step (their Inside Label edits do). _(Sirius Web)_ · `NodeAppearanceChangeRecorder.java`, `RectangularNodeUndoAppearanceChangeRecorder.java`, `EdgeAppearanceChangeUndoRecorder.java`
- **Customized style properties tracking**: Every node, edge and label carries customizedStyleProperties (names of properties the user overrode) with its raw server style; these feed the appearance editors so customized properties can be shown and reset. _(Sirius Web)_ · `RectangleNodeConverter.ts`, `convertDiagram.ts`, `convertLabel.ts`
- **SysON custom node appearance mutations**: editSysMLPackageNodeAppearance, editSysMLImportedPackageNodeAppearance and editSysMLNoteNodeAppearance take {id, editingContextId, representationId, nodeIds[], appearance {background?, borderColor?, borderSize?, borderStyle?}}. editSysMLViewFrameNodeAppearance also accepts borderRadius. Only the given fields are applied, to all listed nodes at once, as one DIAGRAM_APPEARANCE_CHANGE that refreshes the diagram. If any node id is not found, nothing is applied and an ErrorPayload lists the missing ids joined by ' - ' (message 'Node "<id1 - id2>" not found'); a wrong input type gives 'Invalid input type, "<received>" has been received while "<expected>" was expected'. · `sysmlcustomnodes.graphqls`, `EditSysMLPackageNodeAppearanceEventHandler.java`, `EditSysMLViewFrameNodeAppearanceEventHandler.java`
- **Per-property customization persistence for custom nodes**: For Package, Imported Package, Note and View Frame nodes, each changed property is recorded as customized: BACKGROUND, BORDER_COLOR, BORDER_SIZE and BORDER_STYLE, plus BORDER_RADIUS for view frames. A customized value is reapplied on later re-renders even if the description's style changes. Resetting one property removes only its flag, and that property returns to the default while other edits stay; each custom-node style keeps its own background color. At v2026.11.0, the view-frame handler drops the BORDER_STYLE flag when border radius is not customized, so a customized line style reverts on a later refresh unless the radius is customized too. · `SysMLViewFrameNodeAppearanceHandler.java`, `SysMLPackageNodeAppearanceHandler.java`, `EditSysMLPackageNodeAppearanceControllerTests.java`
- **Custom node appearance kept on diagram import**: When a project is imported and its diagrams are recreated by Sirius Web's diagram importer, each customized property of a Package, Imported Package, Note or View Frame node is converted back into the matching appearance change. That covers background, border color, border size, border style and, for view frames, border radius. · `DiagramImporterSysMLPackageNodeStyleAppearanceChangeHandler.java`, `DiagramImporterSysMLViewFrameNodeStyleAppearanceChangeHandler.java`
- **Config property org.eclipse.syson.customImages.pattern**: Set to 'classpath*:/sysonCustomImages/**' in application.properties and application-dev.properties under the heading 'SYSON CUSTOM IMAGES FOR IMAGES NODES', meant to load custom images for image nodes; no Java code in either clone reads it at v2026.11.0. · `application.properties`, `application-dev.properties`

- **SVG (Experimental) native export**: rebuilds a true vector SVG instead of an HTML-in-SVG snapshot: renders the snapshot in a hidden container, walks elements tagged data-svg (rect, text, image, svg, defs) in nodes, edges and edge labels and converts each to native SVG, copies edge <g> paths with the viewport transform, and downloads the result as a Blob URL; its bounds use all nodes, hidden ones included.
