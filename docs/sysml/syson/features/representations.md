## Requirements & tables

### Requirements table: creation and content

- **Create a Requirements Table View**: right-click a Package (or any other element whose type is a SysML Namespace) in the Explorer, choose New Representation, pick "Requirements Table View" (the user manual calls it "Requirement Table View") and give it a name. The default title is "view" followed by the number of existing ViewUsages plus one (e.g. view1). The table is backed by a ViewUsage and starts empty. When the command is run on an element that is not a ViewUsage, SysON's input pre-processor first creates a new ViewUsage named after the representation name, inside the membership kind computed for that container, and attaches the table to it. Unlike the four standard diagrams, this ViewUsage is not typed by any ViewDefinition. Run on an existing ViewUsage, the table attaches to that ViewUsage directly. The project is saved right after creation. Released in v2025.10.0. · `RTVTableDescriptionProvider.java`, `CreateRepresentationInputProcessor.java`, `CHANGELOG.adoc` v2025.10.0
- **One requirements table per ViewUsage**: a ViewUsage that already holds a requirements table (or a General View diagram) no longer offers New representation in the Explorer. Requirements tables also get no "Duplicate representation" entry, unlike most other representations. · `SysONExplorerTreeItemContextMenuEntryProvider.java`
- **Table content is the ViewUsage's exposed elements**: the table keeps its content in the model. It shows only the RequirementUsages that its ViewUsage exposes through MembershipExpose relationships. Adding a requirement to the table creates a MembershipExpose, and removing one from the table deletes it. · `RTVQueryServices.java`, `RTVMutationServices.java`
- **Requirements table rows**: one row per exposed RequirementUsage. The row header shows the RequirementUsage icon and has no label. Row height is automatic (initial height -1), and rows cannot be resized. Exposed requirements are ordered depth-first, so children follow their parent. No index label expression is set on rows or columns, so no row numbers or column letters are shown, and the cells set no tooltip expression, so they have no hover tooltip. · `RTVTableDescriptionProvider.java`, `RTVQueryServices.java`, `table.ecore`
- **Requirements table registration**: the table is contributed as a SysON view description whose view id is "RequirementsTableView" and whose representation description is named "Requirements Table View". Its row candidates are computed by one AQL chain: getExposedRequirements(expandedIds, expandAll), then sortAndFilterRequirements(columnSort, columnFilters, globalFilterData), then toPaginatedData(cursor, direction, size). · `RTVDescriptionProvider.java`, `RTVTableDescriptionProvider.java`
- **Hierarchical requirements (sub-rows)**: sub-rows are enabled, so nested RequirementUsages are shown hierarchically under their parent row. The depth level is 0 for a root requirement (one not owned by a RequirementUsage) and +1 per nesting level, and drives the indentation. A requirement shows an expander only when it owns RequirementUsages (hasChildren). Nested rows appear only when all their parent requirements are expanded, or when expand-all is on. Released in v2026.9.0. · `RTVQueryServices.java`, `RTVTableDescriptionProvider.java`, `2026.9.0.adoc`

### Requirements table: columns and cell editing

- **Requirements table columns**: three columns, "DeclaredName" (initial width 250), "ReqId" (150) and "Documentation" (400). All three are resizable, sortable and filterable. The columns set no filter widget expression, so their filter variant is empty and the frontend's default filter input is used. · `RTVTableDescriptionProvider.java`, `ColumnDescriptionConverter.java`, `2025.10.0.adoc`
- **Edit name and ReqId in cells**: DeclaredName and ReqId cells are always rendered as borderless single-line text fields, so clicking one places the caret in it (there is no separate display mode). Pressing Enter or leaving the field commits the text through a SetValue operation on the requirement's declaredName or reqId. Leaving the field sends the value even when it is unchanged. · `RTVTableDescriptionProvider.java`, `TextfieldCell.tsx`, `requirement-management.adoc`
- **Edit documentation in cell**: the Documentation cell is a text area showing the body of the requirement's first Documentation (empty if there is none). Editing updates that body or, if the requirement has no Documentation, creates one inside a new OwningMembership of the requirement. Enter inserts a new line, so the edit is committed only when the field loses focus. Only the first Documentation is shown or edited; any further Documentation elements are left untouched. · `RTVTableDescriptionProvider.java`, `RTVMutationServices.java`, `TextareaCell.tsx`
- **ReqId mirrors the declared short name**: a requirement's reqId and its declared short name are the same value. Setting reqId sets the short name, and setting the short name changes reqId. This holds for RequirementUsage and RequirementDefinition, and it is the value shown in the table's ReqId column, in the details view and in `<short> name` labels and direct edit. The synchronization arrived in v2026.3.0. The ReqId property of RequirementUsage moved from the Advanced tab to the Core tab of the Details view in v2025.10.0, and RequirementDefinition's ReqId appears in the Core tab since v2026.3.0. · `RequirementUsageImplTest.java`, `2026.3.0.adoc`, `2025.10.0.adoc`

### Requirements table: toolbar tools

- **Create requirement**: an entry in the table's Tools menu, labelled "Create requirement" with the createRequirement.svg icon. The user manual calls it the "New Requirement" button. It creates a RequirementUsage in the namespace that owns the table's ViewUsage, wrapped in the membership kind computed for it. The new requirement gets the default name "requirement<N>" (N = number of RequirementUsages in that namespace) and isComposite true. A new MembershipExpose shows it as a row right away. If no ViewUsage is found it fails with "Unable to create a RequirementUsage". It is defined by the backend as a tool menu entry with id `add-requirement-table-tool-entry`; the toolMenuEntries query on the table returns exactly this entry and `import-existing-requirements-table-tool-entry`. In the integration test, creating one in a namespace that already holds two requirements yields a row named "requirement3". · `RTVTableToolMenuEntriesProvider.java`, `RTVTableCreateRequirementToolExecutor.java`, `RTVMutationServices.java`
- **Import all existing requirements**: an entry in the table's Tools menu, labelled "Import all existing requirements" with the importRequirements.svg icon. It exposes in the table every RequirementUsage owned by the ViewUsage's owning namespace and, recursively, their nested RequirementUsages at any depth, which appear as sub-rows. It adds one MembershipExpose each, pointing at the requirement's owning membership, and skips requirements already shown. Only requirements owned directly by that namespace (and their nested requirements) are imported; requirements inside sub-packages or other elements are not. The two Tools entries appear in the order the provider declares them, not sorted. Failure shows "Unable to import existing requirements". Its tool menu entry id is `import-existing-requirements-table-tool-entry`. The user manual presents it as the way to populate a new, empty table. The user manual still says sub-requirements are not imported, but the v2026.11.0 code imports them. · `RTVTableImportExistingRequirementsToolExecutor.java`, `RTVTableToolMenuEntriesProvider.java`, `requirement-management.adoc`

### Requirements table: row actions

- **Delete from table**: an entry in the row's "..." actions menu, with the graphicalDelete.svg icon. It deletes the MembershipExpose relationships that show the requirement, which removes it from the table but keeps it in the model. Only that requirement's own exposes are deleted, so nested requirements stay exposed. It runs at once, with no confirmation. The row menu lists its three entries sorted by label: "Delete from model", "Delete from table", "New Nested Requirement". · `RTVTableDescriptionProvider.java`, `RTVMutationServices.java`, `RequirementsTableControllerIntegrationTests.java`
- **Delete from model**: an entry in the row's "..." actions menu, with the semanticDelete.svg icon. It deletes the requirement from the model (DeleteService.deleteFromModel), so the row also disappears from the table. No confirmation dialog is shown. · `RTVTableDescriptionProvider.java`, `RowContextMenuContent.tsx`, `requirement-management.adoc`
- **New Nested Requirement**: an entry in the row's "..." actions menu, with the createRequirement.svg icon. It creates a RequirementUsage owned by the row's requirement, with the default name "requirement<N>", and exposes it through a MembershipExpose. The new requirement then appears as a sub-row of its parent. The parent row is not expanded for you, so the new sub-row shows once the parent is expanded (or expand-all is on). Released in v2026.9.0. · `RTVTableDescriptionProvider.java`, `RTVMutationServices.java`, `2026.9.0.adoc`

### Requirements table: sorting, filtering, pagination and display

- **Requirements column sort**: sorting on DeclaredName, ReqId or Documentation (first documentation body) orders rows case-insensitively, ascending or descending, on the server. With several sorts active, each is applied in turn, in the order received, as a stable sort, so the last one applied is the primary key. Global and column filters run before sorting, and pagination comes last. Sorting reorders the flat list of visible rows, so after a sort nested requirements no longer necessarily follow their parent. The DeclaredName and ReqId comparators do not handle unset values, so a sort can fail when some row has no name or no ReqId. · `RTVQueryServices.java`
- **Requirements column filters**: per-column filters keep only rows whose DeclaredName, ReqId or first-documentation body contains the filter text. Matching is a case-sensitive substring test, and the filter value is JSON-decoded first. A row whose value is unset is excluded while that filter is active. If the filter value cannot be JSON-decoded, the row is kept and a warning is logged. Filtering runs on the server, after the expansion step, so only rows visible under the current expansion can match. A matching sub-row whose parent is filtered out is still shown, indented, without its parent. The filter ids are the column target objects ("DeclaredName", "ReqId", "Documentation"). · `RTVQueryServices.java`, `TableComponent.java`
- **Requirements global filter**: the toolbar search keeps rows whose declaredName, reqId or documentation body contains the typed text. Matching is case-sensitive and runs on the server. Blank or whitespace-only text is ignored. The global filter is applied before the column filters. · `RTVQueryServices.java`
- **Requirements table pagination**: rows are paginated with cursors after filtering and sorting, with page size options 10, 20 and 50. No default page size index is set, so the table opens with 10 rows per page. It uses the generic toPaginatedData service: the total row count is the number of filtered rows, and Next/Previous take the page after or before the cursor row. If the cursor row is no longer in the list (e.g. it was deleted), the page comes back empty. · `RTVTableDescriptionProvider.java`, `CursorBasedNavigationServices.java`, `2026.9.0.adoc`
- **Requirements table striped rows**: rows are shown with alternating background stripes (useStripedRowsExpression true). · `RTVTableDescriptionProvider.java`

### Requirements on diagrams: nodes

- **Requirement nodes on the General View**: requirements are created from the diagram background palette (click the background to show it) or inside another element such as a requirement. A Requirement Definition is drawn as a rectangle and a Requirement Usage as a rectangle with rounded corners. A tool to create Requirements inside a RequirementDefinition was added in v2024.7.0, and creating a RequirementUsage from a Package node reveals it since v2026.3.0. The user manual still says only Requirement Definitions and Usages can be created and that Satisfy relationships are not yet available, which is outdated. · `requirement-management.adoc`, `2024.7.0.adoc`, `2026.3.0.adoc`
- **Concern Definition and Concern Usage nodes**: the General View supports ConcernDefinition and ConcernUsage nodes. Their creation tools are in the Requirements section of the palette, and both can be dragged from the Explorer onto the diagram background. Stakeholders of concerns and requirements (definitions and usages) are displayed. Added in v2025.2.0. · `2025.2.0.adoc`
- **Satisfy Requirement Usage nodes**: the General View supports SatisfyRequirementUsage nodes, created from the Requirements section of the palette or dragged from the Explorer onto the background (v2025.4.0). Since v2026.1.0, Interconnection View diagrams can create and show SatisfyRequirementUsage nodes in the interconnection compartment. · `2025.4.0.adoc`, `2026.1.0.adoc`
- **Requirements and concerns compartments on parts**: PartUsage and PartDefinition nodes have "requirements" and "concerns" compartments. The New Requirement and New Concern tools on those nodes create elements in them. Added in v2026.9.0. · `2026.9.0.adoc`
- **Actors and subjects on requirement nodes**: RequirementUsage and RequirementDefinition nodes have an "actors" compartment. The release notes add it to UseCase and Requirement nodes in v2024.9.0, and again to RequirementUsage and RequirementDefinition nodes in v2026.3.0. Since v2026.3.0, subjects of cases, use cases and requirements are also shown as graphical nodes, in addition to the subject compartment. · `2024.9.0.adoc`, `2026.3.0.adoc`
- **Inherited elements in requirement compartments**: the frames, assume constraints, require constraints and stakeholders compartments of requirement nodes, and the satisfy requirements compartment of part nodes, also list the elements inherited from supertypes. Require-constraint inheritance also applies to subtypes of requirements. Added in v2026.9.0. · `2026.9.0.adoc`
- **Compartment item labels for concerns and constraints**: items in the frames, require constraints and assume constraints compartments are labelled as follows:
  - An element with a name and an owned reference subsetting uses subsetting notation (`ElementName ::> SubsettingName`).
  - An element with no name but an owned reference subsetting shows only the subsetted element's name.
  - An element with no reference subsetting shows its name.

  Before v2026.7.0 the label was always the element's name. · `2026.7.0.adoc`

### Requirements on diagrams: drag and drop

- **Framed concern and requirement constraint edge targets**: a framed concern or requirement constraint membership has an edge target when its owned concern or constraint references a different concern or constraint; the edge goes to the referenced one. · `MetamodelQueryElementService.java`
- **Satisfy edge label**: a SatisfyRequirementUsage edge is labelled «satisfy». · `DiagramQueryLabelService.java`

### Generic table: editor and layout

- **Table representation**: a tabular view of the model, with elements as rows and their properties as columns. The table description predefines which rows, columns and actions appear (tables are configured, not free spreadsheets). Every inline change is synchronized at once with other representations and with collaborators. The Sirius Web user manual and studio-maker guide flag tables as experimental ("Before you Start" status box), while the key-features table lists them as available. _(Sirius Web; experimental)_ · `table.adoc`, `key-features.adoc`
- **Table column value types**: columns can display text, numbers, booleans, enumerations, or values computed with AQL expressions. _(Sirius Web)_ · `table.adoc`
- **Table representation editor**: tables open in an editor tab in the main area, built on Material React Table with a sticky header and horizontal scrolling. A loading indicator shows until the table and its saved configuration arrive. When the subscription ends, the message "The table does not exist anymore" replaces the table. The table stays mounted, keeping state such as page size, when its representation id changes and after the dispose timeout. In tests, the table has testid `table-representation` and each row header has `table-row-header`. _(Sirius Web)_ · `TableRepresentation.tsx`, `TableContent.tsx`, `table.spec.ts`
- **Table toolbar layout**:
  - The top toolbar has the "Tools" button on the left.
  - On the right are the global "Search" field (with a clear x button) and the built-in actions: Reset Row Heights, Row filters (only when defined), Show/Hide filters, Show/Hide columns and Toggle full screen.
  - The bottom toolbar shows only when pagination is enabled, and holds "Rows per page" and the previous/next arrows.
  - Column headers show a letter index (A, B, C), an optional icon and the label, with a drag handle and a kebab menu.
  - The row header shows the expand chevron, row index, icon, label and a resize bar.
  - An "Actions" column holds the "..." row menu.
  - The "Toggle density" label exists, but no density button is rendered.
  - The user manual's screenshot and text still show a "SETTINGS" button, which is now "Tools".

  _(Sirius Web)_ · `TableContent.tsx`, `table-description.adoc`, `table.adoc`
- **Table representation icon**: every table representation, the requirements table included, is shown with the generic table icon (`/table-images/table.svg`) wherever representations are listed, e.g. in the Explorer. _(Sirius Web)_ · `TableImageProvider.java`, `TableImagePathService.java`
- **Table feature switches**: the table component takes one flag per feature: column visibility, column resizing, column filters, row sizing, global filter, pagination, column ordering, selection synchronization, sorting and sub-rows. The table representation turns them all on (sub-rows following the description), while embedded uses such as the form table widget turn most of them off. Added in v2025.1.0 to deactivate features not used in some contexts. _(Sirius Web)_ · `TableContent.types.ts`, `TableRepresentation.tsx`, `CHANGELOG.adoc` v2025.1.0

### Generic table: top toolbar

- **Tools menu**: a "Tools" button with a tools icon on the left of the top toolbar opens a menu, with a spinner while entries load. The menu always starts with "Export page data as CSV" (download icon), followed by the table's backend-defined tool menu entries (icon or blank spacer, then label) and any frontend-contributed entries. Entries are disabled only while their mutation runs, not in read-only mode, and the menu stays open after an entry is clicked. Clicking an entry no longer triggers redundant menu-entry queries. Backend entries from all providers are concatenated in provider order, not sorted. Invoking an entry that no executor handles fails with "No existing action for this menu entry". A successful entry returns its own change kind, so a semantic change refreshes the table. In SysON the backend entries are "Create requirement" and "Import all existing requirements". Renamed from "Settings" in v2025.12.0, and backend-provided and contributable since v2026.3.0. Frontend entries are contributed through the toolsButtonMenuEntryExtensionPoint, which was named settingButtonMenuEntryExtensionPoint until v2025.12.0. _(Sirius Web)_ · `ToolsButton.tsx`, `ToolsMenuEntries.tsx`, `CHANGELOG.adoc` v2025.12.0
- **Export page data as CSV**: Tools > "Export page data as CSV" downloads the currently loaded rows only (the current page).
  - It uses the visible columns only, in their display order, with column labels as headers.
  - The separator is ";" and the decimal separator ".".
  - A first `_row_header_` column holds "<index label> <row label>".
  - Text and textarea cells export their text, icon-label cells their label, select cells the chosen option's label, and multi-select cells their option labels joined with " ,".
  - Custom cells such as checkbox cells export as empty strings.
  - In SysON's requirements table, rows have neither an index label nor a header label, so the `_row_header_` column holds only a space.
  - Column headers are the column labels, so two columns with the same label would collide.

### Generic table: state, persistence and protocol

- **Persisted table configuration**: the table's metadata stores its configuration: global filter text, column filters, column sort (column id plus descending flag) and default page size. On opening, a getTableConfiguration query restores them before subscribing, so the table reopens as it was left. A table also exposes its page-size options, row striping, sub-rows (rows with depth and hasChildren) and pagination info (hasPrevious, hasNext, total row count). _(Sirius Web)_ · `useTableConfiguration.ts`, `table.graphqls`
- **Shared vs per-viewer table state**: some state is saved on the table through mutations and shared with every viewer: global search, column filters, column sort, column widths, column order, column visibility and row heights. Other state lives only in the viewer's client and resets when the table is reopened: expanded rows, expand-all, active row filters, the pagination cursor and the chosen page size. _(Sirius Web)_ · `TableRepresentation.tsx`, `useTableConfiguration.ts`, `TableContent.tsx`
- **Table view state encoded in the representation id**: the table subscription id encodes the full view query as URL parameters: cursor, direction (PREV/NEXT), size, globalFilter, columnFilters (id:JSON value), activeRowFilterIds, expandedIds, columnSort (id:desc) and an expandAll flag. The server therefore computes only the requested page of filtered, sorted and expanded rows. _(Sirius Web)_ · `tableIdProvider.ts`
- **Table refresh policy and layout replay**: by default a table is re-rendered only on semantic changes and on table layout changes (column resize, reorder or visibility, row resize, row-height reset). Global filter, column filter and column sort changes do not re-render it; they only push their lightweight events. Layout changes are kept as table events and replayed at each render, so a saved width, order, hidden flag or height overrides the description's initial value. Reset Row Heights puts every row back to its initial height. A table is also re-rendered as soon as it is opened, since the model may have changed since it was saved. A description can register its own refresh policy. Each distinct view query (page, filters, sort, expansion) is served by its own server-side processor, and a missing page size defaults to 10. _(Sirius Web)_ · `TableEventProcessor.java`, `TableEventProcessorFactory.java`, `LineComponent.java`
- **Stable row, column and cell ids**: row ids are derived from the table id, the row description and the row element's id, column ids from the column description and the column's target object, and cell ids from the row and column ids. Rows and columns therefore keep their saved heights, widths, order and visibility across refreshes and pages, as long as their elements stay the same. _(Sirius Web)_ · `LineComponent.java`, `ColumnComponent.java`
- **Filter and sort ids mapped to column targets**: before the row expression runs, the column ids carried by columnFilters and columnSort are translated into each column's target object id (e.g. SysON's "DeclaredName"), and entries for unknown columns are dropped. The table itself keeps the original ids. _(Sirius Web)_ · `TableComponent.java`
- **Cursor pagination AQL services**: tables built with the View DSL, and form table widgets, get two pagination services. toPaginatedData(list, cursor, direction, size) slices an already computed list around the cursor element and reports hasPrevious, hasNext and the total row count; toPaginatedData(list) returns everything as one page. collect(self, cursor, direction, size[, predicate]) walks the containment tree forward or backward from the cursor and reports no total count (-1). SysON's requirements table uses toPaginatedData. _(Sirius Web, studio)_ · `CursorBasedNavigationServices.java`, `TableJavaServiceProvider.java`
- **Table backend extension APIs**: applications plug into tables through backend interfaces:
  - IToolMenuEntriesProvider and IToolMenuEntryExecutor for the Tools menu (SysON's two entries use them).
  - IRowContextMenuEntryProvider and IRowContextMenuEntryExecutor for row actions.
  - IRowFilterProvider for row filters.
  - IEditCellHandler for cell edits.
  - ICustomCellDescriptor for custom cell kinds, with frontend rendering through tableCellExtensionPoint.
  - ICustomCellConverter and ICustomViewEditCellExecutor for custom cells in the View DSL.

  _(Sirius Web)_ · `IToolMenuEntriesProvider.java`, `IRowContextMenuEntryProvider.java`, `ICustomCellDescriptor.java`
- **Table subscription with shared filter and sort**: tableEvent(editingContextId, representationId) streams the table. It also pushes global filter, column filter and column sort changes as separate events, so everyone viewing the same table sees the same filtering and sorting. _(Sirius Web)_ · `table.graphqls`
- **Table column and row model and mutations**: columns have a header label, icons and index label, a width, and resizable, hidden, sortable and filterVariant settings. Rows have a header label, icons and index label, a height, a resizable flag and a depth level. Mutations: resizeTableColumn(width), changeTableColumnVisibility(list of column and visible), reorderTableColumns(reorderedColumnIds), resizeTableRow(height) and resetTableRowsHeight. Filter and sort mutations: changeGlobalFilterValue(globalFilterValue), changeColumnFilter(columnFilters) and changeColumnSort(columnSort list). _(Sirius Web)_ · `table.graphqls`
- **Table cell kinds API**: the cell kinds and their edit mutations are text field (editTextfieldCell), text area (editTextareaCell), select with options (editSelectCell), multi-select (editMultiSelectCell), read-only icon+label, and checkbox (editCheckboxCell, a custom cell from the Sirius Web application). - **Table backend error messages**: table event handlers report "No handler found" when no handler matches a request, "No existing action for this menu entry" when a row context menu entry has no executor, and "Invalid input type, "{0}" has been received while "{1}" was expected" for a wrong input. A French bundle also exists. _(Sirius Web)_ · `sirius-components-collaborative-tables.properties`

## Tree representations

### Tree representation editor

- **Tree representation**: a hierarchical outline of model elements. Users expand or collapse branches, select elements to view or edit them elsewhere, create, edit or delete elements through contextual actions, and reorganize the hierarchy when the description allows it. The user manual suggests it for system breakdowns, component structures, functional trees or requirement hierarchies, used alongside diagrams and forms as a navigable entry point. Its page and the tree-description page are flagged experimental, though the key-features table lists Tree as available. _(Sirius Web, unclear in SysON; experimental)_ · `tree.adoc`, `tree-description.adoc`, `key-features.adoc`
- **Tree representation in the editor area**: description-based tree representations open in the main editor area. A loading indicator shows until the first tree arrives. They support expand/collapse and multi-selection synced with the workbench selection, and use the classic context menu (the palette is disabled). The representation is marked unavailable when its subscription completes, e.g. after it is deleted. Unlike the explorer, it has no toolbar, filter bar or text highlighting. Its expanded items and depth live only in the viewer's client, so the tree reopens collapsed. It is not a target for "Show in" or for selections made elsewhere: other views' selections only highlight its items. _(Sirius Web, studio)_ · `TreeRepresentation.tsx`, `DefaultExtensionRegistry.tsx`
- **Domain Tree representation (studio)**: a built-in "Domain Tree" representation can be created on a Domain of a studio project and opens as a tree in the editor area.
  - Its root is the Domain.
  - Expanding an element lists first the representations attached to it, sorted by label, then its contents.
  - Each Entity also gets a "superTypes" item that lists its super types.
  - Labels and icons come from the label service, with the entity name as fallback.
  - Items can be selected but not renamed or deleted, and entities always show an expand arrow.

  _(Sirius Web, studio)_ · `DomainTreeRepresentationDescriptionProvider.java`

### Tree items

- **Tree filters**: a tree description exposes filters (id, label, defaultState) that users toggle in the tree's filter menu to hide categories of items.
  - The SysON Explorer offers "Hide Memberships" (on by default), "Hide KerML Standard Libraries" (off), "Hide SysML Standard Libraries" (off), "Hide User Libraries" (off), "Hide Root Namespaces" (on), "Hide Expose Elements" (on) and "Hide Expression Internals" (on).
  - The studio explorer adds "Hide In-Memory Studio Color Palettes" (on by default).
  - In the tree view toolbar, the filters menu is a "Filters" button (filter-list icon, greyed while open) that drops down one checkbox per filter. It is shown only when the tree has filters. Since v2024.3.0, tree representations support filters (activeFilterIds).

  _(Sirius Web)_ · `tree.graphqls`, `TreeFiltersMenu.tsx`, `SysONTreeFilterProvider.java`
- **Tree item tooltip**: treeItemTooltip(treeItemId) returns a server-computed tooltip for any tree item, shown on hover. Since v2026.3.0, custom trees have no tooltip by default; view-based trees set one with a tree item tooltip expression, and the explorer keeps its default tooltip. The tooltip is requested only after the pointer has rested on the item for 500 ms (v2026.5.0). It appears at the item's top-left, only when non-empty, and stays hidden while the palette is open (fixed in v2026.9.0). _(Sirius Web)_ · `TreeItem.tsx`, `tree.graphqls`, `CHANGELOG.adoc` v2026.3.0
- **Tree context menu and palette entries**: contextMenu(treeItemId) and palette(treeItemId) return a tree item's actions, shown on right-click or in the tree palette. Single-click entries run on the server, optionally after an impact-analysis preview. Fetch entries return a URL that the client downloads (DOWNLOAD) or opens (OPEN). Every entry has a label, an icon and optional key bindings (Ctrl, Meta, Alt, key). _(Sirius Web)_ · `tree.graphqls`, `core.graphqls`
- **Styled tree labels**: tree item labels are styled strings. Each fragment can be bold, italic or struck out.
  - Underline styles: NONE, HIDDEN, DOTTED, DASHED, SOLID, DOUBLE, GROOVE, RIDGE, INSET, OUTSET.
  - Border styles: NONE, SOLID, DOTTED, DASHED, DOUBLE, GROOVE, RIGE (sic), INSET, OUTSET.
  - Colors: font, background, foreground, strikeout, underline and border.

  Items also carry icons and editable, deletable, selectable, expanded and hasChildren flags. Since v2026.5.0 the backend drops empty label fragments before sending a tree. _(Sirius Web)_ · `tree.graphqls`, `CHANGELOG.adoc` v2026.5.0
- **Non-selectable tree items and single-selection trees**: tree items can be made non-selectable, and a tree can turn off multiple selection (used, for example, in the reference widget's model browser). Added in v2023.8.0. Non-selectable items are drawn at 60% opacity and ignore clicks. _(Sirius Web)_ · `CHANGELOG.adoc` v2023.8.0, `TreeItem.tsx`

### Tree items: generic interactions

- **Tree item row**: each item is a 22px row indented 24px per depth level. It has an expand chevron (right when collapsed, down when expanded), shown only when the item has children; childless items get a blank spacer instead.
  - Clicking the chevron toggles expansion without changing the selection, and double-clicking the icon or label also toggles it.
  - The label is cut with an ellipsis beyond 100 characters, and marked items are shown in bold.
  - A hovered item gets a hover background and a selected one a selection background.
  - The whole row is clickable and draggable: clicking the empty area to the left (indent) or right of the label also selects the item (the clickable zone was widened in v2024.3.0).
  - A selected item is smoothly scrolled into view.
  - The focused item has a dotted black border.
  - Expanding or collapsing no longer makes tree representations flicker (fixed in v2026.1.0).

  _(Sirius Web)_ · `TreeItem.tsx`, `TreeItemArrow.tsx`, `CHANGELOG.adoc` v2026.1.0
- **Tree multi-selection (click, Ctrl+click, Shift+click)**: a plain click selects one item and makes it the range pivot. Ctrl/Cmd+click toggles an item in the selection, and adding an item makes it the new pivot. Shift+click selects every selectable item between the pivot and the clicked item, walking through expanded items in display order, and replaces the selection; Shift+Ctrl/Cmd+click adds that range to it. If no pivot has been set, the first root item is used. Tree representations sync this selection with the workbench. _(Sirius Web)_ · `useTreeSelection.tsx`, `TreeRepresentation.tsx`
- **Tree keyboard navigation**: with a tree item focused, the arrow keys move through the tree (ignored inside text inputs):
  - Up and Down select the previous or next visible item.
  - Right expands a collapsed item that has children, otherwise selects the next item, which for an expanded item is its first child (v2023.6.0).
  - Left collapses an expanded item, otherwise selects its parent.

  _(Sirius Web)_ · `Tree.tsx`
- **Tree item rename (direct edit)**: renaming opens an inline text field (placeholder "Enter the new value") in place of the label, for editable items only and never in read-only mode.
  - Typing a letter, digit or punctuation key on a focused item starts editing with that character. Modifier keys pressed alone and Ctrl/Meta shortcuts do not start editing.
  - The "Rename" menu entry starts editing with the server's initialDirectEditTreeItemLabel, fully selected.
  - Enter (without Shift) commits through renameTreeItem, Escape cancels, and leaving the field also commits. Focus returns to the item afterwards.
  - A failure loading the initial label shows "An unexpected error has occurred, please refresh the page". Server messages are reported as toasts.
  - Clicking inside the field to move the caret no longer ends the edit (fixed in v2024.3.0).
  - Unicode input has been supported since v2025.10.0, and the explorer's initial direct-edit label was restored in v2024.7.0.

  _(Sirius Web)_ · `TreeItemDirectEditInput.tsx`, `TreeItem.tsx`, `sirius-components-trees.json`
- **Tree item context menu**: each item has a small vertical "⋮" (more) button that opens its context menu, anchored bottom-right. Entries appear in this order:
  - Frontend-contributed entries.
  - The backend entries, each with an icon (or a blank spacer), its label and its first key binding shown as a shortcut, all disabled in read-only mode. Contributions can override how an entry is rendered.
  - One "Show in <target>" entry per selection target other than the explorer (e.g. an open diagram), which pushes the current tree selection into it.
  - "Rename" (pencil icon), only for editable items and disabled when read-only.
  - "Delete" (trash icon), only for deletable items and disabled when read-only. It asks for confirmation in the deletion dialog, then runs deleteTreeItem. A failed request shows "An error has occurred while executing this action, please contact the server administrator".

  _(Sirius Web)_ · `TreeItemContextMenu.tsx`, `DeleteMenuItem.tsx`, `RenameMenuItem.tsx`
- **Tree item palette**: when a tree uses the palette (the explorer does; editor-area tree representations do not), the "⋮" button opens the same palette component as diagrams, in a popper to the right of the item and kept inside the tree. It holds quick-access tools and tool sections, and runs single-click or fetch tools. A "Show in" extension section lists the selection targets other than the explorer with a back button, or "No available targets" when there are none. The diagram palette has been reused for trees since v2026.7.0 (the server property `sirius.web.tree.new-palette.enabled=false` brings back the classic menu), and the palette has come from the TreeDescription palette query since v2026.9.0, when tool labels also became translated on the backend and the tree palette reached parity with the diagram palette (search, last used tool). Fixed in v2026.9.0: the impact-analysis dialog now opens after Update Library from the tree palette. _(Sirius Web)_ · `TreeItemPalette.tsx`, `ShowInSection.tsx`, `CHANGELOG.adoc` v2026.7.0
- **Tree context menu key bindings**: pressing a key combination while the tree has focus fetches the focused item's context menu entries and runs the one whose key binding matches exactly (key plus Ctrl, Alt and Meta flags). A modifier pressed alone or a key typed in a text field is ignored. If several entries match, the error toast "Found multiple entries associated to <CTRL + META + ALT + key>: <labels>" appears and nothing runs. If none matches, nothing happens. Added in v2026.3.0. _(Sirius Web)_ · `useTreeKeyBinding.ts`, `CHANGELOG.adoc` v2026.3.0
- **Tree drag and drop**: any tree item can be dragged. If it is part of the selection, the whole selection is dragged; otherwise it is dragged alone, with its icon and label as the drag image.
  - Dropping onto an item sends dropTreeItem with index -1.
  - Dropping onto the thin 2px zone just above an item sends that item's index, to insert before it.
  - The hovered drop zone is highlighted.
  - The tree description must provide a drop handler; otherwise the server answers "No drop handler provided".
  - Since v2025.4.0 the drag data only carries the dragged tree item ids (no kind). A Chrome glitch where item backgrounds stayed highlighted after a drag was fixed in v2025.10.0.
  - Explorer drag and drop came in v2024.11.0. Since v2024.1.0 any kind of element can be dragged, not just semantic ones.

  _(Sirius Web)_ · `TreeItem.tsx`, `tree.graphqls`, `CHANGELOG.adoc` v2024.11.0

### Tree protocol

- **Generic tree representation subscription**: treeEvent(editingContextId, representationId) streams any description-driven tree. modelBrowserEvent and selectionDialogTreeEvent stream the trees inside the model-browser dialog (reference widgets) and in the diagram selection dialogs. _(Sirius Web)_ · `tree.graphqls`, `modelbrowser.graphqls`, `selection.graphqls`
- **Expanded state and tree paths**: the client keeps the expanded item ids and the deepest expanded level. It sends them in the subscribed representation id (`<treeId>?expandedIds=[…]`) and in the subscription's depth, so the server renders only the expanded branches. treePath(treeId, selectionEntryIds) returns the items to expand (and the max depth) to reveal a selection. expandAllTreePath(treeId, treeItemId) returns those needed to expand a whole subtree; it no longer loops forever on cycles (v2024.11.0). _(Sirius Web)_ · `useTreeSubscription.tsx`, `TreeRepresentation.tsx`, `tree.graphqls`
- **Tree mutations and queries**: the mutations are deleteTreeItem(treeItemId), renameTreeItem(treeItemId, newLabel), invokeSingleClickTreeItemContextMenuEntry and dropTreeItem(droppedElementIds, targetElementId, index). TreeDescription also offers initialDirectEditTreeItemLabel, fetchTreeItemContextMenuEntryData (the URL and kind of a fetch entry) and treeImpactAnalysisReport (the preview before an entry with impact analysis). Backend messages: "No existing action for this entry menu" and "Invalid input type, "{0}" has been received while "{1}" was expected". _(Sirius Web)_ · `tree.graphqls`, `sirius-components-collaborative-trees.properties`
- **Tree palette providers and post-processors**: since v2026.9.0 a backend ITreeItemPaletteProvider can supply a tree item's whole palette (quick-access tools, sections, FetchTreeItemTool and SingleClickTreeItemTool). When one exists for a representation, the context menu entry providers are ignored. Post-processors can customize the palette computed for a diagram or a tree. _(Sirius Web)_ · `CHANGELOG.adoc` v2026.9.0, `useTreeItemPaletteContents.tsx`
- **Tree refresh policy**: by default a tree is re-rendered after semantic changes and after a representation is created, deleted or renamed, so representation items stay current. Other change kinds leave it as is. A description can register its own refresh policy. _(Sirius Web)_ · `TreeEventProcessor.java`
- **Tree backend extension APIs**: applications customize trees through backend interfaces:
  - IDeleteTreeItemHandler, IRenameTreeItemHandler and IDropTreeItemHandler for delete, rename and drop.
  - IInitialDirectEditTreeItemLabelProvider for the text shown when rename starts.
  - ITreeFilterProvider for filters.
  - ITreePathProvider and IExpandAllTreePathProvider for reveal and expand-all paths.
  - ITreeItemContextMenuEntryProvider, ISingleClickTreeItemContextMenuEntryExecutor and IFetchTreeItemContextMenuEntryDataProvider for menu entries.
  - ITreeItemPaletteProvider and ITreeItemPaletteCustomizer for palettes.
  - ITreeItemTooltipProvider for tooltips.

  Unhandled requests report "No existing action for this entry menu" or "No drop handler provided". _(Sirius Web)_ · `IDropTreeItemHandler.java`, `ITreeItemPaletteCustomizer.java`, `sirius-components-collaborative-trees.properties`
- **Tree converters (frontend)**: before rendering, a tree view passes the tree through every converter contributed to the treeViewTreeConverterExtensionPoint. This lets an application rewrite items, for example their labels or children. _(Sirius Web)_ · `TreeView.tsx`, `TreeViewExtensionPoints.tsx`
- **Tree item context menu extension point**: frontend code adds entries to tree item menus by registering a component on treeItemContextMenuEntryExtensionPoint (identifier `treeItem#contextMenuEntry`, since v2024.9.0). Each component receives editingContextId, treeId, item, readOnly, expanded, maxDepth, selectedTreeItemIds and callbacks (expandItem, selectTreeItems, onExpandedElementChange, onClose). It must return null when it does not apply, typically by testing the tree id (e.g. `explorer://`) and the item kind, so contributions can target specific trees (v2023.8.0). An action that changes the tree's own selection must call selectTreeItems (v2025.10.0). A separate treeItemContextMenuEntryOverrideExtensionPoint (since v2025.4.0) lets a contribution with a canHandle(entry) test replace how a server-provided entry is rendered. _(Sirius Web)_ · `extend-frontend.adoc`, `TreeItemContextMenuEntryExtensionPoints.tsx`, `TreeItemContextMenuEntry.types.ts`
- **Tree palette tool overrides, last used tool and search**: a tool of a tree item palette can be replaced through paletteToolOverrideExtensionPoint; its canHandle(representationKind, tool) receives `tree` (TREE_REPRESENTATION_KIND) for trees. The overriding component must call onInvoked() after running so the tool becomes the palette's last used tool, shown on top of the tool section, and it gets asLastToolUsed and isToolInPalette flags. While the palette search field holds text, it gets searchedValue and should test its label with the exported fuzzyMatch(candidate, searchTerm) and render nothing when there is no match (search props added in v2026.9.0). Backend code can add, transform or remove tools, sections and quick-access tools of a computed tree palette with an ITreeItemPaletteCustomizer. _(Sirius Web)_ · `tree-services.adoc`, `PaletteToolOverrideContribution.types.ts`, `TreeItemPalette.tsx`
- **Render variable customizers**: an IRepresentationRenderVariableCustomizer adds or changes variables once per render, before any tree item property is computed, so costly or global data is computed a single time (ADR-200, v2025.8.0). Sirius Web uses it to give the explorer an existingRepresentations variable from one database query instead of one per item; SysON contributes its own for its explorer. The order of customizers is not guaranteed. The v2026.11.0 release notes say they are now used for diagrams as well as trees, and ask contributors to check the representation description so they do not pollute other representations. _(Sirius Web)_ · `TreeService.java`, `SysONExplorerRenderVariablesCustomizer.java`, `CHANGELOG.adoc` v2025.8.0

### Tree descriptions (studio)

- **Tree representations in the View DSL**: specifiers define tree representations with the View DSL (tree descriptions with styled labels, context-menu actions and children/parent expressions) and use them as explorers or as standalone trees. Available since v2024.9.0 and v2024.11.0. The studio-maker guide flags tree descriptions as experimental. _(Sirius Web, studio; experimental)_ · `CHANGELOG.adoc` v2024.11.0, `CHANGELOG.adoc` v2024.9.0
- **Tree description: structure expressions**: View model > New Object > Tree Description. elementsExpression returns the root elements. hasChildrenExpression says whether an item can expand without fetching its children eagerly. childrenExpression returns the children on expand, and parentExpression navigates upward (e.g. to synchronize selection). It also holds treeItemLabelDescriptions and contextMenuEntries, an ordered list of entries attached to every node and filtered by their preconditions. SysON's explorer is a tree description built with this model. _(Sirius Web, studio)_ · `tree-description.adoc`, `SysONExplorerTreeDescriptionProvider.java`
- **Tree description: item identity, kind, icon and tooltip**: treeItemIdExpression gives each item a stable id so selection and refresh stay consistent. treeItemObjectExpression resolves the semantic element, defaulting to the current one. kindExpression tags items with a kind so the frontend can group or style them. treeItemIconExpression returns the icon URL, and treeItemTooltipExpression the hover tooltip. SysON's explorer sets all of these, and its expressions also use the variables existingRepresentations, expanded, activeFilterIds and id. _(Sirius Web, studio)_ · `tree-description.adoc`, `tree.ecore`, `SysONExplorerTreeDescriptionProvider.java`
- **Tree description: editable, selectable, deletable**: editableExpression enables or disables inline rename or editing per item. selectableExpression decides whether an item takes part in selection synchronization with other representations. deletableExpression turns delete actions in context menus on or off. All three default to true when the expression is empty or does not return a boolean. Rename and delete are not defined in the tree description; they go to the first generic rename or delete handler that accepts the item. _(Sirius Web, studio)_ · `tree-description.adoc`, `ViewTreeDescriptionConverter.java`
- **Tree description: identity, title and variables**: a View DSL tree description is named "Tree Description" when it has no name. It can be created only on its domainType where preconditionExpression holds, and titleExpression, kindExpression and iconExpression give the tree's title, kind and icon. Its tree id has the form `explorer://?treeDescriptionId=<id>&expandedIds=[…]&activeFilterIds=[…]`, so view-based trees are served like explorers. Item labels use the first TreeItemLabelDescription whose precondition holds, and are empty if none does. Context menu, palette, tooltip and fetch expressions see self (from treeItemObjectExpression), selectedTreeItem, id, tree and editingContext. A failing single-click entry reports "Something went wrong while handling the context menu action". _(Sirius Web, studio)_ · `ViewTreeDescriptionConverter.java`, `ViewSingleClickTreeItemContextMenuEntryExecutor.java`, `ViewTreeItemTooltipProvider.java`
- **Tree item labels from styled fragments**: TreeItemLabelDescriptions (name, preconditionExpression, children) build labels from three kinds of element, added in v2025.2.0:
  - TreeItemLabelFragmentDescription: a labelExpression plus an optional TextStyleDescription for color and font.
  - IfTreeItemLabelElementDescription: a conditional element whose children show only when its predicate holds.
  - ForTreeItemLabelElementDescription: a loop over iterator and iterableExpression, e.g. for tag lists or counters.

  _(Sirius Web, studio)_ · `tree-description.adoc`, `CHANGELOG.adoc` v2025.2.0
- **Tree context menu entry: single click**: SingleClickTreeItemContextMenuEntry (name, preconditionExpression, labelExpression, iconURLExpression, body) runs its operations directly. Its withImpactAnalysis flag first shows an impact analysis, for operations with significant side effects (added in v2025.8.0, in the View DSL too). Bodies use the shared operation language (ChangeContext, CreateInstance, SetValue, UnsetValue, DeleteElement, Let, If, For), so entries can create children, open representations or call validation services. An e2e test checks that a tool with impact analysis opens the impact analysis dialog and that a fetch tool of kind OPEN opens its URL in a new browser tab. _(Sirius Web, studio)_ · `tree-description.adoc`, `tree-item-palette.spec.ts`, `CHANGELOG.adoc` v2025.8.0
- **Tree context menu entry: fetch**: FetchTreeItemContextMenuEntry fetches an external resource from urlExpression, with kind DOWNLOAD or OPEN and optional label and icon expressions. Since v2026.9.0 fetch entries no longer carry withImpactAnalysis, which exists only on single-click entries. _(Sirius Web, studio)_ · `tree-description.adoc`, `CHANGELOG.adoc` v2026.9.0
- **Tree context menu entry: custom frontend contribution**: CustomTreeItemContextMenuEntry points at a frontend-contributed tool by contributionId, with optional withImpactAnalysis and labelExpression. A precondition must restrict each one to compatible item types. Built-in contribution ids:
  - expand-all: expands all children.
  - new-root-object: on a document, opens a modal to create a root object.
  - download-document: on a document, downloads it.
  - new-object: on an EObject, opens a modal to create a child.
  - new-representation: on an EObject, opens a modal to create a representation.
  - duplicate-object: on an EObject, opens a modal to duplicate it.
  - duplicate-representation: on a representation, duplicates it.
  - update-library: on a library, opens the update modal.

  The menu labels of these contributions are "Expand all", "New object" (used by both new-root-object and new-object), "Download", "New representation", "Duplicate object", "Duplicate representation" and "Update Library". Since v2026.9.0, reusing one of these ids also requires a labelExpression, or the label does not render. Expand all is available in read-only workbenches since v2025.12.0. _(Sirius Web, studio)_ · `tree-description.adoc`, `sirius-web-application.json`, `CHANGELOG.adoc` v2026.9.0

## Studio: language & representation authoring

### Studio projects, templates and commands

- **Web Studio: in-browser language and representation authoring**: Studio makers author Domain models (business concepts) and View models (representations, tools, palettes) directly in the browser in a studio project (Explorer + Details view), with no code generation or packaging loop; specifications are interpreted by the runtime and hot-reloaded, so changes take effect without a build or redeployment; more advanced needs use custom Java logic. Positioned as a prototyping accelerator, typically hardened later by packaging the meta-model and views in code. _(Sirius Web, studio; experimental)_ · `studio.adoc`, `sirius-approach.adoc`, `concepts.adoc`
- **Studio anatomy: Domain and View models**: A studio contains Domain descriptions (semantic concepts, equivalent of EMF/Ecore meta-models) and View descriptions (diagrams, forms, tables, decks, gantts, trees, plus palette tools and actions); both are ordinary models managed by the same infrastructure, so they get hot reload and collaborative editing. _(Sirius Web, studio; experimental)_ · `studio.adoc`

### Domain definition

- **Domain editor**: Defines business concepts (entities, attributes, relations) in the browser in a dedicated Domain language, with no code generation or Eclipse install; the domain is immediately live for the View editor and for end users creating instances; targets tree-structured models where each element has at most one container. Edited through the Explorer, Details view and an optional domain diagram. _(Sirius Web, studio; experimental)_ · `domain.adoc`, `domain-tutorial.adoc`, `concepts.adoc`
- **Domain Tree explorer**: A 'Domain Tree' tree description (domain_tree_description) presents domain models, including setting nodes such as an entity's superTypes, with context entries Expand all, New object, Download, New representation, Duplicate object and Duplicate representation. It is a representation created from the New representation dialog on a Domain object only (listed with the label 'Domain Tree', also used as default name), rooted on that Domain; it is not one of the Explorer tree selector's choices. Its items can't be renamed or deleted from the tree (rename and delete are no-ops), every Entity always shows an expand control, an entity's 'superTypes' pseudo-node lists its super types, representations attached to an element appear among its children, and an element with a blank label falls back to its type name; 'New object' is hidden on read-only documents and objects, and the same entries are offered in the tree item palette, with the Explorer's tooltips. _(Sirius Web, studio)_ · `DomainTreeRepresentationDescriptionProvider.java`, `DomainTreeItemContextMenuEntryProvider.java`, `DomainTreeItemPaletteProvider.java`
- **'Domain explorer' tree description and Explorer selector order**: A second built-in tree description 'Domain explorer' (domain_explorer_description) copies the Domain Tree but lists every Domain of the project as roots and can't be created from New representation, so it is reachable only through its explorer representation URL. In the Explorer's tree selector, 'Domain explorer by DSL' is offered only when the editing context holds a Domain element, and when it is present the list is reversed so the default 'Explorer' comes first; the DSL explorer's roots are the documents containing a Domain, sorted by label case-insensitively, its expanded elements show their representations (sorted by label) before their contents, and drag and drop inside it reuses the Explorer's drop executor. _(Sirius Web, studio)_ · `DomainExplorerRepresentationDescriptionProvider.java`, `DomainExplorerTreeDescriptionOrderer.java`, `DomainExplorerServices.java`
- **'Domain explorer by DSL' tree (View-DSL sample explorer)**: Studio-capable projects get an extra in-memory tree description 'Domain explorer by DSL' (title 'Domain explorer DSL', on domain::Domain, precondition aql:false so it is never offered in New representation, only in the Explorers menu). Its labels use a 'Domain Text Style Palette': entities show a blue italic '[Entity] ' prefix, the name in brown bold, ' [abstract]' for abstract entities and ' {attr1, attr2}' listing attribute names (built with If/For label elements); attributes show '[Attribute] ' plus the name; tooltips come from the explorer tooltip service. Context menu entries: 'Expand all' (when the item has children), 'Help' on entities (opens https://eclipse.dev/sirius/sirius-web.html; Ctrl+M / Cmd+M) and 'Toggle abstract' on entities (flips the abstract flag with impact analysis; Ctrl+B / Cmd+B). Drag and drop in it reuses the Explorer's drop behavior. It is chosen from the Explorer's tree descriptions menu (icon button, item 'Domain explorer by DSL'), which only appears when a domain model is in the editing context (a page reload may be needed after uploading one); its entries show up in the tree item palette, 'Toggle abstract' opening the impact analysis dialog first and 'Help' opening the page in a new browser tab; the Explorer filter bar (Ctrl+F) filters it without altering the fragment-built labels. _(Sirius Web, studio)_ · `DomainViewTreeDescriptionProvider.java`, `tree-item-palette.spec.ts`, `key-bindings.spec.ts`
- **Domain package**: The top-level container grouping the entities of one DSL (EMF EPackage equivalent), usually one per studio project; nsURI and nsPrefix are computed from the name (DomainConverter: nsURI 'domain://<name>', nsPrefix the lower-cased name; each Entity becomes an EClass keeping its abstract flag and superTypes, each Relation an EReference keeping its containment flag). Conversion runs in two passes (classes and attributes first, then references and super types, so relations and inheritance may cross domains); a super type outside the converted domains is ignored, and any resulting EPackage that EMF's Diagnostician reports with an error (e.g. an unnamed entity or a relation with no target type) is silently left out, so that whole domain is unavailable to instance projects. _(Sirius Web, studio; experimental)_ · `domain.adoc`, `meta-modeling.adoc`, `DomainConverter.java`
- **Domain entity**: A class-like concept (UML class / EClass) with name, attributes, relations, superTypes (single and multiple inheritance) and an 'abstract' flag; created with New object Entity in the Explorer or the domain diagram; docs advise shallow inheritance (2-3 levels) and preferring composition. _(Sirius Web, studio; experimental)_ · `domain.adoc`, `meta-modeling.adoc`, `domain.ecore`
- **Domain attribute**: A scalar feature (EAttribute) with name, a type from the DataType enum (STRING, BOOLEAN or NUMBER in the code; domain.adoc also lists integer and enum, which the code lacks), an 'optional' flag (default true) and a 'many' flag (default false), both shared with relations. When converted to Ecore, STRING becomes EString, BOOLEAN EBoolean and NUMBER EInt (integers only); optional sets the lower bound to 0 (otherwise 1) and many sets the upper bound to -1 (otherwise 1). _(Sirius Web, studio; experimental)_ · `domain.ecore`, `DomainConverter.java`, `domain.adoc`
- **Domain relation (containment or reference)**: A reference to another entity with name, containment or plain cross-reference (a containment target becomes a child in the project tree) and multiplicity one or many; containment must form a tree (no cycles, no multiple parents); cross-references don't change the hierarchy. _(Sirius Web, studio; experimental)_ · `domain.adoc`, `meta-modeling.adoc`
- **Domain cardinality**: Each attribute or relation can be mandatory or optional, single- or multi-valued. _(Sirius Web, studio; experimental)_ · `domain.adoc`
- **Domain DSL capabilities**: Domains can reference and extend other domains; support single and multiple inheritance, abstract entities, containment references, cardinalities and name validation; custom domains appear first in the new root object dialog. _(Sirius Web, studio)_ · `CHANGELOG.adoc`

### Operations and tools

- **Tools concept**: Tools are interactions users run from the palette, a context menu or a keyboard shortcut; kinds are creation, deletion, edition, reconnect, navigation (opening other representations) and custom domain actions; each has a trigger, a target description and a behavior made of model operations (create, set, delete), optionally extended with expressions or Java services. _(Sirius Web, studio)_ · `concepts.adoc`
- **Shared operation language**: Tool bodies, widget bodies and context-menu entries across diagrams, forms, tables, trees, decks and gantts use the same operations: ChangeContext, CreateInstance, SetValue, UnsetValue, DeleteElement, Let, If, For; tools do nothing until operations are added (New Object in the Explorer); successive sibling operations share the same execution context (self). Operation fields: ChangeContext expression (default aql:self); CreateInstance typeName (domain type), referenceName (containment feature of self) and variableName (default 'newInstance'); SetValue featureName + valueExpression; UnsetValue featureName + elementExpression; DeleteElement (deletes self); Let variableName + valueExpression; If conditionExpression; For expression + iteratorName; every operation nests child operations. _(Sirius Web, studio; experimental)_ · `form-description.adoc`, `tree-description.adoc`, `view.ecore`
- **Operation execution semantics**: Operations run in order, each one's children once per context it yields, and execution stops at the first failing operation (later siblings and children are skipped and the tool reports failure). ChangeContext fails when its expression returns nothing, otherwise rebinds self; Let fails when its value is null; For runs its children once per element with the iterator bound (an empty list runs nothing); If with a false or non-boolean condition just skips its children. SetValue on a multi-valued feature appends the value (or all values of a returned collection) instead of replacing; on a single-valued attribute a String is converted with the attribute's data type (e.g. '42' into an int) and an enum feature accepts a literal name, literal string or integer value; a null result clears the feature; an unknown feature name fails. UnsetValue with a blank elementExpression clears the feature (empties a list or sets null), otherwise removes only the listed elements. CreateInstance resolves typeName written 'package::Class', 'package:Class' or 'package.Class' against the packages registered in the project, fails when the type or the referenceName feature of self can't be found, appends the new element to a many-valued reference and binds it to variableName. DeleteElement deletes self through the platform's edit service and fails only when self isn't a model element. _(Sirius Web, studio)_ · `OperationExecutor.java`, `AddExecutor.java`, `UnsetValueOperationHandler.java`
- **Edge reconnection tool variables**: Source- and target-end reconnection tools on an edge palette run every matching tool body (the reconnection succeeds if any succeeds) with editingContext, diagram, semanticReconnectionSource and reconnectionSourceView (old end), semanticReconnectionTarget and reconnectionTargetView (new end), edgeSemanticElement, edgeView, otherEnd and semanticOtherEnd (the end that doesn't move); self isn't set. _(Sirius Web, studio)_ · `ViewReconnectionToolsExecutor.java`, `diagram.ecore`

### Fork a representation's view model

- **Fork View Model**: For a representation whose descriptions are all view-based (RepresentationMetadata.isViewBased), a 'Fork View Model' entry in the diagram palette (fuzzy-searchable) and in the Explorer/tree item context menu (fork-action) opens the dialog 'Switch to a new view model ?' explaining a new view model will be created from the current one, used by the representation, and that the user will be redirected to a new studio, with Cancel (fork-action-close) and 'Redirect to new studio' (fork-action-open). Confirming runs createForkedStudio(editingContextId, representationId, tableId), creates a studio project holding a copy, switches the representation to it and navigates there; edits to the fork (e.g. a node style Background set to Flow_Orange through the reference widget browse dialog) apply to the original diagram. Keeps node layout strategies, works for tables (replacing the old table-only 'Fork Table View Model'), disabled in read-only mode. Ships in sirius-web-view-fork (Sirius Web sample app), not a SysON dependency. _(Sirius Web, studio)_ · `ForkToolContribution.tsx`, `forkstudio.graphqls`, `fork-description.cy.ts`

### Validation

- **Domain and View validation rules**: Studio models are validated: domains, entities and features need valid names, View diagrams and forms must be well formed and colors set (e.g. error when a node style background is missing, or when an ImageNodeStyle has no Shape); shown in the Validation view / Details diagnostics. Messages in the code: domain names must be well formed ('The name <n> is not well-formed.'), 'Two entities cannot have the same name in the same domain', 'Two features cannot have the same name in the same entity'; diagram and form descriptions, element descriptions, page descriptions and CreateInstance operations need a valid domain class ('The diagram description "<x>" does not have a valid domain class', 'The element description …', 'The create instance operation …', 'The form description …'); conditional styles need a condition ('The condition should not be empty') and a style ('The style should not be empty'); node styles need a background and border color and image styles a shape ('The background should not be empty', 'The border color should not be empty', 'The shape should not be empty'); form widget styles need their background, foreground, color and border colors set. _(Sirius Web, studio)_ · `DomainValidator.java`, `DiagramDescriptionValidator.java`, `FormDescriptionValidator.java`

### SysON and studios

- **Studio projects excluded from SysON behavior**: Editing contexts that can hold a Studio are not set up as SysON projects: no standard libraries copied in, the SysON index not created or updated, default Sirius Web index entries used. · `SysMLEditingContextProcessor.java`, `SysONIndexCreationService.java`, `SysONIndexUpdateService.java`
- **Standard diagram description invariants**: SysON's standard diagrams guarantee every edge has reconnect tools, labelled edges and nodes have direct edit, every node has delete and graphical drag-and-drop tools, nodes aren't collapsible, the diagram has semantic drag and drop, and composition edges exist for nested and owned usages. · `SDVDiagramDescriptionTests.java`
- **Customization through source and modules**: The UI is customized by forking and building a custom version; add-ons are modules on SysON's modular architecture; diagram editors can be customized via viewpoint extensions without changing SysON code; no modeling method ships by default. · `faq.adoc`
- **Extending SysON through Sirius Web**: SysON can be extended with the Sirius Web low-code platform: new views and methodologies, dedicated libraries or specific metadata through new representations, keeping practice consistent across an organization. · `extend.adoc`
