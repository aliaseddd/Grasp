## Explorer view (model tree)

### View and explorer choice
- **Explorer view**: The "Explorer" view in the left side panel shows the project as an expandable, collapsible tree: models (documents) at the root, semantic elements inside them, each representation (diagram, table) as a child of the element it targets, and a "Libraries" directory. The tree comes from a live subscription (`explorer://?treeDescriptionId=...&expandedIds=[...]&activeFilterIds=[...]`, GraphQL `explorerEvent(editingContextId, representationId)`) and refreshes whenever the server pushes an update. The header holds a toolbar, and an optional filter bar sits above the scrollable tree. A loading indicator shows until the first tree arrives, and subscription errors appear as toasts. The view is a collapsible accordion section titled "Explorer" (toolbar in the accordion header), and its workbench configuration saves the active explorer description and the active tree filters. _(Sirius Web)_ · `ExplorerView.tsx`, `useExplorerSubscription.tsx`, `useExplorerViewHandle.ts`
- **SysON Explorer replaces the default explorer**: SysON contributes its own tree representation, titled "SysON Explorer" (icon `/explorer/explorer.svg`), with library directories, SysML filters and SysON menus. Whenever it is available, the default Sirius Web explorer is removed from the list of explorer descriptions, so users of SysML projects cannot select the Sirius Web explorer (since 2025.1.0). In SysON Studio (studio-capable) projects SysON does not contribute it, and the default Sirius Web explorer is used instead. · `SysONExplorerContributionProvider.java`, `SysONExplorerTreeDescriptionOrderer.java`, `SysONExplorerTests.java`
- **Explorers menu (switch tree description)**: When more than one explorer tree description exists (for example an alternate semantic hierarchy or a group-by-type layout such as "Domain explorer by DSL"), the toolbar shows an "Explorers" button (tree icon). Its menu lists the explorers by label and checks the active one. Choosing one re-renders the explorer with that description and clears the shown tree until the new subscription sends its first tree. The first explorer is active by default unless the workbench configuration names one. `editingContext.explorerDescriptions` lists the choices. SysML projects in SysON have a single explorer, so the menu does not appear there. _(Sirius Web)_ · `TreeDescriptionsMenu.tsx`, `ExplorerToolbarRenderer.tsx`, `useExplorerDescriptions.ts`
- **SysON Explorer built as an in-memory View tree description**: The SysON Explorer is defined with Sirius Web's tree View DSL: a TreeDescription named "SysON Explorer" in an in-memory View that is added to every editing context when it loads. Its elements, children, has-children, label fragments (short name, label, ViewDefinition type, library name, read-only tag), icon, kind, tooltip, parent, item id, item object and editable/deletable/selectable expressions all call SysON's tree query service through AQL. Its precondition is always false, so it is never offered as a representation to create. A render-variable customizer loads every representation of the project once per render (`existingRepresentations`) instead of querying the database for each item. The chevron check still asks the database whether any representation targets each element. Item ids are resolved back to objects by first looking for a project resource whose URI contains the id, which is how model items are found, and otherwise through the regular object lookup. Its tree representation metadata (kind Tree, label "SysON Explorer", icon `/explorer/explorer.svg`) is provided by SysON itself. · `SysONExplorerTreeDescriptionProvider.java`, `SysONTreeViewDescriptionProvider.java`, `SysONExplorerRenderVariablesCustomizer.java`
- **Expansion state kept per explorer description**: Expanded item ids and the max depth are stored separately for each explorer description. Switching to another explorer and back restores the earlier expansion. The expansion lives only in browser memory. It is not part of the workbench configuration, which saves only the active description and the filters, so a page reload or a share link opens the tree fully collapsed (max depth 1). It is also reset for every description whenever the list of explorer descriptions is fetched again. _(Sirius Web)_ · `useTreeStateContainer.tsx`, `ExplorerSubscriptionContainer.tsx`
- **Lazy loading by expansion and max depth**: The explorer sends the server only its expanded item ids, with a maxDepth that starts at 1 and only grows. Children are computed only for expanded items, so unexpanded subtrees are never sent. Because GraphQL cannot recurse, the client builds the subscription query with the `children { ... }` selection nested maxDepth levels deep, and the expanded ids and active filter ids are encoded in the explorer representation id, so every expand, collapse or filter change opens a new subscription (no client cache, `fetchPolicy: no-cache`), served by its own server-side tree processor. _(Sirius Web)_ · `useTreeStateContainer.tsx`, `useExplorerSubscription.tsx`, `getTreeEventSubscription.ts`
- **Per-viewer expansion state**: Each viewer's expanded ids are kept on the client and sent with that viewer's own tree subscription, so expanding or collapsing never changes another user's tree. Model changes still refresh every viewer live. _(Sirius Web)_ · `useTreeSubscription.tsx`, `TreeRepresentation.tsx`
- **Open or close the Explorer from the left sidebar**: The Explorer is one of the views in the left panel's vertical icon bar (with Validation and Views). With no saved workbench configuration, the left panel opens expanded with "Explorer" as the active, highlighted view. Clicking another view's icon switches to it, and clicking the icon of the active view collapses or expands the panel. A workbench configuration (e.g. from a share link) can open the panel collapsed. The left panel always shows project-level information, not the current selection. _(Sirius Web)_ · `user-interface-navigation.adoc`, `workbench.adoc`, `workbench-configuration.cy.ts`

### Toolbar
- **Tree toolbar layout**: The Explorer header toolbar shows, from left to right: contributed toolbar components (New model, Upload model; disabled when read-only), the Filters menu (only when the tree description defines filters), view-specific extra buttons (such as the Explorers menu), the Filter (search) button and the Reveal selection button. It stays visible while the tree scrolls. The toolbar renders nothing until the list of explorer descriptions has loaded and an active one is known. _(Sirius Web)_ · `TreeToolBar.tsx`, `ExplorerToolbarRenderer.tsx`, `CHANGELOG.adoc`
- **New model button**: A "+" icon button titled "New model" (test id `new-model`) opens the "Create a new model" dialog. It is disabled when the editor is read-only. _(Sirius Web)_ · `NewDocumentModalContribution.tsx`, `EditProjectView.tsx`, `model-management.adoc`
- **Create a new model dialog**: This extra-small dialog, titled "Create a new model" (`create-new-model`), has two fields. The "Name" field is autofocused, with the placeholder "Enter the name of the model" and the helper text "The name cannot be empty", shown in error once the field has been edited and left blank. The "Model type" select lists the editing context's stereotypes and defaults to the first one. Both fields are disabled while the stereotypes load or the model is being created. "Create" (`create-document`) is disabled while the name is blank or something is loading. It calls `createDocument(editingContextId, stereotypeId, name)`: a blank name fails with "Invalid name" and an unknown stereotype with "Not found". On success the dialog closes and the new model appears in the Explorer. Errors are toasted, with "An unexpected error has occurred, please refresh the page" on network errors. _(Sirius Web)_ · `NewDocumentModal.tsx`, `CreateDocumentEventHandler.java`, `sirius-web-application.json`
- **Model type "SysMLv2"**: This stereotype (id `empty_sysmlv2`) is listed first. It creates a model with the given name and appends ".sysml" when the name does not already end with it (case-insensitive; since 2026.3.0). The new document holds a root Namespace > OwningMembership > Package "Package1". · `SysMLv2StereotypeProvider.java`, `SysMLv2StereotypeHandler.java`, `SysMLv2NewModelTests.java`
- **Model type "SysMLv2-Library"**: This stereotype (id `empty_sysmlv2_library`) is listed second. It appends ".sysml" when the name lacks it and creates a root Namespace > OwningMembership > LibraryPackage "LibraryPackage1". · `SysMLv2StereotypeProvider.java`, `SysMLv2StereotypeHandler.java`
- **Model type "Others..."**: This stereotype (id `empty`) is listed third. It creates an empty document with exactly the given name, with no ".sysml" suffix and no root content, stamped with the latest migration version. · `SysMLv2StereotypeProvider.java`, `SysMLv2StereotypeHandler.java`
- **Editing context actions (quick model creation)**: `editingContext.actions` lists quick model-creation actions, and `invokeEditingContextAction(actionId)` runs one. They are proposed when creating a model or during onboarding. Sirius Web offers "Others..." (adds an empty model named "Others...") for projects without natures. SysON contributes empty "SysMLv2" and "SysMLv2-Library" actions. _(Sirius Web)_ · `core.graphqls`, `DefaultEditingContextActionProvider.java`, `SysMLv2EditingContextActionProvider.java`
- **Upload model button and dialog**: A toolbar button (`upload-document-icon`) opens the "Upload new model" dialog, which uploads an external model file and adds it to the project as a new model. The dialog has a file picker (`input name=file`) and a split button (`upload-document-split-button`) that switches between "Upload" and "Upload (read-only)". It calls `uploadDocument(editingContextId, file, readOnly)`, which returns the new document plus an optional textual import report shown in the dialog. "Close" returns to the workbench. A failed transfer shows "An unexpected error has occurred, the file uploaded may be too large", because a 413 status may be hidden by CORS. The toolbar button is an upload (Publish) icon titled "Upload model", disabled when read-only. The file picker is a clickable area reading "Click here to select a file" that then shows the chosen file's name (one file only). The split button defaults to "Upload" (read-write) and is disabled until a file is chosen, while uploading, and after a document has been uploaded; "Close" turns into the primary (filled) button once the upload is done. Read-only uploaded models cannot be renamed or modified but can still be deleted. Plain Sirius Web accepts XMI and JSON files, and only JSON produced by its own Download can be re-uploaded. The docs say the uploaded model is created and opened automatically. _(Sirius Web)_ · `UploadDocumentModal.tsx`, `FileUpload.tsx`, `model-management.adoc`
- **SysON upload of textual SysML/KerML files**: In SysON, the Upload model dialog accepts SysML v2 textual files and SysON's own JSON export. A file is parsed as textual SysML when its name ends in ".sysml" or ".kerml" (case-insensitive) and its first line does not start with "{". The text is parsed and transformed into a new model flagged as imported, and the parser and transformation messages become the import report shown in the dialog. Only JSON produced by SysON's Download can be re-uploaded. The SysON how-to says only ".sysml" files are processed as textual SysML, although the loader also accepts ".kerml". Requirement derivations, for example, can be created by uploading SysML text (2026.9.0). · `SysMLExternalResourceLoaderService.java`, `model-management.adoc`, `CHANGELOG.adoc` v2025.4.0
- **Filter (search) button**: A magnifier icon button, with tooltip and aria-label "Filter", opens or closes the tree filter bar. _(Sirius Web)_ · `FilterButton.tsx`, `sirius-components-trees.json`
- **Filters menu (tree filters)**: A filter-list icon button titled "Filters" (`tree-filter-menu-icon`, with a tooltip, greyed while open) appears only when the active explorer description defines filters. It opens a menu with one checkbox per filter, each showing its label and starting from the description's defaultState. Toggling a checkbox changes the active filter ids, which are sent with the tree subscription, so the server changes what it puts in the tree. The menu stays open while you toggle, so several filters can be changed in a row, each change re-subscribing at once; it closes on Esc or a click outside, and focus then returns to the button. The current expansion is kept when filters change. The filter list is fetched again when another explorer is chosen, and user-set states are kept for filters with the same id. Filter states are saved in the workbench configuration and in share links. In SysON the menu lists seven filters, in this order: Hide Memberships (on), Hide KerML Standard Libraries (off), Hide SysML Standard Libraries (off), Hide User Libraries (off), Hide Root Namespaces (on), Hide Expose Elements (on), Hide Expression Internals (on). The plain Sirius Web explorer offers none of them. _(Sirius Web)_ · `TreeFiltersMenu.tsx`, `useTreeFiltering.tsx`, `SysONTreeFilterProvider.java`
- **Reveal selected elements button**: A crosshair (LocationSearching) button (`explorer-reveal-selection-button`) reveals the current workbench selection in the tree: elements selected or created in a diagram or table, or an omnibox result. The SysON docs call it "Select element in Explorer". It asks the server for the tree path of the selected elements, expands the missing ancestors, raises the max depth and selects the items. The tooltip defaults to "Reveal selected elements". When it opens it fetches the selected objects' labels, showing "Reveal selected elements (loading details...)" meanwhile, then "Select A, B", or "Select <first 5> (and N more)" when there are more than five. The same path computation runs automatically when another view pushes a selection to the explorer. Clicking it does nothing when the workbench selection is empty. The explorer keeps its own selected items: selecting something in a diagram or table does not change the explorer's highlighted items until this button is used or another view pushes the selection to the explorer ("Show in Explorer"). Picking an element in the omnibox pushes it to the explorer, which reveals and selects it, even on the first search right after the project opens (fix in 2026.1.0). _(Sirius Web)_ · `RevealSelectionButton.tsx`, `ExplorerSelectionContext.tsx`, `explorer.adoc`

### Tree contents and structure
- **Root contents and order**: At the root the SysON Explorer lists every model resource (document) of the project that is not a KerML standard library, a SysML standard library or a user library, in resource-set order, followed by a single "Libraries" directory placed last. With the default filters, root namespaces and memberships are not shown. · `SysONDefaultExplorerServices.java`, `SysONExplorerTests.java`
- **Libraries directory**: The "Libraries" root directory (icon `icons/LibraryResource.svg`) contains a "KerML" directory and a "SysML" directory for the standard libraries, each shown as "KerML [read-only]" / "SysML [read-only]" and listing the standard library models (e.g. "Base" under KerML, holding a LibraryPackage "Base"), and a "User libraries" directory. A child is omitted when its Hide filter is active, and "User libraries" is omitted when empty. "Libraries" itself appears only when it would have children under the active filters. Standard library resources are recognized by their URI scheme (KerML or SysML library scheme) and listed in resource-set order, while user-library models are sorted by resource URI. The directories have fixed name-based UUID ids (e.g. from "SysON_Libraries_Directory"), so their expanded state survives refreshes. The four directories have the fragment class name as their kind. They can be selected but never renamed, deleted or expanded with Expand all, and their menu is empty. This layout replaced the short-lived 2025.1.0 "Standard Libraries" / "Referenced Libraries" folders. · `LibrariesDirectory.java`, `KerMLStandardLibraryDirectory.java`, `SysMLStandardLibraryDirectory.java`
- **User libraries placement**: A document goes under Libraries > "User libraries" when its root namespace contains only LibraryPackages (a Comment or other non-Namespace top-level element is ignored for this check) and it is either imported from a published library by reference or uploaded and flagged as imported (for example a .sysml file containing only `library package` declarations). Libraries with at least one top-level Package (alone or with a LibraryPackage) always appear at the Explorer root, and an empty imported document is not treated as a user library (since 2025.12.0 / 2026.1.0). A by-reference library document is labeled, for example, "Library.sysml - LibraryWithOneLibraryPackage@1.0.0 [read-only]". · `LibrariesDirectory.java`, `SysONExplorerFilterService.java`, `library-import.adoc`
- **Imported models stay where they are**: Creating a LibraryPackage inside an imported model that is not a library does not move that model into "User libraries" (2025.1.0). Creating a child in a user library does not move the library from "User libraries" to the project root (2026.3.0). · `CHANGELOG.adoc` v2025.1.0, `CHANGELOG.adoc` v2026.3.0
- **Library project shows its own library at the root**: When you open a published library's project, the Explorer always shows that library's model at its root, without the [read-only] suffix, even if it contains only top-level LibraryPackages (these used to land under "User libraries"). · `CHANGELOG.adoc` v2025.12.0, `SysONExplorerTests.java`
- **Element children: representations first**: Expanding an element lists first the representations (diagrams, tables) whose target object is that element, sorted by label (plain, case-sensitive string order), and then its semantic contents. A resource node lists its root contents. _(Sirius Web)_ · `ExplorerServices.java`, `SysONDefaultExplorerServices.java`
- **Expand chevron rules**: An element shows an expand chevron when, after the active filters are applied, it has contents other than EMF annotations, or when at least one representation in the project targets it. An element whose only contents are annotations shows no chevron. A document shows one only when its root contents are non-empty after the filters, so with Hide Root Namespaces on, a document whose root Namespace is empty has no chevron. Non-SysML objects fall back to Sirius Web's rule (Ecore contents or a targeting representation). · `SysONDefaultExplorerServices.java`, `ExplorerServices.java`, `explorer.adoc`
- **Expand arrow on non-SysML elements**: Non-SysML model elements also get the fold/unfold arrow, so projects that mix SysML and non-SysML models can be navigated (2025.4.0). · `CHANGELOG.adoc` v2025.4.0
- **EMF annotations always hidden**: EAnnotation objects are always removed from explorer children, whatever filters are active, because they are not part of SysML. · `SysONDefaultExplorerServices.java`
- **Implicit specializations not shown**: Implicit specializations, such as the implicit redefinitions SysON computes for feature chaining (KerML 7.4.7.2/7.4.7.3), never appear as Explorer items, and they are not shown in diagrams either (2025.4.0). · `2025.4.0.adoc`, `CHANGELOG.adoc` v2025.4.0
- **ConjugatedPortDefinition items**: ConjugatedPortDefinition elements are handled in the Explorer, with their own ConjugatedPortDefinition.svg icon, as they are in diagrams and the Details view (2024.5.0). · `2024.5.0.adoc`, `CHANGELOG.adoc` v2024.5.0
- **Default Sirius Web explorer content**: The default Sirius Web explorer ("Explorer", explorer icon) lists every model of the project at the root, sorted case-insensitively by name, with each element's representations among its children. Hovering an element shows "package::Class", and hovering a representation shows its type. SysON hides this explorer when its own is available. _(Sirius Web, unclear in SysON)_ · `DefaultExplorerContentService.java`, `DefaultExplorerTooltipService.java`, `ExplorerDescriptionProvider.java`

### Rows, labels, icons and tooltips
- **Tree item row layout**: Each item is a 22px-high row, indented 24px per depth level, holding an expand arrow, icon, label and a trailing action button. Labels are single-line with ellipsis truncation (max 100ch), and text selection is disabled on rows. A 2px drop zone sits above every row. _(Sirius Web)_ · `TreeItem.tsx`
- **Item icons with overlays**: An item's icon is drawn from a list of icon URLs stacked as overlays (base icon plus decorators), with the item kind as alt text. An item without an icon gets a generic empty-square (CropDin) icon. _(Sirius Web)_ · `TreeItemIcon.tsx`
- **Per-metaclass SysML icons**: Each SysML metaclass has an item provider that supplies an SVG icon (198 files in `icons/full/obj16`, e.g. PartUsage.svg, Package.svg, Comment.svg), used for every element and resource through the label service. Since 2026.11.0 the SysML icons are redrawn in color, matching the diagram icons (e.g. ActionDefinition, ActionUsage, PartUsage, StateUsage, CaseUsage, ConstraintUsage). · `PartUsageItemProvider.java`, `2026.11.0.adoc`, `SysONDefaultExplorerServices.java`
- **Icon variants (direction, parameter, recursive, visibility)**: ItemUsage, ReferenceUsage and PortUsage icons vary by direction (In, Out and Inout suffixes), and item and reference parameters use a parameter icon. Recursive namespace imports use NamespaceImportRecursive.svg. Private and protected namespaces and imports get a visibility overlay (VisibilityKind_private.svg / VisibilityKind_protected.svg). · `ItemUsageItemProvider.java`, `NamespaceImportItemProvider.java`, `NamespaceItemProvider.java`
- **Styled labels**: Tree labels are styled strings made of fragments (`getStyledLabel`). Each fragment can set bold, italic, strike-out, underline style, border style, font, background color, foreground color, strikeout color, underline color and border color. The backend drops empty fragments from item labels before sending them, to reduce the data transferred (2026.5.0). _(Sirius Web)_ · `getTreeEventSubscription.ts`, `TreeItem.tsx`, `CHANGELOG.adoc`
- **Label: short-name prefix**: When an element has a non-blank short name, its label starts with the short name in angle brackets followed by a space (e.g. `<LA> Drone_LogicalArchitecture`), drawn in muted blue #64669b (since 2025.12.0). · `SysONExplorerTreeDescriptionProvider.java`, `SysONDefaultExplorerServices.java`
- **Label: main text**: The main fragment is the fixed label for library directories, the textual SysML form for expression definitions, the name for Types (empty if unnamed), and otherwise the element's label from the label service. · `SysONDefaultExplorerServices.java`
- **Label: ViewDefinition suffix on ViewUsages**: A ViewUsage whose view definition is set gets the suffix " [<ViewDefinition declared name>]" (e.g. " [GeneralView]") in gold #ab8b01, showing which standard view it uses. Default ViewUsage names therefore no longer include the ViewDefinition name (2025.10.0). · `SysONDefaultExplorerServices.java`, `SysONExplorerTreeDescriptionProvider.java`, `CHANGELOG.adoc` v2025.10.0
- **Label: library name and version**: Models of a library imported by reference get the suffix " - <library-name>@<library-version>" in gold. · `SysONDefaultExplorerServices.java`, `CHANGELOG.adoc` v2025.12.0
- **Label: [read-only] tag**: The suffix " [read-only]", in muted blue #64669b, is appended to read-only resources that are not standard library resources and to the KerML and SysML standard library directories. · `SysONDefaultExplorerServices.java`, `SysONExplorerTreeDescriptionProvider.java`
- **Import and expose labels**: A NamespaceImport is labeled `import <qualified name>::*`, or `::**` when recursive. A NamespaceExpose is labeled `expose <qualified name>::*` or `::**`. A MembershipExpose is labeled `expose <member name>` (the member's metaclass name when unnamed), with `::**` when recursive. When the target is unset, the label falls back to `<Type> <name>`. Other elements use the default label service. · `NamespaceImportItemProvider.java`, `NamespaceExposeItemProvider.java`, `MembershipExposeItemProvider.java`
- **Expression labels**: Expression elements show their full textual representation as their label (e.g. "attr1 < 1", "100.0 * minVolume", "pressure <= maxPressure"; since 2026.5.0). Their internal sub-elements are hidden by default. · `SysONDefaultExplorerServices.java`, `SysONExplorerTests.java`, `CHANGELOG.adoc` v2026.5.0
- **Marked (bold) items**: A tree view can be given a set of marked item ids whose labels render in bold, independently of the selection (selection never bolds a label). The reference widget's transfer dialog uses this to bold items already chosen in its right-hand list, and the model browser tree accepts marked items too. _(Sirius Web)_ · `TreeItem.tsx`, `TransferModal.tsx`, `ModelBrowserTreeView.tsx`
- **Hover tooltips**: After an item is hovered for 500ms (debounced), the client fetches a server-computed `treeItemTooltip`. It shows as a non-interactive tooltip above-left of the label (offset 32,-8), placed so it does not block clicks. Empty tooltips are not shown, and the tooltip is hidden while the item's palette is open (2026.9.0). The tooltip appears only while the row itself is hovered, not the drop zone above it, and a failed tooltip query is toasted as an error. _(Sirius Web)_ · `useTreeItemTooltip.ts`, `TreeItem.tsx`, `CHANGELOG.adoc`
- **SysON tooltip content**: A model element's tooltip is "<ePackage>::<EClass>" (e.g. "sysml::PartUsage"). A representation shows its representation type, read from the `type` parameter of its kind URL (e.g. "Diagram"). The Libraries, KerML, SysML and User libraries directories show their label, and documents get an empty tooltip. Delegates and fragments can override the text (`getTreeItemTooltip` / `getTooltip`). · `SysONDefaultExplorerServices.java`, `KerMLStandardLibraryDirectory.java`, `CHANGELOG.adoc`
- **Per-item capability flags**: For every item the server sends its kind and whether it is editable (renamable), deletable and selectable. These flags decide whether Rename and Delete appear, whether direct edit can start, and whether clicking the item selects it. Kinds look like `siriusWeb://document` for models, `siriusComponents://semantic?domain=sysml&entity=PartUsage` for elements and `siriusComponents://representation?type=Diagram` for representations; SysON's library directories use their class name. In the SysON Explorer every item is selectable. _(Sirius Web)_ · `TreeView.types.ts`, `getTreeEventSubscription.ts`

### SysON tree filters
- **Hide Memberships**: On by default (since 2024.3.0). Every Membership child is replaced by the elements it owns, so elements appear directly under their owner without an intermediate membership node. Turn it off to see memberships such as a FramedConcernMembership created from New object. Because each membership is replaced by its owned related elements, a membership that owns nothing (a non-owning Membership, e.g. an alias) disappears entirely while the filter is on. · `SysONExplorerFilterService.java`, `HideMembershipsTreeItemAlteredContentProvider.java`, `2026.7.0.adoc`
- **Hide KerML Standard Libraries**: Off by default. Removes the KerML standard library resources and the KerML directory from "Libraries". It was introduced in 2024.3.0 as a combined "Hide KerML/SysML Standard Libraries" filter and later split in two. · `HideKerMLStandardLibrariesTreeAlteredContentProvider.java`, `LibrariesDirectory.java`, `2024.3.0.adoc`
- **Hide SysML Standard Libraries**: Off by default. Removes the SysML standard library resources and the SysML directory from "Libraries". · `HideSysMLStandardLibrariesTreeAlteredContentProvider.java`, `SysONTreeFilterProvider.java`
- **Hide User Libraries**: Off by default. Removes imported user-library resources and the "User libraries" directory. "Libraries" disappears when nothing else remains in it. · `HideUserLibrariesTreeAlteredContentProvider.java`, `ExplorerViewControllerIntegrationTests.java`
- **Hide Root Namespaces**: On by default (since 2024.9.0). The unnamed root Namespace of each document is replaced by its owned elements, so top-level packages appear directly under the document. Turning it off shows a "Namespace" item under each document. Root objects created on the document then go into that Namespace (as siblings of Package1), and representations can be created on it. The root Namespace is replaced by its owned elements, not by its memberships, so while this filter is on the top-level memberships stay hidden even if Hide Memberships is off. · `HideRootNamespaceTreeItemAlteredContentProvider.java`, `SysONExplorerFilterService.java`, `semanticElementCreationTests.cy.ts`
- **Hide Expose Elements**: On by default (since 2025.12.0). Hides the Expose relationships contained in ViewUsages, which a ViewUsage uses to show elements in a diagram or table. · `HideExposeElementsTreeItemAlteredContentProvider.java`, `SysONTreeFilterProvider.java`, `CHANGELOG.adoc` v2025.12.0
- **Hide Expression Internals**: On by default (since 2026.7.0). Hides the internal elements of a top-level expression (its syntax tree: operands, sub-expressions, parameters), so the expression shows as a single node labeled with its textual form. Technically it drops every child whose owner is a top-level expression (and that is not itself a top-level expression), which also removes the expression's memberships when Hide Memberships is off. Turning it off shows the sub-elements. · `HideExpressionInternalsTreeItemAlteredContentProvider.java`, `expressions.adoc`, `2026.7.0.adoc`
- **Filters scoped to the SysON explorer**: SysON's filters are offered and applied only on the SysON explorer tree description, not on other trees. Filter ids are name-based UUIDs (e.g. from "SysONTreeItemMembershipsFilter"). On every list of children (and on the root list) they are applied in a fixed order: memberships, KerML libraries, SysML libraries, user libraries, root namespaces, expose elements, expression internals. · `SysONTreeFilterProvider.java`, `CHANGELOG.adoc`
- **Explorer filters reused in other SysON trees**: The selection dialogs of diagram node tools apply the Explorer's default filters, hiding Memberships, root Namespaces, expose elements and expression internals while still offering library elements (2026.9.0). The reference widget's model-browser dialogs in the Details view likewise hide Memberships and root Namespaces, consistent with the Explorer. · `2026.9.0.adoc`, `CHANGELOG.adoc` v2026.9.0
- **Mixed filter combinations expand correctly**: Elements can be expanded when "Hide Root Namespaces" is off while the KerML/SysML standard-library filters are on (2025.1.0 fix). · `2025.1.0.adoc`, `CHANGELOG.adoc` v2025.1.0
- **Reveal respects active filters**: When the SysON explorer computes the tree path for revealing an element (after a selection in a diagram or the toolbar reveal action), it drops ancestors hidden by the active filters (memberships, libraries, root namespaces, expose elements, expression internals), so only visible ancestors are expanded. ### Filter bar (type to filter)
- **Open the filter bar (Ctrl/Cmd+F)**: With a tree item focused (not in an input), Ctrl+F (Windows/Linux) or Cmd+F (macOS) toggles a filter bar above the tree, overriding the browser's find. The key listener sits on the Explorer's tree area (not the toolbar) and checks only a lowercase "f". While the focus is in the filter field itself the shortcut is not intercepted, so the browser's own find opens. The shortcut handler always sets the bar to open (it reads the state from when it was registered), so pressing Ctrl/Cmd+F again on a tree item does not close the bar: it keeps it open and resets the highlight text, while the uncontrolled field may still show the old text. Close the bar with its X button or the toolbar Filter button, which does toggle it. Opening or closing the bar always resets the text and the hide-non-matching mode. _(Sirius Web)_ · `FilterBarContext.tsx`, `ExplorerTreeRenderer.tsx`, `keyboard-shortcuts.adoc`
- **Filter bar field**: The bar holds an autofocused small outlined text field (`filterbar-textfield`, placeholder "Type to filter", spellcheck off), an inline filter-toggle icon button and a close (X) button. Typed text is highlighted in every visible label that contains it, exact matches included, live on every keystroke (no debounce, no Enter needed). The field is 24px high and full width. Escape does not close the bar; only the X button or the toolbar Filter button does. Closing the bar clears the text and turns hiding off. _(Sirius Web)_ · `FilterBar.tsx`, `FilterBarContext.tsx`, `sirius-components-core.json`
- **Highlight vs. hide toggle**: The filter-list icon inside the field switches between highlight-only mode (the default, icon in the secondary color) and filter mode (icon in the primary color), which hides every visible item whose label does not contain the text. The mode resets to highlight-only whenever the bar is opened, toggled or closed. _(Sirius Web)_ · `FilterBar.tsx`, `explorer-view.adoc`, `explorer.adoc`
- **Client-side matching rules**: Matching is a case-insensitive substring match on the labels of loaded items. In filter mode, non-matching leaves are hidden and matching items are kept. Collapsed non-matching parents stay visible. An expanded parent is hidden only when none of its direct children match and all of its children are hidden by the same rules. _(Sirius Web)_ · `filterTreeItem.ts`
- **Match highlighting in labels**: Each case-insensitive occurrence of the filter text in a label is highlighted with the navigation background color, comparing segments with the browser's languages and ignoring case and accents. Highlighting never injects extra characters into the labels. _(Sirius Web)_ · `StyledLabel.tsx`, `filter-bar.spec.ts`
- **Filter bar limit: expanded items only**: The filter bar highlights or filters only items that are currently expanded, loaded and visible. It does not search collapsed children, so nested items must be expanded first. _(Sirius Web)_ · `explorer-view.adoc`, `explorer.adoc`
- **Reusable filter bar in dialog trees**: The same "Type to filter" field, with a gray search icon and an always-visible clear (X) button, is used above selection-dialog trees and model-browser trees (reference widget dialogs, Duplicate object). ### Selection and navigation
- **Single-click selection**: A plain click selects only the clicked item, focuses it, and makes it the pivot for later Shift range selections. Successive plain clicks leave only the last item selected. The tree selection is pushed to the workbench-wide selection, which other views follow: the Details view shows a selected semantic element's properties. The SysON docs add that the element's node or edge on an open representation gets selected too, but since Sirius Web 2025.10.0 a diagram's selection no longer follows the workbench selection automatically. It is applied only on request: with the diagram toolbar's "Reveal selected elements" button (`diagram-reveal-selection`, tooltip "Select <labels>"), with the explorer's "Show in <diagram>", or when the omnibox selects an element. On such an explicit request, every top-level node of the element is selected, but not sub-nodes of the same element. _(Sirius Web)_ · `useTreeSelection.tsx`, `RevealSelectionInDiagramButton.tsx`, `CHANGELOG.adoc` v2025.10.0
- **Full-row click and drag zone**: Clicking the empty space at the left or right end of a row (`{label}-fullrow`) selects the item. The clickable and draggable zone spans the whole row. _(Sirius Web)_ · `explorer.spec.ts`, `CHANGELOG.adoc`
- **Ctrl/Cmd+click toggle**: Ctrl+click (Cmd+click on Mac) adds an unselected item to the selection or removes a selected one, down to an empty selection. This also works after a range selection. An item added this way becomes the new range pivot. The same gesture multi-selects in representation editors. _(Sirius Web)_ · `useTreeSelection.tsx`, `selection.spec.ts`, `keyboard-shortcuts.adoc`
- **Shift+click range selection**: Shift+click selects every selectable item between the pivot (the last plainly clicked or Ctrl-clicked item, or the first root item when none is set) and the clicked item. It walks visible items in depth-first display order, including visible children of expanded items, and replaces the selection. Further Shift-clicks recompute the range from the original pivot, and a plain click afterwards resets to a single item. _(Sirius Web)_ · `useTreeSelection.tsx`, `selection.spec.ts`
- **Ctrl/Cmd+Shift+click additive range**: Ctrl/Cmd+Shift+click computes the same pivot-to-item range and merges it into the existing selection instead of replacing it. Both the explorer's own selection and the global selection are updated, and only selectable items are included. _(Sirius Web)_ · `useTreeSelection.tsx`, `ExplorerSelectionContext.tsx`, `selection.spec.ts`
- **Clicking a representation opens it**: Selecting a representation item opens it in a new editor tab, or brings its existing tab to the front. Clicking a representation that is already selected still opens and focuses it, and a representation whose tab was just closed can be opened again the same way. The docs say a new representation opens automatically and appears in the Explorer under its element. _(Sirius Web)_ · `explorer-view.adoc`, `CHANGELOG.adoc`
- **Selected highlight and auto-scroll**: Selected items get the theme's "selected" background, which stays on hover. An item that becomes selected, including through selections made in other views, is smoothly scrolled into view (block/inline "nearest"). _(Sirius Web)_ · `TreeItem.tsx`
- **Hover highlight**: Hovering a selectable row, or dragging over it, paints it with the theme's hover background. Non-selectable rows get no hover highlight. _(Sirius Web)_ · `TreeItem.tsx`
- **Non-selectable items**: Items flagged non-selectable render at 60% opacity without a pointer cursor. Clicking one only focuses it without changing the selection, and range selections skip it. _(Sirius Web)_ · `TreeItem.tsx`, `useTreeSelection.tsx`
- **Keyboard focus ring**: Each item is focusable (tabIndex 0), and the focused row gets a 1px dotted black border. _(Sirius Web)_ · `TreeItem.tsx`
- **Arrow-key navigation**: With a tree item focused and no input being typed in, Down/Up select the next/previous visible item. Right expands a collapsed item that has children, or else selects the next visible item (the first child when expanded). Left collapses an expanded item, or else selects its parent. Moving works by simulating a click on the target row, so it acts like a plain click: it leaves a single selection, and landing on a representation opens it. The Details view follows the selection (SysON tests use this to reach anonymous transitions). _(Sirius Web)_ · `Tree.tsx`, `details.cy.ts`, `CHANGELOG.adoc`
- **Expand/collapse arrow**: Items with children show a 20px chevron-right (collapsed) or expand-more (expanded) icon (`{label}-toggle`). Clicking it toggles expansion without changing the selection. Items without children get a 20px blank placeholder so labels stay aligned. _(Sirius Web)_ · `TreeItemArrow.tsx`, `TreeItem.tsx`, `explorer.spec.ts`
- **Double-click to expand/collapse**: Double-clicking the icon or label of an item with children toggles its expanded state (`data-expanded`) and shows or hides its children. _(Sirius Web)_ · `TreeItem.tsx`, `explorer.spec.ts`, `Explorer.ts`

- **Rename (inline direct edit)**: The "Rename" entry (pencil icon, `rename-tree-item`; `direct-edit` palette tool) appears only for editable items, is disabled in read-only mode, and is registered for every tree palette (Explorer and Views). ### Drag and drop
- **Drag tree items (single or multi-selection)**: Any row can be dragged. An unselected item is dragged alone, without changing the current selection, and an item that is part of the selection drags the whole selection, e.g. several Ctrl+clicked elements dragged onto a diagram together. The payload is a JSON list of item ids under the shared `sirius-component/drag/sources` type, and the drag image is the item's icon and label. Tree rows and drop zones, diagrams, portals and the reference widget (property section and transfer dialog) accept it, and drop targets ignore unsupported elements. _(Sirius Web)_ · `TreeItem.tsx`, `dataTransferTypes.ts`, `flashlight.adoc`
- **Drop onto a tree item**: Dropping onto a row calls `dropTreeItem` with the dropped ids, that row as target and index -1 (append). The tree description's drop handler decides what happens. The row gets the hover background while dragged over (selectable rows only), its background resets correctly afterwards, and the server's success and error messages are toasted. _(Sirius Web)_ · `TreeItem.tsx`, `useDropTreeItem.ts`
- **Drop between tree items (ordered insert)**: A thin 2px drop zone above each row highlights while dragged over. Dropping there calls `dropTreeItem` with the row's index among its siblings, inserting the items at that position. An unexpected failure shows "An unexpected error has occurred, please refresh the page". _(Sirius Web)_ · `TreeItem.tsx`, `useDropTreeItem.ts`
- **SysON move on drop**: In the SysON Explorer, dropping one or more items onto a SysML element moves each one, with its owning membership, under the target through SysON's move-element service (since 2025.2.0), e.g. a PartDefinition onto a Package. Each element moves independently. Refusals are warnings of the form "Unable to move {element} in {target}: {reason}", with the reasons "Unable to move an Element to one of its descendant", "Unable to move a read only Element", "Unable to move a Element to a read only Element" (dragging to or from a read-only library is forbidden) and "Membership can't be used as a target of a move". A dropped non-SysML item gives "The dropped element is not a SysML Element", and a non-element target gives "Unable to move the element in selected target". So models and representations cannot be moved by drag and drop, and nothing can be dropped onto a model item: to move an element to a model's top level, drop it onto the model's top Package (or its root Namespace, shown once Hide Root Namespaces is off). Dropped ids that resolve to nothing are skipped silently, and unnamed elements are named by their metaclass in the messages. The move adapts the owning membership: an element moved into a Package gets an OwningMembership and one moved anywhere else a FeatureMembership, with MembershipExposes redirected to the new membership. A moved Import becomes the target's first owned relationship, and other elements are appended last. · `DropTreeItemHandler.java`, `SysMLMoveElementCheckerService.java`, `explorer.adoc`
- **SysON ignores the drop position**: SysON's drop handler serves only the SysON explorer and reads only the target id, not the index. Dropping on the thin zone above a row therefore moves the items into that row's element, exactly like dropping on the row, rather than inserting them before it as siblings. Explorer drops cannot reorder elements. · `DropTreeItemHandler.java`, `TreeItem.tsx`
- **Partial drop success**: When at least one dropped element moves, the drop succeeds and the model is saved, with each failure reported as a warning. When none moves, the drop fails with the warnings and nothing is saved. · `DropTreeItemHandler.java`, `explorer.adoc`
- **Drop onto itself is ignored**: Dropping an element onto itself (a small accidental drag) counts as a silent success: nothing moves and no message appears, though the model is still saved. Dropping onto one of its own descendants also moves nothing, so the element no longer disappears. · `DropTreeItemHandler.java`, `CHANGELOG.adoc`
- **Drag from the Explorer onto a SysON diagram**: Explorer items dragged onto a diagram's background or onto a container node are shown on the diagram and exposed in its ViewUsage. Only elements in the same resource set as the diagram can be dropped, and elements represented as edges cannot. If the element's node is already there but hidden, the drop reveals it. If it is already visible, a warning reads "The element <name> is already visible in its parent <parent>". A Definition dropped on a Usage (or in a list compartment) types it (2024.9.0). Drops also work on the information box of an empty diagram (2024.11.0). A dropped Comment or Documentation node appears only when its annotated element is on the diagram, linked to it by an edge. Dropped nodes come with their compartments hidden, except the interconnection compartment on Interconnection Views (2026.3.0). When the target node shows no suitable compartment, the element is created on the background and linked to the target by a composition edge (2025.12.0). Dropping onto one of the element's own children is refused (2024.9.0). · `manage-drag-drop.adoc`, `DiagramMutationDndService.java`, `GVDropFromExplorerTests.java`
- **Default Sirius Web drop executor**: In the default explorer, `dropTreeItem(droppedElementIds, targetElementId, index)` moves elements into the first containment feature of the target that accepts them. Index >= 0 reorders them among the target's children, and -1 appends them. Drops into the element's own descendants are refused. Errors: "An element is already present for this mono-valued feature", "No containment feature found for this element", "The dropped object is invalid". _(Sirius Web, unclear in SysON)_ · `ExplorerDropTreeItemExecutor.java`, `tree.graphqls`, `dnd.spec.ts`

- **Tree refresh policy**: The server keeps one tree processor per explorer representation id (description + expanded ids + active filters). ### Supported views and synchronization
- **Standard diagrams are unsynchronized views driven by exposed elements**: the docs describe the General View and Interconnection View as *unsynchronized* diagrams. Users add existing elements to the diagram by hand to see them, and a diagram does not show all the information in the model by default. What it shows comes from the exposed elements of the ViewUsage the diagram is created on. Since 2025.10.0, almost all node descriptions are synchronized on those exposed elements (so View as can switch the ViewDefinition without recreating the diagram). A few node kinds still use the UNSYNCHRONIZED policy: start/done actions and states, annotating elements, imported packages, and the hidden 'fake' node descriptions that only hold reusable child descriptions (e.g. for compartments). Relationship edges are always synchronized, so a relationship edge cannot be deleted from the diagram only. · `view-unsynchronized.adoc`, `2025.10.0.adoc`, `manage-relationships-diagram.adoc`
- **Node and edge synchronization policies**: in a studio, each node or edge description has a synchronizationPolicy. With SYNCHRONIZED, an element is created for every semantic candidate returned by the semanticCandidatesExpression (or relation found) and removed only when the candidate is no longer reachable. With UNSYNCHRONIZED, an element is created only when a tool asks for it, a tool can remove it without deleting the semantic element, and it is still removed automatically once the candidate is unreachable. UNSYNCHRONIZED is recommended for large models to avoid huge diagrams. The semanticElementIds variable lets a description consider only the elements already shown or being added, and since Sirius Web 2026.9.0 the diagramServices.deleteViews(nodes) AQL service lets a group palette tool remove several selected unsynchronized nodes without deleting their semantic elements. _(Sirius Web, studio)_ · `node-description.adoc`, `edge-description.adoc`, `diagram-description.adoc`
- **Multiple synchronized views of one model**: the same system can be shown at once in diagrams, tables and forms, which stay synchronized because they all project the same model data. _(Sirius Web)_ · `sirius-approach.adoc`
- **Supported representation kinds**: Deck, Diagram, Form, Gantt, Table and Tree representations (plus Libraries) are available in the platform; SysON's own descriptions cover the standard SysML diagrams, the requirements table, the explorer tree and the details form; Deck, Gantt and standalone forms only appear when someone authors descriptions for them. _(Sirius Web)_ · `key-features.adoc`, `SysONDetailsViewDescriptionProvider.java`
- **Supported SysML v2 views**: General View, Interconnection View, Action Flow View and State Transition View are supported (partial), plus KerML/SysML libraries; Sequence, Geometry, Grid and Browser views are not available, and sequence diagrams and finer styling are on the roadmap. · `key-features.adoc`, `faq.adoc`
- **Representation scaling limits**: the documented limits are up to 2,000 distinct representations per project and up to 1,000 elements displayed on a single representation; beyond that, rendering and interaction slow down, and the docs recommend several focused representations instead of one overloaded view. · `scaling-limits.adoc`
- **Planned views (not available)**: Sequence View (chronological event occurrences on lifelines), Geometry View (2D/3D spatial items), Grid View (elements and relationships in a rectangular grid, generalizing Tabular, Data Value Tabular and Relationship Matrix views) and Browser View (hierarchical membership structure from an exposed root) are documented but not implemented. · `other-views.adoc`, `sysmlv2-overview.adoc`

### Removed or replaced
- **Requirement View diagram**: a 'requirement-view' diagram released by mistake (not defined by SysML v2) was deleted in 2024.5.0; existing diagrams of that kind can no longer be opened; requirements are handled by the Requirements Table View. · `migration-process.adoc`

- **Expression evaluation API**: evaluateExpression(expression, selectedObjectIds) evaluates expressions starting with aql:, var: or feature:, with self, selection and editingContext; results are typed object, objects, boolean, int, string, strings or void; evaluation can modify the model; an unsupported language gives 'Not found'. self is the first of the selected objects that still resolves (unknown ids are dropped).
