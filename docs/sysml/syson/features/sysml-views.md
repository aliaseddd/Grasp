## SysML General View

### Diagram and view definition

- **General View diagram**: Diagram representation named "General View" (view id `GeneralViewDiagram`, internal element-name prefix "GV") whose domain type is `sysml::Namespace`; it can be created on any Namespace element (canCreateDiagram is true for any Namespace) from the Explorer (New representation > General View). It is the most general SysML view, displaying any members of the elements exposed by the ViewUsage it is created on, and is implemented as an unsynchronized diagram whose node candidates are the ViewUsage's exposed elements. All its nodes, compartments, border nodes, edges and palettes are built by SDVDiagramDescriptionProvider. Diagram-level settings: arrange-layout direction DOWN, no automatic layout (layout option NONE), minimap visible, default toolbar, and a default title "view" followed by one plus the number of existing ViewUsages (e.g. "view1"; only the target Namespace's directly owned members whose exact type is ViewUsage are counted). The manual's tip: being unsynchronized, it does not show all model information by default and users must add existing elements manually. The first General View (early releases) could only be created on Packages and handled Attribute/Enumeration/Interface/Item/Metadata/Part/Port Definitions and Usages plus Package; since v2025.10.0 it is one of the standard diagrams of the syson-standard-diagrams-view module. The user-manual page carries the "experimental" banner. _(experimental)_ · `SDVDiagramDescriptionProvider.java`, `general-view.adoc`, `CHANGELOG.adoc` v2025.10.0
- **Standard view definitions tie**: Standard diagrams are tied to the standard library view definitions `StandardViewDefinitions::GeneralView`, `::InterconnectionView`, `::ActionFlowView` and `::StateTransitionView` (labels "General View", "Interconnection View", "ActionFlow View", "StateTransition View"; short names gv, iv, afv, stv). A ViewUsage with no type is treated as a General View. Used by the View as / Set as view tools and by tool preconditions. · `StandardDiagramsConstants.java`, `DiagramQueryViewService.java`
- **Representable element categories (user manual)**: The manual says six categories of elements can be represented: Definition elements, Usage elements, elements inside Definition compartments, elements inside Usage compartments, Package elements and Annotating elements, plus a set of relationship edges. Each kind of element contained in a Definition or Usage node gets its own compartment, identified by a title, so a node that can contain several kinds has several compartments. _(experimental)_ · `general-view.adoc`
- **Empty-diagram "Add your first element" background**: When the diagram's ViewUsage exposes nothing and the diagram is empty (also after an undo removes the last synchronized or unsynchronized node), a conditional diagram style shows a centered, contained base64 background image (color "AddYourFirstElement") inviting the user to add a first element. It disappears as soon as a first element is created, including a NamespaceImport (fix in v2025.12.0 for #1683, where the changelog calls it the "Add your first element" graphical node). Running Add existing elements (or its recursive variant) when it adds nothing no longer removes the image (v2026.9.0, #2464). The first version (v2024.1.0) was a help background message on empty General Views; in v2024.11.0 Explorer elements could be dropped on that information box and were displayed like elements created from it. · `SDVDiagramDescriptionProvider.java`, `AddYourFirstElement.java`, `CHANGELOG.adoc` v2026.9.0
- **No Case View**: The SysML Case view is intentionally not provided because its concepts and features are available in the General View. · `other-views.adoc`
- **General View listed first**: A SysON representation-description sorter moves the description labeled "General View" to the top of the list of representations offered for creation, keeping the others in their original order. · `SysONRepresentationDescriptionMetadataSorter.java`
- **Fake container node ("GV Node Fake")**: A technical, invisible node description (0x0, transparent style, empty label, no semantic candidates, unsynchronized, domain Element) added at the root of the General View only to hold the shared compartment, custom-node and border-node descriptions that other nodes reuse (list compartments, subject/actors/stakeholders/objective/ends compartments, states and exhibit states, action flow, perform actions and parameters compartments). It never renders anything. · `FakeNodeDescriptionProvider.java`, `AbstractFakeNodeDescriptionProvider.java`
- **Description naming ("GV" prefix)**: Every General View node, compartment, border node and edge description name is generated with the "GV" prefix (e.g. "GV Node PartUsage", "GV Node Stakeholder", "GV Node Fake"); SysON features that must only apply to the General View (such as the Manage visibility eye icon) recognize its nodes by the "GV Node " prefix. · `SDVDescriptionNameGenerator.java`, `ManageVisibilityNodeActionProvider.java`

### Background palette

- **Palette tool sections**: The diagram palette groups node-creation tools into sections by concept: Requirements (Concern, Concern Definition, Satisfy Requirement, Requirement, Requirement Definition, Constraint, Constraint Definition), Structure (Attribute, Attribute Definition, Connection Definition, Enumeration Definition, Interface, Interface Definition, Item, Item Definition, Package, Part, Part Definition, Port, Port Definition), Behavior (Allocation, Allocation Definition, Accept Action, Action, Action Definition, Assignment Action, Occurrence, Occurrence Definition, State, State Definition, View), Analysis (Case, Case Definition, Use Case, Use Case Definition), Extension (Metadata Definition) and View as. Besides one "New <Type>" tool per listed metaclass, Structure also holds New Item In/Out/Inout and New Port In/Out/Inout (ItemUsage and PortUsage are the directional elements), New Namespace Import and New Reference; Behavior also holds New Exhibit State, New Exhibit Parallel State and the six control-node tools (New Start Action, New Done Action, New Join, New Decision, New Fork, New Merge, visible only in an ActionFlow View whose ViewUsage owner is an action); View as holds four set-as-view tools (General View, Interconnection View, ActionFlow View, StateTransition View). Sections introduced in v2024.3.0. · `SDVDiagramDescriptionProvider.java`, `ToolConstants.java`, `2024.3.0.adoc`
- **Background creation tool mechanics**: Each background "New <Type>" tool (icon `/icons/full/obj16/<Type>.svg`, directional variants with the capitalized direction appended to label and icon, e.g. "New Port In" / `PortUsageIn.svg`) creates the element in a new membership of the diagram ViewUsage's owner, initializes it (default name, etc.), sets the direction for directional variants, exposes it in the diagram's ViewUsage, creates the element's own diagram when needed (e.g. a new ViewUsage gets its diagram) and selects the new element. Each tool is guarded by the current view's tool-availability rule for its metaclass. · `ToolDescriptionService.java`, `SDVDiagramDescriptionProvider.java`
- **Background Related Elements tools**: The background palette's last section, "Related Elements", has "Add existing elements" (AddExistingElements.svg) and "Add existing elements (recursive)" (AddExistingElementsRecursive.svg); both run on the ViewUsage owner and add its existing members (recursively for the second) to the diagram's exposed elements. "Add existing connected elements" is only offered on nodes and multi-selections, not on the background. · `ToolDescriptionService.java`, `SDVDiagramDescriptionProvider.java`
- **Background tool availability by ViewUsage owner**: All background creation tools are offered when the ViewUsage owner is a Package or the root namespace; when the owner is a Usage or a Definition, the Definition-creating tools are hidden. · `DiagramQueryToolService.java`
- **Top-level creation tools and initial compartments**: Background tools create Attribute Definition (2 compartments), Attribute (3), Allocation (3), Allocation Definition (4, with 2 end items, 1 visible), Accept Action (2), Action Definition (6), Action (7), Assignment Action (1), Comment/note (0), Concern Definition (8), Concern (8), Constraint Definition (2), Constraint (4), Connection Definition (5), Enumeration Definition (2), Exhibit State (6, selection dialog), Interface Definition (7, with 2 port border nodes), Interface (4), Item Definition (2), Item (4), Metadata Definition (3), Occurrence Definition (3), Occurrence (2), Package (0), Part Definition (13), Part (13), Port Definition (5), Port (5), Reference (0, selection dialog), Requirement Definition (9), Requirement (9), Use Case Definition (5), Use Case (7), Satisfy Requirement (8), State Definition (6), State (6) and View. Compartments are hidden on creation. New elements appear in both the Explorer and the diagram. · `GVTopNodeCreationTests.java`, `nodeCreationTests.cy.ts`, `batmobile.adoc`
- **New Part Definition (background)**: Structure > New Part Definition on the diagram background (right-click the background to open the palette) creates a Part Definition, shown in the Explorer and on the diagram. · `batmobile.adoc`
- **New Part (background or nested)**: Structure > New Part on the background creates a top-level part usage; on a Part Definition or part it creates a nested part (e.g. "engine", "wheels"). · `batmobile.adoc`, `flashlight.adoc`
- **New Package (top-level and nested)**: Structure > New Package on the background creates a package; on an existing package node it creates a nested package (the tutorial builds Requirements, ActionTree, PartsTree, RequirementsAllocation this way). · `flashlight.adoc`
- **New Requirement (background or nested)**: Click the background to open the palette and choose Requirements > New Requirement to create a requirement; the same tool on an existing element (e.g. another requirement) creates a nested requirement. A RequirementUsage created from a Package node is revealed on the diagram (v2026.3.0). RequirementDefinition palettes also create Requirements inside the definition (v2024.7.0). The requirements page of the manual is outdated: it still says the General View can only create Requirement Definitions and Requirement Usages and that satisfy relationships are not yet available. · `requirement-management.adoc`, `flashlight.adoc`, `CHANGELOG.adoc` v2026.3.0
- **New Namespace Import**: Background Structure tool labeled "New Namespace Import" (NamespaceImport icon) that opens a required (non-optional) tree selection dialog titled "New NamespaceImport" with the text "Select a Package to import:" (only Packages selectable), then creates a NamespaceImport of the chosen package in the ViewUsage owner and shows it as a node under the selected node. · `SDVDiagramDescriptionProvider.java`, `NamespaceImportNodeToolProvider.java`
- **Background palette composition**: Besides the six concept sections, the background palette has a section-less New Comment tool, ends with a "Related Elements" section, sorts the tools of each section alphabetically by name, and carries two drop tools: "Drop from Diagram" (accepts nodes of every palette-section kind plus NamespaceImport and ReferenceUsage, running dropElementFromDiagram) and "Drop from Explorer" (dropElementFromExplorer). The New Comment tool is the only tool outside sections and is generated from the Comment node description. · `SDVDiagramDescriptionProvider.java`, `ToolDescriptionService.java`
- **New Reference (background and Package node)**: Background Structure and Package-node tool labeled "New Reference"; it creates a ReferenceUsage in the ViewUsage owner (or the package), creates its view as a child of the selected node and exposes it. An optional selection dialog lists Features and Classifiers: a Classifier (e.g. PartDefinition) types the reference, a Feature is reference-subsetted by it (e.g. a reference to a selected PartUsage), and no selection creates an empty ReferenceUsage (dialog since v2026.11.0). Shown only if the current view's tool-availability rule allows creating a ReferenceUsage. · `ReferenceUsageNodeToolProvider.java`, `PackageNodeDescriptionProvider.java`, `2026.11.0.adoc`

### Definition and usage nodes

- **Definition nodes**: Nodes for ActionDefinition, AllocationDefinition, AttributeDefinition, CaseDefinition, ConcernDefinition, ConnectionDefinition, ConstraintDefinition, EnumerationDefinition, InterfaceDefinition, ItemDefinition, MetadataDefinition, OccurrenceDefinition, PartDefinition, PortDefinition, RequirementDefinition, UseCaseDefinition and StateDefinition, with candidates from the ViewUsage's exposed elements. Drawn as square-cornered rectangles, 208x70 by default, white background and black border, with a top-centered wrapping multi-line label showing «keyword def» and the name (optional icon). A header separator appears only when there are children. Compartments are stacked in a list layout, free-form compartments grow to fill space, and children cannot be dragged out of the list. Resizable in both directions and synchronized. Palette: Delete from Model, Edit, Drop from Diagram, sorted section tools, Show/Hide (plus Show content as Nested and Show content as Tree), and quick access Delete from Diagram and Duplicate Element. · `AbstractDefinitionNodeDescriptionProvider.java`, `DefinitionNodeDescriptionProvider.java`, `general-view.adoc`
- **Usage nodes**: Nodes for AcceptActionUsage, ActionUsage, AssignmentActionUsage, AllocationUsage, AttributeUsage, CaseUsage, ConcernUsage, ConstraintUsage, ExhibitStateUsage, InterfaceUsage, ItemUsage, OccurrenceUsage, PartUsage, PerformActionUsage, PortUsage, RequirementUsage, SatisfyRequirementUsage, UseCaseUsage, StateUsage and ViewUsage (ViewUsage has its own frame node). Drawn as rounded rectangles (border radius 10), 194x60 by default, white background and black border, with a wrapping top-centered multi-line label, list-layout compartments with growable free-form compartments and non-draggable children. Resizable and synchronized; subclasses can add a precondition. Palette: Delete from Model, Edit, sorted section tools, Show/Hide (plus Show content as Nested and Show content as Tree), quick access Delete from Diagram and Duplicate Element; unlike definitions there is no Drop from Diagram tool. · `AbstractUsageNodeDescriptionProvider.java`, `SDVNodeDescriptionProviderSwitch.java`, `general-view.adoc`
- **Requirement node shapes**: A Requirement Definition is drawn as a rectangle and a Requirement Usage as a rounded rectangle. · `requirement-management.adoc`
- **Wrapped node labels**: Labels of Usage nodes (e.g. Part) and Definition nodes (e.g. Part Definition) wrap, so nodes with long names can be resized narrower (v2025.4.0). · `2025.4.0.adoc`, `CHANGELOG.adoc` v2025.4.0
- **Usage nodes exclude actors, subjects and stakeholders**: Regular usage nodes are not created for usages that are actors, subjects or stakeholders (precondition not isActor/isSubject/isStakeholder); these get dedicated node descriptions because they need outside labels and aspect-ratio settings that conditional styles cannot provide. · `UsageNodeDescriptionProvider.java`
- **ActionUsage node excludes standard start/done**: The ActionUsage node is not used for the standard library "start" and "done" actions (not isStandardStartAction / isStandardDoneAction); those use the dedicated Start/Done action nodes. · `SDVNodeDescriptionProviderSwitch.java`
- **ReferenceUsage node**: A ReferenceUsage node description exists although ReferenceUsage is not in any palette section list; it is displayed, accepted by Drop from Diagram, and created by the New Reference tool. · `SDVDiagramDescriptionProvider.java`
- **PerformActionUsage and ExhibitStateUsage nodes**: Node descriptions exist for these although they are not in palette sections; they are created by dedicated tools (New Perform Action, New Exhibit State / New Exhibit Parallel State). · `SDVDiagramDescriptionProvider.java`
- **Actor node (stick figure)**: PartUsages that are actors are drawn as an actor.svg image node (default 41x92, keep aspect ratio, resizable) with the label outside at bottom center; it has no children, border nodes or palette tool sections, so nothing can be created inside it (v2024.9.0). The stick-figure image was reshaped without margins in v2026.7.0. · `ActorNodeDescriptionProvider.java`, `2024.9.0.adoc`
- **Stakeholder node**: PartUsages that are stakeholders get a dedicated "GV Node Stakeholder" node (candidates from getExposedStakeholders), drawn with the regular rounded usage style and given the full PartUsage palette and compartments, unlike actors. Since v2026.5.0 stakeholders are shown by default as separate nodes connected to their parent node (or in the stakeholders compartment). · `StakeholderNodeDescriptionProvider.java`, `2026.5.0.adoc`
- **Subject node**: ReferenceUsages that are subjects get a dedicated "GV Node Subject" node (candidates from getExposedSubjects) with the regular rounded usage style and compartments; its palette comes from the generic Usage case (Set as composite, Set as ref, compartment tools, Related Elements). Since v2026.3.0 subjects can be shown as their own nodes, as well as in the subject compartment, for CaseUsage, CaseDefinition, UseCaseUsage, UseCaseDefinition, RequirementUsage, RequirementDefinition and SatisfyRequirementUsage. · `SubjectNodeDescriptionProvider.java`, `2026.3.0.adoc`
- **Actor, stakeholder and subject node candidates**: Three backend queries over the ViewUsage's exposed elements feed these nodes: getExposedActors (PartUsages that are actors), getExposedStakeholders (PartUsages that are stakeholders) and getExposedSubjects (ReferenceUsages that are subjects), each applying the same exposure and view-filter rules as other nodes. · `DiagramQueryExposeService.java`, `ActorNodeDescriptionProvider.java`
- **Control nodes**: Custom nodes for the standard start action (28x28), done action (36x36), JoinNode and ForkNode (100x12 bars filled with actionGreen #466044), and MergeNode and DecisionNode (36x36), drawn inside action flow compartments. Their palettes offer "Remove Join", "Remove Fork", "Remove Merge" and "Remove Decision" respectively. A Decision, Fork, Join or Merge node at the top level of a diagram whose ViewUsage is typed General View is hidden by default. · `AbstractControlNodeActionNodeDescriptionProvider.java`, `JoinActionNodeDescriptionProvider.java`, `DecisionActionNodeDescriptionProvider.java`
- **Start and Done state nodes**: Custom Start State (28x28) and Done State nodes represent the standard start/done states inside state transition compartments. · `StartStateNodeDescriptionProvider.java`, `SDVDiagramDescriptionProvider.java`
- **Package node**: Drawn as a folder whose label carries the keyword `package` (manual). Package nodes accept every definition and usage kind, Namespace Imports and nested Packages. Elements created from a Package node's palette (Part, sub-Part, sub-Package, ReferenceUsage, Item...) appear only inside the package (a sub-part on the same level, with a composition edge); a Documentation created on a Package is shown beside it; creating an item in a sub-package keeps the parent package's existing items visible. In the General View a Package node reuses (and accepts as drops) every definition, usage and annotating (Comment, Documentation, TextualRepresentation) node, nested Packages, NamespaceImport and ReferenceUsage nodes; its palette has the background's six sections with one tool per section metaclass, plus New Exhibit State / New Exhibit Parallel State (Behavior), New Namespace Import / New Reference (Structure) and four "View as" tools (General View, Interconnection View, ActionFlow View, StateTransition View) that move the package into a new typed ViewUsage. A New Documentation tool was added to Package node palettes in v2025.12.0. Fixes: a Package created inside another Package is no longer also created at the diagram root (v2025.12.0), and an element created inside a sub-Package gives one node instead of two and no longer hides unrelated nodes (v2026.1.0). · `GVPackageTests.java`, `PackageNodeDescriptionProvider.java`, `GVSubNodeStructureCreationTests.java`
- **Annotating element nodes**: Documentation and Comment elements are drawn as note nodes whose label shows the element's body plus its declared name, with the keyword `doc` for Documentation and `comment` for Comment (manual). Dropping a part's Documentation or Comment from the Explorer shows it as a note (default bodies "add doc here" / "add comment here"). The General View also draws TextualRepresentation elements as note nodes (the third annotating kind, created with the section-less New Textual Representation tool). _(experimental)_ · `general-view.adoc`, `dropFromExplorer.cy.ts`, `SDVDiagramDescriptionProvider.java`
- **Package label ellipsis**: In the General View (and State Transition View), a Package label that does not fit ends with an ellipsis to show the name is truncated (v2025.4.0). · `2025.4.0.adoc`, `CHANGELOG.adoc` v2025.4.0
- **ConnectionDefinition node**: ConnectionDefinitions are drawn as nodes (v2025.4.0). Since v2026.3.0 the label reads «connection def» (it used to read «part def»), the node has attributes, doc, parts and ends compartments, and a new ConnectionDefinition starts with two connection ends named "source" and "target". · `2026.3.0.adoc`, `CHANGELOG.adoc` v2026.3.0
- **AllocationDefinition and AllocationUsage nodes**: Handled in the General View (Behavior section > New Allocation / New Allocation Definition) since v2024.5.0; a new AllocationDefinition starts with two ends named "source" and "target". Allocate edges are also displayed in the Action Flow View. · `2024.5.0.adoc`, `AllocateEdgeDescriptionProvider.java`
- **InterfaceDefinition default ports**: A new InterfaceDefinition node starts with two ports named "source" and "target" in its ends compartment, shown as 2 port border nodes. Its ports and ends compartments are hidden on creation; reveal them with the node's Manage Visibility action; more ports are added with New Port as end. · `2026.3.0.adoc`, `InterfaceDefinitionEndCompartmentNodeToolProvider.java`
- **Case and Use Case nodes**: UseCaseDefinition and UseCaseUsage (v2024.5.0, Analysis section > New Use Case / New Use Case Definition) and CaseDefinition and CaseUsage (v2024.11.0, New Case / New Case Definition) nodes, with documentation, subject, objective and actors compartments. · `2024.5.0.adoc`, `2024.11.0.adoc`, `CaseUsageActorsCompartmentNodeDescriptionProvider.java`
- **Occurrence nodes**: OccurrenceDefinition and OccurrenceUsage nodes (Behavior section > New Occurrence / New Occurrence Definition) since v2024.5.0. · `2024.5.0.adoc`
- **Concern Definition and Concern Usage nodes**: Concern Definitions and Concern Usages are drawn as nodes (v2025.2.0), created with Requirements-section tools or by dragging them from the Explorer onto the background. · `2025.2.0.adoc`
- **Satisfy Requirement Usage node**: Satisfy Requirement Usages are drawn as nodes (v2025.4.0), created with a Requirements-section tool or by dragging one from the Explorer onto the background. · `2025.4.0.adoc`
- **State and State Definition nodes**: State, StateDefinition and the other State Transition View concepts are available in the General View (Behavior section > New State / New State Definition) since v2024.7.0. · `2024.7.0.adoc`
- **ConjugatedPortDefinition support**: ConjugatedPortDefinition is handled in diagrams, the Explorer and the Details view (v2024.5.0) and its label shows its actual name instead of "null" (v2024.9.0). Creating a PortDefinition automatically creates its ConjugatedPortDefinition in an OwningMembership linked by a PortConjugation; the conjugated definition's name always mirrors the PortDefinition's name. · `ElementInitializerSwitch.java`, `2024.5.0.adoc`, `CHANGELOG.adoc` v2024.9.0

### Display rules

- **Node display rule**: An exposed element is displayed as a tree node when it has no graphical parent or is a directly owned member of its parent; inside a Package, elements not contained in a sub-package also qualify. ## SysML Interconnection View

### Creating and scoping the view
- **Interconnection View diagram**: shows the encapsulated structural contents of Usage elements (parts, properties, connectors, ports, interfaces); the user manual calls it an unsynchronized diagram. Created from the explorer context menu > New representation > Interconnection View (view id InterconnectionViewDiagram, domain sysml::Element), offered on a Package, Usage or Definition or any subtype (isSuperTypeOf check). History: first only on PartUsage, since 2024.5.0 on any Usage or Definition, in 2024.9.0 the separate for-Definition and for-Usage diagrams were merged into one with a single root node, and since 2025.12.0 also on Packages. The provider is only a registration stub: the diagram actually created is the shared standard diagram (SDV), default name 'view<N>'. On creation from the explorer, a non-ViewUsage element first gets a new ViewUsage (named after the representation) typed through a FeatureTyping by StandardViewDefinitions::InterconnectionView, and the General View description is rendered on it; a ViewUsage is used as is; the project is then persisted. - **Interconnection View node filtering**: any exposed element not indirectly nested under another exposed element is displayed as a node; AttributeUsages are never shown as tree nodes (attributes appear as nodes only in General Views); Packages and non-subject ReferenceUsages are shown unless indirectly nested. · `ViewFilterSwitch.java`
- **Root-level elements**: from the root Usage the view can display Usage parts, ports, and annotating elements (Documentation and Comment). _(experimental)_ · `interconnection-view.adoc`

- **View kind resolution**: every view-specific rule (tool availability, node filtering, compartment preconditions, connector handling) asks which standard view an element is shown in: a ViewUsage is classified by the qualified name of its first type (StandardViewDefinitions::GeneralView, InterconnectionView, ActionFlowView or StateTransitionView); an untyped ViewUsage counts as a General View; any other element takes the kind of the nearest ViewUsage among its graphical ancestors, defaulting to General View. ## Direct edit & label syntax

### Starting a direct edit on the diagram
- **Direct edit triggers (F2, typing, palette Edit)**: a node or edge label can be edited in three ways. Press F2 on a selected element: the editor opens with the editable text fully selected, and F2 works while the palette is open and after it closes, even when another text field has focus. Type any letter, digit, punctuation, symbol or mark character (special characters such as `=` or `$` included) without Ctrl/Meta: the editor opens starting with that character and the cursor at the end (`<` and `>` trigger it since Sirius Web 2024.9.0, so a short name `<id>` can be typed straight away; end-to-end tests type `=`, `$` and `~`). Typing does not trigger while another text field has focus, Alt or Shift alone does nothing, and Space (like any other whitespace) does not open the editor. Or use the palette's 'Edit' tool (id `edit`, `edit.svg` icon), shown both in the quick-access row and in the default 'Edit' section, only when the node description has a label edit handler or the edge description has a center label edit tool; it opens the editor on the client. When opened by typing, the typed character replaces the whole label (the server-computed initial text is ignored). The target is the first selected node's inside label, else its BOTTOM_MIDDLE outside label, else the selected edge's center label. With a node and an edge both selected the node wins, and when the selected node's label is not editable nothing opens (there is no fallback to a selected edge). Editing requires `labelEditable`/`centerLabelEditable` and an editable (not read-only) diagram. The editor state records the trigger (`keyDown`, `F2`, `palette`). A `doubleClick` trigger is declared but nothing sets it, and the renderer sets `zoomOnDoubleClick` to false, so double-clicking neither edits nor zooms. The SysON doc (experimental) describes these triggers as working on node labels in the representation editor. _(Sirius Web)_ · `useDiagramDirectEdit.tsx`, `PaletteDefaultToolsProvider.java`, `manage-labels-diagram.adoc`
- **Direct edit only where a label edit tool exists**: F2 or typing does not open direct edit on a node or edge label whose description defines no label edit tool. _(Sirius Web)_ · `CHANGELOG.adoc` v2024.3.0 (Sirius Web), `CHANGELOG.adoc` v2023.12.0 (Sirius Web)
- **Inline direct-edit input field**: a multiline text field (standard variant, small size) replacing the label content, as wide as the edited label's on-screen width divided by the zoom level (so it does not grow with zoom), with a minimum width of 130px, rendered in place of the label (so it sits at the label's location), marked `nodrag` so dragging inside it selects text instead of moving the node and clicking in the text moves the caret instead of opening the palette (fixed in 2024.3.0), a white (not transparent) background, autofocus, spellcheck off, placeholder 'Enter the new value', and full unicode input. Enter commits, Shift+Enter inserts a line break (multi-line labels), Escape cancels, and blur commits. An empty string is accepted as a value. When opened by typing, the cursor sits after the typed character. Opened by F2 or the palette, the field is empty until the server's initial text arrives, then filled and fully selected; when that text is empty the field stays empty. There is no unchanged-text check: Enter or blur without any change still sends `editLabel`, so SysON re-parses the same text (re-applying its keyword resets). Opening it closes the palette. The `editLabel` mutation saves the text and the editor closes on success, after which keyboard focus goes back to the edited node or edge so shortcuts keep working; on an error payload it stays open (a later blur does not resubmit). Messages carried by a success payload are toasted too. Server messages, or 'An unexpected error has occurred, please refresh the page' (network error on the save or on the initial-text query), are shown as toasts. _(Sirius Web)_ · `DiagramDirectEditInput.tsx`, `sirius-components-diagrams.json`, `CHANGELOG.adoc` v2024.1.0 (Sirius Web)
- **Server-computed initial direct-edit text**: label edit tools can define an Initial Direct Edit Label Expression, which computes the text placed in the editor (served by the `initialDirectEditElementLabel(labelId)` query). It can differ from the displayed label, for example the full textual syntax without values. The expression gets `self`, `view`, `diagram` and, on edges, `semanticEdgeSource`/`semanticEdgeTarget`; its result is used only when evaluation ends at WARNING or better. Without an expression (or on failure) the editor starts from the displayed label text. SysON sets it on every node, list item and border node label edit tool and on the binding, flow, interface, connection and composition edge tools, but not on the dependency and succession edge tools, which start from the displayed label. _(Sirius Web)_ · `ViewInitialDirectEditElementLabelProvider.java`, `diagram.graphqls`, `AbstractDependencyEdgeDescriptionProvider.java`
- **editLabel mutation**: `editLabel(labelId, newText)` applies a direct edit to a node or edge label and returns the refreshed diagram. Nodes declare `labelEditable` and edges `centerLabelEditable`. The backend finds the node owning the label id (else the edge, and which of its begin/center/end labels it is), runs the description's label edit handler with `self` (and, on edges, `semanticEdgeSource`/`semanticEdgeTarget`), and always reports a semantic change. Feedback messages raised by the handler (e.g. SysON's 'The qualified name used for the typing does not exist') come back inside the success payload, so the editor closes and they appear as toasts. A label id found on no node or edge returns an invalid-input ErrorPayload. An invalid value (an IllegalArgumentException from an edge handler) gives 'The value "X" is invalid'. _(Sirius Web)_ · `diagram.graphqls`, `sirius-components-collaborative-diagrams.properties`
- **Direct edit of edge begin, center and end labels**: an edge's center, begin and end labels can each have an edit tool. Edit Begin Label and Edit End Label tools may define an Initial Direct Edit Label Expression with `semanticEdgeSource`/`semanticEdgeTarget` variables. The changelog says a begin or end label is edited by double-click and the center label by F2 or typing. At v2026.11.0 double-click is not wired, so only the center label is reachable (F2, typing, palette Edit). _(Sirius Web)_ · `CHANGELOG.adoc` v2023.10.0 (Sirius Web), `CHANGELOG.adoc` v2023.3.0 (Sirius Web), `useDiagramDirectEdit.tsx`

### Direct-edit grammar: structure
- **Two grammar entry points (node vs list item)**: direct-edit text is parsed by an ANTLR grammar (`DirectEdit.g4`) with two top-level rules: `nodeExpression` for graphical nodes and edges, `listItemExpression` for compartment list items. A listener walks the parse tree and applies each recognized part to the edited element, so different node kinds (compartment item vs container) show and edit different levels of information. Editing can create and delete model elements on the fly; for example 'attr1' to 'attr1 : MyType' creates a FeatureTyping (and MyType if missing), and 'attr1 :>> attr2' back to 'attr1' deletes the Redefinition (ADR-001). · `DirectEdit.g4`, `DiagramMutationLabelService.java`, `001_support_direct_edit_in diagrams.adoc`
- **Node direct-edit syntax order**: `[abstract|variation|variant|timeslice|snapshot]* [ref] [<shortName>] [name] [[multiplicity]] [feature expressions]`. Prefix keywords count only when followed by whitespace (`abstract ` vs `abstractFoo`). · `DirectEdit.g4`
- **List-item direct-edit syntax order**: `[in|out|inout|abstract|variation|constant|derived|end]* [ref] [<shortName>] [name] [[multiplicity]] [ordered] [nonunique] [feature expressions]`. The `ordered`/`nonunique` suffixes must be preceded by whitespace. · `DirectEdit.g4`
- **Feature-expression ordering**: either (redefinition or subsetting, then an optional multiplicity) followed by (typing, then an optional multiplicity); or typing first, then subsetting or redefinition with an optional multiplicity; or a lone multiplicity. Only one of `:>` or `:>>` per edit. · `DirectEdit.g4`
- **Partial edition of labels**: since 2024.3.0, direct edit changes only the parts typed and keeps the others: 'newName' sets only the name, ': newType' a new type, ':> newType' a new subsetting/subclassification, ':>> newType' a new redefinition, '[newRange]' a new multiplicity. An omitted typing, subsetting, subclassification or redefinition operator leaves that relationship untouched. Keyword properties are different: an omitted keyword resets its property (abstract, variation, ref and portion kind on nodes; only direction, ordered and nonunique on list items, where the `abstract`, `variation` and `ref` prefixes can set their flag but omitting them leaves it unchanged, like `constant`, `derived` and `end`). That is why the user doc warns that, when editing a complex label such as 'someElementName[x]:someTypeName:>someElement', you must keep every written part or the corresponding value may be unset. · `DirectEdit.g4`, `2024.3.0.adoc`, `model-management.adoc`
- **Syntax errors logged, not shown**: ANTLR syntax errors are captured by `DiagramDirectEditErrorListener` and written to the server log at info level, never sent to the user. They never block the edit: whatever parts parse are applied. ANTLR's default console listener is not removed from the lexer or the parser, so the same messages also go to the server's standard error. · `DiagramDirectEditErrorListener.java`, `DiagramMutationLabelService.java`, `CHANGELOG.adoc` v2026.1.0
- **Direct-edit options restricting applied parts**: the listener honors the options `NAME_OFF`, `MULTIPLICITY_OFF`, `TYPING_OFF`, `SUBSETTING_OFF` and `REDEFINITION_OFF`, each skipping its part of the label. `TRANSITION_EXPRESSION_OFF` is declared but unused, and nothing passes `MULTIPLICITY_OFF` at v2026.11.0. These options implement the restricted edge edits described above. · `LabelService.java`, `DiagramMutationLabelService.java`
- **Direct edit excludes expression syntax**: since v2026.9.0 the grammar no longer parses or modifies expressions. Direct edit only updates labels and feature syntax, and expressions are created and changed with the dedicated expression tools. · `2026.9.0.adoc`, `CHANGELOG.adoc` v2026.9.0
- **Value expression ignored by direct edit**: for features with a value expression (e.g. an attribute with a default value), the part after `=` is left out of the initial direct-edit text and, per the changelog, is ignored if typed. Only the expression tools are meant to edit values, so that only valid, name-resolving expressions are accepted. In the v2026.11.0 grammar the name part ends at `:=` and ` default` but not at a plain `=`. · `CHANGELOG.adoc` v2026.7.0, `expressions.adoc`, `DiagramQueryLabelService.java`
- **Constraint `{ ... }` part ignored by direct edit**: when a ConstraintUsage node or list item is direct-edited (including renaming a constraint row), everything from the first `{` to the end is stripped before parsing, so the expression shown in braces cannot be changed through the label. The strip uses a single-line pattern: if a line break (Shift+Enter) follows the `{`, nothing is stripped and the brace text goes to the parser. · `DiagramMutationLabelService.java`, `CHANGELOG.adoc` v2026.7.0, `ExpressionsControllersIntegrationTests.java`

### Direct-edit grammar: names and short names
- **Set or clear the declared name**: the name part sets `declaredName` from the original text, with inner spaces kept and outer spaces stripped (typing 'someName' renames the element). A blank name sets `declaredName` to null. The name is stored verbatim (KerML unrestricted names without quotes, e.g. 'My new flashlight'): single quotes typed around it are not stripped and become part of the declared name. Typing only other parts (e.g. '<1.1>' or ': T') leaves the name unchanged. Since 2024.7.0 names may contain whitespace, quotes and special characters, and names containing reserved keywords or starting with one (e.g. 'abstractPart') work. · `DiagramDirectEditListener.java`, `DiagramDirectEditListenerTest.java`, `CHANGELOG.adoc` v2024.7.0
- **Tokens that end the name part**: the name may contain any token except `:`, `:>`, `::`, `:>>`, `:=`, `[`, ` default`, ` ordered` and ` nonunique`, which end it ('default' stays part of a name unless a space precedes it: 'default Attr1' and 'defaultAttr1' are names, while 'Attr1 default' gives the name 'Attr1' and the rest is dropped). The lexer also defines a `const ` prefix token that no rule uses, so 'const x' is simply a name. The user doc gives a different list: `:`, `:>`, `::>`, `:>>`, `=`, `:=`, `[`, ` constant`, ` default`, ` end`, ` nonunique`, ` ordered`, ` variation`; it also wrongly says `::>` sets a redefinition and `:>>` a reference subsetting. To put such tokens in a name, use the 'Declared Name' text field of the Details view. · `DirectEdit.g4`, `model-management.adoc`
- **Short name `<...>`**: since 2024.11.0, `<id>` before the name sets `declaredShortName` (e.g. '<1.1>' keeps the name and sets the short name). An empty `<>` clears it (sets it to an empty string). · `DiagramDirectEditListener.java`, `model-management.adoc`, `CHANGELOG.adoc` v2024.11.0
- **Quoted names and qualified references**: references in feature expressions are qualified names, built from segments separated by `::`. The lexer recognizes single-quoted names (`'...'`) and identifiers `[a-zA-Z_][a-zA-Z_0-9-]*`. Name matching accepts a quoted query even though the quotes are not stored in the model. · `DirectEdit.g4`, `ElementUtil.java`

### Direct-edit grammar: keywords
- **Prefix keywords in any order**: list items accept `in`, `out`, `inout`, `abstract`, `variation`, `constant`, `derived` and `end` in any order; graphical nodes accept `abstract`, `variation`, `variant`, `timeslice` and `snapshot`. Since 2024.9.0, only keywords the label can display are editable. The `constant` prefix replaced `readonly` when the 2025 metamodel alignment renamed isReadOnly to isVariable and added isConstant. A keyword not accepted by the rule in use is not an error: since the name part accepts any token, it simply becomes part of the name (e.g. 'constant x' typed on a graphical node renames it 'constant x', and 'timeslice p' on a list item gives the name 'timeslice p'). · `DirectEdit.g4`, `2024.9.0.adoc`, `CHANGELOG.adoc` v2025.8.0
- **Prefix `abstract`**: `abstract ` sets isAbstract=true on a Usage. When it is absent from a node label edit, isAbstract resets to false unless the usage is a variation (a variation is always abstract); on a compartment list item the reset is not applied, so removing `abstract ` there does not make the usage concrete. On a Definition node the keyword is accepted but neither sets nor clears isAbstract, and a definition's prefilled text shows no prefix keyword at all (only usages get prefixes), so a definition's abstractness cannot be changed by direct edit. · `DiagramDirectEditListener.java`, `DiagramQueryLabelService.java`
- **Prefix `variation`**: `variation ` sets isVariation=true and isAbstract=true on a Usage; when absent from a node label edit, isVariation resets to false (list items never reset it). On Definitions it is parsed but has no effect, and their prefilled text never shows it (the «variation» line appears only in the displayed label). · `DiagramDirectEditListener.java`, `DiagramQueryLabelService.java`
- **Prefix `variant` (accepted, no effect)**: the node grammar accepts a `variant ` prefix (keyword followed by whitespace), but no handler exists, so it changes nothing. Variant status comes from VariantMembership or a variation parent and only shows in labels. · `DirectEdit.g4`, `DiagramDirectEditListener.java`
- **Prefix `timeslice` / `snapshot`**: since 2026.3.0, on node labels `timeslice ` or `snapshot ` sets the portionKind of an OccurrenceUsage or subtype (PartUsage, ItemUsage...) to TIMESLICE or SNAPSHOT (e.g. 'timeslice part1'). When neither is present, portionKind is unset ('part1' removes it). · `DiagramDirectEditListener.java`, `GVDirectEditTests.java`, `CHANGELOG.adoc` v2026.3.0
- **Direction prefixes `in` / `out` / `inout`**: on compartment list items (including port rows), `in `, `out ` or `inout ` sets the Usage direction (the Flashlight tutorial renames a port to 'out dcPwrOutPort'). On port border nodes and graphical nodes, which use the node rule, the keyword is not parsed as a direction and stays in the name. On list items, a missing prefix clears the direction (null). Directed items and ports then show the prefix in their labels ('in onOffCmd', 'out lightOut'). · `DiagramDirectEditListener.java`, `flashlight.adoc`, `DirectEdit.g4`
- **Prefixes `constant`, `derived`, `end` (set-only)**: on list items, `constant `, `derived ` and `end ` set isConstant, isDerived and isEnd to true on a Usage. Nothing resets them, so removing the keywords does not clear the flags (contrary to the general rule that omitted keywords reset). A Cypress test, skipped at v2026.11.0, still expects that editing 'variation end myAttribute ordered nonunique' back to 'myAttribute' clears Is Variation and Is End; the code only resets ordered and nonunique there. · `DiagramDirectEditListener.java`
- **`ref` keyword (referential vs composite)**: since 2024.9.0, `ref ` sets isComposite=false on a Usage (a reference). When `ref` is absent from a node label edit, isComposite goes back to true; on a compartment list item it is not reset, so deleting `ref ` from a row leaves the usage referential. This applies to every Usage, including attributes and ConnectionDefinition ends, whose prefilled label never shows `ref`; Definitions are unaffected. Example: 'ref battery[2]' gives a referential part with multiplicity 2. · `DiagramDirectEditListener.java`, `flashlight.adoc`, `CHANGELOG.adoc` v2024.9.0
- **Suffixes `ordered` / `nonunique`**: on list items, ` ordered` (after the multiplicity) sets isOrdered=true and ` nonunique` sets isUnique=false. When absent, isOrdered resets to false and isUnique to true. · `DiagramDirectEditListener.java`, `DirectEdit.g4`
- **Feature modifier keywords (user doc)**: the doc lists ` constant`, ` default`, ` end`, ` nonunique`, ` ordered` and ` variation` (each preceded by a space) as marking a Feature constant, its value default, an end, non-unique, ordered or a variation. At v2026.11.0, `constant`, `end` and `variation` are prefixes (keyword then space), `ordered`/`nonunique` are list-item suffixes, and ` default` only ends the name, with no effect. _(experimental)_ · `model-management.adoc`, `DirectEdit.g4`

### Direct-edit grammar: multiplicity
- **Multiplicity `[l..u]`**: accepts `[n]` (single digits included, since 2024.7.0), `[l..u]`, `[*]`, `[l..*]` (e.g. `[x]`, `[1..x]`, `[x..*]`) and `[]`. Bounds are integers (negative allowed) or `*`, in either position (the grammar also accepts `[*..5]`, giving a LiteralInfinity lower bound); integers are parsed as 32-bit values, so a bound beyond that range makes the edit fail on the server. It creates or reuses a MultiplicityRange in an OwningMembership, with LiteralInteger or LiteralInfinity bounds; a bound that was another kind of expression (e.g. a feature reference) is replaced by the typed literal. A single bound removes any second bound. Works on graphical nodes, list items, relationships (composition edges), and elements shown as graphical nodes. · `DiagramDirectEditListener.java`, `DirectEdit.g4`, `model-management.adoc`
- **Remove a multiplicity with `[]`**: since 2026.3.0, typing `[]` deletes an existing multiplicity (the grammar accepts an empty multiplicity value). · `DiagramDirectEditListener.java`, `2026.3.0.adoc`, `CHANGELOG.adoc` v2026.3.0
- **Multiplicity before or after typing/subsetting/redefinition**: since 2026.1.0, the multiplicity may follow the name or the typing, subsetting or redefinition part: `part p1[4] :> p2`, `part p1 :> p2[4]`, `part p6 :>> p1[4]` and `part p1 : DefA[4]` are all valid. Either form updates the cardinality of the first element of the expression. · `DirectEdit.g4`, `model-management.adoc`, `CHANGELOG.adoc` v2026.1.0

### Direct-edit grammar: typing, specialization, redefinition
- **Typing `: Type`**: `: Name` (simple, qualified with `::`, short name or qualified short name) types a Usage; on a Definition the typing part is ignored. The name resolves first through namespace scoping from the element (or its owning namespace), then by a global search of all resources by name or short name; with several candidates the closest in scope wins. An import of the type's namespace is added when needed. The existing FeatureTyping is updated (isImplied cleared when the type changes) or a new one is created, and any ConjugatedPortTyping is removed; subsettings, redefinitions and subclassifications follow the same rule (the first existing one is retargeted and loses isImplied, else one is created). ': Type' types without renaming. The type name is read with its inner spaces, so an unquoted name with spaces (': My Type') resolves, or is created, as 'My Type'. Qualified names that go through a namespace publicly importing the target resolve: 'myAttribute : ISQ::MassValue' types with ISQBase::MassValue (2024.9.0). · `DiagramDirectEditListener.java`, `UtilService.java`, `GVDirectEditTests.java`
- **Typing to an unknown simple name creates the definition**: when a simple type name after `:` doesn't resolve, SysON creates a Definition whose metaclass is the usage's with 'Usage' replaced by 'Definition' (PartUsage to PartDefinition, ItemUsage to ItemDefinition). It initializes and names the definition, puts it in an OwningMembership of the nearest containing Package, and types the usage with it. In the Batmobile tutorial, 'wheels[4] : Wheel' creates the Part Definition 'Wheel'. If no such metaclass exists (ReferenceUsage, ExhibitStateUsage, PerformActionUsage, AcceptActionUsage, EventOccurrenceUsage, SatisfyRequirementUsage...), no definition is created and the usage stays untyped, but an empty OwningMembership is still added to the Package. The same auto-creation for unresolved `:>`/`:>>` targets (below) also relies on a containing Package: an element with no Package ancestor (e.g. owned directly by a root Namespace) makes the edit fail on the server. The user doc says the new type is created 'within the same parent container as the selected element'; the code puts it in the nearest containing Package instead. · `DiagramDirectEditListener.java`, `model-management.adoc`, `batmobile.adoc`
- **Typing tests (simple, qualified, short, qualified short)**: backend tests type a part with a part definition by simple name, by full qualified name, by short name, by qualified short name, and by short name with two candidates in scope (the best candidate wins). They also check that the multiplicity can come with a subsetting, a redefinition or a feature typing in one edit, and that a redefinition target with the same name as the redefining part resolves to the other part. · `GVDirectEditTests.java`, `DiagramDirectEditListenerTest.java`
- **Error: qualified typing name not found**: an unresolvable qualified type name (with `::`) creates nothing and shows the error notification 'The qualified name used for the typing does not exist'. · `DiagramDirectEditListener.java`
- **Conjugated port typing `: ~PortDef`**: typing a port with `~PortDef` creates or updates a ConjugatedPortTyping (type, typedFeature, conjugatedPortDefinition) and removes the plain FeatureTyping. An unresolvable `~` name shows 'The conjugated port def used for the typing does not exist' and creates nothing; an unresolvable qualified one (`~Pkg::Def`) shows the qualified-name typing message instead, since that check comes first. · `DiagramDirectEditListener.java`
- **Standard-library type resolution with automatic import**: a library type or feature name resolves in the standard libraries, and the needed import is added automatically. 'actualSpeed : SpeedUnit' adds an import of ISQSpaceTime; 'actualweight :> mass' uses 'mass' auto-imported from ISQBase. 'part : ISQBase::MassValue', the aliased 'ISQ::MassValue' and bare 'MassValue' resolve to ISQBase::MassValue, add 'import ISQBase::*' and create no definition. 'mass :> ISQ::mass' and 'fov:Real' are accepted. · `batmobile.adoc`, `flashlight.adoc`, `directEditTests.cy.ts`
- **Short names in qualified names**: since 2025.12.0, qualified names typed in direct edit can use short names (e.g. `LA::CommonBattery` for `Drone_LogicalArchitecture::CommonBattery`). If several elements share a short name, the best candidate in scope wins; when a short name and a declared name of two different elements clash, the declared name wins. · `2025.12.0.adoc`, `CHANGELOG.adoc` v2025.12.0
- **Subsetting `:> feature` on usages**: on a Usage, `:> Name` resolves a Feature and sets or creates a Subsetting (not a Redefinition or ReferenceSubsetting), adding an import when needed. `name :> other` subsets and renames, `:> other` subsets without renaming, and renaming alone keeps the existing subsetting. A simple name that doesn't resolve creates a usage of the same metaclass in the nearest Package (e.g. 'p1 :> aNewPart'); unlike definitions created by typing, that usage (and the one created for `:>>`) is only named, without the element initializer. An unresolvable qualified name shows 'The qualified name used for the subsetting does not exist'. 'frontRightWheel :> wheels' gives a subsetting edge between part usages. · `DiagramDirectEditListener.java`, `DiagramDirectEditListenerTest.java`, `batmobile.adoc`
- **Subclassification `:> Definition` on definitions**: on a Definition, `:> Name` resolves a Classifier and sets or creates the Subclassification, adding an import when needed (e.g. 'Batmobile :> Vehicle' gives a specialization edge between part definitions). A simple name that doesn't resolve creates a definition of the same metaclass in the nearest Package. An unresolvable qualified name shows 'The qualified name used for the subclassification does not exist'. The user doc puts it as: `:>` makes a Subsetting when both elements have the same type, otherwise a Specialization. · `DiagramDirectEditListener.java`, `model-management.adoc`, `batmobile.adoc`
- **Redefinition `:>> feature`**: `:>> Name` resolves a Feature and sets or creates a Redefinition, adding an import when needed. When the redefining usage has the same name as the target, it is temporarily renamed during lookup so it doesn't resolve to itself. A simple name that doesn't resolve creates a usage of the same metaclass in the nearest Package. An unresolvable qualified name shows 'The qualified name used for the redefinition does not exist'. Example: 'bulletProofWheels[4] :>> wheels' sets multiplicity 4 and shows a 'redefines' edge to 'wheels'. · `DiagramDirectEditListener.java`, `model-management.adoc`, `batmobile.adoc`
- **Delete a part by leaving its operator empty**: a trailing operator with nothing after it deletes that part. `:` deletes the FeatureTyping ('newName :'), `:>` the Subsetting (usages) or Subclassification (definitions), `:>>` the Redefinition, `[]` the multiplicity, and `<>` the short name. The dangling `:`, `:>` or `:>>` deletes only when it is the first feature part after the name (the parser then reports a no-viable-alternative error on it); after another part (e.g. 'p : T :>') nothing is deleted. Each deletion is skipped when the matching option (TYPING_OFF, SUBSETTING_OFF, REDEFINITION_OFF) is set, so restricted edge edits cannot delete those relationships. Partial edits that delete information were fixed in 2024.11.0. · `DiagramDirectEditListener.java`, `DiagramDirectEditListenerTest.java`, `CHANGELOG.adoc` v2024.3.0

### Label text serialization
- **Display mode vs text-compliant serialization**: values and expressions in diagrams serialize in two modes. Display mode uses simple names and no string escaping. Direct-edit (text-compliant) mode uses the shortest resolvable names and escapes backslash and double quote. For example, a value entered as 'RootPackage::p1::p1_1::x3 - RootPackage::p1::p1_1::x2 - 4.5' shows in the attribute's label as 'x1 = x3 - x2 - 4.5', even when the names point to attributes of another part than the default ones in scope. · `DiagramQueryLabelService.java`, `SimpleNameDeresolver.java`
- **Short names for units in display**: in display mode, a referenced element with a short name is shown by it when the reference sits inside a '[' bracket operator expression, i.e. a unit (e.g. '5 [kg]'). Otherwise it is shown by its name. · `SimpleNameDeresolver.java`

### Label rendering (platform)
- **Label overflow strategies**: labels have an overflowStrategy of NONE, WRAP or ELLIPSIS. NONE keeps the label on one unwrapped line at its natural width, which drives the node's minimum width. WRAP wraps on several lines (word breaking, overflow hidden) and ELLIPSIS truncates one line with '...'; both are constrained to the node width (or the style's maxWidth) and don't affect node size. All edge labels use WRAP; SysON's descriptions use WRAP and ELLIPSIS. _(Sirius Web)_ · `Label.tsx`, `convertLabel.ts`, `layoutNode.ts`
- **Label box content and styling**: labels render optional icons before the text (a list of icon URLs drawn stacked on top of each other at 16x16, with a right margin), keep explicit line breaks (multi-line labels), and can have a fixed width/height and their own background and border colors. - **Label header separators**: an inside label flagged to display a header separator draws a line below itself (header at top) or above (header at bottom), styled by its header separator style (the node's border style, full width). - **Outside labels**: nodes can carry outside labels at BOTTOM_BEGIN, BOTTOM_MIDDLE or BOTTOM_END. ### Backend: parsing and semantics
- **Which elements hold expressions**: an element is an expression definition if it is an Expression but neither a Usage nor a BooleanExpression. A top-level expression has no expression ancestor. Through text, an expression attaches as a FeatureValue of a Feature, the guard of a TransitionUsage, or the result expression of a Function or Expression (e.g. a ConstraintUsage). SuccessionAsUsage is supported since 2026.9.0 (expression creation and editing on successions fixed, e.g. editing a succession's feature value from the succession). The user doc lists the supported elements as Attributes, Constraints, Successions and Transitions. "Can contain an expression" is true for every Feature (the only compatible ownership is a FeatureValue), so New Expression is offered on parts, ports, items and successions as well as attributes, constraints and transitions. A single expression is found when exactly one candidate is owned directly or through FeatureValues. When an element owns several candidate expressions (ambiguous), no Edit or Delete expression entry is offered for it and the New expression entry stays available. · `MetamodelQueryElementService.java`, `SysideExpressionEditor.java`, `CHANGELOG.adoc` v2026.9.0
- **Parsing through context-specific templates**: before parsing with the SysIDE CLI, the text is wrapped in a template under a random UUID name, by the first matching case. A TransitionUsage gets it as the guard of 'state <u> { entry action init; state off; transition first init if <expr> then off; }'. A Function or Expression (including ConstraintUsage) gets 'constraint def <u> { <expr> }'. Any other Feature gets 'attribute <u> = <expr>;'. Any other parent gets an empty template, so nothing is created. The guard TransitionFeatureMembership, the result expression membership or the FeatureValue is then extracted into the parent; names are resolved. · `SysideExpressionEditor.java`, `ExpressionsControllersIntegrationTests.java`
- **All-or-nothing validation (warnings count as errors)**: an expression is created or replaced only when parsing and transformation produce no WARNING or ERROR and yield an expression. Otherwise every element added to the model is rolled back in reverse order, nothing changes, and the messages are returned in an ErrorPayload (unlike 'New objects from text', which keeps partial results). By design, malformed expressions are never stored, and the original formatting (whitespace) is not kept once parsed. Parser reports are mapped by severity to INFO, WARNING or ERROR messages (other severities are dropped); after a failure the dialog keeps the typed text so it can be fixed. · `SysideExpressionEditor.java`, `ASTTransformer.java`, `expressions.adoc`
- **Edit replaces in place**: editing parses the text into a new expression, detaches its new owning relationship, and puts the new expression into the old one's owning relationship at the same index, removing the old one. The owning FeatureValue or membership is kept, but the expression gets a new identity and may change type (e.g. LiteralBoolean 'true' to OperatorExpression 'value < limit'). For a non-Feature relationship target (e.g. a FeatureValue), its owning element is the parse context. An invalid new value leaves the old one unchanged. · `SysideExpressionEditor.java`, `EditExpressionEventHandler.java`, `ExpressionsControllersIntegrationTests.java`
- **One expression per element**: creating an expression on an element that already has a single one fails with 'The parent element already has an expression'. An unknown or non-Element parent returns not-found. · `CreateExpressionEventHandler.java`
- **Delete semantics**: deleting finds the element's single expression (or the element itself if it is one) and removes it from the model with DeleteService (deleteFromModel) as a semantic change, together with its owning relationship (attribute value, assume constraint in a concern, transition guard). If none is found, a not-found error is returned. · `DeleteExpressionEventHandler.java`, `ExpressionsControllersIntegrationTests.java`
- **Feature-value flag semantics**: `properties.featureValue {isDefault, isInitial}` sets the flags on the FeatureValue owning the new expression; a null field leaves the current value unchanged. Flags passed on creation are stored for attributes and ignored for constraints. When read, the flags come from the owning FeatureValue: of the selected Expression, of the selected FeatureValue itself, or, for a Feature other than TransitionUsage, Succession, Function or Expression, of its single expression, else its first owned FeatureValue, else false/false. Other elements return no flags, so the checkboxes are hidden. · `ExpressionTextualRepresentationEventHandler.java`, `FeatureValueExpressionPropertiesInput.java`, `SysideExpressionEditor.java`
- **Expression textual representation**: expressions are turned to text by the SysML serializer with '\n' line separators, tab indentation, shortest resolvable (file-name deresolved) names and no escape characters. This text feeds constraint labels, edge begin labels, the Explorer, the dialog and the Details section. · `MetamodelQueryElementService.java`
- **Serializer operator coverage**: binary/unary operators `| & xor .. == != === !== < > <= >= + - * / % ^ ** ~ not`; classification (`istype`, `hastype`, `@`, `as`); bracket `[` units; sequences `,`; conditional binary (`??`, `and`, `or`, `implies`); `meta` casts; feature chains `a.b`; invocations. Unary `+ - ~` are written without a space, `not` with one. · `SysMLElementSerializer.java`
- **Serializer literal formats and unsupported expression kinds**: literals print as `true`/`false`, integers, reals always with a decimal part (5 prints as '5.0' so it is not re-read as an integer), `*` for infinity, `null` for a NullExpression and KerML-quoted strings. Function-typed invocations print as 'Fn(args)', and trigger invocations as their kind keyword (`when`, `at`, `after`) followed by the argument. CollectExpression, SelectExpression, MetadataAccessExpression and other function-operation invocations are not handled: they print as empty text and a 'not handled yet' warning goes to the serializer's callback (discarded for the Explorer, Details and dialog text, logged at info level for diagram labels), so such expressions show blank in labels, the Explorer, the Details view and the dialog prefill. · `SysMLElementSerializer.java`
- **Legacy constraint-expression grammar rule**: `DirectEdit.g4` still has a `constraintExpression` rule. It covers binary operators (`** * / % xor + - | & .. == != === !== < > <= >=`), bracket access `x[...]` (units, as a '[' operator), parentheses, literals and dotted feature chains. The listener builds OperatorExpression trees with 'x'/'y' parameters: Integer to LiteralInteger, digits.digits to LiteralRational, true/false to LiteralBoolean, double-quoted strings to LiteralString with the quotes stripped, a name to a FeatureReferenceExpression, and 'a.b.c' to a FeatureChainExpression. The constraint content is then replaced by a ResultExpressionMembership. Tests cover inputs such as '1 >= 2', 'myAttribute >= 1 [nm]', 'subject >= 1' and 'feature1.feature2.feature3 >= 1'. At v2026.11.0 only tests call this rule. · `DirectEdit.g4`, `DiagramDirectEditListener.java`, `DiagramDirectEditListenerTest.java`

### GraphQL API
- **createExpression mutation**: `createExpression(input: {id, editingContextId, parentElementId, expressionText, properties?})` parses the text and adds the expression to the parent. It returns `CreateExpressionSuccessPayload {id, newExpressionId, messages}` or `ErrorPayload` (already has an expression, not found, parse messages). · `syson-import.graphqls`, `CreateExpressionEventHandler.java`, `MutationCreateExpressionDataFetcher.java`
- **editExpression mutation**: `editExpression(input: {id, editingContextId, elementId, newExpressionText, properties?})` takes the id of a top-level Expression or of an element owning exactly one expression and replaces it. It returns `EditExpressionSuccessPayload {id, newExpressionId, messages}`, `ErrorPayload` with the messages, or not-found. · `syson-import.graphqls`, `EditExpressionEventHandler.java`, `ISysMLExpressionEditor.java`
- **deleteExpression mutation**: `deleteExpression(input: {id, editingContextId, parentElementId})` deletes the single expression held by the element and returns `SuccessPayload`, or `ErrorPayload` with the standard not-found message. · `expressions.graphqls`, `MutationDeleteExpressionDataFetcher.java`, `DeleteExpressionInput.java`
- **Expression textual representation query**: `EditingContext.expressionTextualRepresentation(elementId): ExpressionEditorState {textualRepresentation, featureValueProperties {isDefault, isInitial}}` returns the text of a top-level Expression, or of the single expression owned by the given element (an empty string when there is none), together with the feature-value properties used to prefill the dialog (null when the element does not support them, which hides the checkboxes). An unknown element id is not an error: it returns an empty text and null properties. · `expressions.graphqls`, `ExpressionTextualRepresentationEventHandler.java`, `FeatureValueExpressionPropertiesPayload.java`
