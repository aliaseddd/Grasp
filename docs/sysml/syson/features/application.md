## App shell, navigation, theming & notifications

### Navigation bar
- **Navigation bar layout**: every page (project browser, new/upload project, project settings, libraries, library display, error page, project editor) starts with a navigation bar: a 4px colored strip (palette navigationBar.border) above a dense AppBar (min height 36px, palette navigationBar.background) laid out as a 3-column grid. Left: home icon, then left contributions. Center: page-specific content such as the project or library title. Right: right contributions such as the omnibox button, then the navigation menu button. _(Sirius Web)_ · `NavigationBar.tsx`, `NavigationBarExtensionPoints.tsx`
- **Homepage action (SysON logo button)**: the leftmost navigation-bar item, on every page that has the bar, is an icon button showing the SysON logo instead of Sirius Web's Sirius icon. It is wrapped in a router link to '/', which redirects to /projects, the Projects browser and homepage. Its tooltip reads 'Back to the homepage' (the same text as Sirius Web's default), and hovering darkens the button background slightly (emphasize of the secondary color). The docs list it as the 'Homepage' action. · `SysONNavigationBarIcon.tsx`, `homepage-action.adoc`, `NavigationBarIcon.tsx`
- **SysON logo icon**: a custom 64x64 SVG brand mark (a three-faced isometric cube drawn with three paths) that inherits the current text color. It is used in the navigation bar. · `SysONIcon.tsx`
- **Navigation bar menu button (hamburger)**: SysON replaces Sirius Web's default menu trigger, a Help (question-mark) icon, with a classic hamburger (Menu) icon button (data-testid 'user-menu') at the top right of the navigation bar. Hover slightly emphasizes the background. It opens the navigation bar menu. · `SysONNavigationBarMenuIcon.tsx`, `SysONExtensionRegistry.tsx`, `CHANGELOG.adoc` v2025.4.0
- **Navigation bar menu (Libraries / Projects / Help)**: the dropdown opened from the menu button, available on every page, holds in order:
  - an optional header contribution;
  - 'Libraries' (FileCopy icon), which routes to /libraries, the published-library browser, and is shown only when the viewer has the libraries canList capability (the libraries page itself redirects to /errors/404 without it);
  - 'Projects' (Folder icon), which routes to /projects and is shown only when the viewer has the projects canList capability;
  - any extension-contributed entries;
  - 'Help' (Help icon), always placed last (after any contributed entries, since Sirius Web 2024.9.0), which opens the help URL in a new tab.

  SysON's 2025.4.0 release notes still call it the 'help' menu in the top right corner, the place to reach the libraries page. The menu (navigationbar-menu, entries libraries-link and projects-link) is anchored to the menu button and closes on click-away or Escape. Its entries have no close handler of their own: Libraries and Projects are router links, so the menu disappears with the page they leave, and choosing Help (rel noopener noreferrer) opens the new tab while the menu stays open on the original page. Integrators can replace the menu container, header, trigger icon, help URL and add entries through extension points. _(Sirius Web)_ · `NavigationBarMenu.tsx`, `NavigationBarMenuExtensionPoints.tsx`, `libraries-action.adoc`
- **Help action (SysON documentation link)**: the 'Help' menu entry opens the online help in a new browser tab (target _blank, noopener). Integrators can customize the URL through the help-URL data extension. Sirius Web's default is https://eclipse.dev/sirius/sirius-web.html; SysON sets it to https://doc.mbse-syson.org. · `index.tsx`, `help-action.adoc`, `NavigationBarMenu.tsx`
- **Editor toolbar groups**: the docs describe the project editor's top toolbar in groups. SysON's editor page lists three: Homepage, Project Actions (labeled with the project name) and an Actions menu. Sirius Web's workbench page lists four: Homepage (back to the home screen), Project Actions (shown with the project name), Omnibox (run commands and search elements) and Help (documentation, support and other resources). SysON's homepage page describes the project browser's toolbar in three groups: Homepage, Command Palette (project-level commands such as creating a blank project or searching elements across projects) and Links (Projects, Libraries, Help). _(Sirius Web)_ · `workbench.adoc`, `editor.adoc`, `homepage.adoc`
- **Project title and project menu in the editor navigation bar**: on the edit-project page, the center of the navigation bar shows the project name (navbar-title) as a one-line h6, truncated with an ellipsis after 100 characters. The title area is compact and the menu icon is aligned with it. A small white vertical-dots ('more') button next to the title opens the project menu (navbar-contextmenu) with, in this order:
  - Rename (rename; needs canRename)
  - Share (share-project; always shown)
  - Duplicate (duplicate; needs canDuplicate): while it runs a 15px spinner replaces the icon and the entry is disabled; on success the browser does a full page load of /projects/<newId>/edit
  - Download (download-link; needs canDownload): a plain link to /api/projects/<id> (plus ?name=<name> for a named editing context)
  - any entries contributed through the editProjectNavbarMenu#entry extension point
  - Settings (project-settings-link; needs settings.canView)
  - Delete (delete; needs canDelete): opens the delete-project dialog, and after a successful deletion the page redirects to /projects

  Entries the user lacks the capability for are not rendered. The whole menu can be wrapped or replaced through editProjectNavbarMenu#container (Sirius Web 2024.11.0). The title updates live through the projectEvent subscription when a ProjectRenamedEventPayload arrives, e.g. after another user renames the project. _(Sirius Web)_ · `EditProjectNavbarContextMenu.tsx`, `ProjectTitle.tsx`, `DuplicateProjectMenuItem.tsx`

It keeps the core's 12px base font, responsive sizes and h1-h6/subtitle/body settings: h1 3.42rem, h2 2.5rem, h3 2.142rem, h4 1.7rem (all weight 400); h5, h6, subtitle1 and subtitle2 bold (700); body1/body2 weight 400 with line heights 1.5/1.43.
  - Primary and secondary: main #292253 for both; primary dark #64669B, primary light #534E75; secondary dark #64669B, secondary light #D2D3D9.
  - Text: #292253, disabled #29225354.
  - Status: error #DE1000, success #43A047, warning #FF9800, info #2196F3, the same as Sirius Web.
  - Surfaces: divider #E0E0E0; left/right side navigation backgrounds #E8E9F0; navigation bar background #292253 with a yellow #FBBF52 top border strip; view (header) background #F1F0F6.
  - States: selected color #8321FF; action hover #A1A4C436; action selected #A1A4C460; disabled background #E0E0E0.
  - Components: the AppBar uses the secondary color; MUI Avatars default to the primary color #292253 (no avatar is rendered by the default Sirius Web/SysON UI, so this only affects contributed components); tooltips have a black background.
  - Links: unlike Sirius Web's theme (magenta #BE1A78 and navy), SysON's does not underline links only on hover.

  The core fallback uses white navigation backgrounds, a black navigation bar and a gray selected color. · `sysonTheme.ts`, `index.tsx`, `theme.ts`
- **Theme color tokens for navigation bar, selection and toasts**: the platform theme defines dedicated palette entries for the navigation bar (border, background), selected elements (selected) and toast messages (success, warning and info, each with main/dark/light). _(Sirius Web)_ · `CHANGELOG.adoc`, `siriusWebTheme.ts`
- **Snackbar toast color**: SysON's theme sets a #64669B background on MUI SnackbarContent. The app's toasts are notistack 3 snackbars, though, which do not use SnackbarContent; only Sirius Web's unused single-Toast component does. So SysON's toasts are colored by variant like Sirius Web's: default #292253 (primary), success #43A047, error #DE1000, warning #FF9800, info #2196F3. · `sysonTheme.ts`, `ToastProvider.tsx`, `Toast.tsx`
- **Menus and tooltips work in full-screen mode**: both the SysON and Sirius Web themes mount MUI Menus and Tooltip poppers into document.fullscreenElement when one exists, otherwise into document.body. Context menus and tooltips therefore stay visible while an element such as a diagram is shown full screen. _(Sirius Web)_ · `sysonTheme.ts`, `siriusWebTheme.ts`
- **Roboto font**: the app bundles and loads the Roboto font in weights 300, 400, 500 and 700, which the theme uses, so every machine renders the UI identically. _(Sirius Web)_ · `index.tsx`, `CHANGELOG.adoc`
- **Server startup banner**: when the backend starts, the console prints a SysON ASCII-art logo followed by ':: Spring Boot ::' and the Spring Boot version in green, instead of Spring's default banner. · `banner.txt`
- **Label ellipsis and length limit**: long representation, document and project labels are shown with an ellipsis in the UI and can be stored up to 1024 characters. Editor tab titles do not hide their close button, and view titles do not overflow. _(Sirius Web)_ · `CHANGELOG.adoc`

### Toasts and feedback messages
- **Toast notifications (snackbars)**: notifications are notistack snackbars (#notistack-snackbar) stacked at the bottom right of every page. At most 5 show at once; each auto-hides after 10 seconds and has a small close (X) button. The variants default, success, error, warning and info are colored with the theme's primary, success, error, warning and info colors. The close button has aria-label 'close'. A message's level picks the variant (ERROR, INFO, WARNING, SUCCESS). Client-side errors raised through addErrorMessage (network/GraphQL failures, 'An unexpected error has occurred...', query errors) pass the lowercase level 'error'. That level matches none of these, so they fall back to the default variant and show in the primary color (#292253 in SysON), not in error red. Only server messages with level ERROR are red. _(Sirius Web)_ · `ToastProvider.tsx`, `MultiToast.ts`, `useReporting.ts`
- **Server feedback messages as multi-toasts**: backend success and error payloads (ErrorPayload#messages) carry a list of messages, each with a body and a level (ERROR, INFO, WARNING or SUCCESS). Each message becomes its own snackbar with the matching variant; any other level uses the default variant. This is supported for tool actions, DropOnDiagram, DeleteFromDiagram, ReconnectEdge, EditLabel, form operations, insert text and other mutations. Examples: 'The element part1 is already visible in its parent ...', 'Cannot drop part1 on itself', or entering an invalid value such as '1r' in a number field of the Details view. Successful operations such as Arrange all show no snackbar. _(Sirius Web)_ · `useReporting.ts`, `CHANGELOG.adoc` v2026.9.0, `details.cy.ts`
- **Generic error toasts in the application shell**: when a mutation fails at the network or GraphQL level, the app shows 'An unexpected error has occurred, please refresh the page'. This covers create project, rename, delete, duplicate, create model, invoke action, create representation and publish library. A failed file upload shows 'An unexpected error has occurred, the file uploaded may be too large'; SysON's server accepts multipart uploads of up to 256MB per file and per request (spring.servlet.multipart max-file-size and max-request-size). A query failure shows the raw error message, and a server ErrorPayload shows each of its messages. These client-side error toasts use the default (primary-colored) variant rather than the red error variant, because of the lowercase 'error' level. _(Sirius Web)_ · `useCreateProject.ts`, `UploadProjectView.tsx`, `sirius-web-application.json`
- **Generic diagram error toasts**: the toast 'An unexpected error has occurred, please refresh the page' surfaces when any of these fail: drop from the explorer, node drag-and-drop, fade, hide, pin, edge reconnection, layout synchronization, palette fetch, tool invocation or action invocation. Failing to fetch hover or manage-visibility actions shows 'An unexpected error has occurred while retrieving actions, please refresh the page'. _(Sirius Web)_ · `sirius-components-diagrams.json`, `useActions.tsx`, `useInvokeAction.tsx`
- **Form edit feedback toasts**: every Details/form widget edit returns a success or error payload, and the messages it carries (body plus level) are shown as toasts. Network or GraphQL failures show 'An unexpected error has occurred, please refresh the page', or the raw error message for text fields, reference widgets and the form description editor. _(Sirius Web)_ · `CheckboxPropertySection.tsx`, `sirius-components-forms.json`, `sirius-components-widget-reference.json`
- **Toasts for tree and table mutations**: every tree and table mutation reports the server's success or error messages, each with a body and a level, as toasts. This covers rename, delete, drop, context entries, cell edits, resize, reorder, visibility, filter, sort and tools. Query errors are shown as error toasts too. _(Sirius Web)_ · `useDropTreeItem.ts`, `useEditTextfieldCell.tsx`, `useInvokeToolMenuEntry.ts`
- **Error toasts for workbench view subscriptions and queries**: these workbench views report subscription or query errors as error toasts: Explorer, Views, Details, Related Elements, Related Views, Search and the diagram filter. Their mutation results report server messages with their levels. _(Sirius Web)_ · `useExplorerSubscription.tsx`, `useDetailsViewSubscription.tsx`, `useSearch.tsx`
- **SysON diagram tool feedback messages**: SysON diagram tools report outcomes as feedback messages at INFO, WARNING or ERROR level, shown as toasts. Examples include duplicate relationships, refused drops, owner changes and unresolved names. Some messages embed the element's SysML text, produced with simple names and no escaping. · `DiagramQueryElementService.java`, `ViewLabelService.java`
- **'Update incoming references' ignored notice**: if 'Update incoming references' is checked in the Duplicate object dialog, SysON ignores it. After Duplicate it shows the info message "The option 'Update incoming references' is ignored. It is not yet handled in SysON." · `SysONDuplicateDelegate.java`
- **Display toggle load errors**: if reading a diagram display toggle's initial value fails (show icons, show inherited members), an error toast shows the GraphQL error message. A failed toggle mutation (network error or error payload) is recorded in the checkbox component but not shown to the user, so the checkbox simply keeps the clicked state. · `useShowDiagramsIcons.ts`, `ShowHideDiagramsIcons.tsx`, `ShowHideDiagramsInheritedMembers.tsx`
- **Standard backend error and status messages**: the server's standard user-facing messages, shown in toasts and error payloads and also available in French, are:
  - 'Invalid input type, "{0}" has been received while "{1}" was expected'
  - 'Unable to create a new instance of "X" in feature "f" because it has reached its upper-bound cardinality'
  - 'Invalid name'
  - 'Not found'
  - 'An unexpected error has occurred, please contact the server administrator'
  - 'The file is unreadable'
  - 'No containment feature found for this element'
  - 'An element is already present for this mono-valued feature'
  - 'The dropped object is invalid'
  - 'The duplication of the object has failed'
  - 'The object with id "X" does not exist'
  - 'You are not authorized to perform this operation'
  - 'An error occurred while executing the operation: {0}'
  - 'Failed to delete the element'
  - 'Failed to rename the element'
  - 'Failed to find the dependencies of the project.'
  - 'The creation of the new object has failed'
  - 'The request has been interrupted due to a timeout'
  - 'The object has not been found'

  _(Sirius Web)_ · `messages.properties`, `sirius-components-collaborative.properties`, `sirius-components-collaborative_fr.properties`

### Confirmation dialogs
- **Deletion confirmation dialog**: when confirmation dialogs are enabled, a deletion first asks "Are you sure?", explaining "This action will delete the selected element(s)." and "You won't be able to revert this.", with a Delete button. It applies to delete actions in the explorer (context menu 'Delete', tree palette delete, tree 'Delete' menu item), diagram tools flagged withDeletionConfirmationDialog, list and reference widget item removal in forms, and deletions in the form description editor. The docs list model deletion from the Explorer, representation deletion and 'Delete from model' in the palette. The dialog does not open when the selected node or edge cannot be deleted (Sirius Web 2026.1.0). It is on by default for every new project, and turning it off for one project leaves it on for the others. _(Sirius Web)_ · `sirius-components-core.json`, `delete-dialog.spec.ts`, `CHANGELOG.adoc` v2026.1.0
- **Confirmation dialog look and buttons**: the generic confirmation dialog (confirmation-dialog) shows a large (50px) red warning icon above the title, a centered multi-line message, and two buttons: the confirm button (confirmation-dialog-button-ok) filled in the error red, darker on hover, labeled by the caller (e.g. 'Delete'), and an outlined 'Cancel' button (confirmation-dialog-button-cancel) that has the initial focus, so pressing Enter right away cancels. Clicking outside or Escape cancels. When browser localStorage is available it also shows a small hard-coded English checkbox 'Disable this confirmation dialog' (confirmation-dialog-checkbox-disabled, red when checked); the choice is saved only when the user confirms. Once disabled, later confirmations run the action immediately with no dialog. _(Sirius Web)_ · `ConfirmationDialog.tsx`, `ConfirmationDialogContext.tsx`, `useConfirmationDialog.tsx`
- **Disable/re-enable confirmation dialogs (browser-stored preference)**: the dialog offers a 'disable confirmation dialog' choice. It is saved in browser localStorage under the key 'sirius-confirmation-dialog-disabled' as a JSON list of project ids, so it applies per browser and per project. To turn dialogs back on, clear browser data (as the docs suggest) or use the 'Enable confirmation dialogs' switch in Project settings > General. The switch is tagged 'Personal' with the note 'This setting is stored in your browser.' (full description: 'Show confirmation prompts before deleting items or performing critical actions. This setting is stored in your browser.'; tooltip: 'When enabled, you will see confirmation prompts before deleting items or performing critical other actions that cannot be undone.'), sits in a 'General Settings' card subtitled 'Your personal preferences - these settings are stored in your browser' under 'Client settings for this project', and it is disabled when local storage is unavailable. A corrupt or non-array stored value is treated as an empty list. _(Sirius Web)_ · `useConfirmationDialogSettings.tsx`, `ProjectGeneralSettingsView.tsx`, `representation-operations.adoc`

- **Impact analysis confirmation dialog**: tools flagged withImpactAnalysis (e.g. the Explorer's 'Update library' and 'Remove library') first open a medium, full-width dialog (impact-analysis-dialog) with a primary-colored warning-circle icon and the title 'You are about to <tool label>'. A spinner shows until the report arrives. The report reads 'The <label> tool will have the following effects on your model:', then bullets 'Elements added: N', 'Elements deleted: N' and 'Elements modified: N' (each only when N > 0), any additional report lines, an optional 300px scrollable tree of the impacted elements, and 'Are you sure you want to proceed?'. Unlike the deletion dialog, it has a single filled 'Execute' button (impact-analysis-dialog-button-ok, disabled while loading) that has the initial focus, so Enter confirms; there is no Cancel button (Escape or a click outside cancels), and the 'disable confirmation dialog' preference does not apply to it. _(Sirius Web)_ · `ImpactAnalysisDialog.tsx`, `ImpactAnalysisDialogContext.tsx`, `sirius-components-core.json`

### Error pages, loading and startup
- **Error page**: the route /errors/:code shows the navigation bar, then a card with an error icon, the title 'Error {code}' and a message, a 'Back to the homepage' link, and the footer. Code 404 shows 'The content that you are looking for has not been found'. Any other code shows 'An unexpected error has occurred, please contact the server administrator for additional information'. Pluggable message providers can override these texts. _(Sirius Web)_ · `ErrorView.tsx`, `ErrorViewExtensionPoints.tsx`, `sirius-web-application.json`
- **Crash fallback message**: if a page crashes while rendering, it is replaced by the text 'An error has occurred, please contact your administrator or refresh the page...' and the error is logged to the console. Components wrapped with withErrorBoundary show the same text and recover automatically when their children change. _(Sirius Web)_ · `Router.tsx`, `ErrorBoundary.tsx`
- **Pages wait for viewer capabilities and translations**: each routed page is wrapped in a viewer context provider that renders nothing until the getViewer query returns. Until then every capability defaults to false: projects canList, canCreate and canUpload, and libraries canList. The whole application likewise renders blank until the locale and translation namespaces have loaded. A failure of either query shows its error message as a toast. _(Sirius Web)_ · `ViewerContext.tsx`, `useViewer.ts`, `I18nContext.tsx`
- **Loading indicators**: loading indicators appear:
  - while uploading a project or document;
  - in the publish, import and update library dialogs;
  - while a representation loads;
  - while form actions execute;
  - during long Query view evaluations.

  _(Sirius Web)_ · `CHANGELOG.adoc`
- **Blank page outside a secure context**: opened over plain HTTP from another machine, the app shows an empty page, and the browser console reports 'Uncaught TypeError: crypto.randomUUID is not a function'. The frontend calls crypto.randomUUID for its mutation input ids, e.g. when creating a representation. The troubleshooting guide points to the HTTPS setup how-to, which says HTTPS must be enabled when several users reach a server installed on a local machine. · `troubleshooting.adoc`, `https.adoc`

### Internationalization
- **Server-driven UI language (English and French)**: the UI language comes from the server. Viewer.language is the language of the spring.mvc.locale property (default en_EN, so 'en'), and Viewer.namespaces lists every distinct file name found under classpath i18n/*/*.json.
  - Loading: the frontend loads each namespace from GET /api/locales/{lng}/{ns}.json (404 when missing), falls back to English, and waits for all namespaces before rendering.
  - Bundles: English and French are maintained for the core, diagrams, palette, selection, validation, form description editors, forms, trees, tables, reference widget and application namespaces. Other languages can be added as i18n/{language}/{namespace}.json files.
  - Backend messages: these are translated too (e.g. 'Blank project' / 'Projet vide').
  - SysON text: SysON ships no i18n bundles, so SysON-specific UI text stays in English, as do some hard-coded Sirius Web strings such as 'Settings', 'Upload (read-only)' and 'Publish'.
  - No language picker: the language is read once from the server's configured locale (not from the browser or the user), so every user of a server sees the same language and changing it means changing spring.mvc.locale and restarting. i18next runs with English fallback, no HTML escaping of interpolated values and no React Suspense.

  _(Sirius Web)_ · `useCreateI18nInstance.ts`, `ViewerLanguageDataFetcher.java`, `LocaleController.java`
- **English/French label bundles for application, trees and tables**: application labels (dialogs, view messages, menu entries) and the diagram filter labels are provided in English and French bundles. So are tree labels (Delete, Rename, Filters, Enter the new value, Reveal selected elements, Show in, Filter...) and table labels (pagination, tools, export, Material React Table strings). The whole UI follows the selected language. _(Sirius Web)_ · `sirius-web-application.json`, `sirius-components-trees.json`, `sirius-components-tables.json`
- **Localized table controls**: every Material React Table in the shell (projects, libraries, libraries import, style customizations) takes its built-in texts from the sirius-components-tables translation bundle. That includes actions, search and filter mode labels, clear filter/search/selection/sort, copy, expand/collapse (all) and the filter operator names, so table controls follow the server language. _(Sirius Web)_ · `useTableTranslation.tsx`, `ProjectsTable.tsx`, `LibrariesImportTable.tsx`
- **Localized explorer context-menu labels**: the platform's explorer menu labels come from message bundles. English: Expand all, Download, New object, New representation, Duplicate object, Duplicate, Update library, Remove library. French: Tout développer, Télécharger, Nouvel objet, Nouvelle représentation, Dupliquer l'objet, Dupliquer, Mettre à jour la bibliothèque, Supprimer la bibliothèque. SysON's own entries (New objects from text, Create/Edit/Delete Expression) are hard-coded in English. _(Sirius Web)_ · `sirius-web-application.properties`, `sirius-web-application_fr.properties`

### Accessibility
- **Accessibility affordances in the shell**: the shell's ARIA and keyboard support comes from individual components; there is no accessibility settings page.
  - Workbench: sidebar view-selector buttons carry aria-label = the view title. Each view header is a button with aria-expanded/aria-controls, a 1px primary-color focus-visible outline, and its content is a role="region" labelled by the header. Representation tabs carry a11y ids (simple-tab-<id>, aria-controls simple-tabpanel-<id>).
  - Dialogs and icons: dialogs (confirmation, share, rename, new model/object/representation, upload, delete) use aria-labelledby. Toast close buttons and the filter-bar clear button have aria-labels ('close', 'clear'). The SysON and Sirius logos are SVGs with role="img".
  - Keyboard: tree items are tabIndex 0 with arrow-key navigation, and the omnibox and palette search lists support arrow keys.
  - Gaps: the diagram canvas has tabIndex -1, so Tab does not reach it.

  _(Sirius Web)_ · `ViewAccordion.tsx`, `Sidebar.tsx`, `SysONIcon.tsx`

### Documentation, support and client requirements
- **Documentation, contributing guide and support channels**: SysON ships documentation (installation guide, user manual) and contributing guidelines, including how to submit bug reports and feature requests. It points to the GitHub repository, issue tracker and discussions as support channels. The documentation was first contributed in 2024.7.0. · `2023.12.0.adoc`, `CHANGELOG.adoc` v2024.7.0
- **Supported client browsers and minimum screen resolution**: clients are desktop browsers: the latest stable Chrome or Firefox on Windows 10+, macOS 13 Ventura+, Linux or ChromeOS. Internet Explorer is not supported. The installation guide says mobile devices are not supported, while the FAQ says the app can be opened from mobile devices. The app is optimized for at least 1024 x 768 in a maximized browser window. Browser extensions can cause speed, upload, download or interface problems. · `requirements.adoc`, `faq.adoc`, `index.adoc`
- **Feature status banner on documentation pages**: most SysON and Sirius Web user-manual feature pages (Projects browser, Editor, Keyboard shortcuts, Direct edit...) open with a 'Before you Start' box stating the feature's status and audience. The experimental banner reads '🔥 This feature is currently considered experimental. Try it out and give feedback by reporting bugs and suggesting new features. It's not recommended for production use.' A stable variant exists too. Further badge partials state availability and audience: '🔓 The open source SysON project includes this feature.', '🔐 Access to this feature is restricted to admin users.' and '👥 This feature is available to all users.' · `before-you-start-experimental-all.adoc`, `feature-status-experimental.adoc`, `feature-os.adoc`
- **'Tour the interface' and 'Find your way around' pages (no in-app tour)**: the user manual's 'Tour the interface' page links image cards to the Projects browser and Editor pages, and the Editor/Workbench pages say 'we provide a guided tour for you to familiarize yourself with the platform'. ### Homepage layout and concepts

- **Projects browser (homepage)**: The application's homepage and the central place to create new projects or manage existing ones, at route `/projects` (also `/`). - **Project count and sizing limits**: SysON documents support for up to 1,000 concurrent projects per server (each project adds computational and storage load, so server capacity should scale with it) and up to 2,000 representations per project. ### Backend and API

- **Project list query**: `viewer.projects(first, last, after, before, filter)` returns a cursor-paginated list (default page size 20), filtered by `filter.name.contains` as a case-insensitive substring and sorted by creation date (newest first), then name, then id. Callers without the Project list capability get an empty list. Cursors are Relay global ids of type 'Project'; `first`/`last` have no upper cap, and contradictory arguments (e.g. `before` with `first`, or both `first` and `last`) return an empty page. The filter text goes into an SQL LIKE unescaped, so '%' and '_' typed in the search box act as wildcards. `pageInfo` carries hasNextPage/hasPreviousPage, start/end cursors and `count`, which is the number of projects on the returned page, not a total. _(Sirius Web)_ · `ViewerProjectsDataFetcher.java`, `ProjectSearchRepositoryDelegate.java`, `siriusweb.graphqls`
- **Single project query**: `viewer.project(projectId)` returns a project's id, name, natures, capabilities, images, style customizations and current editing context, used when opening `/projects/:id/edit`. It returns null when the caller lacks the Project view capability or the project doesn't exist. _(Sirius Web)_ · `ViewerProjectDataFetcher.java`, `siriusweb.graphqls`
- **Project templates query (browser cards vs. modal)**: `viewer.projectTemplates(page, limit, context)` returns templates sorted by label (default limit 20). With context PROJECT_BROWSER the Blank Project template moves to the end, followed by the `upload-project` card (only with the upload capability) and the `browse-all-project-templates` card (when any template exists); PROJECT_TEMPLATE_MODAL (also the default) returns the plain sorted page, in which Blank Project keeps its alphabetical place among the other templates. The label sort is a plain, case-sensitive string order (upper-case letters before lower-case). The Blank Project, upload and browse-all entries carry no image URL (their cards draw an icon tile instead). Callers without the create capability get nothing. A page or limit that is missing or not positive falls back to page 0 and limit 20. The total `count` excludes the special cards in the PROJECT_BROWSER context. As coded, both contexts compute the start index as the page offset multiplied by the page size again, so only page 0 works: any later page (e.g. page 1 with limit 12, start index 144) fails with a server error instead of returning the next templates. _(Sirius Web)_ · `ProjectTemplateApplicationService.java`, `ViewerProjectTemplatesDataFetcher.java`
- **All project templates query**: `viewer.allProjectTemplates` returns every template (id, label, imageURL, requiredLibraries) sorted by label, without paging, for the New project template select; empty without the create capability. _(Sirius Web)_ · `ViewerAllProjectTemplatesDataFetcher.java`
- **Templates hidden when required libraries are missing**: If any library a template requires (namespace, name, version) cannot be found on the server, the template is left out of every template list and a warning is logged. _(Sirius Web)_ · `ProjectTemplateApplicationService.java`
- **Project template images**: A template's imageURL is served under `/api/images`; the `/project-templates` classpath folder is registered as a publicly accessible image path so thumbnails load on the cards. _(Sirius Web)_ · `ProjectTemplateImageURLDataFetcher.java`, `ProjectTemplateImagePathService.java`
- **createProject mutation and lifecycle**: `createProject(input: {id, name, templateId, libraryIds})` creates a project from a template, with published libraries attached at creation; it returns `CreateProjectSuccessPayload` with the project, or an `ErrorPayload` with messages. GraphQL first checks the PROJECT create capability ('You are not authorized to perform this operation'); the REST endpoint builds the input directly. The name must be non-empty and at most 1024 characters once trimmed ('Invalid name'), but the backend stores it as sent: the New project page trims it before sending, while a GraphQL or REST client that sends surrounding spaces keeps them. An unknown template id gives 'Not found'; on error nothing is saved. The new project gets a random UUID id and the template's natures. Once the project commits, its semantic data and a 'main' project-semantic-data link are created, the first semantic-data initializer that handles the template id fills in the content (e.g. SysON's SysML v2 templates), and the requested libraries are imported, each step in its own transaction. _(Sirius Web)_ · `MutationCreateProjectDataFetcher.java`, `ProjectCreationApplicationService.java`, `project-creation-lifecycle.adoc`
- **renameProject mutation**: `renameProject(projectId, newName)` requires 1-1024 characters after trimming ('Invalid name'), but stores the name untrimmed, and the rename dialog sends the text as typed, so leading and trailing spaces stay in the project name. It returns 'Not found' for an unknown project, and needs the rename capability. A successful rename raises a project-name-updated domain event that also carries the previous name (2026.9.0); it feeds the `projectEvent` subscription. _(Sirius Web)_ · `MutationRenameProjectDataFetcher.java`, `ProjectUpdateService.java`
- **deleteProject mutation with cleanup**: `deleteProject(projectId)` needs the delete capability. It first disposes the project's running editing-context processor, then deletes the project; domain-event listeners (not database cascades) delete its semantic data, its project-semantic-data link, all representation metadata, all project images, its Elasticsearch indices and its enabled style-customization settings. _(Sirius Web)_ · `MutationDeleteProjectDataFetcher.java`, `ProjectImageCleaner.java`, `ProjectStyleCustomizationCleaner.java`
- **duplicateProject mutation**: `duplicateProject(projectId)` exports the project to an in-memory zip and re-imports it as a new project named '<name> - Copy' with the same natures, models and representations. It needs the duplicate capability and fails with 'Not found' for an unknown project. It always copies the project's default editing context (not a named one). If the copy cannot be created, e.g. because '<name> - Copy' exceeds 1024 characters, the error payload has an empty message; an unreadable intermediate archive gives 'An unexpected error has occurred, please contact the server administrator'. _(Sirius Web)_ · `ProjectDuplicationApplicationService.java`, `MutationDuplicateProjectDataFetcher.java`
- **Project download endpoint and archive manifest**: `GET /api/projects/{projectId}[?name=<semanticDataName>]` checks the DOWNLOAD capability and streams the project as an attachment '<project name>.zip' (application/zip, with Content-Length), or 404 when the capability, the project or the named editing context is missing. Only resources accepted by every persistence filter are exported, and a document is written only if it has a UUID id and a name; representations are exported in their migrated (current) form, and each manifest 'representations' entry records type, descriptionURI, targetObjectURI, migrationVersion and latestMigrationPerformed. The archive holds the models, representations (with their targetObjectURI) and library dependencies, laid out as `<project name>/manifest.json`, `<project name>/documents/<documentId>.json` and `<project name>/representations/<representationId>.json`; besides 'representations' and 'dependencies' entries, its `manifest.json` has 'metamodels' (sorted nsURIs of the editing context's EPackages), 'natures' and 'documentIdsToName' (document UUID to name). The Explorer has no 'copy document id' action, so this manifest, or the UUID returned when a document is created or uploaded, is how users find a document id for the document download endpoint. _(Sirius Web)_ · `ProjectDownloadController.java`, `ProjectSemanticDataExportParticipant.java`, `retrieve_project_documents_recipe.adoc`
- **uploadProject mutation**: `uploadProject(file)` creates a project from an exported zip, taking the name from the zip's top folder and the natures from the manifest. It needs the upload capability. Directory entries are ignored; a missing or unparsable `manifest.json` is treated as empty, so the project is created without natures or dependencies. The dependency check accepts only manifest dependency ids that exist as editing contexts on this server. A folder name that fails the 1-1024 character rule yields an error payload with an empty message. An unreadable zip fails with 'The file is unreadable'; library dependencies are kept through download/upload and validated, and missing ones fail with 'Failed to find the dependencies of the project.'. Archives whose models reference each other are supported; if some documents contain invalid references, only the self-contained subset without invalid external references is imported. _(Sirius Web)_ · `ProjectUploadApplicationService.java`, `ProjectZipContentValidator.java`, `messages.properties`
- **Project import preserves diagram state**: Importing a project restores diagram layout, unsynchronized nodes and their hidden/faded/normal state, custom handles, label positions, custom appearances, and diagrams with child node descriptions. Nodes targeting library objects do not crash the import, representations with unknown descriptions no longer deadlock it (2026.3.0), and the upload is not blocked when some representations cannot be created (2025.10.0). Changelog milestones: layout and unsynchronized nodes restored and representation creation on whole-project upload fixed (2025.6.0), custom appearances kept and projects exported before 2025.6.0 importable again (2025.8.0), custom handles kept (2026.5.0); much earlier, exporting and re-importing studio projects was fixed (2023.8.0) and the manifest's missing targetObjectURI fixed (2025.2.0). _(Sirius Web)_ · `CHANGELOG.adoc` v2025.6.0, v2025.8.0, v2026.5.0
- **Upload pipeline: new ids, reference rewriting, representation re-creation**: Upload and Duplicate both create the project, then fill its new 'main' editing context from the archive. (1) The manifest's library dependencies are added to the new semantic data. (2) Each `documents/<id>.json` is loaded under a fresh document UUID, with its name from `documentIdsToName`, and proxies are allowed. Migration participants run when a predicate asks for them, and element ids may be remapped. (3) Cross-document references (proxies) in every non-read-only resource are rewritten from old to new document and element ids. (4) Documents that still hold unresolved references are removed, repeatedly until none remain, with the warning 'Some documents with invalid references were not imported'. (5) The content is saved. (6) Each `representations/<id>.json` (id, projectId, descriptionId, targetObjectId, label, kind, representation) is unserialized with the manifest's migration info (defaults 'none' and '0') and re-created on the remapped target object, keeping its label. Representation-importer update services then restore layout and appearance. Unparsable representation files are skipped with a warning. _(Sirius Web)_ · `SemanticDataProjectContentImportParticipant.java`, `RepresentationProjectContentImportParticipant.java`, `RewriteProxiesService.java`
- **What project archives leave out**: The archive holds only models, representations, natures, metamodel URIs and library dependency ids. Project images, enabled style customizations (Appearances) and the browser-stored General settings are not exported. A downloaded-then-uploaded or duplicated project therefore has no project images and all style customizations off. _(Sirius Web)_ · `ProjectExportService.java`, `ProjectDuplicationApplicationService.java`, `ProjectImageDeletionService.java`
- **SysML standard libraries excluded from archives**: SysON's persistence filter keeps the SysML/KerML standard library resources out of project downloads (and so out of duplicates). On upload, its proxy-rewriting filter skips standard library resources, so references to standard library elements are left unchanged and resolve against the libraries the server loads. · `SysMLv2EditingContextPersistenceFilter.java`, `SysMLv2RewriteProxiesResourcesFilter.java`
- **Project archive extension API**: The archive format is assembled by `IProjectExportParticipant` beans: each writes its zip entries and returns manifest entries, merged into `manifest.json`. The built-in participants cover semantic data, representations and dependencies. Reading back goes through `IProjectContentImportParticipant` beans, triggered by the creation events of the uploaded project. `IEditingContextPersistenceFilter` decides which resources are exported, and `IRewriteProxiesResourceFilter` decides which resources get their references rewritten (by default, every resource that is not read-only). _(Sirius Web)_ · `ProjectExportService.java`, `ProjectContentImporter.java`, `DefaultRewriteProxiesResourceFilter.java`
- **Project natures**: A project carries a set of natures (named tags such as 'studio', exposed as `Project.natures`) that come from its template at creation, are written to and read back from the zip manifest, and enable or disable capabilities (e.g. filtering the domains available in a project). The domain layer can add or remove natures (ProjectNaturesAdded/Removed events), but no GraphQL mutation exposes this. A project with no nature gets the generic 'Others...' empty-model action. _(Sirius Web)_ · `Project.java`, `ProjectUpdateService.java`, `DefaultEditingContextActionProvider.java`
- **Project data model and domain events**: A project record holds a random UUID id, a name, a set of natures, createdOn and lastModifiedOn; lastModifiedOn changes on rename and on nature changes, and createdOn drives the newest-first list order. GraphQL exposes only id, name and natures (plus the computed capabilities, images, style customizations and current editing context), not the timestamps. Every change raises a domain event (project created, name updated with the previous name, natures added or removed, deleted) that the other modules listen to. _(Sirius Web)_ · `Project.java`, `siriusweb.graphqls`, `ProjectNameUpdatedEvent.java`
- **Project access and activity logging**: Since 2026.5.0 the server writes INFO log lines for access to the main parts of the application and for project manipulation, using structured key-value data: '{n} project template(s) retrieved', '{n} project(s) retrieved', 'Project {id} retrieved', 'Project {id} created' (with the projectTemplateId), 'Project {id} renamed', 'Project {id} deleted', 'The project {new} has been created by duplicating the project {old}', 'Project {id} uploaded', image uploaded/renamed/deleted (with projectId and imageId), '{n} style customization(s) of project {id} retrieved' and 'Project style customization {id} updated'; failures are logged as warnings (e.g. 'Project creation failed' with the template id). There is no user-facing audit view. _(Sirius Web)_ · `ProjectCreationApplicationService.java`, `ViewerProjectTemplatesDataFetcher.java`, `CHANGELOG.adoc` v2026.5.0
- **Project semantic data ('main' editing context)**: Creating a project also creates one semantic data (the editing context that holds its models) linked to the project under the name 'main'. `currentEditingContext(name)`, the download endpoint's `?name=` and the editor URL's `projectId@name` select a link by name; with no name, the project's semantic data is used. The domain layer can rename a link (a blank name gives 'Invalid name', and a name already used in the project gives 'Failed to rename the element'), but no UI or GraphQL operation creates or renames extra editing contexts. Since 2025.2.0 the editing context id is the semantic data's own id, not the project id, so a project id and its editing context id differ; the project-semantic-data links of a project are sorted by creation date (2026.7.0) and can be deleted by project id and name (2026.9.0). _(Sirius Web)_ · `ProjectSemanticDataCreator.java`, `ProjectEditingContextService.java`, `ProjectSemanticDataUpdateService.java`
- **Project and viewer capabilities in GraphQL**: `viewer.capabilities` returns `projects {canList, canCreate, canUpload}` and `libraries {canList}`. `project.capabilities` returns `canDownload`, `canRename`, `canDelete`, `canDuplicate`, `canEdit`, `canUpdateStyleCustomizationsState` and `settings {canView, tabs(tabIds) {tabId, canView}}`. ### Editor area and representation tabs
- **Editor area with multiple representation editors**: the main area edits models and representations (diagrams, forms, tables...). Users can open as many editors as they like and switch between them without leaving the editor. _(Sirius Web)_ · `workbench.adoc`, `editor.adoc`
- **Representation tabs**: above the editor, a scrollable tab bar with scroll buttons lists every opened representation as a tab (representation-tab-{label}, carrying its representation id).
  - Each tab shows a 12px computed icon of the representation (possibly overlaid icons), an ellipsized label, a tooltip with the full label, and a small close (X) button (close-representation-tab-{label}). Tabs are compact (24px minimum height, 6px padding), and labels keep their original case rather than MUI's default uppercase. Clicking the X closes the tab without first activating it.
  - The active tab is underlined in the primary color.
  - Clicking a tab sets the global selection to that representation, which displays it, and the URL becomes /projects/{id}/edit/{representationId}.
  - Creating a representation opens its tab immediately. Selecting a representation in the explorer opens it in a new tab, or focuses its tab if it is already open. On every selection change the workbench queries representation metadata for all selected ids. If several representations are selected at once, all of them are added as tabs and the first becomes active. New tabs are appended at the end.
  - Only the active tab's editor is mounted (keyed by editingContextId#representationId), so switching tabs unmounts the previous editor and remounts the new one.
  - A recently closed representation can be opened again.
  - Closing the active tab activates the tab that takes its place (the next one), or the previous one when the closed tab was last; closing the last tab leaves the onboard area. Closing an inactive tab keeps the current one.

  _(Sirius Web)_ · `RepresentationNavigation.tsx`, `Workbench.tsx`, `explorer.adoc`

### Selection synchronization
- **Single global selection**: one global selection (a list of entry ids) is shared by the whole workbench. Applying a selection pushes it to every visible view that supports it and to the displayed representation. Selecting an element in the Explorer shows its properties in the Details view and the other selection-driven views. _(Sirius Web)_ · `SelectionContext.tsx`, `Workbench.tsx`, `explorer.adoc`
- **Explicit cross-view synchronization**: selecting a node in a diagram does not automatically select or reveal it in the explorer, and selecting an item in the explorer does not select the node in the diagram. Synchronization is explicit, through the explorer's Reveal selection button, the diagram toolbar's reveal button, the 'Show in' menus and the omnibox. Opening a diagram does not steal the workbench selection. _(Sirius Web)_ · `selection.spec.ts`, `CHANGELOG.adoc` v2025.10.0
- **Selection applied to views**: the workbench can push a selection into each view. The Explorer and Views explorer then select the items and expand the tree to reveal them. Details, Query, Related Views and Related Elements switch to the new objects. The Search view ignores pushed selections. _(Sirius Web)_ · `ExplorerSelectionContext.tsx`, `ViewsExplorerView.tsx`, `useSearchViewHandle.ts`
- **Diagram selection published to the workbench**: whenever the diagram selection changes, the semantic elements (targetObjectId) of all selected nodes and edges become the global workbench selection, with the last-selected node first. With several nodes selected, the Details view shows the last one. The diagram keeps a stable order of selected element ids: previously selected first, new ones appended. _(Sirius Web)_ · `useDiagramSelection.ts`, `selection.spec.ts`
- **Workbench selection applied to the diagram**: the diagram editor registers with the workbench. A selection pushed into it (Show in, reveal button, omnibox) selects every visible node showing a selected element, except nested nodes whose ancestor is already selected for that element. Visible edges are selected only if their element was not already selected through a node, and their end nodes count as revealed. The selected elements are revealed in the viewport. An element whose node is hidden on the diagram is not selected there. _(Sirius Web)_ · `useApplySelection.ts`, `DiagramRepresentation.tsx`, `CHANGELOG.adoc`
- **Reveal selected elements in diagram (toolbar button)**: a diagram toolbar button (LocationSearching icon) applies the current workbench selection (e.g. elements selected in the Explorer) to the diagram, selecting and revealing the matching elements. Hovering it fetches the selected objects' labels. While they load, the tooltip shows 'Reveal selected elements (loading details...)'. It then shows 'Select A, B', or beyond 5 labels 'Select A, B, C, D, E (and N more)'. With no labels it reads 'Reveal selected elements'. _(Sirius Web)_ · `RevealSelectionInDiagramButton.tsx`, `sirius-components-diagrams.json`, `manage-toolbar-diagram.adoc`
- **Pin/unpin a view to the selection (synchronization button)**: Details, Query, Related Views and Related Elements have a toggle in their header toolbar, with its tooltip placed left.
  - Unpinned (sync icon): the view follows the global selection. Tooltip: 'Unpinned. Click to pin the view to the current selection.'
  - Pinned (sync-lock icon): the view keeps showing the objects selected when it was pinned. Tooltip: 'Pinned. Click to follow the global selection.' Other views can still update a pinned view with 'Show in <view>' (e.g. Show in Details).
  - Unpinning re-applies the current selection.
  - Display: Details, Related Views and Related Elements show the unpinned icon while nothing is selected; the Query view always shows its real pin state.

  _(Sirius Web)_ · `SynchronizationButton.tsx`, `DetailsView.tsx`, `sirius-web-application.json`
- **'Show in' selection targets**: a 'Show in' list pushes a local selection from one representation or view into another. - **Explorer context menu 'Show in <target>'**: the tree item context menu has one 'Show in <target>' entry per available selection target (other workbench views, excluding the explorer itself), each with the target's icon. ### URL routing and deep links
- **Application routes**: the client routes are:
  - '/' (redirects to /projects)
  - /projects (project browser)
  - /new/project?templateId= (new project form)
  - /upload/project
  - /projects/:projectId/edit/:representationId? (editor, with ?selection= and ?workbenchConfiguration= deep links)
  - /projects/:projectId/settings/:tabId?
  - /libraries
  - /libraries/:namespace/:name/:version (read-only library view; links inside it are built as .../edit/:representationId, but no route matches that path, so they lead to /errors/404)
  - /errors/:code

  Apart from /errors/:code and the catch-all redirect to /errors/404, every route comes from the router#routes data extension point (SysON adds none). Each contributed route gets the crash fallback as its ErrorBoundary and is wrapped in the viewer-capabilities provider. _(Sirius Web)_ · `DefaultExtensionRegistry.tsx`, `Router.tsx`, `DisplayLibraryView.tsx`
- **Edit-project route**: a project's workbench opens at /projects/{projectId}/edit, from where the explorer, Details view and representation editor area load. _(Sirius Web)_ · `EditProjectView.tsx`, `Project.ts`
- **Named editing context in the project URL (projectId@name)**: the projectId route segment can carry a suffix after '@', which is passed as the name argument of currentEditingContext(name) so that a named editing context of the project opens. The suffix is kept when the URL is rewritten on representation changes and in links built inside the workbench, and the project download link adds ?name=<name>. _(Sirius Web)_ · `EditProjectView.tsx`, `useSynchronizeSelectionAndURL.ts`, `DownloadProjectMenuItem.tsx`
- **Unknown routes and forbidden pages redirect to 404**: any URL that matches no route redirects to /errors/404. So do pages the viewer lacks the capability for: project browser, new project, upload project, libraries, project settings, and an unknown library or settings tab. _(Sirius Web)_ · `Router.tsx`, `ProjectBrowserView.tsx`
- **Unknown project redirects to 404**: if the project query finishes with no project or no current editing context, the editor replaces the URL with /errors/404. Errors from the project/representation metadata query are also shown as error toasts. _(Sirius Web)_ · `EditProjectView.tsx`, `useProjectAndRepresentationMetadata.ts`
- **Open a representation from its URL**: when the URL contains a representationId, the editor queries that representation's id, label, kind, iconURLs and description id within the project's editing context, then opens it as the initial representation in the main area. Components inside the workbench build links to a representation with the same path, /projects/<rawProjectId>/edit/<representationId>. _(Sirius Web)_ · `useProjectAndRepresentationMetadata.ts`, `EditProjectView.tsx`
- **URL follows the displayed representation**: whenever the displayed representation changes (tab click, selection, closing a tab), the URL becomes /projects/<id>/edit/<representationId>, keeping existing query parameters. Closing the last representation goes back to /projects/<id>/edit/. The history entry is replaced when the URL had no representation yet, and pushed otherwise. _(Sirius Web)_ · `useSynchronizeSelectionAndURL.ts`, `Workbench.tsx`, `EditProjectView.tsx`
- **Selection stored in the URL (?selection=)**: the global selection is written to the URL as ?selection=id1,id2,... (comma-separated element ids), replacing the history entry, and the parameter is removed when nothing is selected. On load it becomes the initial global selection, so a URL restores which elements were selected. For example, opening the diagram palette on the background sets selection=<diagramId>. _(Sirius Web)_ · `SelectionSynchronizer.tsx`, `EditProjectView.tsx`, `palette.spec.ts`
- **Workbench configuration URL parameter (?workbenchConfiguration=)**: a JSON workbenchConfiguration parameter on /projects/{id}/edit[/{representationId}] is merged into the server-provided layout when the editor first loads. It can set:
  - the open representation editors and the active one (mainPanel representationEditors [{representationId, isActive}], both fields required); opened editors appear as tabs and only the active one is rendered;
  - each side panel's (left/right) isOpen state;
  - each view's {id, isActive} plus view-specific settings such as explorer filters or the search query.

  The parameter is removed from the URL once applied. A null configuration gives the default layout, and views not available in the project (e.g. 'papaya-view') are ignored. If none of the listed editors is marked active, they are still added as tabs but nothing is displayed: the main area shows the onboard area and the tab bar stays hidden until a representation is selected. _(Sirius Web)_ · `useInitialWorkbenchConfiguration.ts`, `workbench-configuration.cy.ts`, `workbench-configuration.data.ts`
- **Browser back/forward in the workbench**: navigation pushes browser history states, so the browser's back and forward buttons work reliably inside the workbench, and URL search params are kept while using it. _(Sirius Web)_ · `2026.7.0.adoc`, `CHANGELOG.adoc`
- **Single-page-app routing on the server**: any GET request is answered with the frontend's index.html (no-store cache) unless it is an API path (/api/**, /v3/api-docs/**, /subscriptions), a static asset (css, html, js, json, ico, fonts, images) or another backend path. Deep links such as /projects/<id>/edit or /new/project?templateId=... therefore open directly. Without a bundled index.html those paths return 404. Integrators can declare more server-handled paths with an IBackendPathPredicate (Sirius Web 2025.2.0). _(Sirius Web)_ · `FrontendRouterConfiguration.java`, `CHANGELOG.adoc` v2025.2.0
- **?mode=png-viewer / ?mode=svg-viewer diagram URLs**: adding ?mode=png-viewer (or svg-viewer) to a diagram's URL replaces the diagram's export button with an always-open, extra-wide (xl) 'PNG Viewer' (or 'SVG Viewer') dialog, which shows the rendered image after a fixed 5-second wait. Any other mode value opens the 'SVG Viewer' dialog with no image. A diagram picture can be opened directly from a link (Sirius Web 2025.2.0). _(Sirius Web)_ · `ExportImageButton.tsx`, `CHANGELOG.adoc` v2025.2.0
- **?showIcons=false URL parameter**: opening a diagram URL with showIcons=false turns diagram icons off about 200 ms after load (it calls the showDiagramsIcons mutation with show=false) and opens the Diagrams Options menu. This gives a shareable link to an icon-free diagram, e.g. for screenshots. · `ShowHideDiagramsIcons.tsx`, `SysONDiagramPanelMenu.tsx`

## Omnibox, commands & keyboard shortcuts

### Opening the omnibox
- **Ctrl+K / Cmd+K toggles the omnibox**: pressing Ctrl+K (Cmd/Meta+K on macOS) anywhere in the document opens the omnibox, a command palette for running commands and searching elements, or closes it if it is already open. The browser default for that key is suppressed. Only a lowercase 'k' key value matches, so with Shift or Caps Lock held (key 'K') the shortcut does nothing. The dialog component is unmounted while closed, so each opening starts fresh. The listener is on the document and does not check the focused element, so it also fires while typing in a text field. It exists only while the project editor or project browser is mounted; on other pages the key is not intercepted. Escape or a click outside the dialog also closes it. It is available in the project workbench and on the project browser (homepage). The command palette was introduced in 2024.11/2025.1.0; at that SysON release its only command was element search ('Click to select the element'), and SysON's library commands came later. _(Sirius Web)_ · `OmniboxProvider.tsx`, `workbench.adoc`, `2025.1.0.adoc`
- **'Run commands...' omnibox button in the navigation bar**: a navigation-bar button shows a '>' chevron, the text 'Run commands...' and a small bold key hint in a rounded outlined box at 70% opacity ('⌘ + K' on Apple platforms, detected from navigator.platform matching Mac, iPhone, iPod or iPad; 'Ctrl + K' elsewhere). The hint is only a label: both Ctrl+K and Cmd+K work on every platform. Clicking it opens the omnibox. It appears only on the project browser (/projects) and the project editor (/projects/:projectId/edit/...), not on settings, libraries or error pages. _(Sirius Web)_ · `OmniboxButton.tsx`, `DefaultExtensionRegistry.tsx`, `sirius-components-core.json`

### Omnibox dialog
- **Omnibox command dialog**: a full-width dialog (testid omnibox) positioned 10% from the top, with a large '>' icon, a borderless autofocused input (1.5rem font) and a submit button. The submit button shows a return-arrow icon, which a spinner replaces while loading. The placeholder is "Hit 'Enter' to search a command..." in Command mode and "Hit 'Enter' to search an element..." in Search mode. The result list scrolls, with a maximum height of 330px. _(Sirius Web)_ · `Omnibox.tsx`, `sirius-components-core.json`
- **Omnibox query and keyboard behavior**: when the omnibox opens, it immediately lists all commands for an empty query, fetching commands on each open.
  - Enter or the submit button sends the typed query only if it changed since the last send, so the submit button stays disabled until the input changes and while a query runs.
  - ArrowDown from the input focuses the first result, and ArrowUp/ArrowDown move focus between results. Navigation does not wrap, and ArrowUp on the first result stays there rather than returning to the input.
  - Clicking the submit button sends the query and puts focus back in the input.
  - The omnibox always reopens in Command mode.

  _(Sirius Web)_ · `Omnibox.tsx`, `OmniboxCommandList.tsx`, `omnibox.cy.ts`
- **Omnibox result list states**: results are dense rows (data-testid = the command label) with an icon and an ellipsized label only: the description each command or result carries (e.g. 'Click to select the element', "Previous search '<value>'") is returned by the backend but not displayed. While a query runs, a grayed row reads 'Fetching results...' (fetch-omnibox-result); when nothing matches, the list shows 'No result' (omnibox-no-result). _(Sirius Web)_ · `OmniboxCommandList.tsx`, `sirius-components-core.json`, `omnibox.cy.ts`

### Workbench omnibox commands
- **Context-aware command mode**: in Command mode, the typed query and the ids of the selected objects are sent to the backend (workbenchOmniboxCommands(editingContextId, selectedObjectIds, query)). The backend returns the commands available for the current project, configuration and selection, each with an icon, a label and a description. The command list is extensible, so studios and derived products such as SysON add their own commands. The Sirius Web docs say results narrow as you type part of a command name, representation type or element label and that the best candidates are highlighted; in the code the query is only sent on Enter and rows are not highlighted. _(Sirius Web)_ · `WorkbenchOmnibox.tsx`, `workbench-omnibox.graphqls`, `workbench.adoc`
- **Frontend command overrides (commands that open a dialog)**: a command whose id matches a registered omnibox command override contribution (canHandle) is rendered by that contribution's own component instead of the default row. Clicking it runs frontend code, typically opening a dialog, rather than executing the command on the backend, and the row still takes part in ArrowUp/ArrowDown navigation. SysON registers two overrides: 'publishProjectSysMLContentsAsLibrary' (opens the Publish library dialog) and 'importPublishedLibrary' (opens Sirius Web's 'Import libraries' dialog). SysON's extension-registry merge strategy appends its overrides to Sirius Web's own ('publishStudio' and 'importLibrary') instead of replacing them, and does the same for Apollo client configurers, tree context-menu overrides, form widgets and palette tool contributions. The first matching override wins. _(Sirius Web)_ · `OmniboxCommandList.tsx`, `SysONExtensionRegistryMergeStrategy.ts`, `DefaultExtensionRegistry.tsx`
- **Command filtering and ordering**: the backend gathers commands from every provider and keeps those whose label contains the query (case-insensitive substring). A pluggable orderer (ComposedOmniboxCommandOrderer, defaulting to DefaultOmniboxCommandOrderer) is meant to put 'Search' first, but at v2026.11.0 the search services discard its result, so commands appear in provider order. Since 2026.9.0, downstream applications plug in their own ordering by implementing IOmniboxCommandOrdererDelegate; without one, the default orderer applies. _(Sirius Web)_ · `WorkbenchOmniboxCommandSearchService.java`, `ComposedOmniboxCommandOrderer.java`, `CHANGELOG.adoc` v2026.9.0
- **Omnibox command execution**: picking a command runs it on the backend (executeWorkbenchOmniboxCommand) with the project and current selection. A success can return a new workbench selection, which is applied, plus messages shown as toasts. Error payload messages are also toasted; an unknown command fails with 'The object has not been found'; a network error shows 'An unexpected error has occurred, please refresh the page'. The omnibox closes once execution returns. _(Sirius Web)_ · `useExecuteWorkbenchOmniboxCommand.ts`, `WorkbenchOmniboxCommandExecutor.java`, `WorkbenchOmnibox.tsx`
- **'Search' command and element search mode**: the 'Search' command ('Search an element in the project', search icon) switches the omnibox to Search mode and clears the input, with the placeholder "Hit 'Enter' to search an element...".
  - Searching: Enter sends the query and current selection to workbenchOmniboxSearch. It matches every element in the project whose label contains the query (case-insensitive), including elements hidden in the current view, and lists results with icons, shortest label first, each described 'Click to select the element'. The backend walks every content of the editing context's resource set: documents themselves and, in SysON, the loaded standard and referenced libraries. There is no result limit, and an empty query (Enter right after choosing Search) lists everything. Labels are the elements' styled labels.
  - Picking a result: closes the omnibox and makes the element the global selection. The selection is applied to every view and to the open representation, so the element is selected in the diagram, shown in the Details view (whose page tab appears) and revealed in the Explorer, even on the first search right after the project opens.

  _(Sirius Web)_ · `WorkbenchOmnibox.tsx`, `WorkbenchOmniboxSearchEventHandler.java`, `omnibox.cy.ts`
- **Omnibox search history**: each search query is saved in browser localStorage under 'sirius_web_search_history': most recent first, non-empty, without duplicates, at most 10 entries, including searches with no results. Choosing the Search command lists earlier searches as "Search '<value>'" rows described "Previous search '<value>'". Clicking one fills the input and reruns the search. A rerun from history is not saved again, so it does not move that entry back to the top. If localStorage is unavailable, no history is kept. With no saved history, choosing Search leaves an empty list, which shows the 'No result' row until a search is sent. _(Sirius Web)_ · `WorkbenchOmnibox.tsx`, `omnibox.cy.ts`, `CHANGELOG.adoc`

## Collaboration, undo/redo & change safety

### Sharing and concurrent authoring

- **Concurrent authoring without locks**: several users can author the same project/model at the same time (listed as supported in the key features; collaborative by nature as a web app). Model changes (property edits, added nodes, representation rearrangements) are pushed to every connected user; there is no locking by default, so users are told not to edit the same element simultaneously unless their environment adds explicit locking. _(Sirius Web)_ · `collaboration.adoc`, `key-features.adoc`, `faq.adoc`
- **Share link**: project actions menu (workbench navbar) > Share opens a full-width dialog titled 'Share project' with a URL to the project or to the active representation (`/projects/{id}/edit/{representationId}`); its query string encodes the current workbench configuration (panels, open views and editors) and the current selection. The URL text (testid share-path) is pre-selected, and when the browser's clipboard API is available and the page has focus it is copied automatically and the title becomes 'Share project (copied into the clipboard)'. Teammates with access to the same instance land on the same workbench state; the docs say recipients can open it directly because everything in SysON is public. Projects and models can also be exchanged via interoperability (export/import). _(Sirius Web; experimental)_ · `ShareProjectModal.tsx`, `ShareProjectMenuItem.tsx`, `collaboration.adoc`
- **Share representation link**: the Share button of a representation's own toolbar (diagram toolbar tooltip 'Share diagram', portal toolbar 'Share portal', deck and Gantt toolbars 'Share') opens a full-width dialog titled 'Shareable link' showing only `<origin>/projects/{id}/edit/{representationId}` (no workbench-configuration or selection query string; `/libraries/{ns}/{name}/{version}/edit/{id}` inside a library). The text is pre-selected and, when the clipboard API is available and the page has focus, it is copied and the title becomes 'Shareable link (copied into the clipboard)'. _(Sirius Web)_ · `ShareRepresentationModal.tsx`, `DiagramToolbar.tsx`, `representation-operations.adoc`
- **No built-in version control**: SysON has no versioning or change-management tooling of its own; the docs advise downloading the project as a zip archive for each version or iteration and committing it to an external Git repository. · `cm.adoc`

### Real-time synchronization

- **Real-time diagram subscription**: each open diagram subscribes to `diagramEvent` for its editing context and diagram id; every server change pushes a DiagramRefreshedEventPayload with the full diagram, a cause ('refresh' for semantic changes, 'layout' for layout changes) and an optional referencePosition (parentId, positions, causedBy) used to place new elements. Layout data computed by one client (including reference positions) is shared with all subscribers, and new subscribers always get the latest state. ErrorPayload messages and subscription errors show as toasts. _(Sirius Web)_ · `useDiagramSubscription.tsx`, `diagramEventSubscription.ts`, `CHANGELOG.adoc`
- **Diagram refresh merging**: on a pushed refresh only changed nodes are replaced; the current node/edge selection, the last-selected marker and drag/drop state are preserved. On a semantic refresh the client lays out new or changed elements (using the last creation's reference position) and, unless read-only, sends the computed layout back; on undo/redo the stored node layout data is applied first. _(Sirius Web)_ · `DiagramRenderer.tsx`
- **Real-time tree refresh**: trees (Explorer and others) subscribe to `treeEvent` with no client cache and re-render on every TreeRefreshedEventPayload, so changes by any user appear live; subscription errors show as error toasts and the end of the subscription marks the representation unavailable. _(Sirius Web)_ · `useTreeSubscription.tsx`, `TreeRepresentation.tsx`
- **Real-time table synchronization**: tables subscribe to `tableEvent` with no client cache; TableRefreshedEventPayload carries the whole table (pagination, striping, sub-rows, page size options, filters, sort, columns, lines, cells), while lighter payloads update only the global filter value, column filters or column sort, so every viewer sees edits and filter/sort changes live. _(Sirius Web)_ · `useTableSubscription.ts`
- **Live form synchronization**: Details, Related Elements, Related Views, diagram filter and standalone forms subscribe to `formEvent` without caching; every FormRefreshedEventPayload pushes the whole form (pages, groups, widgets, toolbar actions), so edits made by other users, other tabs (e.g. a rich text description changed in a second tab) or other views show up immediately. Details edits modify the model directly with no save step. Subscription errors show as toasts. _(Sirius Web)_ · `useFormSubscription.tsx`, `rich-text-link.spec.ts`, `details.adoc`
- **Text fields keep local edits during remote refresh**: while a text field or text area has focus, incoming refreshes don't overwrite what the user is typing; the server value is applied once the field loses focus. _(Sirius Web)_ · `TextfieldPropertySection.tsx`
- **Live project rename**: the editor navbar subscribes to `projectEvent(projectId)`; a ProjectRenamedEventPayload(projectId, newName), e.g. after another user renames the project, updates the displayed name immediately; the stream completes when the project is deleted; errors show as toasts. _(Sirius Web)_ · `useProjectSubscription.ts`, `ProjectSubscriptionListener.java`, `siriusweb.graphqls`
- **Live representation rename (editing context events)**: the workbench subscribes to `editingContextEvent(editingContextId)`, which streams project-wide events (currently RepresentationRenamedEventPayload(representationId, newLabel)); the matching open tab and lists update their titles in real time; errors show as toasts. _(Sirius Web)_ · `useEditingContextEventSubscription.tsx`, `Workbench.tsx`, `core.graphqls`
- **One-at-a-time processing of every user's changes**: each loaded project (editing context) has its own single-threaded executor (thread 'Editing context <id>'); queries and mutations from all users are queued and run strictly one after another in arrival order, each finishing before the next starts, so concurrent edits never interleave but the last change applied wins (no merge, no conflict detection). - **Project loaded on demand, unloaded when idle**: a project's editing context is loaded from the database on first access and kept in memory while representations are subscribed; when the last representation processor is disposed, it is unloaded after `sirius.components.editingContext.disposeDelay` (default 1s) unless a new subscriber arrived meanwhile. ### Undo and redo

- **Undo/redo keyboard shortcuts**: in the edit-project workbench (window-level keydown listeners), Ctrl+Z / Cmd+Z undoes the last recorded action and Ctrl+Y or Ctrl+Shift+Z (Cmd variants) redoes it; result messages and errors appear as toasts. Introduced in Sirius Web v2024.11 / SysON v2025.2.0 for semantic changes from the Explorer and Details only (resource deletion excluded), later extended to diagram changes. There is no Undo/Redo button or menu entry: keyboard only. The listeners don't check focus and don't call preventDefault, so the shortcuts also fire while typing in a text field (where the browser's own text undo runs too). Each press sends one undo/redo for the top entry of the stack and does nothing when the stack is empty. Each tab's stack holds only the mutations sent from that tab, so a user undoes their own operations, not other users'. Library pages don't mount the handler. _(Sirius Web)_ · `UndoRedo.tsx`, `2025.2.0.adoc`, `CHANGELOG.adoc` v2025.2.0
- **Undo and redo mutations**: `undo(editingContextId, inputId)` and `redo(editingContextId, inputId)` revert or replay the change made by a previous operation identified by its input id; model changes are recorded per operation and undo applies the reverse change. Before each non-ignored input the server starts an EMF change recorder over every resource of the editing context and afterwards stores the summarized change under the input's id in an in-memory map of the editing context; undo and redo both call applyAndReverse on that stored change (so the same record toggles between undone and redone), then let the diagram change handlers revert or replay diagram-only state, and emit a semantic change so every open representation of every connected user refreshes. An input id with no recorded change still returns success (a silent no-op). The history lives only in the loaded editing context, so it is lost when the project's editing context is disposed or the server restarts. _(Sirius Web)_ · `UndoEventHandler.java`, `UndoRedoRecorder.java`, `EditingContext.java`
- **Client-side undo/redo stacks**: every GraphQL request passes through ApolloLinkUndoRedoStack; each mutation whose variables carry an input.id (except undo, redo and layoutDiagram) is pushed on the sessionStorage 'undoStack' and the 'redoStack' is cleared. The id is pushed when the request is sent, before the server answers, so failed mutations and mutations outside the model (e.g. project rename) also land on the stack; the stacks have no size limit. A successful undo moves the entry to the redo stack and a redo moves it back; an undo/redo that returns an error leaves both stacks unchanged. Both stacks are reset to empty arrays at application start and when the project editor loads, so history is per browser tab and session. _(Sirius Web)_ · `ApolloLinkUndoRedoStack.tsx`, `UndoRedo.tsx`, `DefaultExtensionRegistry.tsx`
- **Layout changes are undoable**: each layout mutation with cause 'layout' has its id pushed onto the session undo stack, so node moves, resizes, label moves and edge path edits can be undone like semantic changes. _(Sirius Web)_ · `useSynchronizeLayoutData.ts`, `CHANGELOG.adoc`
- **Diagram-state undo/redo**: undo/redo also reverts diagram-only state: collapse/expand, hide/show, fade, pin, node, edge and label layout, node appearance (rectangular, image, ellipse), label appearance, edge appearance, reset of view modifiers, and created or deleted views. Undoing a delete from the diagram re-creates the view with its previous position, labels, appearance and pinned/faded/hidden state. _(Sirius Web)_ · `DeleteFromDiagramChangeRecorder.java`, `ViewRequestChangeRecorder.java`, `DiagramLayoutChangeRecorder.java`
- **Undo of a deleted diagram node**: after deleting a node (e.g. one created with New Part), undo restores it correctly on the diagram (fixed in v2025.12.0). · `GVUndoTests.java`, `2025.12.0.adoc`, `CHANGELOG.adoc` v2025.12.0
- **Operations excluded from undo history**: these inputs skip model-change recording: child creation description lookups, explorer description lookups, object lookups, representation description lookups, expand-all tree paths, action and editing-context action lists, palette lookups, selection dialog and selection status message lookups, initial direct-edit labels (diagram and tree), diagram layout updates, reference value options, search, tree context menus, tree palettes, tree tooltips, tree paths, and undo/redo themselves. Diagram layout updates stay undoable through the separate diagram layout recorder. Downstream applications can exclude more inputs by implementing `IUndoRedoIgnoreInputPredicate` (v2026.1.0). _(Sirius Web)_ · `UndoRedoIgnoreInputPredicate.java`, `DiagramLayoutChangeRecorder.java`
- **Undo/redo marked as partial support**: SysON's key-features table marks undo/redo (together with editing graphical properties and copy/paste) as partially supported in the diagram editor, whereas Sirius Web's own key-features table lists Undo/Redo among fully supported diagram-management features. SysON's keyboard-shortcuts page doesn't list the undo/redo keys. · `key-features.adoc`, `keyboard-shortcuts.adoc`
- **Portal layout undo/redo (proposal only)**: ADR-176 proposes undo/redo for portal layout actions (finishing a move or resize, adding or removing a view), since serialized portal changes can't use EMF change tracking; no implementation exists in the portals packages at v2026.11.0. _(Sirius Web, unclear in SysON)_ · `176_add_support_for_undo_redo_on_portal_representation.adoc`, `CHANGELOG.adoc`
