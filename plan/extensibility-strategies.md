# Extensibility strategies for SysON's features

This is the first step in choosing how Grasp's architecture should grow to take SysON's features: which design strategies it needs so that the 620 entries of [`core.md`](../docs/sysml/syson/port/core.md) (132) and [`useful.md`](../docs/sysml/syson/port/useful.md) (488) in `docs/sysml/syson/port/` can be added later, one at a time, mostly as new code in a feature folder of their own rather than as edits to code other features share. Later steps choose between the alternatives, set priorities and write a decision record for each strategy; this one researches and recommends, and changes no code.

Each entry's need from the architecture was recorded (for a `partly` entry, the part Grasp lacks), the needs were grouped into capabilities, and each capability was matched to a strategy. Every strategy keeps Grasp what it is: one HTML file with its script inline, built by `canvas/build.mjs` from plain scripts in `canvas/src/`, opened as a file or published on claude.ai with the model in the page's own store, no libraries, no server, and anything that needs Java on Claude's side. Entries are cited as `file › group › entry`, as in the working records.

How a feature is added today, which the strategies build on: a folder in `canvas/src/` holds its `lib.js`, `page.js` and `style.css`, and `canvas/build.mjs` lists each file. `lib.js` adds rows to the library's tables (`addKinds`, `addRelationships`, `VIEW_KINDS`, `FIELDS`, `BODY` and `EXTRA` in `core/lib/model.js`), and `page.js` to the page's (`TOOLS`, `ACTIONS`, `VIEW_PANELS` and `FIELD_HOOKS` in `core/page/base.js`; `SHAPES`, `MARKERS`, `COMPARTMENTS` and `RENDERERS` in `core/page/drawing.js`; `ROUTES` in `core/page/layout.js`). What has no table is edited in shared code: every panel field's markup, the header's buttons and the floating panels in `core/page.html`, the keys in `core/page/pointing.js`, the one selected item in `core/page/state.js` and `core/page/panel.js`, undo in `core/page/changes.js`, what a saved model holds in `core/lib/model.js` and `core/lib/stored.js`. Most of the strategies below turn one of those into a table that feature folders add to; the rest add a capability no file has yet.

Of the 620 entries, 568 need at least one of the 23 strategies, 52 need no new architecture, and none only makes sense with a server (16 have a part that does). The 12 `unclear` entries are mapped like the rest and listed again at the end. Statuses: 328 missing, 280 partly, 12 unclear.

## The strategies

In order of how many entries need them.

### Commands registered with where they apply

SysON describes the tools of each diagram in sections (Requirements, Structure, Behavior, Analysis, Extension, View as) in its diagram descriptions (`SDVDiagramDescriptionProvider`, `ToolSectionDescription`, `DiagramDefaultToolsFactory`), adds tree-row entries through `SysONExplorerTreeItemContextMenuEntryProvider` and omnibox commands through `SysONOmniboxCommandProvider`, and merges what the client contributes in its extension registry. These entries need the same reach in a page with no server: one table of commands that feature folders add to, each saying where it shows (which palettes and menus, for which kinds and view kinds, in which section and order), when it applies, which keys run it, and what it does (arm a creation tool with preset values, start a connection, or change the model at once through `edit()`). The header palette, a pop-up palette at the pointer, a row's ⋮ menu, a view's toolbar, the command palette and the key handler all ask the table what applies to the thing at hand. The alternative is a list per place in shared code, as today: the `tools` row of each view kind (`core/lib/model.js`), a `switch` for keys (`core/page/pointing.js`), a hand-written button per action (`core/page.html`). It is simpler, but every new metaclass or command would edit lists that other features own, and two keys could collide without anyone noticing. I chose the table because the entries in eight groups need actions placed by what was clicked, and the same table gives the command palette and the palette's tool search their list. Confidence: medium. It would drop if you keep Grasp's header palette as the only place where elements are made, without SysON's right-click palettes; a smaller table of commands and keys would then do.

### Namespaces, memberships and imports in the saved model

SysON keeps a project as an EMF resource set: documents, each with a root namespace, memberships between owners and members, and import relationships; names resolve by scoping (`MembershipComputer`, `DeresolvingNamespaceProvider`), and `SysMLElementSerializer` writes each reference as the shortest name that resolves. These entries need that structure in Grasp's saved model: packages to put things in, views that belong to the element they are made on, imports that make names visible, and more than one root. One alternative is to keep the single package and imitate packages by naming or by grouping views; the text and the qualified names would then be wrong, and libraries, imports and owned views would have nowhere to live. The other, which I chose, builds on what Grasp has: a package kind that owns elements through the `owner` links every element already carries (`core/lib/model.js`), an `owner` on views, import kinds as relationship rows, visibility as a value, and a list of root packages for documents, brought in as version 3 of the saved format with its upgrade in `UPGRADES`, the way `canvas/src/README.md` ("The saved format") says a saved model changes. Confidence: medium. It would change if memberships need an identity of their own (SysON's tree can show them as rows); until an entry needs that, they can be worked out from the owner links.

### How each element appears in a view, by mapping rules

SysON's diagram descriptions map each metaclass to node descriptions (definition and usage nodes, list compartments with compartment items, free-form compartments, border nodes) and edge descriptions, among them composition edges for nested usages (`AbstractUsageNestedUsageEdgeDescriptionProvider`) and inherited items (`getInheritedCompartmentItems`); a node's compartments are shown or hidden per diagram. Grasp's graph layout has one mapping built in (`graphLayout`, `core/page/layout.js`), and these entries need several: the same usage as a nested box in one view and as a row in its owner's parts compartment in another, inherited features as read-only rows, a nested usage drawn apart with a diamond line. One alternative is to special-case each new form in the graph renderer's layout and drawing; every metaclass's feature would then edit core layout code. I chose mapping rules in a table that features add to, deciding for each element in a view which form it takes, with the view's own choice for that element (kept as per-view state) taking precedence. Compartments become rows bound to elements and drawn as element groups with their own rects, so the core's hit testing, marks, pins, badges and label editing work on them as they do on boxes; inherited rows come from `inheritedFeatures`, which the library already has (`core/lib/model.js`). Confidence: medium. Whether layouts with rows keep the scale tests' limits (a keystroke under 50 ms at 5,000 elements) is unclear until tried; if not, rows need their own redraw path.

### Per-view state as registered keys of layout entries

## Questions for you

Decisions the files can't settle. Each names the strategies that hang on it.

1. **The plane or tabs.** Grasp draws every view on one endless plane, and `canvas/README.md` presents that as the canvas; SysON opens one representation per tab. Should Grasp keep the plane as one tab among view tabs (my recommendation), switch to SysON's tabs, or keep the plane alone? Views opened as tabs (13 entries) and part of the workbench depend on it.
2. **One model per page, or several.** SysON's project browser, templates, and its pages to publish and import libraries assume several projects in one place; Grasp's page holds one model, and the loop with Claude reads `model/current`. Keep one model per page, a project being a file or a published page of its own, or keep several models in the page's store? Several projects kept in the page (18 entries) and the publishing half of the library entries depend on it.
3. **How much library to bundle.** SysON loads 94 KerML and SysML library files into every project. Bundling all of them makes the one HTML file much larger, by how much is unclear until they are converted. All of them, a subset (which: scalar values, SI and ISQ, parts, ports, items, actions, states?), or none for now? Libraries held read-only beside the model (58 entries) depends on it.
4. **Reading SysML text.** Is reading text on Claude's side (the pilot implementation, as `canvas/check.sh` runs the validator) enough, or must the page read text without Claude? If in the page, which part of the grammar first? Model formats as reader-writer pairs (19 entries) and part of the expression entries depend on it.
5. **A selection in every view, or per view.** Grasp marks its one selection in every frame that draws it (`core/page/render.js:254`); SysON keeps a selection per view and carries it across only by commands such as Show in and Reveal. Keep Grasp's way, or follow SysON's? The selection strategy and three of the `unclear` entries depend on it.
6. **Two changes to the saved format.** Namespaces (packages, owned views, memberships, documents) and feature-path ends (connectors as elements, ends through chains) each need a new version of the format. And SysON draws documentation as a note element where Grasp keeps `doc` as a field of each element. Do you want documentation to become elements, or a note drawn from the field? This decides part of the namespace and mapping work.
7. **Files leaving the published page.** Download state is offered only when the page is opened as a file (`core/page/store.js:54`), and the files don't say why. Image export, the `.sysml` and CSV downloads, and downloading a project all hand the user a file. Should they work on the published page too, through whatever the host allows when the page is published?
8. **The header palette.** SysON creates elements from right-click palettes in sections; Grasp's palette sits in the header. Keep both, or move to SysON's palettes only? My confidence in the commands strategy assumes the right-click palettes come.
9. **Live sharing.** The page's store on claude.ai is shared by everyone the page is shared with. The parts of 16 entries that share filters, sorts and layouts live with other people could run through it later. Do you want any of that, or is Grasp a one-person tool?
